# Changelog

All notable changes to Acta Diurna are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Structured list and steps block (story 7.10):** an ordered or unordered structured list, including a numbered-steps / procedure variant, so remediation procedures and checklists render as first-class blocks instead of ad-hoc prose (Epic 7 Phase B, FR2 parity). A new additive `list` block carries an `ordered` flag and a list of `items`, each a bold lead `term` and an OPTIONAL rich-text `description` that reuses the text block's paragraph / inline-run vocabulary verbatim (the same bold/italic, the 7.8 inline-code chip, and http(s)-link marks the text and callout blocks honour) - so the description renders escaped through the shared marked-run snippet, no raw HTML. At least one of `term` / `description` is required per item (a schema refine); the items are capped at 100 (a procedure past that is a structural smell, split it into sections), the description at 50 paragraphs (the callout body ceiling), and the term at 200 characters. The renderer emits a real `<ol>` when `ordered` (a numbered procedure / steps list) or a real `<ul>` otherwise, with real `<li>` items - semantically correct for screen readers - and the step numbering is the NATIVE list ordinal: the schema carries no per-item number, so reordering items renumbers automatically and a hand-authored number can never drift from its position. Every value is Svelte text interpolation (no `{@html}`), so a term or run reading `<script>` shows as visible inert text. The block is an additive member of the block union - a schema-v1 document without it validates unchanged, no version bump - and a `list` block editor (an ordered/unordered toggle, then add/edit/remove items each with a term and an optional plain-text-edited rich-text description) completes the authoring surface. Zero hydration, no new dependency: static SSR markup, AAA report content on the default theme, reader budget 72.5 KB / 200 KB.
- **Card grid block (story 7.9):** a responsive grid of icon + title + description cards, the "vision / benefits" summary that presents a set of takeaways, features or highlights without a table or prose (Epic 7 Phase B, FR2 parity). A new additive `card-grid` block carries a `columns` desktop column count (1-4, schema-capped so the cards never crowd the reader column) and a list of `items`, each an OPTIONAL `icon` (the 7.6 registry, by name), a bold `title` and a short one-line `description` - author-written prose, NOT bound data (no `binding` field), both strings plain bounded text (title 200, description 500 characters), the list capped at 24 like the field grid. The renderer is a pure SSR `<ul>` of cards (escaped values through Svelte text interpolation, no `{@html}`, so a title or description reading `<script>` shows as visible inert text), the desktop column count threaded through a `--card-columns` custom property so the grid template is data-driven, collapsing to a single stacked column at the reader mobile breakpoint (768px) via CSS only - zero hydration, no JS. The icon is DECORATIVE (`aria-hidden`, from 7.6): the title and description carry the meaning, so the icon is never the sole signal (NFR14), and a card with no icon renders title + description only. An unknown icon name fails validation with the FR2 actionable problem-details error naming the offending field (the icon enum carries the valid set as its hint). The block is an additive member of the block union - a schema-v1 document without it validates unchanged, no version bump - and a `card-grid` block editor (a column-count select, then add/edit/remove cards each with an optional icon picker, a title and a description) completes the authoring surface. Zero hydration, no new dependency: static SSR markup, AAA report content on the default theme.
- **Code block and inline-code mark (story 7.8):** a monospace code block and an inline-code mark, so commands, snippets and literal identifiers render faithfully in technical reports (Epic 7 Phase B, FR2 parity). A new additive `code` block carries a literal `code` source string, an optional short `language` caption, and an optional list of `annotations` (each a short note with an optional 1-based `line`). The source is bounded for DoS the way other blocks bound their content - 20000 characters AND 500 lines, with annotations capped at 100 and each note at 280 characters - and is rendered escaped through Svelte text interpolation (no `{@html}`) inside a static, selectable `<pre><code>` with `white-space: pre`, so every space and newline survives verbatim and a snippet reading `<script>` shows as visible inert text, never markup nor execution (the renderer-purity guarantee). `language` is a free-form CAPTION ONLY, never a highlighter directive: there is no syntax-highlighter library and no new dependency, the label is shown as a small caption and the code is plain monospace. The block ships NO copy-to-clipboard button - a copy affordance needs client JS and would move the reader budget (NFR3, the Phase B zero-hydration stance); a copy affordance is explicitly out of scope. The inline-code mark is an ADDITIVE member of the text block's inline-run vocabulary (`code?: boolean` on `inlineRunSchema`), rendered as an escaped monospace `<code>` chip; a run without it validates and renders exactly as before, and the marks nest (a bold inline-code run is `<strong><code>`). Because the callout body (7.7) reuses the text rich-text vocabulary, inline code works there too. A new system monospace token (`--font-mono`, a `ui-monospace` stack, no self-hosted font and no network fetch so it stays within the reader's strict no-CDN CSP) drives both the block and the chip. The block is an additive member of the block union - a schema-v1 document without it validates unchanged, no version bump - and a `code` block editor (a monospace source textarea, an optional language caption, and an annotation list) completes the authoring surface. Zero hydration, no new dependency: static SSR markup, reader budget 71.8 KB / 200 KB.
- **Callout / admonition block (story 7.7):** a tinted, left-accent-bordered box that elevates a verdict, a summary, a warning or a resource list above the body flow (Epic 7 Phase B, FR2 parity). A new additive `callout` block carries a `tone` (a CLOSED enum - `info`, `success`, `warning`, `danger`, `neutral`), an optional `icon` (the 7.6 registry, by name), an optional `kicker` header label, and a rich-text `body` that reuses the text block's paragraph / inline-run vocabulary verbatim, so the body renders escaped (Svelte text interpolation, no `{@html}`, the same bold/italic/http(s)-link marks the text block honours) with no raw HTML. The tone is deliberately NOT a document scale: a callout's colour language is a fixed, theme-owned semantic set (`--report-tone-{info,success,warning,danger,neutral}`, defined for both the default and midnight themes in `app.css`), so a callout renders with no `scales` declaration and an existing document gains the block with zero authoring overhead - the same stance the comparison-matrix treatment tint takes for its closed status enum. The renderer reads ONLY those tokens (a `tone-<tone>` class sets a single `--tone-color` seam); no raw hex lives in the component, so a new theme re-skins every callout with no component change (the FR39 token stance). The box is a low (8%) wash of the tone over the surface with the tone-coloured left accent border and an optional header row of the decorative icon + the uppercase kicker. Tone is conveyed by MORE than colour (NFR14): the kicker label and/or the icon carry the meaning in words and glyph, so the callout survives without colour; the body text stays `--report-text` and holds AAA on the default theme. The tone accent (border + icon + kicker) is a DECORATIVE accent, not prose, so its contract is the AA floor on the report background, the documented stance the categorical swatches and the KPI trend colours already take - all ten tone/theme pairs clear it (most clear AAA), asserted by the contrast regression test so a future token edit cannot regress it silently. An invalid tone or an unknown icon name fails validation with the FR2 actionable problem-details error naming the offending field (the icon enum carries the valid set as its hint). The block is an additive member of the block union - a schema-v1 document without it validates unchanged, no version bump. A `callout` block editor (pick a tone, an optional icon, a kicker, and edit the rich-text body) completes the authoring surface. Zero hydration, no new dependency: the callout is static SSR markup, reader budget 71.3 KB / 200 KB. This is the first general report brick stories 7.5 (status) and 7.6 (icons) feed into.
- **Curated inline-SVG icon set (story 7.6):** a small FIXED registry of inline-SVG icons selectable by name, so the upcoming callout (7.7) and card grid (7.9) carry meaningful glyphs without an icon font, an external/CDN asset, or any new dependency (Epic 7 Phase B foundation, consistent with the self-hosted-fonts / no-CDN CSP posture). A new isomorphic `iconNameSchema` (`src/lib/schema/icons.ts`) is a `z.enum` of twelve generic, domain-neutral names - `check`, `cross`, `alert`, `info`, `question`, `arrow-right`, `clock`, `database`, `shield`, `bolt`, `flag`, `link` - that a block references by name; an unknown name fails validation with the FR2 actionable problem-details error whose hint LISTS every valid name (the enum's `invalid_value` issue carries the allowed set), so a producer learns the whole vocabulary from one rejection. The matching SSR `<svg>` markup lives in the render tier (`src/lib/render/blocks/icons.ts`), one stroke-only single-weight glyph per name in the project's line language (compare the brand mark), modelled as path-`d` data so the `Icon.svelte` component renders real `<path>` elements through Svelte - never `{@html}` - keeping the renderer-purity boundary intact. The icon is DECORATIVE by contract (`aria-hidden="true"`, `focusable="false"`): the adjacent text always carries the meaning, so the glyph is never the sole signal (NFR14). It is sized and coloured entirely by the surrounding token context - a `1em` square that strokes in `currentColor`, with no dimension or colour baked in - so a caller controls size via `font-size` and colour via `color`. A lockstep test holds the render registry and the schema enum in exact step (an entry for every name, no extra), so the two can never drift. Zero hydration, no new dependency: the inlined SVGs are static markup well within the reader budget (70.0 KB / 200 KB, unchanged - no block consumes the icon yet). This is the foundation stories 7.7 (callout) and 7.9 (card grid) build on.
- **Background data hygiene (backlog hardening):** a periodic, boot-registered sweep purges ephemeral verification state and reclaims orphaned uploads, so attacker traffic and report churn can no longer grow the database or the uploads volume without bound. Spent or expired `verification_tokens` (single-use reader magic-link tokens an attacker can mint up to the rate-limit ceiling) are deleted each sweep; a data set whose report was deleted (its `report_id` nulled) and that has then sat unbound past a grace window (`DATA_SET_ORPHAN_RETENTION_DAYS`, default 30) has its row and its on-disk file reclaimed - the unlink path is guarded to stay under the uploads volume and tolerates an already-missing file, and one failed file never strands the rest. The sweep interval is operator-tunable (`PURGE_INTERVAL_MINUTES`, default 60), runs only after boot migrations, never holds the process open, and is disabled under test. Reader access-audit records are deliberately out of scope: their retention is governed by FR24 (Epic 6 story 6.3 "Access Audit & Retention"), not a blind janitor. A `data_sets.report_id` index (migration 0011) supports the orphan scan and future per-report listing.
- **Connection-pool sizing from the environment (backlog hardening):** `DB_POOL_MAX` (default 10, bounded 1-100) sizes the PostgreSQL connection pool so an operator can scale it for reader-realm load without a code change; the existing pool error handler is unchanged.
- **Container vulnerability scanning in CI (backlog hardening):** the CI image build now runs a pinned Trivy scan that fails the pipeline on HIGH or CRITICAL OS/library CVEs (no-fix findings are surfaced but not blocking; any waived fixable finding is justified inline in `.trivyignore`), closing the docker.md scan gap before an image is pushed.
- **Opt-in hardened reverse proxy (backlog hardening):** the compose file ships a Caddy `proxy` profile (`docker compose --profile proxy up -d --build`) that terminates TLS with automatic HTTPS and OVERWRITES any client-supplied `X-Forwarded-For` with the real peer IP, so a directly-reachable instance is secure-by-default against an attacker spoofing XFF to mint a fresh rate-limit bucket per request. It is opt-in (set `CADDY_DOMAIN`, `ORIGIN=https://<domain>`, and `ADDRESS_HEADER=x-forwarded-for`); the app + database core is unchanged for operators who already run their own ingress. The app now reads `ADDRESS_HEADER` from the environment (empty by default, so it trusts the socket peer and never an unverified header). Documented in `docs/ops/deployment.md`.
- **Outline-first AI generation (story 5.4):** the AI proposes a report outline the author approves before any content is written, so a generated report follows the author's narrative, not the model's (FR32, Epic 5). From the report editor (when AI is configured and opted in - the entry point is hidden when AI is off, never offering a capability that 503s), the author enters an intent, optionally picks a skeleton and a data set, and requests a BOUNDED outline (sections + per-block key points, clamped to the schema DoS ceilings of 100 sections / 200 blocks-per-section so a runaway model output is truncated, never passed through). A two-stage orchestration (`src/lib/server/ai/generate.ts`) runs ENTIRELY over the story 5.3 connector - it never `fetch`es directly, so a disabled instance throws the 5.3 `/problems/ai-generation-disabled` 503 and makes no call. The outline is returned for the author to review, edit inline, and approve; approval is bound to the EXACT approved outline by a SHA-256 content hash that travels with the fill request (a stateless round-trip, no new table, no stored outline). At fill time the posted outline is re-hashed and compared - a since-edited or stale approval is rejected with a 409 BEFORE any LLM call, so content can never be generated from an outline the author did not approve (the re-approval discipline). Every model output is treated as UNTRUSTED: the JSON is parsed DEFENSIVELY (prose-wrapped, malformed, oversized, or wrong-shape output is extracted-or-rejected, never crashing), the assembled document gets SERVER-OWNED slug ids (the model's ids are never trusted), and the result is persisted through the EXACT `updateReportDocument` / `createReportWithDocument` validate-on-write path every other surface uses (AR5, no bypass) - so a hallucinated invalid document is rejected by `validateDocument` with the FR2 actionable `errors[]` and the draft is left UNTOUCHED, exactly as a bad API/MCP write is. Generation writes ONLY on a fully valid fill: a failure at either stage (endpoint unreachable, unparseable model output, or an invalid assembled document) leaves the existing draft unchanged and surfaces a problem-details error NAMING the failing stage (outline / content-fill / validation) with a retry action. Workspace-triggered only for V1 (an agent-triggered generation API is deferred); the generation orchestration is server-only, absent from the client bundle, reader budget 69.2 KB / 200 KB. With this story Epic 5 (AI-native authoring) is complete end to end: MCP discovery (5.1), MCP authoring (5.2), LLM endpoint configuration (5.3), and outline-first generation (5.4).
- **LLM endpoint configuration with explicit opt-in (story 5.3):** configure an OpenAI-compatible LLM endpoint for AI-assisted report generation, with no call made anywhere before a deliberate opt-in (FR33, NFR18, Epic 5). The connection is configured entirely from environment variables - `LLM_BASE_URL` (any OpenAI-compatible base: the OpenAI API, a local runtime, or an Anthropic-compatible proxy - there is NO default cloud endpoint, the connector talks ONLY to the URL you set, no phone-home), `LLM_MODEL`, and an OPTIONAL `LLM_API_KEY` (omit it for an unauthenticated local endpoint) - validated for SHAPE at boot but never tested for reachability, so a misconfigured or down endpoint cannot stop the container (the SMTP boot-vs-call split). The block is optional and all-or-nothing: the app boots without it, and setting any `LLM_*` value requires `LLM_BASE_URL` + `LLM_MODEL` together (a half-configured endpoint fails fast at boot). A SECOND, deliberately separate gate `AI_GENERATION_ENABLED` (default false) is the explicit opt-in: the connector refuses to issue ANY outbound `fetch` unless BOTH the endpoint is configured AND the opt-in is true, so configuration alone never enables a call - the load-bearing "no call before opt-in" contract, proven by a test that the `fetch` mock is never invoked when disabled. The connector (`src/lib/server/ai/`) is the one place an outbound call happens, built over the platform `fetch` with no new dependency, no SDK: it POSTs an OpenAI Chat Completions request to `${LLM_BASE_URL}/chat/completions` with a `Bearer` key when configured (omitted for a no-auth endpoint), a 60s `AbortController` timeout, and returns the typed assistant message content. Generation requested while disabled throws `/problems/ai-generation-disabled` (503) whose detail tells the operator HOW to enable it; a transport, HTTP, abort, or parse failure throws `/problems/ai-generation-failed` (502) with a client message redacted of the endpoint host, response body, and key (the full error logged server-side at `warn`). The API key is never logged (added to the pino redaction list, like `SMTP_PASSWORD`), never placed in a client-facing error, and never returned by the settings load. A Settings "AI generation" panel reports the three states (not configured / configured-but-disabled / enabled with the model and base URL, key never shown) and, when enabled, offers an explicit "Test connection" probe that reports success or the redacted failure inline. The connector is server-only, absent from the client bundle, reader budget unchanged at 68.9 KB / 200 KB. This is the foundation story 5.4's outline-first generation consumes.
- **MCP authoring surface (story 5.2):** an AI agent can now create, update, and publish reports over the Model Context Protocol, so authoring is native from any MCP-capable assistant (FR31, AR5, Epic 5). Five write tools register on the SAME `McpServer` / `/api/mcp` Streamable HTTP route / PAT gate the 5.1 read surface built - `create_report` (a blank starter with an optional title, or an instantiated `document`), `update_report` (title and/or document with an `expectedUpdatedAt` optimistic-concurrency token), `publish_report`, `unpublish_report`, and `delete_report` - each a thin delegation to the EXACT documents/publish service the REST `/api/v1/reports` endpoints call, with no business logic, validation, or database access in the tool handlers (the AR5 one-service-layer, four-surface contract). The combined `{title, document}` update is composed through a shared helper so the MCP tool and the REST PATCH share one atomic single-guarded write (the title is merged into the document and written once under the concurrency guard, never as a second unguarded write that could lose a concurrent edit). Validation and error semantics are byte-for-byte identical to the REST API: an invalid document surfaces the FR2 actionable problem-details with the block path, field, and fix hint; a stale concurrency token is a 409, a delete of a published report is a 409, an unknown id is a 404 - each carried as an `isError` tool result whose content is the SAME RFC 9457 body REST returns, so an agent reuses its existing `errors[]` parser. A write against a revoked or missing PAT is the transport-level 401 before any tool runs, never a tool result. Write tools advertise `readOnlyHint: false` and `delete_report` advertises `destructiveHint: true`. No new dependency, route, auth realm, or database table. The MCP surface is now complete (discovery in 5.1, authoring in 5.2); it stays server-only, reader budget unchanged at 68.9 KB / 200 KB.
- **MCP discovery surface (story 5.1):** an AI agent can discover an instance over the Model Context Protocol, so it orients itself (schema, skeletons, reports) without bespoke integration (FR31, Epic 5). The MCP server is the FOURTH entry surface over the SAME service layer (reader cookie / author cookie / REST PAT / MCP PAT, AR5): it runs inside the SvelteKit app at `/api/mcp` over Streamable HTTP using the official `@modelcontextprotocol/sdk`, and exposes four read-only tools - `get_schema` (the published `{ version, schema, examples }`, the exact composition the public `/api/v1/schema` endpoint serves, via a shared helper so the MCP-advertised schema cannot drift from the REST artifact), `list_skeletons` (the skeleton library summaries), `list_reports` (the report summaries), and `get_report` (one full report by id) - each a thin delegation to the same documents/skeletons/schema service the REST API and workspace call, with no business logic, validation, or database access in the tool handlers. The surface is read-only; the write tools land in 5.2 on this same server. It is PAT-authenticated by reusing Epic 4's `/api/*` boundary verbatim: a connecting agent sends `Authorization: Bearer <acta_pat_...>`, and a missing, invalid, or revoked token is rejected by the existing `apiAuth` hook with the standard 401 `application/problem+json` (`WWW-Authenticate: Bearer`) BEFORE the route runs - the handshake fails revealing nothing beyond authentication failure (no tool list, no schema), and the same per-IP plus global rate limiters cover the auth attempt with no second limiter. Authentication is stateless-per-request - the PAT is the credential and the session, so no `Mcp-Session-Id` state is kept (NFR13). A service error inside a tool is carried into the MCP tool error channel as an `isError` result whose content is the SAME RFC 9457 problem-details JSON the REST API returns (so an agent reuses its existing `errors[]` parser); an unexpected error becomes a JSON-RPC internal error, never a leaked tool result. The MCP server is server-only and adds zero reader-path JS - the SDK is absent from the client bundle, reader budget unchanged at 68.9 KB / 200 KB.
- **Status badge, chip cluster and conditional table formatting (story 7.5):** a reusable status pill that renders a categorical scale value as colour plus label, so status updates, roadmaps, requirements and findings tables read at a glance without hand-coloured cells (Epic 7 Phase B, FR2 parity). A shared `Badge` render helper resolves one scale entry to its colour (the same theme-palette-or-explicit-hex resolution the legend and the matrix pill use) and its label, with the label text ALWAYS present so colour is never the sole signal (NFR14); it is reused by the new chip-cluster block and the table conditional column. A new additive `chip-cluster` block lists several entry keys of one referenced document scale (`scaleRef` + `entries`, with an optional `title`) and renders them as a wrapped row of pills - no colour or label authored on the block. The `table` block's columns gain an OPTIONAL `scaleRef`: a column declaring one renders its cells as scale-driven badges (colour plus label computed at render, never authored per cell) while every other column renders plain escaped text exactly as before, so an existing table with no scaleRef column validates and renders byte-identically (additive and optional, no schema-version bump). Both surfaces are pure SSR HTML with zero hydration (reader budget unaffected at 70.0 KB / 200 KB) and escaped values only. An unknown chip-cluster scale or entry key, an unknown table column scale, or a cell value absent from the referenced scale each yield an actionable problem-details error - the chip names the offending entry, the table cell names its row and column - via the document-level cross-reference pass story 7.1 established (extended to resolve chip-cluster and table column references). A `chip-cluster` block editor (pick a scale, then its entries) and a per-column scale selector in the table editor complete the authoring surface.
- **Set-Membership (UpSet) block (story 7.4):** an UpSet-style coverage matrix derived from a comparison-matrix block's findings with zero extra data entry, so coverage by source-combination is visible at a glance (Epic 7's novel visualization, FR42). A `set-membership` block references a `comparison-matrix` block in the same document by id (`sourceBlockId`, with an optional `title`) and re-enters no data: it derives one row per present intersection - findings grouped by the exact set of sources that FOUND them - and renders each row as a dot pattern (one dot per source in the sources-scale order, filled when the source is in the set, with a line connecting the filled dots) plus the intersection's findings as severity-coloured pills (from the severity scale) carrying their short `tag`/`label`. The membership predicate is found-only (the conventional coverage UpSet, "which sources detected this finding"); `missing`, `none` and an absent record key are out of the set. Rows order by descending finding count, then descending membership size, then the canonical key (the conventional, deterministic UpSet sort). Findings no source found are surfaced as an explicit "(none)" intersection row so they are never silently dropped - except when every finding is empty-set, where there is no coverage to chart and the block renders a neutral "No source coverage to chart yet." state rather than an empty SVG. The renderer is an SSR SVG built with d3-scale/d3-shape (zero hydration, no LayerChart, no new dependency, reader budget unaffected at 68.8 KB / 200 KB) carrying an accessible text alternative (`role="img"` + `<title>`/`<desc>` and a visually-hidden per-row list) that summarises each intersection in words ("Found by SIEM and EDR: ..."), so the dot pattern is never the sole signal; it passes axe-core on the default theme (NFR14). The block is an additive member of the block union - a schema-v1 document without it validates unchanged, no version bump. A `sourceBlockId` matching no block, or matching a block that is not a comparison-matrix, yields an actionable problem-details error at `sections[i].blocks[j].sourceBlockId` (FR2 parity), via the document-level cross-reference pass story 7.1 established (extended to resolve the reference against the document's comparison-matrix block ids). A `set-membership` block editor (a select of the document's comparison-matrix blocks plus an optional title) and a `setMembership` template brick (pairing the UpSet with a companion comparison-matrix in the same section so it is useful standalone) complete the surface. With this story Epic 7 renders a complete correlation report end to end - field grid, comparison matrix, legend and UpSet.
- **Field Grid and Legend blocks (story 7.3):** two small additive blocks that close the report's render header and matrix legend (Epic 7), so a correlation report (cover text + field grid + comparison matrix + legend) now renders end to end. A `field-grid` block holds a compact list of `{ label, value }` metadata pairs (e.g. Author / Date / Scope / Status), author-written prose, not bound data (no `binding`), bounded at 24 items; the renderer is a pure SSR description list (`<dl>`/`<dt>`/`<dd>`, escaped values only, no raw HTML, zero hydration) that auto-fits two columns on desktop and collapses to one at the reader mobile breakpoint via CSS only. A `legend` block references a document scale by `scaleRef` (with an optional `title`) and renders one swatch per entry of that scale - colour from the same scale resolution the matrix uses (so the legend's colours match the matrix's), the entry label, and the optional sublabel - all derived entirely from the scale, with no colour or label re-authored on the block; every swatch carries its text label so colour is never the sole signal (AAA), and the chip is decorative (aria-hidden). Both blocks are additive members of the block union - a schema-v1 document without them validates unchanged, no version bump - and both pass axe-core on the default theme (NFR14). An unknown legend `scaleRef` yields an actionable problem-details error naming the missing scale at `sections[i].blocks[j].scaleRef` (FR2 parity), via the document-level cross-reference pass story 7.1 established. Per-block editors (the field grid adds/edits/removes items; the legend picks a scale and an optional title) and `fieldGrid` + `legend` template bricks (the legend seeding its companion sources scale) complete the surface. Reader-path JS budget: 67.0 KB / 200 KB.
- **Comparison Matrix block (story 7.2):** a findings-by-sources coverage matrix authored once on a `comparison-matrix` block, so a multi-source audit reads as a single coverage table without hand-colouring cells (Epic 7 core block, FR41). Each finding carries a `category`, `label`, a `severity` key, a per-source `{ state: found|missing|none, text? }` record, a `treatment: { before, after, status: action|deferred }`, and an optional short `tag`; the block references the severity and sources scales (story 7.1) by key. The block is an additive member of the block union - a schema-v1 document with no matrix validates unchanged, no version bump. The renderer is a pure SSR HTML table (escaped values only, no raw HTML, zero hydration, reader budget unaffected): rows group under a category banner that repeats when the category changes (authored order preserved), a severity pill takes its colour and label from the severity scale, one cell per source follows the sources-scale entry order so every row aligns to the same columns (a `found` cell tints with the source's scale colour, a `missing` cell shows a fixed neutral hatch, a `none` cell a neutral dash), and the treatment-before/after cells tint by a fixed two-state status token. All colour is computed at render from the scales, never authored per cell; every colour-coded cell also carries text (the state name, the severity label, the source note) so colour is never the only signal, and the matrix passes axe-core on the default theme (NFR14). A dangling severity/source scale reference, a finding severity not in the severity scale, or a source record key absent from the sources scale each yields an actionable problem-details error naming the offending finding and field (FR2 parity), via the document-level cross-reference pass story 7.1 established. A `comparison-matrix` block editor (structured-JSON authoring, no data binding) and a `comparisonMatrix` template brick (seeding the companion severity + sources scales) complete the surface. Reader-path JS budget: 66.5 KB / 200 KB.
- **Document-level categorical scales (story 7.1):** declare named scales of `{ key, label, color?, sublabel? }` entries (severity, source sets) once on the document and reference them by key, so every matrix and legend shares one colour and label source instead of redefining it per block (Epic 7 foundation). The `scales` field is additive and optional - a schema-v1 document with no scales validates and renders unchanged, no version bump. Unique scale keys and unique entry keys within a scale are enforced with an actionable problem-details error naming the duplicate; colours are 6-digit hex only. An entry with no explicit colour resolves deterministically to a categorical theme swatch by its index in the scale (stable, mirroring chart series colours), so an author who supplies no colours still gets a legible report. A pure contrast helper (`scaleContrastWarnings`) flags an explicit author hex below AAA on the report background for the workspace to surface - a warning, never a render gate (FR39 "AAA default, author may degrade"). A single document-level cross-reference pass (`validateScaleReferences`) is the seam stories 7.2-7.4 extend to validate block-to-scale references.
- **Project foundation (story 1.1):** SvelteKit + TypeScript strict scaffold on Node 22 with `@sveltejs/adapter-node`, exact-pinned dependencies, and a CI pipeline (lint, svelte-check, vitest, build).

The link is shown exactly once at creation with one-gesture copy; only its SHA-256 hash is stored, so a database leak exposes no usable link. A draft report refuses sharing with a clear "publish first" message (FR6). The share-management surface lists each link's status (active, expired, revoked) without ever re-exposing the token.
- **Reader verification by magic link (story 3.3):** a reader opening a share link is met by a themed, branded verification card (never a generic auth wall) and verifies their email once; a single-use, 15-minute, email-and-share-bound magic link (256-bit token, hashed at rest) opens a persistent reader-realm session, after which they read freely with no re-verification while the session and share remain valid (FR18, FR22, FR23, NFR6). The reader realm is a second, strictly separated session realm (its own `acta_reader` cookie, no expiry by default so the share's own expiry and revocation govern access, with an optional `READER_SESSION_TTL` to force sessions to age out, and per-share scope so a session for one report grants nothing for another) (NFR12). Verification responses never reveal whether an email is authorized or known - every email yields the same neutral "check your email" confirmation, and a closed or unknown share serves one identical neutral 404 (NFR9). Each verified access is recorded for audit (one global reader identity per email, many access records).
- **Restricted and open share modes (story 3.4):** each share is either restricted to an author-managed recipient allow-list or open to anyone who holds the link and verifies their email (FR19, FR22). In restricted mode an email absent from the list receives the exact same neutral "check your email" confirmation as a listed one but is never sent a magic link and never gets a token, so the refusal reveals nothing about who is on the list (NFR9). The author manages the recipient list per share from the share surface (add or remove emails, switch a share between restricted and open); recipient emails are normalized so case and whitespace never split one address into two entries.
- **One-click revocation and leak-free posture (story 3.5):** an author revokes any share in one click (a two-step destructive confirm); revocation is immediate and irreversible, takes effect on the reader's very next request with no cache window, and cuts off any already-verified reader mid-session (FR20). A revoked link - exactly like an expired link or a never-existed token - serves one byte-for-byte identical neutral page ("This link is not available") that leaks nothing: not the report title, not the reason the link is closed, not whether the token ever matched a share (FR20, FR21, NFR9). The whole reader surface is hardened (NFR10): `noindex/nofollow` on every share, verify, and neutral route; `Cache-Control: no-store` on every sensitive response so a revoked link's prior content is never replayed from a cache; no OpenGraph or Twitter-card metadata, so a link pasted into chat or email unfurls nothing about the report; and a strict Content-Security-Policy with zero third-party assets (self-hosted fonts, no CDN). A mis-sent link is a non-event.
- **Data push and published schema (story 4.3):** push a data set onto a report over `/api/v1/data-sets` and fetch the document schema over `/api/v1/schema`, so the inject-and-render cycle runs unattended (FR13, FR14/15 parity, AR2, FR31 groundwork). The push is a thin adapter over the SAME ingestion and binding services the workspace upload uses: the raw file bytes are the request body with the format taken from `Content-Type` (`text/csv` / `application/json`; an Excel content-type gets the honest 415), an optional `?reportId` targets a draft report, and an optional `X-Filename` header labels the set (the bytes are stored under a UUID, never the client value). With a target the push parses, inspects, stores, and auto-rebinds every matching block (FR14), returning the same per-block diagnostics and binding summary the workspace refill surfaces - green/drifted/unresolved with the closest-match proposal for a drift (FR15) - as JSON; a push onto a published report is a clean 409, and the 50 MB cap is enforced from `Content-Length` before the body is buffered. `GET /api/v1/schema` is PUBLIC (no token, like the OpenAPI spec) and returns `{ version, schema, examples }` - the current document version, the live draft-2020-12 JSON Schema (byte-equal to the committed `static/schema/v1.json`, the single source of truth), and the minimal and full example documents - cacheable per version, the agent-discoverable read surface Epic 5's MCP consumes. The OpenAPI spec now describes both endpoints. With this story the V1 MVP is complete end to end: create and publish over the API (4.2), push data and rebind unattended (4.3), and read over the public reader surface (Epic 3) - the dogfooding gate opens.
- **Reports API with workspace parity (story 4.2):** full report CRUD and publish lifecycle over `/api/v1/reports` for scripts and agents, behaving identically to the workspace because every endpoint is a thin adapter over the SAME service layer (FR30, AR5). `POST` creates a draft (a blank starter with an optional title, or an instantiated `document`); `GET /reports` lists in a `{ items }` envelope (forward-compatible for pagination); `GET /reports/:id` reads; `PATCH /reports/:id` updates the title and/or document with an `expectedUpdatedAt` body field for optimistic concurrency (a stale token is a 409); `POST /reports/:id/publish` and `/unpublish` drive the lifecycle; `DELETE /reports/:id` removes a draft (a published report refuses with 409). An invalid document yields the exact same actionable RFC 9457 problem+json (block path, field, fix hint) the workspace produces, because validation lives in the shared service (FR2 parity). A hand-assembled OpenAPI 3.1 spec is served at `/api/v1/openapi.json` (public, no token) describing every endpoint, the PAT bearer security scheme (D10), and the RFC 9457 Problem shape, and embedding the generated document JSON Schema as the single source of truth (D8).
- **Reports API duplicate endpoint (API parity):** `POST /api/v1/reports/:id/duplicate` mints a fresh editable draft from a deep copy of any report (FR10), closing the workspace-vs-API gap where the Duplicate action had no programmatic equivalent. It is a thin adapter over the same `duplicateReport` service the workspace uses: a published source duplicates into a draft, an unknown id is a 404 problem+json, and the response is the created draft (201) in the same envelope the create endpoint returns. - **API tokens (story 4.1):** create and revoke personal access tokens from the workspace settings so scripts and agents can authenticate to the programmatic API (D10). A token is a high-entropy bearer credential (`acta_pat_` prefix + 256-bit body) shown exactly once at creation with one-gesture copy; only its SHA-256 hash is stored, so a database leak exposes no usable token. The settings list shows each token's name, a non-secret last-four display fragment, creation and last-used timestamps, and an active/revoked status chip; revocation is one click (a two-step confirm) and never deletes the row (an audit trail). API requests authenticate via `Authorization: Bearer <token>` only - this is a third, strictly separated auth realm (a browser cookie never authorizes the API, and a token never opens a workspace or reader session, NFR12). A missing, invalid, or revoked token gets an RFC 9457 problem+json 401 with `WWW-Authenticate: Bearer` (never a redirect to login), and API authentication failures are rate-limited per-IP with a global brake (AR4, AR12). This establishes the `/api/*` PAT-bearer path and the shared `/api/*` error boundary that maps any thrown `AppError` to problem+json, on which the rest of the programmatic surface builds.

### Changed

- **Boot migrations retry transient connection errors (backlog hardening).** A migration run that fails because PostgreSQL is not yet accepting connections (the cold `docker compose up` race) is now retried a bounded number of times with a short backoff instead of crashing the container on the first attempt; a genuine migration or DDL error still surfaces immediately and is never retried. The boot behavior, failure logs, and recovery steps are documented in the new [`docs/ops/migrations.md`](docs/ops/migrations.md) runbook.
- **Reader sessions no longer expire on their own by default.** A reader session is now governed entirely by its share - the share's optional expiry and revocation, which the reader gate re-checks on every load - rather than by a session lifetime. `READER_SESSION_TTL` becomes an optional operator override: leave it unset (the new default) and reader sessions have no time bound; set it to N days to force sessions to age out after N days. The reader cookie for a no-expiry session is still persistent, capped at the browser's ~400-day cookie-lifetime maximum, so a returning reader re-verifies at most every ~400 days while the share status governs real access. Author sessions are unchanged (fixed 7 days).

### Fixed

- **Every form POST was rejected in the browser with "Cross-site POST form submissions are forbidden".** The app set `Referrer-Policy: no-referrer` on all responses, which makes Chrome send `Origin: null` on a form submission, tripping SvelteKit's CSRF origin check - breaking login, all authoring actions, and the reader verification card in a real browser (the e2e suite masked it by injecting an explicit Origin through Playwright's request context). Fixed by serving `Referrer-Policy: same-origin`, which still sends no `Referer` to any cross-origin destination (preserving the leak-free reader posture, story 3.5) while sending the `Origin` the CSRF check requires for same-origin POSTs.

### Security

- Session cookies carry the `__Host-` name prefix and are always `Secure` (backlog hardening): a browser honours a `__Host-` cookie only when it is `Secure`, `Path=/`, and carries no `Domain`, so a sibling subdomain or a downgraded channel cannot plant a cookie that shadows the author or reader session. It works on `http://localhost` (a browser secure context) and, in production, the https-`ORIGIN` guard guarantees the `Secure` flag is never sent over a plaintext non-loopback channel. Note: this renames the session cookies, so existing author and reader sessions are invalidated once on upgrade (the author signs in again, readers re-verify).
- The `/api/v1/reports` JSON body is capped before `JSON.parse` (backlog hardening): an over-cap declared `Content-Length` is rejected up front and an under-reported body is caught after read but before parse, both returning a 413 problem-details, so the parse cost is bounded well below the adapter's 50 MB transport limit. The document within is still separately capped at `MAX_DOCUMENT_BYTES` by the validate-on-write service. The workspace save paths already enforced this; this closes the API path.
- Reader-verification DoS hardening (3.3 follow-up): a per-share verification brake, independent of client IP, now sits between the per-IP limiter and the instance-wide global brake, so a flood against one share can no longer starve email-verification for readers of every other share. The shared per-share and global brakes are charged only on a genuine verification attempt (a real magic-link token, or a plausibly-shaped email submission), so an empty-token probe by a holder of a share link is bounded on the per-IP bucket alone and cannot drain the shared brakes for everyone. Closed or unknown shares stay byte-for-byte indistinguishable (NFR9) and a throttled response opens no new enumeration oracle.
- Test-send rate limiting (3.1 follow-up): the workspace test-email action is now rate-limited per author session (about five per hour), returning the same 429 problem-details the other limited actions use, so a hijacked author session cannot turn the SMTP relay into a spam or sender-reputation vector; the operator can still test any address.
- Session cookies are forced Secure in production: environment validation now rejects an `http://` `ORIGIN` when `NODE_ENV=production`, so an operator behind a TLS-terminating proxy cannot accidentally ship author or reader session cookies without the `Secure` attribute. The https-`ORIGIN` deployment contract is documented in [`docs/ops/deployment.md`](docs/ops/deployment.md).
- Central `workspaceGuard` enforcing authentication on every workspace request, including form actions and endpoints (SvelteKit layout `load` does not guard actions).
- XSS structurally prevented in the renderer (no raw HTML; links restricted to http(s); images by UUID asset reference only); strict CSP with zero third-party assets; `noindex` on all report routes; secrets only in environment variables, never logged.
- Reader verification hardening (story 3.3): a share whose report is unpublished after the link is created serves the same neutral 404 as a revoked or unknown share (no 409 enumeration oracle); the magic-link landing now enforces its rate limit (a throttled landing is indistinguishable from a failed verification); and request-verification dedups one live magic link per (share, email) within the 15-minute window, capping mail amplification to a victim address while keeping the response identical whether a mail was sent or suppressed.
- Restricted-mode timing-equivalence (story 3.4, NFR9): the restricted recipient-list check runs behind the neutral confirmation, and the magic-link send is fire-and-forget on every path, so an off-list email and an on-list email are indistinguishable in practice over the network - the variable SMTP round-trip (the only network-scale separator) is never on the response path, and the residual on-list-vs-off-list difference is sub-millisecond local database work below the network noise floor. A forwarded magic link still verifies only the address it was issued to (the token is email-and-share bound), so a restricted share cannot be bypassed by forwarding a link to an unlisted third party.
- Recipient-list bound (story 3.4): a restricted share's allow-list is capped at 500 recipients (counted after normalization and de-duplication), rejecting an over-large submission with a clear error before any write, so a single submission cannot insert an unbounded set of rows. Replacing a non-existent or malformed share's recipient list now returns a clean "share not found" instead of a server error.
- Revocation and enumeration-safety (story 3.5, FR20/NFR9/NFR10): revoking a share is idempotent (a double-revoke is a no-op that preserves the original instant) and sweeps every live reader session bound to it, so a verified reader is cut off immediately rather than reading until their session expires. The reader gate re-checks share liveness on every request before reading the session, so a revoked or expired share short-circuits to the neutral page even for a holder of a still-valid reader cookie. Revoked, expired, and unknown share links are byte-for-byte indistinguishable (same 404 status, same neutral body, same `no-store` header), closing the enumeration oracle that distinct "revoked" vs "expired" vs "not found" responses would open. The strict Content-Security-Policy (default-src 'self', no third-party origins, self-hosted fonts) applies across the reader surface, and no link-preview metadata leaks a confidential report's title to a chat or email unfurler.
- Upload-form streaming cap parity (2.4 follow-up): the workspace multipart upload now enforces the 50 MB cap by streaming the raw request body and aborting the instant cumulative bytes exceed it, so an oversized upload is rejected with the same 413 before the multipart body is ever fully buffered - matching the API push (4.3) guard. A declared over-cap `Content-Length` is the cheap pre-read rejection; the streaming abort is the real bound for a chunked or under-reported body. The cap logic is now a single shared helper (`readStreamToCap`) both ingestion entries use, so the two cannot drift. The existing 413 response shape, success path, and diagnostics are unchanged.
- API token realm separation (story 4.1, D10/NFR12/AR12): the programmatic `/api/*` surface accepts a PAT bearer token only and never a cookie, while the author and reader cookie realms never accept a PAT - the two directions are enforced (the API auth hook consults only the `Authorization` header; the cookie guard excludes `/api/*` entirely) and tested. An unauthenticated API call returns a 401 problem+json, not a 302 to login, so a script gets a machine-actionable error rather than an HTML redirect. Tokens are stored only as a SHA-256 hash (the raw token is shown once and never logged - pino redaction covers `authorization`/`token`/`cookie`, and no PAT value ever reaches a log line), the bearer prefix is verified before any database lookup, and authentication failures are rate-limited per-IP plus a global brake to bound bearer guessing. The `/api/*` error boundary maps a thrown `AppError` to its problem+json status and turns any unexpected error into an opaque 500 with no internal detail leaked to the client.
