# Changelog

All notable changes to Acta Diurna are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Per-report reader width (full-bleed or a fixed max width).** After the content column went fluid, the `/view` and published reader were always full-bleed, with no per-report control. The document now carries an optional `width` (CSS px, additive - absent means full-bleed, the prior default, so every existing report renders unchanged and no schema version bumps). A compact "Width" control in the editor tool strip opens a popover with a Full / Fixed segmented toggle, one-click presets (960 / 1080 / 1280 / 1600), a px stepper, and a live diagram showing the column's share of a wide viewport so the value reads as a proportion before publishing; the popover dismisses on Escape or a pointer press outside it; the width is bounded 640-2400 px and validated before it lands. The reader render applies it as a single `--reader-width` override on the report root, which the content column, the change summary and each section already read - so `/view`, the published reader and the editor's live preview all cap at the author's chosen width (prose still holds its 70ch measure, so a fixed width mainly contains the wide blocks and the overall column). Threaded onto the reader/preview view-models, covered by schema-bounds, view-threading, render-application, control-component and an end-to-end e2e suite. (Romain G.)
- **In-editor document-level scales CRUD with key-rename cascade.** Document scales (the shared severity / source category sets that legend, comparison-matrix, chip-cluster, table and timeline blocks reference by key) were only writable through a whole-document `PATCH` - out of reach of an author working in the browser, who could edit blocks and bind data but never retouch the scales themselves. A collapsible "Scales" panel now sits at the top of the editor (a document-level surface, like the theme picker, not the per-selection inspector): declare and reorder scales, edit each entry's label / colour / sublabel freely, mark a scale ordinal or nominal, and add / remove entries. The delicate part is the KEY: a scale key and an entry key are referenced across the document, so renaming one would dangle every referrer at validation. Renaming a key here therefore cascades through every reference via pure, isomorphic transforms (`renameScaleKey` / `renameEntryKey` in `lib/schema/scale-cascade.ts`, the exact mirror of the cross-reference validator - `legend.scaleRef`, `chip-cluster.scaleRef` + `entries`, `comparison-matrix.severityScale` / `.sourceScale` / `findings[].severity` / `findings[].sources` object keys, `table.columns[].scaleRef` + cell values, `timeline.status.scaleRef` / `.entry`), and the editor reseeds its working copy from the result, exactly as a binding reconcile does. A key change is validated for slug shape and uniqueness before it fires (and reverts with a notice otherwise), and a scale or entry that is still referenced cannot be deleted - the guard names the referring blocks instead of orphaning them. Read-only when the report is published. The cascade transforms are covered by an exhaustive unit suite (every reference site, plus a `validateDocument` round trip proving a renamed document stays valid), the panel by a component suite, and the add-and-persist round trip by an e2e. (Romain G.)
- **Configurable SMTP sender display name (`SMTP_FROM_NAME`):** an optional env var sets a friendly sender name so recipients see, for example, `Acta Diurna <reports@example.com>` instead of the bare address. When set, the mailer sends the From header in nodemailer's `{ name, address }` form (which RFC 2047-encodes the name); when unset, the bare `SMTP_FROM` address is sent unchanged - fully backward compatible. The value is part of the all-or-nothing SMTP block and rejects a line break at boot, so it can never inject an extra mail header. Documented in `docs/ops/deployment.md`. (Romain G.)
- **Persistence UX - autosave status, in-tab undo/redo, conflict handling, and publish (story 10.7):** the WYSIWYG editor's persistence UX is now complete on the SAME 10.1 working-copy / debounced-preview / validated-save seam - no parallel model, no new write path, no schema change. AUTOSAVE: the existing 800 ms debounced autosave (validate-on-write through `?/save` -> `updateReportDocument`, each save asserting the loaded `expectedUpdatedAt` for optimistic concurrency) now drives an accessible status indicator (`role="status"` + `aria-live="polite"`) that announces saving / saved-at-<time> / "Save failed - retry" with an explicit retry control; an infrastructure failure (server unreachable, 413 / 400 / 5xx with no inline errors) shows the retry-able failed state, while a validation failure still renders inline at the failing block (not in the indicator), and a 409 keeps its own conflict banner. UNDO/REDO: a genuine in-tab document-history of `$state.snapshot(doc)` snapshots (`EditHistory`), coalesced so a burst of typing is ONE undo step (records off the same ~200 ms settle the preview and validation use), bounded depth 50, with Ctrl/Cmd+Z / Shift+Ctrl/Cmd+Z (and Ctrl/Cmd+Y) plus visible labelled Undo / Redo buttons (an undo affordance is never keyboard-only, NFR15). An undo/redo MUTATES the working copy and rides the same validated-save seam (it is just another edit that autosaves). The key correctness point: a SERVER reseed - a binding reconcile (10.5), a publish / unpublish, or a 409-resolved reload - establishes a NEW baseline the author cannot step PAST into stale state; the history is reseeded to that baseline (both stacks cleared), so undo can never resurrect a pre-reconcile / pre-publish document the server has moved beyond. The previewed audience level is a VIEW concern owned by `LivePreview`, never part of the working copy, so it is excluded from the history by construction (10.6 Dev Notes) - switching the preview level is not an undoable edit. CONFLICT: the 10.1 optimistic-concurrency 409 banner (preserve the in-memory edits, offer reload-and-reapply, never a silent last-writer-wins) is confirmed and now COMPOSES with undo - an undo after a conflict reverts the working copy without advancing or corrupting the concurrency token (the 409 path never touches `expectedUpdatedAt`). PUBLISH / UNPUBLISH from the editor is confirmed: it flushes / guards pending edits (the existing dirty-guard), reseeds the concurrency token from the action result, and now reseeds the undo baseline too. Everything is WORKSPACE-only behind the author cookie: the reader path ships zero editor code and the reader bundle is byte-identical (76.0 KB / 200 KB, NFR3, verified equal to the pre-change build) and `pnpm schema:export` is unchanged. Covered by a pure `EditHistory` unit suite (undo / redo / burst-coalescing / bounded depth / fork-on-edit / reseed-no-step-past / deep-clone isolation), component tests (undo restores and redo re-applies, a publish removes the steppable history, the status indicator, a view-only interaction is not an undoable edit), and a desktop e2e (edit / undo / redo reflected in the document and the preview, a keyboard undo, a stale-token conflict preserving edits with undo composing after, publish-from-editor, axe-clean). (Romain G.)

The switcher's chosen level is now lifted into `LivePreview` and re-seeded across the editor's settled-snapshot remount (`{#key document}`), so the author keeps authoring against the level they picked instead of the preview snapping back to `full` on every edit; a new `onlevelchange` callback on `Report` reports the embedded switch up (the reader passes none, so it tree-shakes out of the reader path). Audience TAGS are set through the existing `AudiencePicker` (section and block level, already mounted), the tag lands on the in-edit working copy and the level-switched preview reflects it immediately, and it persists through validate-on-write. SPEAKER NOTES are now edited in place: a new `SectionNotesEditor` edits the author-only section `notes` field on the working copy through the same 10.1 validated-save seam. CRITICAL PRIVACY: notes are author-only and the reader-serving chokepoint already strips them (`stripSpeakerNotes` at `getPublishedDocument`, story 6.2) - the render tier never reads the field, so notes never appear in the reader render or the reader-facing preview output; the editor cannot make them reader-visible. A no-leak tripwire pins this on the editor preview path (`toPreviewView` carries no `notes`) and the e2e mints a real reader share and asserts the note is absent from the served DOM and the SSR HTML. Everything flows through the working-copy / debounced-preview / validated-save seam; accessible (labelled controls, the reader switcher's operable visually-hidden radios, an axe-clean editor surface) and workspace-only - the reader bundle is byte-identical (75.9 KB / 200 KB, NFR3) and the schema export is unchanged. A clean seam is left for 10.7 (autosave / undo / publish). QA hardening: the notes-privacy guarantee is now type-enforced (`SectionView.notes?: never` makes any render-tier `notes` a compile error, not just a discipline); the embedded preview no longer reads the reader URL hash on remount, so an editor URL fragment can never transiently promote the previewed level off the author's choice; the `level` prop's one-time-seed caller contract is documented on `Report`. - **Data binding from the WYSIWYG editor (story 10.5):** an author binds, rebinds and remaps a bindable block (table / chart / kpi) to an uploaded data set from WITHIN the editor, at the block being edited, instead of a separate screen. It reuses the EXISTING binding engine end to end - the `?/bind` / `?/rebind` / `?/remap` actions and the `bindBlock` / `rebindReport` / `remapField` services with their closest-field (Levenshtein) diagnostics - and surfaces the same green / amber / red per-block diagnostic chips and the remap affordance (the existing `BindingChip` / `DiagnosticPanel`) AT the block, not only on the refill panel; nothing is re-implemented. The block shows its bound-vs-static state clearly (a "Bound to data set" badge with the FR16 "Data as of" freshness instant, or "Static data" when it carries only authored rows / series / items), and the static shape (edited in 10.3 / 10.4) and the bound shape coexist per the schema's existing `requireStaticDataOrBinding` contract - no schema change. The key correctness wiring is the optimistic-concurrency reconciliation: a bind / rebind / remap is a server mutation that advances the report's `updatedAt`, so each action now returns the re-resolved document plus its new timestamp, and the editor reseeds its working copy and advances `expectedUpdatedAt` from that result (the same self-contained reconciliation publish / unpublish use, plus the document reseed), so a subsequent document save asserts the post-binding state instead of spuriously 409-ing. The binding panels no longer `invalidateAll` (which would clobber in-flight edits and leave the token stale); they report their result up to the editor. The binding write inherits the single write chokepoint's `MAX_DOCUMENT_BYTES` (413) and owner scope. Workspace-only: the reader bundle is byte-identical (75.9 KB / 200 KB, NFR3) and the schema export is unchanged; the diagnostic types are type-only imports that erase at build. (Romain G.)

- **Per-block-type field editing for the five core blocks (story 10.3):** each CORE block type (text, table, chart, kpi, image) now has its own direct-manipulation field editor wired to the live preview, so an author edits a table as a grid, a chart as series config, and text as inline-formatted runs - not raw JSON. TEXT is the headline gap: the 1.5 editor was a textarea that flattened a paragraph to one unformatted run, discarding marks; it is now a RUN-level editor where each run carries the schema's mark vocabulary (`inlineRunSchema`: bold / italic / inline-code toggles and an http(s) link href - the exact set `InlineRuns.svelte` renders), with runs and paragraphs added / removed / reordered. - **Block palette and structural editing (story 10.2):** the workspace editor now carries a BLOCK PALETTE and direct-manipulation structural editing of blocks and sections, so an author builds and restructures a report visually instead of through one big form. The palette offers exactly ONE entry per member of the block discriminated union (text, table, chart, kpi, image, comparison-matrix, field-grid, legend, set-membership, chip-cluster, callout, code, card-grid, list, timeline - the meta-strip is the field-grid `layout: 'strip'` variant, not a separate union member, so it is reached through the field-grid editor); the catalogue (`blockPaletteEntries`, `editor-state.ts`) is `satisfies Record<BlockType, ...>`, so a new block type added to the union is a COMPILE error here and the palette can never silently omit or stale-list a type. Picking an entry inserts a default-shaped block of that type SEEDED FROM `newBlock` at the end of the section - no new block type, no new block shape, the existing catalogue exposed - so the new block is at most one keystroke from valid (an empty-field block is the author's inline guidance, never a blocker). Structural editing covers ADD (from the palette, or a new section via `newSection`), REORDER (keyboard-accessible move up / move down via `moveItem` - the NFR15 baseline; drag is deliberately deferred, see below), and DELETE for both blocks and sections. Every structural change flows through the SAME validated working-copy + save path the shell (10.1) established: the change mutates the in-edit `$state` document, the debounced live preview re-renders it through the pure `$lib/render` tier, the validated save persists it, and optimistic concurrency holds - no parallel model, no second write path; a structural edit that leaves the document invalid (an emptied section) is the actionable 422 inline at the offending element on save, never a silently dropped or half-saved document (the server validate-on-write stays the authority). ACCESSIBILITY: the palette is a labelled group ("Add a block to <section>") with an explicit `aria-label` and a visible one-line description per entry, and add / delete / move manage FOCUS so a keyboard / screen-reader user never loses their place - a moved block keeps focus (repeated up/down presses keep working), an added block is focused, and after a delete focus lands on the neighbour that took its place (or the palette / "Add section" button when the list empties); the block and section cards are `tabindex="-1"` scripted focus targets (out of the tab order) with a visible focus ring. The editor stays a WORKSPACE-only desktop surface: the reader path ships zero editor code and the reader bundle is byte-identical at 75.8 KB / 200 KB (NFR3), and the document JSON Schema is unchanged (`pnpm schema:export` no diff - no new block types). This story scopes STRUCTURAL editing only; per-block-type FIELD editing is 10.3/10.4 - a newly-added block is a default shape here, and the per-block editors already mounted by `BlockEditor` are the seam they refine.
- **Block palette and structural editing QA remediation (story 10.2):** the palette entry list is now derived from the TYPED public Zod API (`blockSchema.options.map((o) => o.shape.type.value)`, the same expression the palette exhaustiveness test asserts on) instead of `Object.keys(BLOCK_CATALOGUE) as BlockType[]` - the unsafe cast that discarded the compile-time exhaustiveness the `satisfies Record<BlockType, ...>` design rests on. The TYPES come from the schema (a sound `BlockType`, no cast) and the LABEL/DESCRIPTION from the catalogue (still `satisfies`-exhaustive), so both guards hold and the palette still lists all 15 types in the catalogue's declared order. The exhaustiveness BACKSTOP (`BlockRenderer.exhaustiveness.test.ts`) is aligned to the SAME public path, dropping the defensive internal-chain introspection (`.def.shape.type.def.values`) that could silently degrade to empty strings and still pass the count check - one canonical introspection now backs both the unit test and the backstop. The emptied-section focus fallback no longer walks the DOM (`closest('section').querySelector('[data-block-palette] button')`): `BlockPalette` exposes a bindable `ref` to its first entry button and `removeBlock` focuses it directly, mirroring the ref-anchored "Add section" fallback. The binder and set-membership source lists (`bindableBlocks`, `matrixBlocks`) now derive off the debounced `settledSnapshot` rather than the live `doc`, taking those structural flatMaps off the keystroke hot path (they are fine to lag the 200 ms settle), and the adjacent `moveItem` reorder is a single in-place swap instead of two array splices. Workspace-only and behaviour-preserving for the author: the reader bundle is byte-identical at 75.8 KB / 200 KB and the document JSON Schema is unchanged. Tests added: a component test for section reorder (move-down on the first of two sections swaps them and focus follows) and for the emptied-section inline 422 (the message surfaces at that section's IssueList, not document-level), an e2e for keyboard-only section move (mirroring the block keyboard-move spec), and the duplicated e2e helpers (`createDraft`, `FORM_HEADERS`) are extracted to `e2e/helpers.ts` and imported from one source.
- **WYSIWYG editor shell - load, edit-in-place, validated save (story 10.1):** the workspace editor now carries an authoritative live preview rendered by the SAME pure `$lib/render` tier the reader uses, so what the author edits is what the reader gets - not a lookalike. The editor reuses the existing embedded preview component (`LivePreview`, `src/routes/(workspace)/reports/[id]/preview/LivePreview.svelte`), fed the LIVE in-edit document snapshot, so the preview re-renders through `toPreviewView` on every edit (a transiently-invalid snapshot still renders valid blocks and flags the rest rather than crashing). This EXTENDS the existing edit route, it is not a second editor or a parallel write path: every save still flows through the one validate-on-write service (`updateReportDocument` -> `validateOrThrow`, `src/lib/server/documents/reports.ts`), an invalid document returns the RFC 9457 422 `errors[]` rendered inline at the failing block, and a published report refuses document writes (409) and loads read-only. OPTIMISTIC CONCURRENCY is now wired through (the service already supported `expectedUpdatedAt`; the save action did not pass it): the editor records the loaded `updatedAt` and asserts it on every save, so a write that lands after a concurrent edit (a second tab, an API push, an MCP write) is rejected with the 409 `/problems/report-conflict` and surfaced with a reload-to-reconcile affordance, never a silent last-writer-wins overwrite. Client-side OPTIMISTIC VALIDATION places inline guidance before any round-trip by parsing the live document against the SAME isomorphic `documentSchemaV1` the server validates with (`optimisticDocumentIssues`, `editor-state.ts`); it imports the schema OBJECT (which the renderer already ships), never the server-side `validateDocument` error machinery, so the editor adds ZERO bytes to the reader path - the reader bundle stays byte-identical at 75.8 KB, well within the 200 KB budget (NFR3). The editor stays a workspace-only, owner-scoped, author-cookie surface: no realm change, no reader-bundle JS. This story is the SHELL only (load -> editable working copy -> live preview -> validated save -> optimistic concurrency -> published read-only); the block palette and structural editing (10.2), per-block editing (10.3/10.4), data binding from the editor (10.5), audience-aware preview and speaker notes (10.6), and autosave/undo/redo/publish UX (10.7) build on the seams left here.
- **WYSIWYG editor shell QA remediation (story 10.1):** the live preview and the optimistic inline validation no longer recompute on every keystroke. Both now read a single DEBOUNCED "settled" snapshot of the in-edit document (one `$state.snapshot` per ~200 ms instead of two deep clones per keystroke), so the expensive work - the full `documentSchemaV1` safeParse with its three cross-reference passes, and the embedded preview's `{#key}` remount of the whole `Report` tree (re-running its onMount, IntersectionObserver, and every chart's d3 geometry) - fires ~200 ms after typing stops rather than per character. Inline errors and the preview update smoothly, not on every key; the 800 ms autosave debounce stays separate. The autosave CONCURRENCY contract is now explicit ahead of 10.2-10.7 adding more save triggers: a single named `scheduleSave()` seam, an explicit `pendingSave` flag (at-most-one-in-flight, at-most-one-queued, flushed in the enhance callback's `finally`), and an owned `conflict`-flag transition (cleared on the cancel-when-in-flight path and dropped on a 409, never left stale). Publish/unpublish now reseed the concurrency token from the action RESULT (the action returns the new `updatedAt`) instead of depending on prop-update ordering after `invalidateAll`. The reader-purity boundary is now VERIFIED, not trusted: a focused test builds the `/r/[token]` static-import closure and asserts no reader chunk carries the version-registry / migration-chain fingerprints, and an ESLint `no-restricted-imports` forbids the render tier from importing `validateDocument` / `migrateToVersion` / `schemaRegistry` from `$lib/schema`. The duplicated `formatIssuePath` is removed - the editor and the server `errors.ts` now share one canonical formatter in a dependency-free leaf module (`$lib/schema/issue-path`), keeping the reader path at 75.8 KB / 200 KB. No user-facing API change; reader bundle unchanged.
- **Reader-facing change summary, opt-in and audience-aware (story 9.5):** an author can optionally show readers a "changes since the previous issue" panel so a returning reader orients on the deltas instead of re-reading the whole report. The summary surfaces, per AC1, the sections added/removed/updated since the previous issue plus the headline data movements under them (the already-baked KPI deltas). It is OPT-IN and OFF by default: a new additive, optional `changeSummary` field on the document (`{ enabled, entries? }`, `src/lib/schema/blocks/shared.ts`) carries the author's opt-in; a document without it, or with `enabled: false`, validates and renders byte-unchanged (no schema version bump). The leak-safe `entries` are BAKED server-side at publish time (`publishReport`, `src/lib/server/documents/bake-change-summary.ts`), AFTER the 9.4 delta bake so the headline movements read the freshly-baked deltas: the platform diffs this issue's published snapshot against the predecessor's under the SAME owner scope (the 9.2 engine, owner-scoped like the delta bake, so a cross-author predecessor is the same neutral 404 and a summary never spans authors), distills the `SeriesDiff` to sections-plus-movements (`src/lib/schema/change-summary.ts`), and freezes the result into the snapshot. The PURE reader component (`src/lib/render/ChangeSummary.svelte`) reads it straight off the validated document - SSR, escaped values only (no `{@html}`), no `$lib/server`, no client compute - and is audience-aware: each entry carries its section's own audience tags on `data-audiences`, so the SAME reader CSS that hides a section at the reader's level hides its summary line, and the panel never references a section the level conceals (AC2). No prior-issue raw content, speaker notes, or draft content ever enters the summary - only the leak-safe facts the reader is already served (section ids/titles, the change verdict, audience tags, and the baked deltas). The panel is omitted entirely on a first issue, an unpublished predecessor, a substantial-drift pair, or when the opt-in is off (omit-rather-than-mislead). Renderer-pure, axe-clean on the default theme, and the neutral/revoked/expired share posture holds unchanged (AC4). Reader-path JS stays at 75.8 KB, well within the 200 KB budget (NFR3). QA remediation: a headline movement now carries its OWN leak-safe audience tags on `data-audiences` (the intersection of the section's and the KPI block's tags, additive on the movement schema), so the SAME reader CSS that hides a block hides its movement line - a `technical`-tagged KPI inside a section visible at `summary` no longer leaks its baked figure into the `summary` panel. A movement whose KPI has no usable label is omitted entirely (rather than borrowing the section title), and an added section emits no movements by an explicit short-circuit.
- **Numeric delta annotations on KPI figures (story 9.4):** a data-bound KPI now shows an up/down/flat movement against the same figure in the previous issue of the series (e.g. "revenue 1.2M, +200,000 (+20%) vs previous issue"), so a reader sees the change without the author hand-typing it every cycle. The delta is computed SERVER-SIDE at publish time (`publishReport`, `src/lib/server/documents/bake-delta.ts`): the platform resolves the predecessor's published snapshot under the SAME owner scope (reusing the 9.1 lineage edge and the 9.2 owner-scoped snapshot read, so a cross-author or unknown predecessor is the same neutral 404 and a delta never spans authors), matches the KPI block by its stable id, and bakes the resulting delta (prior value, direction, signed absolute and relative change) onto the binding - the same precompute-onto-the-binding pattern as the `data_as_of` caption (story 6.4). - **API tokens (story 4.1):** create and revoke personal access tokens from the workspace settings so scripts and agents can authenticate to the programmatic API (D10). A token is a high-entropy bearer credential (`acta_pat_` prefix + 256-bit body) shown exactly once at creation with one-gesture copy; only its SHA-256 hash is stored, so a database leak exposes no usable token. The settings list shows each token's name, a non-secret last-four display fragment, creation and last-used timestamps, and an active/revoked status chip; revocation is one click (a two-step confirm) and never deletes the row (an audit trail). API requests authenticate via `Authorization: Bearer <token>` only - this is a third, strictly separated auth realm (a browser cookie never authorizes the API, and a token never opens a workspace or reader session, NFR12). A missing, invalid, or revoked token gets an RFC 9457 problem+json 401 with `WWW-Authenticate: Bearer` (never a redirect to login), and API authentication failures are rate-limited per-IP with a global brake (AR4, AR12). This establishes the `/api/*` PAT-bearer path and the shared `/api/*` error boundary that maps any thrown `AppError` to problem+json, on which the rest of the programmatic surface builds.

### Security

- **Magic-link verification survives mail-gateway link scanners (audit finding A1).** The author and reader magic-link landings consumed the single-use token inside the GET that the emailed link points to. A mail-gateway link scanner (Microsoft Defender SafeLinks, Proofpoint URL Defense, Mimecast) GET-prefetches delivered links, so the scanner atomically consumed the token before the human clicked, landing them on the expired path - and in MULTI mode the author email magic link is the only auth path, so a scanning gateway could lock out every author. Both landings (`/login/verify`, `/r/[token]/verify`) are now prefetch-safe POST-to-consume interstitials: the GET `load` PEEKS the token (a read-only validity SELECT, `peekAuthorVerificationToken` / `peekVerificationToken`, no `consumed_at` write) and renders a minimal "Confirm sign-in" / "Confirm and view report" page whose only action is a same-origin POST that runs the unchanged atomic consume + session mint. A scanner's prefetch only renders the interstitial; the human's click still consumes the live token. Every prior property is preserved: enumeration-neutrality (an unknown / expired / already-consumed / wrong-share token peeks false and shows the SAME neutral expired state, no oracle), single-use + 15-minute TTL (enforced at the POST consume, atomically, unchanged), the same per-IP / per-share / global rate-limit envelope on the GET (the peek does not consume the token, so a prefetch costs only rate-limit budget), CSRF (the POST is a same-origin SvelteKit form action, so the built-in origin check applies and is never disabled), the reader leak-neutral 404 posture (the closed-share neutral 404 runs before the mode branch), and no-store + noindex on both routes. The interstitial carries no report title and no author identity, so a scanner-rendered page leaks nothing, and the reader interstitial is a no-JS form POST so the reader JS budget is unaffected (72.9 KB / 200 KB). Server-only, no schema change, no migration.
- **MCP generation tools are now metered by the same per-author LLM cost brake as the REST surface.** The `generate_outline` and `generate_report` MCP tools issued metered `chatComplete` calls with no rate limit - the `apiAuth` hook consumes a rate token only on an auth FAILURE, so an authenticated PAT could drive unbounded paid LLM calls through `/api/mcp`, a cost/DoS gap the REST `POST /api/v1/reports/generate/{outline,fill}` routes already closed with `aiGenerationLimiter`. Both tools now consume the SAME `aiGenerationLimiter` BEFORE any LLM call, keyed per AUTHOR (`mcpGenerationRateKey(scope.authorId)`, since the MCP tool boundary carries the `AuthorScope`, not a token id) - so one author's MCP generation burst is capped across all their PATs, and a single logical call still costs exactly one token on whichever surface issued it (no double-charge across surfaces). On deny the tools return the standard RFC 9457 429 problem via the MCP tool error channel and make no call. The REST routes are unchanged (still keyed per token); server-only, no schema change, no migration, reader budget unaffected.
- **MCP `push_data_set` rejects an oversize body before buffering it.** The tool encoded the full JSON-RPC `content` string to bytes before `ingestBytes` checked the 50 MB cap, so an over-cap push got a full UTF-8 copy here on top of the one the service does. The shipped `BODY_SIZE_LIMIT` already bounds the transport body, so this was a residual extra-copy concern, not unbounded - but the tool now rejects an over-`MAX_UPLOAD_BYTES` `content` up front with a cheap `Buffer.byteLength` measure (allocating nothing), returning the same `tooLarge` 413 problem-details the REST push returns before the encode. Reuses the existing `MAX_UPLOAD_BYTES` constant and `tooLarge` factory; server-only, no schema change.
- **Boot warning when a remote database link is unencrypted (audit finding A2).** The pg pool was built from `DATABASE_URL` with no explicit TLS, so a non-loopback database host with no `sslmode=` directive would ship queries in cleartext over the network with no signal. The default docker-compose path (the app talking to a sibling Postgres container by service name) is non-loopback but a private-network link that does not use TLS, so failing boot would break the primary deployment; instead, under `NODE_ENV=production`, the app now logs a single clear `logger.warn` at first connect when the `DATABASE_URL` host is non-loopback AND the connection string declares no TLS (`sslmode=` other than `disable`, or `ssl=true`), stating that DB traffic is unencrypted and that a remote database should set `sslmode=require`. Loopback hosts and any URL already declaring TLS are exempt (no warn), and the warning is never fatal. The `isUnencryptedRemoteDbLink` predicate is unit-tested and documented under "Database transport security" in [`docs/ops/deployment.md`](docs/ops/deployment.md). Server-only, no schema change, no migration.
- **Boot warning when ADDRESS_HEADER trusts an inbound forwarded-for header (audit finding B1).** Per-IP rate limiting keys on the client IP adapter-node derives, and setting `ADDRESS_HEADER` makes adapter-node trust an inbound `X-Forwarded-For` header for that IP - spoofable if no fronting proxy overwrites the client-supplied value (the default ships `ADDRESS_HEADER` unset, which trusts the socket peer and is safe). The app now logs a single boot `logger.warn` when `ADDRESS_HEADER` is set, reminding the operator that per-IP limits are spoofable unless the proxy overwrites inbound XFF (the bundled Caddy profile does). It is advisory - there is no trusted-proxy assertion to validate against, so it warns whenever the header is non-empty and never fails boot. `ADDRESS_HEADER` is read straight from the environment (adapter-node consumes it, not the Zod schema), and the `trustsInboundForwardedHeader` predicate is unit-tested. Server-only, no schema change, no migration.
- **Author email-domain is re-checked when the magic link is consumed (audit finding A3).** The author sign-in domain gate (`isAuthorEmailInDomain`) ran only at link ISSUE, not at consume, so a token issued while an email was in-domain would still provision an author and open a session even if `AUTHOR_EMAIL_DOMAIN` had been narrowed in between. `completeAuthorSignIn` now re-runs the domain check after consuming the token and before `ensureAuthor`/session mint; a now-out-of-domain email is discarded onto the SAME neutral null (expired) path - no author minted, no session opened (one pure env read). Three fixes landed. (1) A cross-author skeleton IDOR (the High): the original ownership pass threaded the `AuthorScope` through reports, data sets, shares, and API tokens but missed the `skeletons` table, so in multi mode any author could list / read / instantiate / delete another author's skeleton and the `skeleton-name-taken` 409 leaked a skeleton's existence cross-author.
