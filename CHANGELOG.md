## [Unreleased]

### Added

- **Cursor pagination across the list services, with the audit trail truncation now signalled (full-audit C2):** the report, data-set, API-token, and access-audit list services were capped full scans (a fixed 500/100 ceiling) with no way to page past the cap, and the access-audit log in particular accrued one row per reader access and SILENTLY dropped the oldest past the cap with no signal - audit data lost invisibly. A single shared keyset-pagination contract (`src/lib/server/db/cursor.ts`) is frozen NOW while callers are few, so the shape never ossifies into the REST surface as a later breaking change: a list service takes an optional `{ limit?, cursor? }` and returns `{ items, nextCursor }`, where `nextCursor` is null on the last page and an opaque cursor to pass back otherwise. The keyset orders on `(timestamp DESC, id DESC)` with the time-ordered UUIDv7 `id` as the unique tiebreak, so paging is O(log n) on the index and stable under concurrent inserts (no OFFSET skip/duplicate); fetching `limit + 1` rows is how a further page is detected without a second count query, and a malformed cursor is treated as "start from the newest", never a 500. The access-audit log (`listAccessRecords`) is FULLY reshaped: it keysets on `(accessed_at, id)`, and the audit view now renders a "Load older" affordance (carrying the active report/reader filters) whenever older accesses remain - so the trail is never silently cut off at a page boundary. `listReports`, `listDataSets`, and `listApiTokens` get the same `{ limit?, cursor? }` parameter and `{ items, nextCursor }` envelope; the REST `GET /api/v1/reports` exposes `?cursor=` / `?limit=` and returns the `nextCursor` (the OpenAPI artifact gains both query params and the `nextCursor` response field), and the MCP `list_reports` tool gains an optional `cursor` and returns the page cursor, so the programmatic contract is set from day one. Single-mode owner scoping is unchanged (the owner predicate stays a no-op, the un-cursored single-mode query stays byte-identical), and the audit-view owner scoping is intact. The owned-report dropdown options query is left on a simple cap deliberately (a bounded picker of an author's own reports, not a growing log). Server-only, no schema change, no migration, no new dependency, reader budget unaffected.
- **Type-adjacent tenancy guard over the owning tables (full-audit C3):** multi-author isolation (Epic 8) is enforced by service discipline - every query against an `owner_id` table ANDs `ownerFilter` into its WHERE - but that was not type-enforced: a new owning table whose list forgot `ownerFilter` would COMPILE and PASS the single-mode suite (the predicate is a no-op there), leaking rows only in multi mode where no single-mode test exercised it. A new grep-based vitest (`src/lib/server/authors/tenancy-guard.test.ts`) closes the gap structurally: it discovers the set of owning tables straight from the schema source (so a future `owner_id` table is covered automatically, with no edit to the guard), then asserts every `src/lib/server` file that queries one of those tables (`.from` / `.update` / `.delete`) routes through `ownerFilter` - unless the file is on an explicit, REASONED allowlist of sanctioned unscoped operations. The allowlist documents the three deliberate bypasses: the reader path's `getRowUnscoped` (share-gated, not author-gated), the boot-time legacy-ownership backfill (`inheritance.ts`, a SYSTEM `WHERE owner_id IS NULL` sweep), and the retention/janitor purge (`purge.ts`, an age-policy delete across the whole instance) - each a system operation with no tenant scope, never reachable from a tenant request. A future owning query that forgets the predicate fails this test in single mode, before review. Test-only, no production change.
- **Outline-first AI generation over the REST API and MCP (item 18):** an agent or script can now drive the FR32 outline-first flow Epic 5 deliberately kept workspace-only, at full parity with the workspace. The REST surface adds `POST /api/v1/reports/generate/outline` (intent + optional skeleton/data set -> a bounded outline plus its approval hash) and `POST /api/v1/reports/generate/fill` (the approved outline + its hash -> a schema-valid draft: 201 for a fresh draft, 200 when a `reportId` fills an existing one). The MCP server adds the matching `generate_outline` and `generate_report` tools on the same `/api/mcp` PAT-gated transport. Both surfaces are THIN adapters over the EXACT two-stage generation service the workspace drives (`generateOutline` then `fillFromOutline`) - no generation logic, no prompt bounds, and no validation duplicated in the adapters - so the four surfaces cannot drift (AR5). Both AI gates are enforced IDENTICALLY to the workspace and inside the service: every model call goes through `chatComplete`, which asserts the endpoint is configured AND `AI_GENERATION_ENABLED=true` BEFORE any outbound request, so a disabled instance returns `/problems/ai-generation-disabled` (503, as problem+json over REST, as a problem-details tool error over MCP) and makes NO call. The whole flow is OWNER-SCOPED through the same `resolveApiAuthorScope` -> `AuthorScope` the other endpoints and tools use: the skeleton and data set are read under the caller's scope and the filled report is owned by the caller, so generation can never reach another author's resources (single mode resolves to the implicit author, a no-op). The approval binding is the service's stateless SHA-256 content hash: `fillFromOutline` re-hashes the posted outline and rejects a mismatch with `/problems/ai-outline-stale` (409) BEFORE any LLM call, so content can never be generated from an outline the caller did not approve. SECURITY: because a single PAT identity drives outline -> fill and the hash is a value the caller holds (not server-side redeemable approval state - there is no approval table, nothing globally redeemable), the content-hash binding is sufficient on this single-principal flow; the item-19 server-minted-nonce concern only bites when approval and fill run against SHARED state by DIFFERENT principals, which this design has no surface for, so no nonce was introduced. Each generation issues a metered LLM call, so both surfaces apply the same per-token cost/DoS brake (the `aiGenerationLimiter`) before any call, returning the workspace's 429 on deny. Untrusted model output is parsed defensively and written through the same validate-on-write every surface uses, so a hallucinated invalid document is the 422 with actionable `errors[]` and the draft is left untouched - no bypass. The OpenAPI artifact gains both paths and the outline/request schemas; the MCP server identity bumps to 0.8.0. Server-only, no schema change, no migration, no new dependency, reader budget unaffected.
- **MCP data-push tool (`push_data_set`):** an MCP-capable agent can now push CSV or JSON data onto a report and auto-rebind its blocks over `/api/mcp`, the FR13/14/15 parity of the existing REST `POST /api/v1/data-sets` and the data-push equivalent of the report-authoring verbs Epic 5 shipped. The tool is a thin delegation to the EXACT ingestion + binding services the REST push and the workspace upload call (`ingestBytes` then `rebindReport`): no reparse, no Drizzle, no binding logic in the tool, so the four surfaces cannot drift (AR5). The only transport difference from REST is the body - MCP is JSON-RPC, so the file arrives as a `content` string (the agent's CSV/JSON text) instead of raw request bytes, UTF-8 encoded into the bytes the service takes; `format` (`csv` / `json`) is an explicit argument since there is no `Content-Type` header on a tool call. With a `reportId` the matching draft report auto-rebinds and the result carries the same per-block diagnostics + binding summary the REST push returns; without one the data set is stored unbound. The push is OWNER-SCOPED through the same `resolveApiAuthorScope` -> `AuthorScope` the other MCP tools and the REST surface use, so an agent only ever reaches its own reports and data sets (the multi-author IDOR boundary); single mode resolves to the implicit author, a no-op. A published target is the service 409, an unparseable body the 422, a foreign/unknown `reportId` the scoped 404 - the same problem-details bodies REST returns, carried into the MCP tool error channel. The MCP server identity bumps to 0.7.0. No schema change, no migration, reader budget unaffected (server-only).
- **Theme selection (story 6.5):** an author can pick among multiple built-in themes from the editor header, so different report series carry different identities (FR39, AR10). Two new light themes join the existing pair: **Cool Aurora** (`aurora`, cool paper, slate-teal ink, deep teal accent - a glacial, analytical identity) and **Warm Meridian** (`meridian`, cream paper, sepia ink, terracotta accent - a warm editorial identity), each a complete `--report-*` token block in `app.css` with hex twins in `palette.ts` so the contrast math runs without a browser. Both accents are deliberately darkened from their vivid form because the contrast contract treats the accent as inline/link text, which must hold AAA (7:1) on the paper. A single registry (`BUILT_IN_THEMES` + `THEME_OPTIONS`) is the source of truth the schema, the editor picker and the renderer all share - a lockstep test asserts the palette / categorical / tone tables match the registry, so a half-skinned theme (a name with no token set) fails before render. Theme application is pure CSS and zero JS: every render component already reads only the semantic tokens, so a theme re-skins the whole report (cover, sections, every block, the chrome, the TOC scrim) with no component change, via a `data-theme` on the report root that the embedded editor preview shares so author and reader cannot drift. The fallback path is exactly one place: `resolveTheme(slug)` is TOTAL - a known slug resolves to itself, anything else (absent, unknown, removed) resolves to `default` - so a stored or published document carrying a since-removed theme still validates and renders cleanly in the default (the schema stays soft, `theme: idSchema.optional()`, not an enum, precisely so a stale reference never becomes un-loadable), while a new author selection can only ever be a known theme because the picker offers a closed `THEME_OPTIONS` list. An unknown stored slug surfaces an amber workspace advisory next to the picker (`themeFallbackWarning`, informational not error - the report still renders), distinct from the Epic 7 scale-contrast warning. Each new theme is asserted to the SAME contract axe-core gates for the default - report content (body / muted / heading text, accent-as-link, text on surface) holds AAA (7:1) and the decorative surfaces (accent fill, the six categorical swatches, the five callout tones, the two trend tints) hold the AA floor (4.5:1) on the theme's own paper - machine-checked by the extended contrast tests, and the reader axe e2e now runs on `aurora` (the `full` fixture selects it). No schema-version bump and no JSON Schema artifact change (the registry lives in the render tier); reader budget unchanged at 72.8 KB / 200 KB (themes add CSS, not JS). With this story Epic 6 is complete.
- **Presenter view (story 6.2):** an author can run a meeting from the same published document the readers received, via a separate local presenter window (FR29). The presenter route (`(workspace)/reports/[id]/present`) is an author-only, owner-scoped workspace view (`resolveAuthorScope` + `getReport`, so a non-owner or unknown id is the same 404 - no existence oracle, story 8.2 tenancy) that shows the current section (rendered through the reader `SectionSlide` so the stage looks like what readers see), author-only speaker notes, a next-section preview, an elapsed timer with reset, prev/next + keyboard navigation, and a meeting-mode toggle that hides annex-marked sections from the presented flow (and from the next preview and position counter). All presenter state - current index, meeting mode, timer - lives in the one window: no websocket, no device sync, no real-time (the FR29 non-goal). To carry the notes, `sectionSchema` gains an OPTIONAL bounded `notes` string (additive, 20000-char ceiling, no version bump - a section without notes validates and renders exactly as before; the published `static/schema/v1.json` gains one optional property). Speaker notes are author-only and the privacy is triple-layered: (1) the reader view-model (`toReportView`) maps a section to a `SectionView` with no `notes` field, so the rendered HTML carries none; (2) the reader-served document is STRIPPED at the single reader chokepoint - `getPublishedDocument` runs `stripSpeakerNotes` over every section before the document leaves the server, so notes never ship in the hydration payload even though the HTML already hid them; (3) the presenter view, the only path allowed to read notes, deliberately does NOT use `getPublishedDocument` (which strips them) - it loads the owner's own `publishedDocument` through the owner-scoped `getReport` and pairs notes onto presenter section pairs only, never onto the reader `SectionView`. The draft and the stored snapshot keep their notes untouched; only the served copy is stripped. Published-only (a draft returns a "publish first" state), FR7 version-tolerant via `validateStoredDocument`. A "Present" affordance on the published report in the reports list opens the window. Reader budget unaffected (the presenter is a hydrated workspace route outside the `/r/[token]` reader closure, 72.5 KB / 200 KB).
- **Audience levels (story 6.1):** a reader can switch a report between summary, full, and technical levels, so one report serves their role (FR28). Audience tags have existed on blocks and sections since schema v1; this story adds the reader switcher, the author per-level preview, and the shared visibility logic - no schema change. A single isomorphic helper (`src/lib/schema/audience.ts`: `isVisibleAtLevel` / `hasAudienceTags` / `audiencesAttr`, default level `full`) is the one source of truth the reader switcher, the author preview and the no-JS fallback all derive from, so they cannot drift. The content is rendered SSR at EVERY level exactly as before; the only added reader behaviour is a small native radio group (`LevelSwitcher.svelte`) that sets `data-level` on the report root, and visibility is pure CSS - each block wrapper and section host carries a canonical-order `data-audiences` attribute (untagged elements carry none, so no rule matches and they stay visible at every level) and a scoped `:global([data-audiences]:not([data-audiences~='X']))` rule hides the non-matching elements with `display: none`. `display: none` is chosen deliberately because it removes the excluded block from layout AND the accessibility tree, so a screen reader at "summary" never reaches "technical" content; switching is an instant attribute swap, no re-render and no round-trip, keeping the reader JS budget flat (72.4 KB at this story). The switcher is rendered ONLY when the document carries audience tags - a report with no tags renders identically for everyone and the switcher is hidden (AC2). With JS disabled the root carries no `data-level`, so no hide rule matches and every block renders - the no-JS reader gets the full report, a superset of the default `full` view, not a broken one. The author per-level preview embeds the same `Report` component with the same switcher and `data-level` mechanism, so the author sees exactly what the reader sees (AC3). IMPORTANT - audience tags are a presentation / reading-comfort filter, NOT a confidentiality boundary: every level renders into the authorized reader's DOM (hidden only by CSS), so confidential or per-reader-restricted content must never be gated behind an audience tag; the confidentiality boundary is the share (Epic 3), and the only author-private field (section speaker notes, story 6.2) is stripped server-side before a reader sees it. This invariant is recorded in the code at the audience helper and the `audiences` schema field.
- **Data freshness timestamps (story 6.4):** a data-bound block (table, chart, KPI) now shows a small, unobtrusive "Data as of <date>" caption below its content, so a reader never mistakes stale numbers for fresh ones (FR16). The timestamp is resolved server-side at bind time and baked onto the binding, keeping the renderer pure (no `$lib/server`, no database in the render path): the binding schema gains an optional `dataAsOf` ISO-8601 field (additive, no version bump - a legacy bound block, a placeholder binding, or a static-only block validates and renders unchanged), and `resolveDataAsOf` applies the single precedence rule - the data set's explicit `data_as_of` wins, its injection time (`injected_at`, NOT NULL) is the fallback - so a bound data set always yields a usable instant. The instant is stamped onto the binding by `applyBinding` across all three write paths (bind, FR14 auto-rebind, FR15 remap), so it persists in the document and rides into the published snapshot, and `toReportView` stays untouched and pure (the bound block already carries it). A single shared `DataAsOf` caption component feeds the three bindable blocks so the treatment cannot drift; it renders the date in a fixed locale and UTC (`Intl.DateTimeFormat('en-GB', ...)`, e.g. "8 Jun 2026") so the SSR string is byte-identical on the server and any client (no hydration mismatch, no locale or timezone leak), in the established muted-caption token treatment so it never dominates the block (AAA on the default theme). When a binding carries no usable timestamp (no data set, no `data_as_of`, no parseable instant) the caption is OMITTED entirely - never a placeholder or a misleading "unknown" date - and a non-data-bound block (static rows/series/items) shows nothing. The caption is static SSR markup with zero hydration, so the reader budget is unaffected (72.8 KB / 200 KB). The published `static/schema/v1.json` gains only the optional `dataAsOf` property on each binding node.
- **Mode-aware login and workspace identity, plus operator docs (story 8.6):** the login screen and the workspace now reflect the operating mode, and the deployment guide documents how to run, validate, and recover both modes. The login field split (already driven by the one mode resolver since story 8.3) is refined: SINGLE mode shows only the password field, MULTI mode shows only the email field with a "No password needed." hint and a clearer single-use "Check your email" confirmation - never both, no password field reintroduced in multi mode. In MULTI mode the workspace rail surfaces the logged-in author's identity ("Signed in as <email>") above Sign out, resolved from the magic-link session's author id via a new `authorDisplayEmail`; in SINGLE mode the password author is anonymous (no email shown) and the rail is byte-identical to before. The implicit author's reserved sentinel email is never displayed. The own-resources-only guarantee is the story 8.2 tenancy filtering; this story adds no new affordance that could reveal another author's existence. `docs/ops/deployment.md` gains an "Authentication modes (single vs multi-author)" section documenting the two modes and how the SMTP env selects them, the identity env vars (`AUTHOR_EMAIL_DOMAIN`, `INITIAL_OWNER_EMAIL`, `READER_EMAIL_DOMAINS`, the all-or-nothing SMTP block), the fail-fast boot rules (multi requires `AUTHOR_EMAIL_DOMAIN` + an in-domain `INITIAL_OWNER_EMAIL`), the bare port-25 / no-TLS / no-auth relay support, the `pnpm smtp:test` CLI helper, the first-multi-boot legacy-report inheritance to `INITIAL_OWNER_EMAIL`, and the lockout/recovery procedure (multi mode has no password and no break-glass - fix or remove the SMTP env in compose and restart; removing SMTP regains single-password access, and the multi->single downgrade collapses multi-era reports under the single password author). The README cross-links the new section from its Configuration and Documentation listings. With this story Epic 8 is complete.
- **Mode-aware reader sharing (story 8.4):** reader sharing now branches on the operating mode (story 8.1's `isMultiAuthor()`), so a no-SMTP instance can share again while an SMTP instance keeps verified reader access unchanged. In SINGLE mode a share is an unverified CONSULTATION TOKEN: opening a live share link grants the published reader view DIRECTLY, with no email prompt, no magic-link verification, and no reader session - the high-entropy token IS the consultation grant. The restricted / per-recipient allow-list mode is unavailable without email, and the share services enforce that at the boundary: `createShare` mints a consultation (`open`) token and refuses an explicit `restricted` request (409), and `setShareMode` / `setShareRecipients` refuse restricted/recipient operations (409) in single mode - never silently writing a list that could not gate anyone. The share-management UI hides the restricted-mode and recipient-list controls in single mode and explains the consultation behaviour. In MULTI mode the Epic 3 verified magic-link flow is byte-identical (restricted or open, per-recipient verification, reader-realm sessions). The TRANSITION across a mode change is defined and safe via a single `servesConsultation` predicate that always honours the CURRENT mode, never the mode a share was minted in: a SINGLE-era consultation share viewed under newly-enabled SMTP now requires verification (a stricter gate, never an escalation), and a MULTI-era `restricted` share viewed after SMTP is removed falls back to CLOSED (the neutral 404), never silently opening a recipient-gated link to anyone holding it - closed-not-opened, so a stale share can never escalate access. The leak-free posture holds identically in both modes: the closed-share check (revoked / expired / unknown -> ONE byte-identical neutral 404 with `no-store`) runs BEFORE the mode branch, every serving exit sets `cache-control: no-store`, the `/r/*` `noindex`/`X-Robots-Tag` and strict CSP are route-scoped (mode-independent), and revocation + expiry are unchanged (a revoked or expired consultation link is the same neutral 404, the per-load liveness re-check cuts a consultation read off immediately). The magic-link landing (`/r/[token]/verify`) and the `request-verification` action are inert in single mode (they open no session, issue nothing, and bounce to the neutral state). No schema change and no migration: consultation shares reuse the existing `shares.mode = 'open'` value and all the Epic 3 status / revoke / expiry machinery.
- **Operating-mode foundation and SMTP transport hardening (story 8.1):** the instance now resolves a SINGLE vs MULTI operating mode purely from the SMTP environment at boot, the seam Epic 8 (identity and multi-author) branches on, with no behaviour change yet in single mode (Epic 8 foundation). A new mode resolver (`src/lib/server/mode.ts`, `operatingMode()` / `isMultiAuthor()`) is the single source of truth: SMTP absent resolves to `single` (the password author and consultation-token shares, exactly as today), SMTP configured resolves to `multi`. It is pure and reads the cached, already-validated env, so no separate mode flag can drift from the SMTP config. The env schema gains three identity variables - `AUTHOR_EMAIL_DOMAIN` (a bare email domain), `INITIAL_OWNER_EMAIL` (an email), and `READER_EMAIL_DOMAINS` (an optional comma-separated pattern list, parsed to a trimmed lowercased array) - all OPTIONAL when SMTP is absent so single mode is unaffected. When SMTP is present (multi mode), the boot validation now ALSO requires `AUTHOR_EMAIL_DOMAIN` and `INITIAL_OWNER_EMAIL`, and `INITIAL_OWNER_EMAIL` must sit inside `AUTHOR_EMAIL_DOMAIN` (case-insensitive): a missing or out-of-domain value fails the boot with an actionable message, so configuring SMTP can never silently lock everyone out (multi mode has no password fallback). The SMTP transport is hardened for a bare internal smarthost: `SMTP_TLS_MODE=none` with no `SMTP_USER`/`SMTP_PASSWORD` now builds a transport with `secure:false`, NO `requireTLS` key at all, and NO `auth` object (an `auth: { user: undefined }` would coerce an unwanted AUTH; a `requireTLS` would probe STARTTLS on a relay that does not advertise it), so `transporter.verify()` succeeds on the anonymous profile; the STARTTLS (`requireTLS:true`) and implicit-TLS (`secure:true`) profiles are unchanged. A `pnpm smtp:test` CLI (`scripts/smtp-test.ts`, also `docker compose exec app node scripts/smtp-test.ts`) builds the transport from the env and runs `verify()`, reporting success or the credential-redacted failure (the SMTP response code only, never the host/user/password) and exiting non-zero when SMTP is unconfigured - a pure ops debug helper that never changes the mode. This story adds only the seam and the transport hardening; authentication, ownership, and sharing are unchanged (stories 8.2-8.4), and an SMTP-absent instance behaves byte-identically to before.
- **Field-grid meta-strip layout (story 7.12):** an optional horizontal, centred meta-strip variant on the existing `field-grid` block, so a report header can show Author / Date / Scope / Status as a single divided row under the title rather than a two-column grid (Epic 7 Phase B, the final brick). The block gains an OPTIONAL `layout` enum (`grid` | `strip`): `grid` is the default and current behaviour, `strip` renders the SAME `{ label, value }` items as a horizontal row of label-over-value cells separated by thin dividers, centred, wrapping to a stacked column at the reader mobile breakpoint (768px) via CSS only. The field is additive and optional - this is NOT a new block type, so the block union size, the block-type-hint guards and the structure-tree switch are untouched, and a `field-grid` with no `layout` (or `layout: 'grid'`) validates and renders BYTE-IDENTICALLY to before, no schema-version bump (the published `static/schema/v1.json` gains only the optional `layout` property). The strip styling is purely additive in the renderer: the default path carries no extra class, and the strip path adds zero client JS (the dividers are pure-CSS `::before` pseudo-elements collapsed at the mobile breakpoint), so it is SSR, renderer-pure (every value escaped through Svelte text interpolation, no `{@html}`, so a value reading `<script>` shows as inert text), AAA on the default theme, and within the reader budget (73.2 KB / 200 KB, unchanged). A layout toggle (grid / strip) on the existing field-grid editor completes the authoring surface. With this story Epic 7 Phase B is complete.
- **Timeline / roadmap block (story 7.11):** a milestone timeline with a per-milestone date and status, so an action plan or roadmap reads as a sequence rather than a status table (Epic 7 Phase B, FR2 parity). A new additive `timeline` block carries an optional `title` and an ordered list of `milestones` (capped at 50 - a roadmap past that is a structural smell, split it into phases), each a required `label`, an optional free-form `date`/phase sub-label (free text, NOT a parsed date - a roadmap mixes "2026-06-12", "Q3 2026" and "Phase 1", shown verbatim), an optional rich-text `detail` (the text block's paragraph / inline-run vocabulary, capped at 50 paragraphs, so bold/italic, the 7.8 inline-code chip, and http(s) links all work, rendered escaped through the shared marked-run snippet, no raw HTML), and a `status` that REUSES the document scales (7.1): a `{ scaleRef, entry }` pair carried per milestone (not one scale named once for the whole block as the chip-cluster does, so two milestones may carry statuses from different scales), rendered by the shared status `Badge` (7.5) as a pill with the entry's colour and label - the label text ALWAYS present so colour is never the sole signal (NFR14). The renderer is a pure SSR `<ol>` of milestones (the order is the native list order, the schema carries no per-milestone number, so reordering renumbers automatically) with a pure-CSS connector down the decorative node markers - no SSR SVG, so there is no separate accessible text alternative to maintain: the list IS the structure, the connector is decorative, every value escaped through Svelte text interpolation (no `{@html}`) so a label or detail run reading `<script>` shows as visible inert text. A milestone whose `status.scaleRef` or `status.entry` does not resolve against the document scales yields an actionable problem-details error NAMING the offending milestone (by label) and value at `sections[i].blocks[j].milestones[m].status.scaleRef` / `.status.entry` (FR2 parity), via the document-level cross-reference pass story 7.1 established (extended to resolve the per-milestone status refs the way 7.5 resolves chip-cluster and table cell refs). The block is an additive member of the block union - a schema-v1 document without it validates unchanged, no version bump - and a `timeline` block editor (an optional title, then add/edit/remove milestones each with a label, a date, a status scale + entry picker, and a plain-text-edited rich-text detail) completes the authoring surface. Zero hydration, no new dependency: static SSR markup, AAA report content on the default theme, reader budget 73.2 KB / 200 KB.
- **Structured list and steps block (story 7.10):** an ordered or unordered structured list, including a numbered-steps / procedure variant, so remediation procedures and checklists render as first-class blocks instead of ad-hoc prose (Epic 7 Phase B, FR2 parity). A new additive `list` block carries an `ordered` flag and a list of `items`, each a bold lead `term` and an OPTIONAL rich-text `description` that reuses the text block's paragraph / inline-run vocabulary verbatim (the same bold/italic, the 7.8 inline-code chip, and http(s)-link marks the text and callout blocks honour) - so the description renders escaped through the shared marked-run snippet, no raw HTML. Zero hydration, no new dependency: static SSR markup, AAA report content on the default theme, reader budget 72.5 KB / 200 KB.
- **Card grid block (story 7.9):** a responsive grid of icon + title + description cards, the "vision / benefits" summary that presents a set of takeaways, features or highlights without a table or prose (Epic 7 Phase B, FR2 parity). A new additive `card-grid` block carries a `columns` desktop column count (1-4, schema-capped so the cards never crowd the reader column) and a list of `items`, each an OPTIONAL `icon` (the 7.6 registry, by name), a bold `title` and a short one-line `description` - author-written prose, NOT bound data (no `binding` field), both strings plain bounded text (title 200, description 500 characters), the list capped at 24 like the field grid. - **Automatic rebinding and binding diagnostics (story 2.5):** inject a fresh data set onto an already-bound report and every matching block re-resolves in one action, no manual re-mapping (FR14). When a field is renamed or missing, an actionable per-block diagnostic names the block, the expected field, and the closest available match (hand-written string distance); the author remaps it in place and the remap persists in the binding (FR15). Per-block status chips (green bound, amber drifted, red unresolved) and a header "N bindings - all green" summary make the weekly refill glanceable (UX Flow B). The recurring cycle - skeleton, instantiate or duplicate, inject, glance, share - is now complete end to end.
- **SMTP mail service (story 3.1):** authenticated SMTP relay (nodemailer over STARTTLS/TLS/none) configured entirely from environment variables, validated for shape at boot but never tested for reachability so an unconfigured or down relay cannot stop the container (FR36, NFR7). A Settings page sends a test email and reports success or the exact, credential-redacted failure inline, so a delivery problem is always surfaced to the author and never dropped silently (NFR16). Provides the `sendMail` transport and a template seam that the reader magic-link flow builds on.
- **Share links with expiry (story 3.2):** generate a high-entropy share link (256-bit token, hashed at rest) on a published report, with an optional author-chosen expiry (FR17, FR21, NFR6). The link is shown exactly once at creation with one-gesture copy; only its SHA-256 hash is stored, so a database leak exposes no usable link. A draft report refuses sharing with a clear "publish first" message (FR6). The share-management surface lists each link's status (active, expired, revoked) without ever re-exposing the token.
- **Reader verification by magic link (story 3.3):** a reader opening a share link is met by a themed, branded verification card (never a generic auth wall) and verifies their email once; a single-use, 15-minute, email-and-share-bound magic link (256-bit token, hashed at rest) opens a persistent reader-realm session, after which they read freely with no re-verification while the session and share remain valid (FR18, FR22, FR23, NFR6). The reader realm is a second, strictly separated session realm (its own `acta_reader` cookie, no expiry by default so the share's own expiry and revocation govern access, with an optional `READER_SESSION_TTL` to force sessions to age out, and per-share scope so a session for one report grants nothing for another) (NFR12). Verification responses never reveal whether an email is authorized or known - every email yields the same neutral "check your email" confirmation, and a closed or unknown share serves one identical neutral 404 (NFR9). Each verified access is recorded for audit (one global reader identity per email, many access records).
- **Restricted and open share modes (story 3.4):** each share is either restricted to an author-managed recipient allow-list or open to anyone who holds the link and verifies their email (FR19, FR22). In restricted mode an email absent from the list receives the exact same neutral "check your email" confirmation as a listed one but is never sent a magic link and never gets a token, so the refusal reveals nothing about who is on the list (NFR9). The author manages the recipient list per share from the share surface (add or remove emails, switch a share between restricted and open); recipient emails are normalized so case and whitespace never split one address into two entries.
- **One-click revocation and leak-free posture (story 3.5):** an author revokes any share in one click (a two-step destructive confirm); revocation is immediate and irreversible, takes effect on the reader's very next request with no cache window, and cuts off any already-verified reader mid-session (FR20). A revoked link - exactly like an expired link or a never-existed token - serves one byte-for-byte identical neutral page ("This link is not available") that leaks nothing: not the report title, not the reason the link is closed, not whether the token ever matched a share (FR20, FR21, NFR9). The whole reader surface is hardened (NFR10): `noindex/nofollow` on every share, verify, and neutral route; `Cache-Control: no-store` on every sensitive response so a revoked link's prior content is never replayed from a cache; no OpenGraph or Twitter-card metadata, so a link pasted into chat or email unfurls nothing about the report; and a strict Content-Security-Policy with zero third-party assets (self-hosted fonts, no CDN). A mis-sent link is a non-event.
- **Data push and published schema (story 4.3):** push a data set onto a report over `/api/v1/data-sets` and fetch the document schema over `/api/v1/schema`, so the inject-and-render cycle runs unattended (FR13, FR14/15 parity, AR2, FR31 groundwork). The OpenAPI spec now describes both endpoints. With this story the V1 MVP is complete end to end: create and publish over the API (4.2), push data and rebind unattended (4.3), and read over the public reader surface (Epic 3) - the dogfooding gate opens.
- **Reports API with workspace parity (story 4.2):** full report CRUD and publish lifecycle over `/api/v1/reports` for scripts and agents, behaving identically to the workspace because every endpoint is a thin adapter over the SAME service layer (FR30, AR5). `POST` creates a draft (a blank starter with an optional title, or an instantiated `document`); `GET /reports` lists in a `{ items }` envelope (forward-compatible for pagination); `GET /reports/:id` reads; `PATCH /reports/:id` updates the title and/or document with an `expectedUpdatedAt` body field for optimistic concurrency (a stale token is a 409); `POST /reports/:id/publish` and `/unpublish` drive the lifecycle; `DELETE /reports/:id` removes a draft (a published report refuses with 409). An invalid document yields the exact same actionable RFC 9457 problem+json (block path, field, fix hint) the workspace produces, because validation lives in the shared service (FR2 parity). A hand-assembled OpenAPI 3.1 spec is served at `/api/v1/openapi.json` (public, no token) describing every endpoint, the PAT bearer security scheme (D10), and the RFC 9457 Problem shape, and embedding the generated document JSON Schema as the single source of truth (D8).
- **Reports API duplicate endpoint (API parity):** `POST /api/v1/reports/:id/duplicate` mints a fresh editable draft from a deep copy of any report (FR10), closing the workspace-vs-API gap where the Duplicate action had no programmatic equivalent. It is a thin adapter over the same `duplicateReport` service the workspace uses: a published source duplicates into a draft, an unknown id is a 404 problem+json, and the response is the created draft (201) in the same envelope the create endpoint returns. The OpenAPI spec describes the new path.
- **API tokens (story 4.1):** create and revoke personal access tokens from the workspace settings so scripts and agents can authenticate to the programmatic API (D10). A token is a high-entropy bearer credential (`acta_pat_` prefix + 256-bit body) shown exactly once at creation with one-gesture copy; only its SHA-256 hash is stored, so a database leak exposes no usable token. The settings list shows each token's name, a non-secret last-four display fragment, creation and last-used timestamps, and an active/revoked status chip; revocation is one click (a two-step confirm) and never deletes the row (an audit trail). API requests authenticate via `Authorization: Bearer <token>` only - this is a third, strictly separated auth realm (a browser cookie never authorizes the API, and a token never opens a workspace or reader session, NFR12). A missing, invalid, or revoked token gets an RFC 9457 problem+json 401 with `WWW-Authenticate: Bearer` (never a redirect to login), and API authentication failures are rate-limited per-IP with a global brake (AR4, AR12). This establishes the `/api/*` PAT-bearer path and the shared `/api/*` error boundary that maps any thrown `AppError` to problem+json, on which the rest of the programmatic surface builds.

### Security

- **Magic-link verification survives mail-gateway link scanners (audit finding A1).** The author and reader magic-link landings consumed the single-use token inside the GET that the emailed link points to. A mail-gateway link scanner (Microsoft Defender SafeLinks, Proofpoint URL Defense, Mimecast) GET-prefetches delivered links, so the scanner atomically consumed the token before the human clicked, landing them on the expired path - and in MULTI mode the author email magic link is the only auth path, so a scanning gateway could lock out every author. Both landings (`/login/verify`, `/r/[token]/verify`) are now prefetch-safe POST-to-consume interstitials: the GET `load` PEEKS the token (a read-only validity SELECT, `peekAuthorVerificationToken` / `peekVerificationToken`, no `consumed_at` write) and renders a minimal "Confirm sign-in" / "Confirm and view report" page whose only action is a same-origin POST that runs the unchanged atomic consume + session mint. A scanner's prefetch only renders the interstitial; the human's click still consumes the live token. Every prior property is preserved: enumeration-neutrality (an unknown / expired / already-consumed / wrong-share token peeks false and shows the SAME neutral expired state, no oracle), single-use + 15-minute TTL (enforced at the POST consume, atomically, unchanged), the same per-IP / per-share / global rate-limit envelope on the GET (the peek does not consume the token, so a prefetch costs only rate-limit budget), CSRF (the POST is a same-origin SvelteKit form action, so the built-in origin check applies and is never disabled), the reader leak-neutral 404 posture (the closed-share neutral 404 runs before the mode branch), and no-store + noindex on both routes. The interstitial carries no report title and no author identity, so a scanner-rendered page leaks nothing, and the reader interstitial is a no-JS form POST so the reader JS budget is unaffected (72.9 KB / 200 KB). Server-only, no schema change, no migration.
- **MCP generation tools are now metered by the same per-author LLM cost brake as the REST surface.** The `generate_outline` and `generate_report` MCP tools issued metered `chatComplete` calls with no rate limit - the `apiAuth` hook consumes a rate token only on an auth FAILURE, so an authenticated PAT could drive unbounded paid LLM calls through `/api/mcp`, a cost/DoS gap the REST `POST /api/v1/reports/generate/{outline,fill}` routes already closed with `aiGenerationLimiter`. Both tools now consume the SAME `aiGenerationLimiter` BEFORE any LLM call, keyed per AUTHOR (`mcpGenerationRateKey(scope.authorId)`, since the MCP tool boundary carries the `AuthorScope`, not a token id) - so one author's MCP generation burst is capped across all their PATs, and a single logical call still costs exactly one token on whichever surface issued it (no double-charge across surfaces). On deny the tools return the standard RFC 9457 429 problem via the MCP tool error channel and make no call. The REST routes are unchanged (still keyed per token); server-only, no schema change, no migration, reader budget unaffected.
- **MCP `push_data_set` rejects an oversize body before buffering it.** The tool encoded the full JSON-RPC `content` string to bytes before `ingestBytes` checked the 50 MB cap, so an over-cap push got a full UTF-8 copy here on top of the one the service does. The shipped `BODY_SIZE_LIMIT` already bounds the transport body, so this was a residual extra-copy concern, not unbounded - but the tool now rejects an over-`MAX_UPLOAD_BYTES` `content` up front with a cheap `Buffer.byteLength` measure (allocating nothing), returning the same `tooLarge` 413 problem-details the REST push returns before the encode. - **Boot warning when a remote database link is unencrypted (audit finding A2).** The pg pool was built from `DATABASE_URL` with no explicit TLS, so a non-loopback database host with no `sslmode=` directive would ship queries in cleartext over the network with no signal. The default docker-compose path (the app talking to a sibling Postgres container by service name) is non-loopback but a private-network link that does not use TLS, so failing boot would break the primary deployment; instead, under `NODE_ENV=production`, the app now logs a single clear `logger.warn` at first connect when the `DATABASE_URL` host is non-loopback AND the connection string declares no TLS (`sslmode=` other than `disable`, or `ssl=true`), stating that DB traffic is unencrypted and that a remote database should set `sslmode=require`. The `isUnencryptedRemoteDbLink` predicate is unit-tested and documented under "Database transport security" in [`docs/ops/deployment.md`](docs/ops/deployment.md). Server-only, no schema change, no migration.

It is advisory - there is no trusted-proxy assertion to validate against, so it warns whenever the header is non-empty and never fails boot. `ADDRESS_HEADER` is read straight from the environment (adapter-node consumes it, not the Zod schema), and the `trustsInboundForwardedHeader` predicate is unit-tested. Server-only, no schema change, no migration.
- **Author email-domain is re-checked when the magic link is consumed (audit finding A3).** The author sign-in domain gate (`isAuthorEmailInDomain`) ran only at link ISSUE, not at consume, so a token issued while an email was in-domain would still provision an author and open a session even if `AUTHOR_EMAIL_DOMAIN` had been narrowed in between. `completeAuthorSignIn` now re-runs the domain check after consuming the token and before `ensureAuthor`/session mint; a now-out-of-domain email is discarded onto the SAME neutral null (expired) path - no author minted, no session opened (one pure env read). Unit-tested; server-only, no schema change.
- **AI generation asserts the enabled gate before reading any skeleton or data set (audit finding A4).** `generateOutline` and `fillFromOutline` called `loadContext` (skeleton + data-set reads) before the AI gate was reached deeper in `chatComplete`, so a disabled instance did DB/disk work before returning its 503. Unit-tested (the context readers are never called when disabled); server-only, no schema change.

This moves the trust boundary from the final validator onto a clear message at the tool entry. Unit-tested; server-only, no schema change.

- **Epic 8 (Identity & Multi-Author) security + penetration audit and remediation.** The multi-author tenancy is the load-bearing security change of the epic, so it ran a dedicated security + attacker-mindset penetration pass with a remediation round. Three fixes landed. (1) A cross-author skeleton IDOR (the High): the original ownership pass threaded the `AuthorScope` through reports, data sets, shares, and API tokens but missed the `skeletons` table, so in multi mode any author could list / read / instantiate / delete another author's skeleton and the `skeleton-name-taken` 409 leaked a skeleton's existence cross-author. Closed by `skeletons.owner_id` (FK -> authors, RESTRICT, indexed; migration `0015`), the boot inheritance backfill extended to skeletons, an `AuthorScope` threaded through all five skeleton service functions and every caller, and the unique index changed from global `name` to composite `(owner_id, name)` (two authors may reuse a name; the 409 only fires within one author). (2) A stale null-author session purge on mode flip: single-mode password sessions carry `authorId: null`, so on a flip to multi mode such a session is purged at boot rather than resolving defensively to the implicit author, removing a tenancy ambiguity at the mode boundary (the operator re-authenticates by magic link). (3) Ingest report-ownership validation: the data-set push now validates that an optional target `report_id` is owned by the pushing author's scope before binding, so a multi-mode author cannot push or rebind a data set onto another author's report by supplying its id. The core multi-author tenancy - the read-path authorization that closes the IDOR - passed the audit with no Critical or High finding; the auditors verified the auth-realm separation (NFR12), enumeration-safety (NFR9), the no-lockout fail-fast boot guard, and the single-use author-token atomicity sound. Single mode stays byte-identical throughout.
- Two audit Low hardening nits: the upstream LLM response body is truncated before it can enter the logs (a hostile or misconfigured endpoint can no longer dump a large or secret-bearing body into a free-text error message that key-based pino redaction does not scan), and the `Authorization: Bearer` parser accepts RFC 7235 bracketed whitespace (a tab or multiple spaces) instead of 401-ing a well-formed header.
- Pinned SvelteKit's cross-site origin check (`csrf.trustedOrigins: []`, the secure default) so the form-POST CSRF defense cannot be silently disabled by a future proxy-origin workaround; a `SECURITY.md` now documents vulnerability reporting and the supply-chain posture (the audited dependency tree carries no open CVE).
- Session cookies carry the `__Host-` name prefix and are always `Secure` (backlog hardening): a browser honours a `__Host-` cookie only when it is `Secure`, `Path=/`, and carries no `Domain`, so a sibling subdomain or a downgraded channel cannot plant a cookie that shadows the author or reader session. It works on `http://localhost` (a browser secure context) and, in production, the https-`ORIGIN` guard guarantees the `Secure` flag is never sent over a plaintext non-loopback channel. Note: this renames the session cookies, so existing author and reader sessions are invalidated once on upgrade (the author signs in again, readers re-verify).
- The `/api/v1/reports` JSON body is capped before `JSON.parse` (backlog hardening): an over-cap declared `Content-Length` is rejected up front and an under-reported body is caught after read but before parse, both returning a 413 problem-details, so the parse cost is bounded well below the adapter's 50 MB transport limit. The document within is still separately capped at `MAX_DOCUMENT_BYTES` by the validate-on-write service. The workspace save paths already enforced this; this closes the API path.
- Reader-verification DoS hardening (3.3 follow-up): a per-share verification brake, independent of client IP, now sits between the per-IP limiter and the instance-wide global brake, so a flood against one share can no longer starve email-verification for readers of every other share. The shared per-share and global brakes are charged only on a genuine verification attempt (a real magic-link token, or a plausibly-shaped email submission), so an empty-token probe by a holder of a share link is bounded on the per-IP bucket alone and cannot drain the shared brakes for everyone. Closed or unknown shares stay byte-for-byte indistinguishable (NFR9) and a throttled response opens no new enumeration oracle.
- Test-send rate limiting (3.1 follow-up): the workspace test-email action is now rate-limited per author session (about five per hour), returning the same 429 problem-details the other limited actions use, so a hijacked author session cannot turn the SMTP relay into a spam or sender-reputation vector; the operator can still test any address.
- Session cookies are forced Secure in production: environment validation now rejects an `http://` `ORIGIN` when `NODE_ENV=production`, so an operator behind a TLS-terminating proxy cannot accidentally ship author or reader session cookies without the `Secure` attribute. The https-`ORIGIN` deployment contract is documented in [`docs/ops/deployment.md`](docs/ops/deployment.md).
- Central `workspaceGuard` enforcing authentication on every workspace request, including form actions and endpoints (SvelteKit layout `load` does not guard actions).
- XSS structurally prevented in the renderer (no raw HTML; links restricted to http(s); images by UUID asset reference only); strict CSP with zero third-party assets; `noindex` on all report routes; secrets only in environment variables, never logged.
- Reader verification hardening (story 3.3): a share whose report is unpublished after the link is created serves the same neutral 404 as a revoked or unknown share (no 409 enumeration oracle); the magic-link landing now enforces its rate limit (a throttled landing is indistinguishable from a failed verification); and request-verification dedups one live magic link per (share, email) within the 15-minute window, capping mail amplification to a victim address while keeping the response identical whether a mail was sent or suppressed.
- Restricted-mode timing-equivalence (story 3.4, NFR9): the restricted recipient-list check runs behind the neutral confirmation, and the magic-link send is fire-and-forget on every path, so an off-list email and an on-list email are indistinguishable in practice over the network - the variable SMTP round-trip (the only network-scale separator) is never on the response path, and the residual on-list-vs-off-list difference is sub-millisecond local database work below the network noise floor. A forwarded magic link still verifies only the address it was issued to (the token is email-and-share bound), so a restricted share cannot be bypassed by forwarding a link to an unlisted third party.
- Recipient-list bound (story 3.4): a restricted share's allow-list is capped at 500 recipients (counted after normalization and de-duplication), rejecting an over-large submission with a clear error before any write, so a single submission cannot insert an unbounded set of rows. Replacing a non-existent or malformed share's recipient list now returns a clean "share not found" instead of a server error.
- Revocation and enumeration-safety (story 3.5, FR20/NFR9/NFR10): revoking a share is idempotent (a double-revoke is a no-op that preserves the original instant) and sweeps every live reader session bound to it, so a verified reader is cut off immediately rather than reading until their session expires. The reader gate re-checks share liveness on every request before reading the session, so a revoked or expired share short-circuits to the neutral page even for a holder of a still-valid reader cookie. Revoked, expired, and unknown share links are byte-for-byte indistinguishable (same 404 status, same neutral body, same `no-store` header), closing the enumeration oracle that distinct "revoked" vs "expired" vs "not found" responses would open. The strict Content-Security-Policy (default-src 'self', no third-party origins, self-hosted fonts) applies across the reader surface, and no link-preview metadata leaks a confidential report's title to a chat or email unfurler.
- Upload-form streaming cap parity (2.4 follow-up): the workspace multipart upload now enforces the 50 MB cap by streaming the raw request body and aborting the instant cumulative bytes exceed it, so an oversized upload is rejected with the same 413 before the multipart body is ever fully buffered - matching the API push (4.3) guard. A declared over-cap `Content-Length` is the cheap pre-read rejection; the streaming abort is the real bound for a chunked or under-reported body. The cap logic is now a single shared helper (`readStreamToCap`) both ingestion entries use, so the two cannot drift. The existing 413 response shape, success path, and diagnostics are unchanged.
- API token realm separation (story 4.1, D10/NFR12/AR12): the programmatic `/api/*` surface accepts a PAT bearer token only and never a cookie, while the author and reader cookie realms never accept a PAT - the two directions are enforced (the API auth hook consults only the `Authorization` header; the cookie guard excludes `/api/*` entirely) and tested. An unauthenticated API call returns a 401 problem+json, not a 302 to login, so a script gets a machine-actionable error rather than an HTML redirect. Tokens are stored only as a SHA-256 hash (the raw token is shown once and never logged - pino redaction covers `authorization`/`token`/`cookie`, and no PAT value ever reaches a log line), the bearer prefix is verified before any database lookup, and authentication failures are rate-limited per-IP plus a global brake to bound bearer guessing. The `/api/*` error boundary maps a thrown `AppError` to its problem+json status and turns any unexpected error into an opaque 500 with no internal detail leaked to the client.
