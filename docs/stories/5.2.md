# Story 5.2: MCP Authoring

Status: Approved

## Story

As an AI agent,
I want to create, update, and publish reports through MCP tools,
So that authoring is native from any MCP-capable assistant.

## Acceptance Criteria

**Given** the MCP write tools
**When** an agent authors a report
**Then** the same service layer, validation, and error semantics apply as the REST API (FR31, AR5)

**Given** an invalid document from an agent
**When** validated
**Then** the MCP error payload carries the actionable detail (block path, field, hint - machine-recoverable)

**Given** an MCP write against a revoked PAT or a published report being mutated illegally
**When** attempted
**Then** the tool result carries the same problem-details semantics as the REST API (FR30 parity)

## Tasks / Subtasks

- [ ] MCP write TOOLS registered on the SAME `McpServer` instance the 5.1 read surface built, over the SAME transport bridge and PAT auth - no new route, no new dependency, no new auth (5.2 extends 5.1's server). Every write tool is a THIN ADAPTER over the EXACT documents/publish services the REST API (4.2) and the workspace call - NO business logic, NO validation, NO Drizzle in the tool handler (the AR5 four-surface parity contract). Tools mirror the 4.2 reports endpoints:
  - `create_report` -> `createReport(title)` (blank starter) or `createReportWithDocument(document)` (an initial document) (1.5); returns the created report resource, the same shape `POST /api/v1/reports` returns.
  - `update_report` -> `updateReportDocument(id, document, expectedUpdatedAt?)` and/or `updateReportTitle(id, title)` (1.5), composed exactly as the 4.2 PATCH handler (the combined `{title, document}` case sets `document.title = title` and does ONE guarded `updateReportDocument` write - reuse the 4.2 handler logic, do not re-derive it; extract a shared helper if needed so MCP and REST share one update composition). Document validation runs INSIDE the service and a bad document throws the FR2 actionable `AppError`.
  - `publish_report` -> `publishReport(id, expectedUpdatedAt?)`; `unpublish_report` -> `unpublishToDraft(id)` (1.7). A non-publishable report surfaces the existing publish-lifecycle `AppError` unchanged.
  - `delete_report` -> `deleteDraft(id)` (1.5); the existing 409 if the report is not a deletable draft.
  - Each tool's input schema is derived from the SAME Zod schemas the REST API uses (the document schema for `create`/`update`, ids for the rest) so the MCP tool advertises a typed input contract from the single source of truth (1.2), and a malformed tool call is rejected with the actionable detail.
- [ ] FR2 validation parity through the MCP error channel (the AC): an invalid document submitted via a write tool yields the EXACT problem-details `errors[]` the REST API and the workspace save produce - `{path, message, hint?}` with the block path, field, and hint (the 1.2 `errors.ts` actionable layer surfaced by `validateDocument`/`updateReportDocument`). This is automatic because the tool is a thin adapter (the service throws, the MCP error mapping from 5.1 carries `toProblemDetails`). The agent receives MACHINE-RECOVERABLE detail it can act on (the same payload it parses from the REST API), per the AC.
- [ ] Optimistic-concurrency parity (4.2): the write tools accept the SAME `expectedUpdatedAt` token (an ISO 8601 string the agent last saw), passed to the service signature; a stale value yields the service's 409 `/problems/report-conflict` carried into the MCP tool error; an omitted token is last-write-wins (the same omitted-guard behavior the workspace and REST have); a present-but-invalid value is a 400 (a typo fails loudly). Reuse the 4.2 transport decision verbatim (the body field), not a new mechanism.
- [ ] Revoked-PAT + illegal-mutation parity (the third AC): a write against a revoked PAT fails at the 5.1 PAT gate with the 4.1 401 (the handshake/auth-stage rejection, not a tool result) - a revoked token never reaches a tool. An illegal mutation that DOES reach a tool (mutating a published report - `updateReportDocument`/`deleteDraft` refuse a published report with the existing 409) surfaces the SAME problem-details semantics as the REST API in the tool error channel (FR30 parity). Both are reused, not reimplemented.
- [ ] No new tables, no new migration: pure surface over existing services (documents 1.5, publish 1.7), exactly like 4.2. The MCP write tools add no storage.
- [ ] Tests: each write tool calls its exact service and serializes the result (mock the service, assert the call + result, assert NO business logic / NO Drizzle in the handler); create/update/publish/unpublish/delete happy paths + their error statuses carried as MCP tool errors; an invalid document returns the FR2 problem-details with path/field/hint IDENTICAL to the REST API for the same bad document (assert byte-parity of `errors[]` between the MCP tool error and the 4.2 endpoint, the 4.2 `parity.test.ts` discipline); the optimistic-concurrency 409 round-trips through a write tool; a write against a published report returns the 409 in the tool error (no silent skip); a write against a revoked PAT is the 4.1 401 handshake rejection (never a tool result); the combined `{title, document}` update is a single guarded write (the 4.2 atomic-update invariant holds on the MCP surface too). An e2e drives a real MCP client with a real PAT through the full lifecycle: create -> update -> publish -> (read back via 5.1 `get_report`) -> unpublish -> delete, plus a bad-document write returning the actionable `errors[]`.

## Dev Notes

- Authority: AC verbatim from epics.md Epic 5 Story 5.2 (FR31 authoring via MCP, AR5 one service layer, FR2 machine-recoverable validation detail, FR30 parity on revoked-PAT/illegal-mutation). Architecture line 299 (one service layer, now four surfaces), line 219 ("never Drizzle in a route or component"), line 313 (FR30-33 = `routes/api/v1/` + MCP as a thin adapter over services), D9 (problem+json everywhere). Scopes: `mcp` (the write tools on the 5.1 server), `api` (the reused 4.2 service composition), `schema` (the tool input contracts derive from the 1.2 Zod schemas), `docs`.
- DEPENDS ON 5.1: the write tools register on the SAME `McpServer` instance, use the SAME Streamable HTTP transport bridge, the SAME PAT auth gate, and the SAME error mapping 5.1 established. Implement 5.1 first. REUSES 4.2's exact services and update composition (this is 4.2's contract applied to a fourth surface). Independent of 5.3/5.4 (the LLM connectors; no shared seam).
- Seam reuse - the EXACT 4.2 workspace/REST services, "just an MCP tool instead of an HTTP route", NO new logic:
  - Documents (1.5, `src/lib/server/documents/`): `createReport(title)`, `createReportWithDocument(document)`, `getReport(id)`, `updateReportDocument(id, document, expectedUpdatedAt?)`, `updateReportTitle(id, title)`, `deleteDraft(id)`.
  - Publish lifecycle (1.7, `src/lib/server/documents/reports.ts`): `publishReport(id, expectedUpdatedAt?)`, `unpublishToDraft(id)`.
  - Update composition: the 4.2 PATCH handler's atomic combined-write logic (set `document.title = title`, one guarded `updateReportDocument`; explicit title wins over `document.title`). Extract it to a shared `composeReportUpdate(...)` helper if it still lives inline in the 4.2 route, so the MCP tool and the REST PATCH share ONE composition rather than two copies that can drift (the 4.2 QA-iteration-1 atomicity fix must not be re-introduced as a bug here).
  - Validation + errors: `validateDocument` / the 1.2 `errors.ts` actionable layer (inside `updateReportDocument`/`createReportWithDocument`); `AppError` + `toProblemDetails` (`src/lib/server/problem.ts`) for the MCP error channel - the SAME mapping 5.1 wired. The FR2 `errors[]` travels for free because the tool is a thin adapter.
  - PAT auth + transport: the 5.1 PAT gate (`authenticateApiToken` / `locals.apiIdentity`) and the 5.1 transport bridge - unchanged.
- The "thin adapter" rule is load-bearing exactly as in 4.2/4.3/5.1: a write tool that grows a validation branch, an ownership check, or a Drizzle call breaks the four-surface parity. The mock-the-service test strategy enforces it.
- WATCH-POINT (carry the 4.2 lesson): the 4.2 combined PATCH was a QA-iteration-1 atomicity fix (two non-atomic writes silently lost a concurrent edit). The MCP `update_report` tool MUST reuse the fixed single-guarded-write composition, not a fresh two-write implementation - hence the shared-helper recommendation. A test asserts the combined `{title, document}` MCP update calls `updateReportDocument` once with `document.title === ` the new title and never calls `updateReportTitle`.
- This story COMPLETES the MCP surface (read 5.1 + write 5.2): an MCP-capable assistant can now discover and author natively, at full parity with the REST API. It is independent of the LLM connector stories (5.3/5.4).
- Reader JS budget (NFR3): server-only surface, ZERO reader JS added - confirm `pnpm reader:budget` unchanged.
- AMBIGUITY for the product owner (do not invent): (a) whether the MCP write tools mirror ALL workspace/REST actions (create/update/publish/unpublish/delete - the 4.2 set) or a SUBSET (e.g. no `delete_report` over MCP, to keep an agent from destroying drafts) - recommend full parity with 4.2 (the AR5 contract is parity; an agent that can create should be able to delete its own draft) but FLAG it: a product owner may want delete gated to the workspace only; (b) whether a data-push write tool (the 4.3 `/api/v1/data-sets` equivalent) belongs in 5.2 or a later story - the AC names "create, update, and publish reports" only, so recommend deferring an MCP data-push tool to a follow-up and keeping 5.2 to the report-authoring verbs the AC lists, but flag the gap (an agent authoring data-bound reports will eventually want it); (c) the MCP tool naming convention (`create_report` snake_case vs `report.create` dotted vs `createReport` camel) - recommend snake_case verb_noun (the common MCP tool convention) but confirm, since renaming a published tool is a breaking change for connected agents.
