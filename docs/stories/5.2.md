# Story 5.2: MCP Authoring

Status: Done

## Story

As an AI agent,
I want to create, update, and publish reports through MCP tools,
So that authoring is native from any MCP-capable assistant.

## Acceptance Criteria

**Given** the MCP write tools
**When** an agent authors a report
**Then** the same service layer, validation, and error semantics apply as the REST API (FR31, AR5)

**Given** an invalid document from an agent
**When** validated
**Then** the MCP error payload carries the actionable detail (block path, field, hint - machine-recoverable)

**Given** an MCP write against a revoked PAT or a published report being mutated illegally
**When** attempted
**Then** the tool result carries the same problem-details semantics as the REST API (FR30 parity)

## Tasks / Subtasks

- [x] MCP write TOOLS registered on the SAME `McpServer` instance the 5.1 read surface built, over the SAME transport bridge and PAT auth - no new route, no new dependency, no new auth (5.2 extends 5.1's server). Every write tool is a THIN ADAPTER over the EXACT documents/publish services the REST API (4.2) and the workspace call - NO business logic, NO validation, NO Drizzle in the tool handler (the AR5 four-surface parity contract). Tools mirror the 4.2 reports endpoints:
  - `create_report` -> `createReport(title)` (blank starter) or `createReportWithDocument(document)` (an initial document) (1.5); returns the created report resource, the same shape `POST /api/v1/reports` returns.
  - `update_report` -> `updateReportDocument(id, document, expectedUpdatedAt?)` and/or `updateReportTitle(id, title)` (1.5), composed exactly as the 4.2 PATCH handler (the combined `{title, document}` case sets `document.title = title` and does ONE guarded `updateReportDocument` write - reuse the 4.2 handler logic, do not re-derive it; extract a shared helper if needed so MCP and REST share one update composition). Document validation runs INSIDE the service and a bad document throws the FR2 actionable `AppError`.
  - `publish_report` -> `publishReport(id, expectedUpdatedAt?)`; `unpublish_report` -> `unpublishToDraft(id)` (1.7). A non-publishable report surfaces the existing publish-lifecycle `AppError` unchanged.
  - `delete_report` -> `deleteDraft(id)` (1.5); the existing 409 if the report is not a deletable draft.
  - Each tool's input schema is derived from the SAME Zod schemas the REST API uses (the document schema for `create`/`update`, ids for the rest) so the MCP tool advertises a typed input contract from the single source of truth (1.2), and a malformed tool call is rejected with the actionable detail.
- [x] FR2 validation parity through the MCP error channel (the AC): an invalid document submitted via a write tool yields the EXACT problem-details `errors[]` the REST API and the workspace save produce - `{path, message, hint?}` with the block path, field, and hint (the 1.2 `errors.ts` actionable layer surfaced by `validateDocument`/`updateReportDocument`). This is automatic because the tool is a thin adapter (the service throws, the MCP error mapping from 5.1 carries `toProblemDetails`). The agent receives MACHINE-RECOVERABLE detail it can act on (the same payload it parses from the REST API), per the AC.
- [x] Optimistic-concurrency parity (4.2): the write tools accept the SAME `expectedUpdatedAt` token (an ISO 8601 string the agent last saw), passed to the service signature; a stale value yields the service's 409 `/problems/report-conflict` carried into the MCP tool error; an omitted token is last-write-wins (the same omitted-guard behavior the workspace and REST have); a present-but-invalid value is a 400 (a typo fails loudly). Reuse the 4.2 transport decision verbatim (the body field), not a new mechanism.
- [x] Revoked-PAT + illegal-mutation parity (the third AC): a write against a revoked PAT fails at the 5.1 PAT gate with the 4.1 401 (the handshake/auth-stage rejection, not a tool result) - a revoked token never reaches a tool. An illegal mutation that DOES reach a tool (mutating a published report - `updateReportDocument`/`deleteDraft` refuse a published report with the existing 409) surfaces the SAME problem-details semantics as the REST API in the tool error channel (FR30 parity). Both are reused, not reimplemented.
- [x] No new tables, no new migration: pure surface over existing services (documents 1.5, publish 1.7), exactly like 4.2. The MCP write tools add no storage.
- [x] Tests: each write tool calls its exact service and serializes the result (mock the service, assert the call + result, assert NO business logic / NO Drizzle in the handler); create/update/publish/unpublish/delete happy paths + their error statuses carried as MCP tool errors; an invalid document returns the FR2 problem-details with path/field/hint IDENTICAL to the REST API for the same bad document (assert byte-parity of `errors[]` between the MCP tool error and the 4.2 endpoint, the 4.2 `parity.test.ts` discipline); the optimistic-concurrency 409 round-trips through a write tool; a write against a published report returns the 409 in the tool error (no silent skip); a write against a revoked PAT is the 4.1 401 handshake rejection (never a tool result); the combined `{title, document}` update is a single guarded write (the 4.2 atomic-update invariant holds on the MCP surface too). An e2e drives a real MCP client with a real PAT through the full lifecycle: create -> update -> publish -> (read back via 5.1 `get_report`) -> unpublish -> delete, plus a bad-document write returning the actionable `errors[]`.

### Debug Log

- **Shared update composition extracted (the WATCH-POINT)**: the 4.2 combined-PATCH atomicity logic lived INLINE in `src/routes/api/v1/reports/[id]/+server.ts`. Extracted it to `src/lib/server/documents/update-composition.ts` (`composeReportUpdate({ id, title?, document?, expectedUpdatedAt? })`), and pointed BOTH the REST PATCH and the MCP `update_report` tool at it - so the surfaces share ONE composition and the 4.2 QA-iteration-1 fix (combined `{title, document}` -> a single guarded `updateReportDocument` write with `document.title = title`, explicit title wins, `updateReportTitle` never called when a document is present) cannot be re-introduced as a bug on the MCP surface. The REST `[id]/server.test.ts` mocks `$lib/server/documents/reports` directly, so its assertions on `updateReportDocument`/`updateReportTitle` still intercept the same mocked functions through the helper - all 4.2 PATCH tests pass unchanged (no test rewrite needed).
- **`expectedUpdatedAt` at the tool boundary**: the REST surface reads the token from the JSON body (`readExpectedUpdatedAt`, a `new Date(raw)` lenient parse, 400 on a typo). The MCP tool args are already structured, so the token is a zod `z.string().datetime()` inputSchema field - a malformed value is rejected by the SDK's zod validation AT the tool boundary (the same "a typo fails loudly" intent the REST 400 has), and a valid ISO string is converted to a `Date` in the handler before the service call. `.datetime()` is the strict ISO 8601 primitive; it accepted `2026-06-12T10:00:00.000Z` through the live SDK round-trip in both the unit and the e2e.
- **Permissive `document` arg (NOT re-validated at the boundary)**: the `document` inputSchema is `z.record(z.string(), z.unknown())` (assert "a JSON object", nothing more). The SERVICE's `validateDocument` is the real validator (FR2), so an invalid document reaches the service and surfaces as the 422 with the actionable `errors[]` - asserted byte-for-byte (`{ path, message, hint }`) in both the unit suite and the live e2e. Re-validating in the handler would break four-surface parity, so it deliberately does not.
- **Tool-boundary UUID**: every id arg is `z.string().uuid()` (the 5.1 `get_report` fix pattern). A malformed UUID is rejected before the handler runs (asserted on `delete_report`), a valid-but-unknown id still reaches the service and 404s.
- **Annotations**: write tools carry `readOnlyHint: false`; `delete_report` adds `destructiveHint: true`. `idempotentHint`: `create_report` false (each call mints a fresh report), `update_report`/`publish_report`/`unpublish_report` true (re-applying the same input on an unchanged report is a no-op; the concurrency guard makes a stale re-apply a 409 rather than a silent overwrite), `delete_report` false. Asserted in `server.test.ts` via the live SDK `listTools()`.
- **Live SDK e2e (the write round-trip)**: the 5.1 e2e drove only `initialize` over raw JSON-RPC (a `tools/call` over raw HTTP needs the full initialize+initialized handshake, impractical to hand-roll). For 5.2 the e2e drives a REAL MCP client (`Client` + `StreamableHTTPClientTransport` with the PAT as a bearer header) against the LIVE server: create_report -> get_report shows it -> update_report -> publish_report -> delete_report-on-published 409 -> unpublish_report -> delete_report 204-equivalent -> a bad-document create returning the 422 `errors[]`. This is the full lifecycle through the real service + DB, not a mock. Desktop-only (the workspace mints the PAT via the settings UI).
- **Gates (all green)**: `pnpm lint` clean; `pnpm check` 1101 files 0 errors / 0 warnings; `pnpm test` 944 unit (+23 net from 921); `pnpm build` adapter-node done; `pnpm reader:budget` 68.9 KB / 200 KB unchanged (server-only; grep of `.svelte-kit/output/client/` for `modelcontextprotocol`/`McpServer`/`registerTool`/`composeReportUpdate` = zero matches); `pnpm test:e2e` 39 passed / 14 mobile-skip including the new write round-trip. No new dependency (the MCP SDK + zod were already in from 5.1).

### Completion Notes

- **Write tool set (5, each a thin delegation to the EXACT 4.2 service)** in `src/lib/server/mcp/tools.ts`, registered in `buildMcpServer()` (`src/lib/server/mcp/server.ts`):
  - `create_report` (`{ title?, document? }`) -> `createReportWithDocument(document)` when a document is given, else `createReport(title ?? DEFAULT_REPORT_TITLE)`; returns the created report. Mirrors `POST /api/v1/reports`.
  - `update_report` (`{ id, title?, document?, expectedUpdatedAt? }`) -> the shared `composeReportUpdate`: combined `{title, document}` is ONE guarded `updateReportDocument(id, { ...document, title }, expectedUpdatedAt)`; document-only -> `updateReportDocument`; title-only -> `updateReportTitle`. A stale `expectedUpdatedAt` -> the service 409.
  - `publish_report` (`{ id, expectedUpdatedAt? }`) -> `publishReport(id, expectedUpdatedAt?)`; idempotent on a published report.
  - `unpublish_report` (`{ id }`) -> `unpublishToDraft(id)`; idempotent on a draft, no concurrency token.
  - `delete_report` (`{ id }`) -> `deleteDraft(id)`; a published report is the service 409 (no silent skip); returns `{ id, deleted: true }`.
- **Merged-update parity (the WATCH-POINT)**: `composeReportUpdate` is the single composition both the REST PATCH and `update_report` use. Combined `{title, document}` does ONE guarded `updateReportDocument` write with `document.title = title` (explicit title wins); `updateReportTitle` is NEVER called when a document is present; a stale token 409s and writes nothing. Asserted on both surfaces (the MCP tool test + the live SDK e2e + the unchanged 4.2 PATCH tests).
- **Error parity with REST (byte-for-byte)**: the write tools reuse the 5.1 `withProblemMapping`/`problemResult` mapping unchanged. A service `AppError` (422 invalid document with `errors: [{ path, message, hint? }]`, 409 stale `/problems/report-conflict` or published `/problems/report-published`, 404 `/problems/report-not-found`) is carried as an `isError: true` tool result whose text content is the SAME RFC 9457 body `problemResponse` builds for REST (`{ type, title, status, detail?, errors? }`). An unexpected (non-AppError) throw is re-thrown so the SDK renders a JSON-RPC internal error - no internal detail leaks in a tool result. The 422 `errors[]` (with the accessibility hint) was asserted identical to the REST shape in both unit and e2e.
- **Annotations**: read tools `readOnlyHint: true`; write tools `readOnlyHint: false`; `delete_report` `destructiveHint: true`. `idempotentHint` per the SDK semantics (create false, update/publish/unpublish true, delete false). `openWorldHint: false` throughout (a self-contained instance).
- **Auth / transport / rate-limit unchanged**: the write tools register on the SAME `McpServer`, over the SAME `/api/mcp` Streamable HTTP route, behind the SAME 4.1 PAT gate (a revoked/missing PAT is the transport-level 401 before any tool runs - never a tool result, the third AC) and the SAME 4.1 rate limiters. No new route, no new auth, no new dependency, no new table/migration.
- **Server metadata**: the `instructions` string updated from the read-only discovery wording to the authoring flow (discover then create/update/publish/unpublish/delete); name/version unchanged (`acta-diurna` / `0.6.0`).
- **Server-only / reader budget (NFR3)**: the write tools live under `$lib/server/*` and the route is a `+server.ts`, so the SDK and the tools never enter the client closure (grep confirmed zero matches). `pnpm reader:budget` 68.9 KB / 200 KB, unchanged from 5.1.
- **Ambiguities (5.2 Dev Notes) - resolved per the prompt's DECIDED full-parity mandate**: (a) full 4.2 parity including `delete_report` over MCP (an agent that can create can delete its own draft); (b) an MCP data-push tool (the 4.3 `/api/v1/data-sets` equivalent) is DEFERRED - the AC names "create, update, and publish reports" only, so 5.2 stays the report-authoring verbs (a follow-up can add the data-push tool when an agent authoring data-bound reports needs it); (c) `verb_noun` snake_case naming (`create_report`, ...), the common MCP convention, matching the 5.1 read tools.
- **This story COMPLETES the MCP surface**: read (5.1) + write (5.2). An MCP-capable assistant can now discover and author natively at full parity with the REST API. Independent of the LLM connector stories (5.3/5.4): nothing depends on this, and the MCP authoring surface needs no follow-up to be usable.
