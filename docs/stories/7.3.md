# Story 7.3: Field Grid and Legend Blocks

Status: Review

## Story

As an author,
I want a metadata field grid and a source legend block,
So that the report header and the matrix are self-explanatory without prose.

## Acceptance Criteria

**Given** a Field Grid block with `[{ label, value }]` items
**When** rendered
**Then** a compact metadata grid (e.g. Author / Date / Scope / Status) renders with escaped values, responsive down to the reader mobile breakpoint

**Given** a Legend block referencing a scale (e.g. the sources scale)
**When** rendered
**Then** it renders one swatch per entry (colour + label + optional sublabel), derived entirely from the scale - no colour or label re-authored on the block

**Given** a Legend referencing an unknown scale
**When** validated
**Then** a problem-details error names the missing scale (FR2 parity)

**Given** either block
**When** audited
**Then** it is SSR, Zod-validated, AAA on the default theme, within the reader budget

## Tasks / Subtasks

- [x] New block type `field-grid` (`src/lib/schema/blocks/field-grid.ts`), additive member of the `blockSchema` discriminated union. Frame reuses `idSchema` + `audiencesSchema`. `items: array({ label, value }).min(1).max(MAX_FIELD_ITEMS)`. Both `label` and `value` are plain bounded strings (a metadata grid is author prose, not bound data - NO `binding`). Export from `src/lib/schema/index.ts`.
- [x] New block type `legend` (`src/lib/schema/blocks/legend.ts`), additive member of the union. Frame reuses `idSchema` + `audiencesSchema`. `scaleRef: idSchema` (a document `scales` key) and NOTHING else colour/label-bearing - the swatches derive ENTIRELY from the referenced scale (epic: "no colour or label re-authored on the block"). An optional `title` (bounded string) is allowed for the legend heading. Validation that `scaleRef` resolves uses the 7.1 cross-reference seam at the document superRefine locus; an unknown scale -> FR2 actionable error naming the missing scale (the AC). Export from `index.ts`.
- [x] Render component `src/lib/render/blocks/FieldGridBlock.svelte` (pure SSR): a compact two-column metadata grid (`<dl>` with `<dt>`/`<dd>`, the semantic metadata element), escaped values (Svelte interpolation, no `{@html}`), responsive - collapses to a single stacked column at the reader mobile breakpoint via CSS only (no JS). Wire into `BlockRenderer.svelte`.
- [x] Render component `src/lib/render/blocks/LegendBlock.svelte` (pure SSR): resolves the referenced scale from the document `scales`, renders one swatch row per entry - a colour chip (`scaleEntryColor` from 7.1, the same `var(--report-chart-N)`/explicit-hex resolution the matrix uses, so the legend's colours MATCH the matrix's), the entry `label`, and the optional `sublabel`. Derived entirely from the scale; the block re-authors no colour or label. A swatch is never colour-only - the label is the text signal (AAA). Wire into `BlockRenderer.svelte`. The component needs the document `scales` in scope (see the dev-note seam decision).
- [x] Scale access at render: `LegendBlock` (and 7.2's matrix, 7.4's UpSet) need the document `scales` to resolve a `scaleRef`. Establish the render-tier plumbing here (smallest of the three scale-consuming blocks): thread the document `scales` into the block render context so a block component can resolve a ref. RECOMMEND extending the `BlockView`/`ReportView` in `document-view.ts` to carry `scales` (the validated document already has them) and passing them through `BlockRenderer` to the scale-consuming components, rather than a Svelte context - explicit props match the existing pure-prop render tier. Document the chosen plumbing as the reference 7.2/7.4 reuse. (Plumbing already in place from 7.2; LegendBlock reuses it unchanged.)
- [x] Bricks (`src/lib/bricks/index.ts`): a `fieldGrid` brick (placeholder Author/Date/Scope/Status items) and a `legend` brick (referencing a placeholder sources-scale key, seeding or assuming the companion `scales` per the 7.2 brick decision). Add both to `BRICKS` + the `BrickId` union.
- [x] Tests: a valid `field-grid` parses and renders an escaped responsive grid (a `value` with `<script>` renders inert); a valid `legend` parses; a `legend` with an unknown `scaleRef` fails with the FR2 actionable error naming the missing scale; the legend renders one swatch per scale entry with the SAME resolved colour the matrix would use for that entry (colour-language parity test); axe-core pass on both; the brick factories yield validating sections.

## Dev Notes

- Authority: epics.md Epic 7 Story 7.3 AC verbatim (field grid `[{label,value}]` escaped + responsive; legend swatches derived entirely from a scale, no re-authored colour/label; unknown-scale FR2 error; SSR/Zod/AAA/reader budget) + the "Foundational design" (scales referenced by key, SSR renderer-pure). FR2 parity (1.2 `errors.ts`). NFR3/NFR14. Scopes: `schema` (two small blocks), `render` (two components + the scale-threading plumbing), `ui` (two bricks). The SMALL story - two simple blocks that close the report's render (header + matrix legend); after this a useful correlation report exists (epic build-order note), UpSet (7.4) is the bonus.
- DEPENDS ON 7.1 (`scales` + `resolveScaleRef`/`scaleEntryColor` + the cross-ref validation seam). The Legend reuses 7.2's colour resolution so its swatches MATCH the matrix - but 7.3 does not depend on 7.2's block existing; it can ship after 7.1 alone. Build order 7.1 -> 7.2 -> 7.3; 7.3 could swap before 7.2 if needed, but the legend is most useful beside the matrix.
- The scale-threading plumbing (the one new render seam this story owns): the validated `DocumentV1` already carries `scales`; `toReportView` (`document-view.ts`) currently drops everything but title/theme/sections/toc. Add `scales` to `ReportView` and pass it down to the scale-consuming block components through `BlockRenderer`. This is the seam 7.2's matrix and 7.4's UpSet both consume, so define it cleanly here (or in 7.2 if it lands first - whichever scale-consuming block is implemented first owns the plumbing; the later story reuses it). Keep it explicit props (the render tier is pure-prop, no Svelte context elsewhere).
- DoS bounds: `MAX_FIELD_ITEMS = 24` (a metadata header is short; 24 is generous, matching 7.1's `MAX_SCALE_ENTRIES = 24`). Legend has no array of its own - it derives from the scale, itself bounded by that same `MAX_SCALE_ENTRIES = 24`. Strings reuse the 300-char cap.
- `field-grid` is deliberately NOT data-bound (no `binding`): it is author-written metadata (Author/Date/Scope/Status), authored as JSON like the other Epic 7 blocks, not the 2.4 upload path. If a later need arises to bind a field-grid value to a data set, that is an additive `binding` extension then - do not add it speculatively now.
- Renderer purity + escaping mirror `TableBlock.svelte`/7.2: Svelte text interpolation only, no `{@html}`, SSR-only zero-hydration so the reader budget (NFR3) is unaffected (verify `pnpm reader:budget`). Use semantic elements: `<dl>/<dt>/<dd>` for the field grid (a description list IS a metadata grid), a list of swatches for the legend. AAA: a legend swatch always carries its text label, never colour alone; the field grid is plain text. axe-core gates both in e2e.
- AMBIGUITY for the product owner (do not invent): (a) whether the Legend should let the author choose WHICH entries to show or always render the whole scale - recommend the whole scale (the legend explains the scale; a partial legend invites drift), but confirm; (b) whether `field-grid` `value` should accept inline links/rich text (like the text block's inline runs) or stay plain strings - recommend plain strings for V1 (a metadata grid is labels + values, not prose), but flag that adding rich values later is additive; (c) the field-grid responsive breakpoint and column count (2-up on desktop, 1-up on mobile proposed) - a render/UX detail, confirm against the reader chrome's existing breakpoints rather than inventing a new one.

## Dev Agent Record

### Debug Log

- **Render-tier scale plumbing was already established by 7.2.** The `scales`/`theme` thread (`document.scales` -> `ReportView.scales` -> `Report -> SectionSlide -> BlockRenderer`) landed with the comparison-matrix. `LegendBlock` reuses it verbatim (same props, same `scaleEntryColor`), so this story added no new render seam - it consumes the one 7.2 defined. `FieldGridBlock` needs neither (it is scale-free), so `BlockRenderer` dispatches it without passing `scales`/`theme`.
- **Legend brick shares the matrix's `sources` scale (QA Low fix).** Author intent for "comparison matrix + source legend" is ONE shared sources scale (the legend explains the matrix's source columns), not two near-duplicates. The two bricks now reference the same `sources` key via a single `sharedSourceScale()` constant, so they are identical by construction. The real `appendBrick` composer already merges companion scales by key, so adding both bricks collapses the two `sources` declarations into one (covered by a new `compose-state.test.ts` case). The "assemble every brick into one document" test helpers (`bricks/index.test.ts` `scalesFor`, `structural-equality.test.ts` `documentFrom`, `skeletons.test.ts` `companionScales`) previously flatMapped all companion scales raw, which would trip the unique-scale-key constraint on the duplicate; they now dedup by key, mirroring `appendBrick`. A new `bricks/index.test.ts` case asserts assembling matrix + legend yields exactly one `sources` scale and a valid document (both blocks resolve their refs). Replaces the earlier `legend-sources` split.
- **Exhaustive switch in the composer StructureTree.** `blockSummary` ends with a `const exhaustive: never = block` guard, so the two new block types had to add their own `case` (a field count for `field-grid`, the scale ref for `legend`) or `pnpm check` would fail the `never` assignment. Added both.
- **Generated hints update automatically.** The "Valid block types" hint (`errors.ts`) and the JSON Schema union are derived from the union options, so they auto-listed `field-grid` + `legend`; only the test expectations needed updating (`errors.test.ts` hint string, `json-schema.test.ts` 6 -> 8 members). `static/schema/v1.json` regenerated via `pnpm schema:export` (now eight union members).
- **Legend editor has no add/remove, so no `Button` import.** The legend renders the whole scale; the author only picks the `scaleRef` and an optional `title`. The first draft imported `Button` out of habit; ESLint flagged it unused. Removed.
- **AudiencePicker is frame-level (verified, unchanged from 7.2).** The shared `BlockEditor.svelte` renders one `<AudiencePicker>` above the type switch for every block, so the two new editors carry none of their own - adding one would duplicate the frame-level disclosure.

### Completion Notes

- **Field Grid Zod shape** (`blocks/field-grid.ts`): `fieldItemSchema = { label: 1..200, value: 1..500 }`; `fieldGridBlockSchema = { type: literal('field-grid'), id: idSchema, audiences?, items: array(fieldItemSchema).min(1).max(MAX_FIELD_ITEMS=24) }`. No `binding`, no scale reference (so no `validateScaleReferences` change for this block). Plain single-line strings (decision #b: plain text for V1, rich values are an additive extension later if needed).
- **Legend Zod shape** (`blocks/legend.ts`): `legendBlockSchema = { type: literal('legend'), id: idSchema, audiences?, scaleRef: idSchema, title?: 1..200 }`. The block carries no colour/label of its own; the swatches derive entirely from the referenced scale (decision: the WHOLE scale, every entry, not an author-selected subset).
- **Legend cross-reference addition** (`validateScaleReferences` in `scales.ts`): a `validateLegendRefs` branch mirrors the comparison-matrix one. For each `legend` block, resolve `scaleRef` against `document.scales` via `resolveScaleRef`; an unknown key pushes a `ScaleReferenceIssue` at `['sections', i, 'blocks', j, 'scaleRef']` with a hint naming the missing scale, which the document superRefine re-emits as the FR2 problem-details error at `sections[i].blocks[j].scaleRef`. The block is typed structurally (`LegendRefView`) so the isomorphic module does not import the block schema.
- **Field Grid responsive approach** (`FieldGridBlock.svelte`): a CSS grid `repeat(2, minmax(0, 1fr))` (two columns desktop) with one `@media (max-width: 768px)` rule collapsing to `minmax(0, 1fr)` (single stacked column) - the SAME 768px reader mobile breakpoint `KpiBlock.svelte` and `SectionSlide.svelte` already use (decision #c: reuse the existing chrome breakpoint, do not invent one). Pure CSS, no JS. Semantic `<dl>`/`<dt>`/`<dd>` (a description list IS a metadata grid), every value Svelte-interpolated so a `<script>`-looking value renders inert.
- **Legend colour parity** (`LegendBlock.svelte`): one `<li>` per scale entry; the chip's `--swatch-color` comes from `scaleEntryColor(scale, index, theme)` - the SAME render-tier helper the matrix uses, so a default-palette entry resolves to `--report-chart-N` and an explicit author hex is used verbatim. The unit test asserts the colour-language parity (siem index 0 -> `#66023c`, the matrix's colour for that entry; an explicit `#7a2e3a` used as-is). The chip is `aria-hidden` and the entry label is always present text, so colour is never the sole signal (AAA). A missing scale renders the shared `BlockPlaceholder` rather than throwing (preview path tolerance).
- **Bricks:** `fieldGrid` (scale-free, Author/Date/Scope/Status placeholders) and `legend` (referencing the SHARED `sources` scale - the same one the comparison-matrix brick declares, via a single `sharedSourceScale()` constant - seeded via `Brick.scales`, merged by `appendBrick`). Both added to `BRICKS` + the `BrickId` union. Tests prove the field-grid brick validates standalone (no scales), the legend brick validates with its companion scale but flags a dangling `scaleRef` without it (FR2), and assembling matrix + legend yields one shared `sources` scale.
- **e2e:** extended the existing default-theme `MATRIX_FIXTURE_DOCUMENT` to carry a field-grid header section and a legend block beside the matrix - so the axe spec exercises all three Epic 7 blocks on the default theme (NFR14) and the fixture IS the MVP correlation report (cover/field grid + matrix + legend) rendered end to end. Added a dedicated axe e2e for the field grid + legend.
- **Gates:** `pnpm lint` clean, `pnpm check` 0 errors / 0 warnings, `pnpm test` 858 passing (was 817; +41: two block schemas + bounds/additivity, legend cross-ref, two render components incl. escaping + colour parity, two bricks, two editor starters), `pnpm build` ok, `pnpm reader:budget` **67.0 KB / 200 KB** (was 66.5; two SSR-only zero-hydration components, the +0.5 is shared-chunk shift). `pnpm test:e2e` (Docker): 35 passed / 12 skipped (skips are the mobile-project duplicates of API/data specs), including the new field-grid + legend axe spec and the existing matrix axe spec on the default theme.
- **MVP-after-7.3 milestone reached:** a full correlation report (cover text + field grid + comparison matrix + legend) now validates and renders end to end - confirmed by the extended default-theme e2e fixture rendering all four block kinds in one published report with axe clean. UpSet (7.4) is the bonus.
