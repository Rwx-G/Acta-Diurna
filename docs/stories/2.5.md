# Story 2.5: Automatic Rebinding & Binding Diagnostics

Status: Approved

## Story

As the author,
I want fresh data to rebind automatically and mismatches to be diagnosed precisely,
So that the weekly cycle is "inject, glance, share" - even when an export format drifts.

## Acceptance Criteria

**Given** a report with bound blocks
**When** a fresh data set matching the existing bindings is injected
**Then** all bound blocks re-render with the new data, without manual rebinding (FR14)

**Given** a fresh data set with a renamed or missing field
**When** binding resolves
**Then** the report is flagged with an actionable diagnostic naming the block, the expected field, and the closest candidate (FR15)
**And** I can remap the binding from the diagnostic and re-render
**And** binding states and diagnostics follow UX Flow B in `ux-design-specification.md`

## Tasks / Subtasks

- [ ] Automatic rebinding: injecting a fresh data set whose fields match existing block bindings re-resolves every bound block with the new data, no manual re-mapping (FR14). Match by the binding contract from 2.4.
- [ ] Binding diagnostics: when a fresh data set has a renamed/missing field, produce an actionable diagnostic per affected block - name the block, the expected field, and the closest candidate (string-distance match against available fields). Problem-details shaped, consistent with the schema error model.
- [ ] Remap-in-place: from a diagnostic, the author maps the expected field to an available field and re-renders; the remap persists in the document binding.
- [ ] Binding state surface per UX Flow B: per-block status chips (green bound/fresh, amber drifted -> diagnostic + closest-match remap, red unresolved) + a header BindingSummary aggregate ("N bindings - all green"). Components: BindingChip, BindingSummary, DiagnosticPanel.
- [ ] Tests: matching fresh data rebinds all blocks (FR14); renamed field -> diagnostic with correct closest candidate; missing field -> diagnostic; remap persists and re-renders; binding summary aggregation; the closest-match algorithm (edge cases: no candidate, multiple equidistant)

## Dev Notes

- Authority: FR14/FR15, ux-design-specification.md UX Flow B (the refill experience - the product's defining interaction) + Component Strategy (BindingChip, BindingSummary, DiagnosticPanel). This story makes "the refill" real.
- Builds directly on 2.4's binding contract (the per-field slot mapping). Closest-candidate: a simple, tested string-distance (Levenshtein or similar) over the data set's available field names; deterministic on ties (document the tie-break).
- The diagnostic is "errors are guidance" (UX principle): every drift names its one-click fix. Reuse the problem-details + inline-rendering patterns from 1.5/the schema error model.
- This is the last Epic 2 story; after it the recurring-cycle motion (skeleton -> instantiate/duplicate -> inject -> glance-at-green -> ready) is complete end to end.
