# Story 5.1: MCP Discovery Surface

Status: Review

## Story

As an AI agent,
I want to discover the schema, skeletons, and reports through MCP,
So that I can orient myself in an instance without bespoke integration.

## Acceptance Criteria

**Given** the MCP server (official TypeScript SDK, read-only first per validation guidance)
**When** an agent connects with a valid PAT
**Then** it can list skeletons and reports and fetch the document schema with examples (FR31 read surface)

**Given** an invalid or revoked PAT
**When** an agent connects via MCP
**Then** the handshake fails with the standard 401 problem detail - no information beyond authentication failure

## Dev Notes

- Authority: AC verbatim from epics.md Epic 5 Story 5.1 (FR31 read surface; official TypeScript SDK; read-only first per validation guidance; the 401-only-on-auth-failure leak rule). Architecture D8 (REST under `/api/v1`, the surface MCP parallels), D10 (PAT bearer), D9 (RFC 9457 problem+json), AR5 (one service layer, routes thin - line 299 "three entry surfaces, one service layer"; MCP makes it four), the FR30-33 mapping (line 313: "MCP P2 = new thin adapter over services"), the Deferred Decisions note (line 107: "MCP SDK - official TypeScript SDK expected"). The 1.2 schema is the published contract (line 254, FR31). Scopes: `mcp` (the route + server), `api`/`ops` (the route lives under `/api/*` and reuses the boundary), `schema` (the discovery surfaces the export), `auth` (reuses the PAT realm, adds none).
- DECIDED architecture (bake in, do not re-litigate): **MCP transport = Streamable HTTP, PAT-authenticated, reusing Epic 4's auth.** The MCP server is an HTTP route inside the SvelteKit app using the official MCP TS SDK with its Streamable HTTP server transport. A connecting agent authenticates with `Authorization: Bearer <acta_pat_...>` via the 4.1 `authenticateApiToken` path (a third realm, no cookies). An invalid/revoked PAT yields the standard 401 problem-details, nothing beyond auth failure. The server's tools/resources call the SAME documents/skeletons/schema services the REST API uses - one service layer, four surfaces (workspace cookie, reader cookie, REST PAT, MCP PAT).
- THE KEY RISK - the SvelteKit <-> MCP-SDK integration (flag as the main integration spike for this story): the SDK's Streamable HTTP transport expects Node `req`/`res` (or a transport adapter), while SvelteKit hands the route a web `Request` and expects a `Response`. Two paths, pick the cleaner one during the spike and document it: (a) adapt the SDK's `StreamableHTTPServerTransport` to the SvelteKit `RequestEvent` (wrap/bridge the web Request/Response to the Node-style req/res the transport drives), preferred IF it adapts cleanly with no monkey-patching; otherwise (b) a thin JSON-RPC handler over the existing route that parses the JSON-RPC envelope from the request body and dispatches to the `McpServer` instance directly (the SDK exposes the server's request handlers), returning the JSON-RPC response as the SvelteKit `Response`. Recommend trying (a) first; fall back to (b) if the transport resists the web-stream bridge. Either way the route stays a thin adapter and the handlers stay service-only.
- Seam reuse - NO new auth, NO new service logic:
  - PAT auth: the 4.1 `authenticateApiToken(rawToken) -> ApiIdentity | null` (`src/lib/server/auth/api-tokens.ts`) and the `apiAuth` handle / `event.locals.apiIdentity` seam (4.1 Completion Notes). If `/api/mcp` is under `isApiPath`, `apiAuth` 401s before the route runs and the route reads `locals.apiIdentity` (recommended). The `/api/*` error boundary + the 4.2 `runApi(handler)` wrapper are available for any throw on the route.
  - Schema export: the 4.3 `/api/v1/schema` composition - `CURRENT_SCHEMA_VERSION` + `toJsonSchema()` + `examples/minimal`/`full` (1.2, `src/lib/schema/`). Reuse the exact composition (extract a shared `getPublishedSchema()` helper if 4.3 inlined it, so MCP and REST share one code path) - the served schema must not drift from `static/schema/v1.json`.
  - Reports + skeletons services: `listReports()`, `getReport(id)` (1.5, `src/lib/server/documents/`); `listSkeletons()` (2.2, `src/lib/server/skeletons/`). The SAME functions the REST endpoints and the workspace call.
  - Error model: `AppError` + `problemResponse`/`toProblemDetails` (`src/lib/server/problem.ts`, 1.2/1.4) - the MCP error channel carries the SAME problem-details shape, no second error model.
- The "thin adapter" rule is the load-bearing contract here exactly as in 4.2/4.3: if an MCP handler grows validation, an ownership check, or a Drizzle call, the four-surface parity is broken. The test strategy (mock the service, assert the call) enforces it structurally.
- This story is the PREREQUISITE for 5.2 (write tools build on this same MCP server instance, transport bridge, and PAT auth). Implement 5.1 first; 5.2 extends it. 5.1/5.2 are INDEPENDENT of 5.3/5.4 (the LLM connectors share nothing risky with the MCP surface - different transport, different dependency); they can proceed in parallel, but the MCP pair and the LLM pair each have an internal order.
- Reader JS budget (NFR3): the MCP route is server-only (like the whole `/api/*` surface), so it adds ZERO reader-path JS - confirm `pnpm reader:budget` is unchanged, and verify the SDK is absent from the client bundle (the 3.1 `grep` discipline: `$lib/server`/server-route boundary keeps it server-only).
- AMBIGUITY for the product owner (do not invent): (a) the route path - `/mcp` (a clean conventional MCP mount) vs `/api/mcp` (inside the existing `/api/*` auth + boundary + rate-limit machinery) - recommend `/api/mcp` to reuse the 4.1 seam verbatim with no new auth/limiter wiring, but confirm; (b) whether MCP discovery should also list DATA SETS / published-vs-draft report filtering, or only skeletons + reports + schema as the AC names - recommend exactly the AC set (skeletons, reports, schema) for 5.1 and defer data-set discovery, but flag it; (c) the MCP error transport - a JSON-RPC error object vs a problem-details payload inside an `isError` tool result - recommend the problem JSON in the tool result content (the agent reuses its REST `errors[]` parser), but confirm; (d) whether the SDK's session management (the Streamable HTTP transport can issue an `Mcp-Session-Id`) is used or each request is stateless PAT-authed - recommend stateless-per-request PAT auth (no MCP session state, the PAT IS the session) to keep the bounded-scale, no-extra-state posture (NFR13), but flag that a stateful SDK session would need a store decision.

## Dev Agent Record

### Debug Log

- **Dependency**: `@modelcontextprotocol/sdk@1.29.0`, license **MIT** (Apache-2.0-compatible, as the AC anticipated). Added exact-pinned via `pnpm add -E`; lockfile committed. Its zod peer is `^3.25 || ^4.0`, satisfied by the project's `zod@4.4.3` (no second zod). `pnpm audit` after the add: still **2 pre-existing findings only** (esbuild moderate dev-only via drizzle-kit, cookie low via @sveltejs/kit - the 1.3/1.4/4.1 set); NO HIGH/CRITICAL, and grep of the audit output confirms NO advisory paths through `@modelcontextprotocol/sdk` or its `@cfworker/json-schema` dep.
- **Integration spike - PATH (a) chosen, no fallback needed.** The SDK ships `WebStandardStreamableHTTPServerTransport` (in `server/webStandardStreamableHttp.js`) whose `handleRequest(req: Request): Promise<Response>` speaks Web Standard `Request`/`Response` - exactly what a SvelteKit `+server.ts` route is handed and must return. The bridge is a direct `transport.handleRequest(event.request)`: no Node `req`/`res` adapter, no monkey-patching, no JSON-RPC hand-rolling (path (b) was unnecessary). The Node-oriented `StreamableHTTPServerTransport` the story flagged as the risk is NOT used; this web-standard transport supersedes it for non-Node hosts (the SDK's own Hono/Workers/Deno example is the same call).
- **Stateless-per-request** (NFR13): `sessionIdGenerator: undefined` disables MCP session state and `enableJsonResponse: true` returns a single JSON response instead of holding an SSE stream open. A fresh `McpServer` + transport is built per request and closed in a `finally`. The PAT is the credential and the session; no `Mcp-Session-Id` store. The route test asserts no `Mcp-Session-Id` header is issued.
- **Import path**: the SDK's `exports` map has a `./*` wildcard, so `@modelcontextprotocol/sdk/server/mcp.js`, `.../server/webStandardStreamableHttp.js`, `.../client/index.js`, and `.../inMemory.js` all resolve. The `.js` suffix is required (ESM exports).
- **Type gotcha**: the SDK's `CallToolResult` carries an open index signature (`[x: string]: unknown`); a plain `{ content, isError }` interface is NOT assignable to the `registerTool` callback return without it. Added `[key: string]: unknown` to `McpToolResult` so the thin handlers are directly usable as tool callbacks (svelte-check was the signal, 4 errors -> 0).
- **Server test drives the REAL SDK** via a `Client` over `InMemoryTransport.createLinkedPair()` - the strongest assertion: it proves the wiring, that `tools/list` returns EXACTLY the four read tools with `readOnlyHint`, that NO write-verb tool is registered (a hint-word scan over the names), and an end-to-end `tools/call` for each. The handler-level test (`tools.test.ts`) mocks the services and asserts delegation + the problem-details error mapping + the static-artifact drift discipline (the 1.2/4.3 test reused).
- **e2e gotcha**: the first MCP e2e run failed because the `data-push-api` e2e had already minted a PAT, so `.token-list` held two `Revoke` buttons (strict-mode violation). Fixed by scoping the revoke to the `<li>` filtered by the token's own name (`e2e mcp`), not the whole list.

### Completion Notes

- **Route + auth flow**: `/api/mcp` (`src/routes/api/mcp/+server.ts`, POST) sits UNDER `/api/*`, so the existing `apiAuth` hook is the gate verbatim - a missing/invalid/revoked/malformed PAT is rejected with the standard 401 `application/problem+json` (`type: /problems/unauthorized`, `WWW-Authenticate: Bearer`) BEFORE the route runs, revealing nothing beyond auth failure (no tool list, no schema). `/api/mcp` is deliberately NOT in `isPublicApiPath` (asserted in `hooks.server.test.ts`); the route reads no token itself - by the time it runs, `apiAuth` has populated `locals.apiIdentity`. The 4.1 per-IP + global rate limiters cover the auth attempt with no second limiter.
- **Read tools (4), each a thin delegation** (`src/lib/server/mcp/tools.ts` -> `src/lib/server/mcp/server.ts`): `get_schema` -> `getPublishedSchema()` (the new shared helper); `list_skeletons` -> `listSkeletons()`; `list_reports` -> `listReports()`; `get_report` (input `{ id: string }`) -> `getReport(id)`. No validation, no ownership check, no Drizzle in the handlers (AR5 four-surface parity). Each tool carries `annotations: { readOnlyHint: true, idempotentHint: true, openWorldHint: false }`.
- **Schema single source of truth**: extracted `getPublishedSchema()` into `src/lib/server/schema/published.ts` (`{ version: CURRENT_SCHEMA_VERSION, schema: toJsonSchema(), examples: { minimal, full } }`) and refactored the 4.3 REST `/api/v1/schema` endpoint to call it. REST and MCP now compose the schema through ONE code path, so the MCP-advertised schema cannot drift from the REST artifact or the committed `static/schema/v1.json` (the 4.3 endpoint test and the new MCP drift test both still pass).
- **Error-result shape (decided: problem JSON in an `isError` tool result, per the recommended ambiguity (c)).** A service `AppError` thrown in a handler is caught and returned as `{ content: [{ type: 'text', text: JSON.stringify(problem) }], isError: true }` where `problem` is the SAME RFC 9457 body `problemResponse` builds: `{ type, title, status, detail?, errors? }`. So `get_report` on an unknown id returns the service's 404 problem-details as an `isError` tool result, and a 422 carries its actionable `errors[]` - the agent reuses its REST parser. An unexpected (non-AppError) throw is RE-THROWN so the SDK renders a JSON-RPC internal error; no internal detail leaks in a tool result. The 401 (auth failure) is the transport-level handshake rejection, NOT a tool result.
- **Server metadata**: name `acta-diurna`, version `0.6.0`, with `instructions` describing the read-only discovery flow; capabilities advertise the four tools (`readOnlyHint`).
- **Server-only / reader budget**: the route and all MCP code import through `$lib/server/*` and live under `src/routes/api/` (a `+server.ts`), so the SDK never enters the client closure. Confirmed by grep of `.svelte-kit/output/client/` for `modelcontextprotocol`/`McpServer`/`webStandardStreamableHttp` - zero matches. `pnpm reader:budget` = **68.9 KB / 200 KB** (the route adds zero reader JS; the closure is the three `/r/[token]` chunks, none referencing the SDK).
- **Gates (all green)**: `pnpm lint` (prettier + eslint clean), `pnpm check` (1100 files, 0 errors / 0 warnings), `pnpm test` (**917 unit tests pass**, +16 MCP across 3 files plus the 2 hooks assertions), `pnpm build` (adapter-node done), `pnpm reader:budget` 68.9 KB, `pnpm audit` clean of HIGH/CRITICAL (2 pre-existing). `pnpm test:e2e` (Docker up): **38 passed / 13 mobile-skipped**, including the new `mcp-api.e2e.ts` (no PAT -> 401 problem+json no info leak; valid PAT -> initialize handshake 200 identifying as `acta-diurna`; revoked PAT -> 401).
- **For 5.2 (write tools on this same server)**: (1) register write tools in `buildMcpServer()` (`src/lib/server/mcp/server.ts`) with input schemas and `annotations.readOnlyHint: false` (or omitted) + the write-verb name (`create_report`, `update_report`, ...); add the thin handlers to `src/lib/server/mcp/tools.ts` delegating to the same documents/skeletons/ingestion services the REST 4.2/4.3 endpoints call - keep them service-only (no Drizzle). (2) The error mapping is reusable as-is: a service `AppError` (422 validation with `errors[]`, 409 published, 404) maps to the `isError` problem-details result via `withProblemMapping`/`problemResult`; reuse it. (3) The transport + auth are unchanged - the same PAT gate, the same stateless-per-request server build. (4) The server test's `WRITE_TOOL_HINTS` read-only assertion will need to be relaxed/retargeted when write tools land (it currently asserts ZERO write-verb tools - that is the 5.1 contract). (5) `locals.apiIdentity` is available on the route if a write tool ever needs the author identity (it does not today - single-author MVP).
