# Story 7.6: Curated Inline-SVG Icon Set

Status: Done

## Story

As the platform,
I want a small fixed registry of inline-SVG icons selectable by name,
So that callouts and card grids carry meaningful glyphs without an icon font, an external asset, or any new dependency.

## Acceptance Criteria

**Given** the icon registry (a fixed name enum, ~8-16 generic icons: e.g. `check`, `alert`, `info`, `cross`, `arrow-right`, `clock`, `database`, `shield`)
**When** a block references an icon by name
**Then** the matching SSR `<svg>` is inlined at render (no icon font, no external/CDN fetch, no new dependency), sized and coloured by the surrounding token context

**Given** an icon reference
**When** rendered
**Then** the `<svg>` is decorative (`aria-hidden="true"`, `focusable="false"`) and the meaning is carried by adjacent text, so the icon is never the sole signal (NFR14)

**Given** an unknown icon name
**When** validated
**Then** an actionable problem-details error names the offending reference and (ideally) lists the valid names (FR2 parity)

**Given** the icon set
**When** the reader bundle is measured
**Then** the inlined SVGs stay within the reader JS/asset budget (NFR3) - they are static markup, zero hydration

## Tasks / Subtasks

- [x] Schema icon-name enum (`src/lib/schema/icons.ts`): `ICON_NAMES` (a readonly tuple of twelve generic, domain-neutral names) + `iconNameSchema = z.enum(ICON_NAMES)` + the inferred `IconName` type. Isomorphic (imports nothing from `$lib/server`/`$lib/ui`). Exported from `src/lib/schema/index.ts` so blocks (7.7 callout, 7.9 card grid) reference an icon by name. An unknown name fails with the FR2 actionable error: the enum's `invalid_value` issue already carries `Allowed values: ...` as its hint via `errors.ts` `hintForCode`, listing every valid name.
- [x] Icon registry (`src/lib/render/blocks/icons.ts`): a `Record<IconName, IconPaths>` mapping each enum name to its glyph as a list of path-`d` strings on a 24x24 grid, plus the shared `ICON_VIEW_BOX`. Modelled as path data (NOT raw SVG strings) so the component renders real `<path>` elements through Svelte, never `{@html}` - the renderer-purity boundary holds. Imports only the `IconName` type from the schema.
- [x] `Icon.svelte` render component (`src/lib/render/blocks/Icon.svelte`): renders the registry glyph for `name` as ONE SSR `<svg>` - no icon font, no external/CDN fetch, no new dependency. Decorative (`aria-hidden="true"`, `focusable="false"`). `1em` square, strokes in `currentColor`, no colour or dimension baked in, so a caller controls size via `font-size` and colour via `color` on the parent (token context). Zero hydration.
- [x] Lockstep test (`src/lib/render/blocks/Icon.svelte.test.ts`): the registry has an entry for EVERY enum name and no extra, so the schema enum and the render registry can never drift.
- [x] Tests: (a) every enum name resolves to a rendered `<svg>` carrying `aria-hidden` (and `focusable="false"`); (b) the enum rejects an unknown name and the actionable error hint lists the valid names (FR2); (c) registry-vs-enum lockstep; (d) the icon strokes in `currentColor` with no hardcoded colour (no per-path fill/stroke), so it inherits the context, and sizes 1em-square. Mirror the existing component-test style (`*.svelte.test.ts`, vitest-browser-svelte) and the schema-test style.
- [x] Gates run: `pnpm lint`, `pnpm check`, `pnpm test`, `pnpm build`, `pnpm reader:budget`.

## Dev Notes

- **Foundation story, no consumer yet.** 7.6 ships the icon vocabulary, the SSR render, and the schema enum standalone; no block in the union carries an `icon` field yet (7.7 callout and 7.9 card grid add the `icon?: iconNameSchema` reference and dispatch `Icon.svelte`). So this story adds NO block, does NOT touch the discriminated union, does NOT regenerate `static/schema/v1.json` (the published artifact is unchanged - no new block type, no new document field), and adds zero reader JS (the icon is never reached on the reader path until a block uses it). Reader budget is consequently UNCHANGED at 70.0 KB / 200 KB.
- **FR2 without a document-level cross-reference pass.** Unlike a scale `scaleRef` (which resolves against the document's `scales` and so needs the `validateScaleReferences` document-superRefine seam), an icon name validates against a FIXED set known at schema-compile time. A plain `z.enum` is therefore the whole validation: an unknown name is an `invalid_value` issue whose code-hint (`errors.ts` `hintForCode`) is `Allowed values: <every name>`, so the AC's "ideally lists the valid names" is satisfied for free, no per-block branch. When 7.7/7.9 add `icon?: iconNameSchema` to their block schema, the enum validates inline (no cross-reference pass), and a bad icon surfaces at `sections[i].blocks[j].icon` with the full vocabulary in the hint.
- **The name list.** Twelve names, all generic and domain-neutral, drawn from the epic's suggested set plus the admonition glyphs the callout (7.7) needs: a verdict pair (`check`/`cross`), the admonition icons (`alert`/`info`/`question`), motion and time (`arrow-right`/`clock`), and object glyphs (`database`/`shield`/`bolt`/`flag`/`link`). Inside the AC's ~8-16 band, asserted by a test so it stays in band.
- **Renderer purity: path data, not raw SVG.** The registry holds path-`d` strings, and `Icon.svelte` iterates them into `<path {d} />` elements - no `{@html}` anywhere, so the no-raw-HTML rule holds even though the icon markup is a trusted internal constant. This matches the explicit-element approach of `Brand.svelte` / the legend swatch and keeps the render tier free of any `{@html}` escape hatch.
- **Decorative + token-driven (NFR14).** The `<svg>` is `aria-hidden="true"` and `focusable="false"`; the adjacent text in a consuming block carries the meaning, so the glyph is never the sole signal. It is `1em` square and strokes `currentColor`, so size follows `font-size` and colour follows `color` from the surrounding token context - the caller controls both via CSS, nothing is hardcoded. No axe e2e was added here because no block renders an icon yet; the consuming blocks (7.7/7.9) carry the icon-in-context axe assertions on the default theme.
- **Internal helper, not a public render export.** Like `Badge.svelte` (the 7.5 helper), `Icon.svelte` and the registry are consumed by sibling block components, not by route code, so they are NOT added to `render/index.ts` (the render-tier public surface). 7.7/7.9 import `Icon.svelte` directly.
- **Gates:** `pnpm lint` clean (prettier + eslint), `pnpm check` 0 errors / 0 warnings (1130 files), `pnpm test` 1103 passing (was 1092; +11: icon-name schema valid/unknown/hint + the Icon render, decorative, currentColor, sizing and lockstep tests), `pnpm build` ok, `pnpm reader:budget` **70.0 KB / 200 KB** (unchanged - static SSR, zero hydration, no consumer yet). The published `static/schema/v1.json` is deliberately NOT regenerated: this story adds no block type and no document field.

### Completion Notes

- The lockstep test is the load-bearing anti-drift guard: `Object.keys(ICON_REGISTRY).sort()` must equal `[...ICON_NAMES].sort()`, so adding a name to the enum without an SVG (or vice versa) fails immediately. Adding a glyph is therefore a two-file edit (`schema/icons.ts` enum + `render/blocks/icons.ts` registry) the test enforces.
- FR2 with zero extra code: the `z.enum` rejection already lists every valid name in its hint, proven by a test that asserts each name appears in the hint string. No document-level cross-reference branch was needed (the icon name resolves against a fixed compile-time set, not the document).
- No block consumes the icon yet (foundation only), so no union change, no schema-artifact regeneration, no reader-budget movement.
