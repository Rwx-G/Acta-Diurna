# Story 2.2: Save Skeletons & Instantiate Reports

Status: Done

## Story

As the author,
I want to save a skeleton and create new reports from it,
So that every issue of a recurring report has an identical structure.

## Acceptance Criteria

**Given** an assembled structure
**When** I save it as a named skeleton
**Then** it is stored (skeletons table - created by this story's migration) and listed in my skeleton library (FR9)

**Given** a skeleton name already in use
**When** saved
**Then** a problem-details error asks for a distinct name

**Given** a saved skeleton
**When** I create a report from it
**Then** the report's sections, blocks, and bindings mirror the skeleton exactly (FR11)

**Given** two reports created from the same skeleton
**When** compared
**Then** their structures are identical (automated structural equality test)

### Completion Notes

- **Migration**: `drizzle/0004_skeletons.sql` (generated by `drizzle-kit generate --name skeletons`, dummy `DATABASE_URL`, no connection). `skeletons` table: `id` uuid PK, `name` text + unique index `skeletons_name_idx`, `schema_version` int, `document` jsonb (`$type<DocumentV1>()`), `created_at`/`updated_at` timestamptz default now. Added to `schema.ts`; the drizzle client picks it up via `import * as schema` (no client change). Boot migrations apply it (the migrator is idempotent).
- **Service** (`src/lib/server/skeletons/skeletons.ts`, now async + persisting): `saveSkeleton(structureInput)` validates-on-write (422 with `errors[]` on an invalid structure, unchanged contract), inserts a fresh-UUIDv7 row (`name` = document title), and translates a pg unique violation (23505) to a 409 `/problems/skeleton-name-taken`. `listSkeletons` (id/name/updatedAt, updated_at desc), `getSkeleton(id)` (404 on unknown/malformed id, UUID boundary check), `deleteSkeleton(id)` (read-then-delete so unknown is a 404), `instantiateReport(skeletonId)` (404 on unknown skeleton, else a draft report via the reports service).
- **Instantiation path**: added `createReportWithDocument(documentInput)` to the reports service - the validate-on-write report-creation path seeded with an arbitrary document instead of the blank starter. `instantiateReport` reads the skeleton and calls it with the skeleton document, so a report from a skeleton goes through the same write contract as a blank report (only the seed differs). **Id choice**: the skeleton's own section/block ids are copied verbatim (not regenerated); only the report row id is a fresh UUIDv7. Structural equality holds regardless because the helper ignores ids; preserving them keeps instantiation a pure copy and avoids a needless id-rewrite pass.
- **Structural equality** (`src/lib/skeletons/structural-equality.ts`, isomorphic, schema types only): reduces a document to a content-free fingerprint - per section the `annex` flag, sorted audience set, and per block the `type` plus the binding's field name+type pairs (sorted, order-insensitive). Ignores every id, all titles/text/rows/series/items/image data, chart kind/axis labels, and `binding.dataSetId` (data arrives at refill). `structurallyEqual(a, b)` compares fingerprints by deep JSON equality. Backs the FR11 test (two instantiations from one skeleton are structurally identical) and is reusable by the 2.5 resolver. Approach: compare a derived fingerprint, not the raw documents - explicit about what "same shape" means and cheap to assert.
- **Nav decision**: kept `/skeletons/compose` as the composer; `/skeletons` is now the library list (load = `listSkeletons`, actions `instantiate` + `delete`). The rail "Skeletons" link points to `/skeletons` (was `/skeletons/compose`). The library has a "New skeleton" -> compose CTA (a styled `<a>`, not a Button-in-anchor) and per row a "Create report" (instantiate, redirects to the new report's editor) and a confirm-then-delete button (the same destructive pattern as the reports list). The composer save action redirects to `/skeletons` on success so the new skeleton is immediately visible.
