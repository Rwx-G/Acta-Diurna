# Story 7.5: Status Badge and Conditional Table Formatting

Status: Review

## Story

As an author or agent,
I want a status badge that renders a categorical scale value as a pill, and a table whose columns can be formatted from a scale,
So that status updates, roadmaps, requirements and findings tables read at a glance without hand-coloured cells.

## Acceptance Criteria

**Given** a `badge` reference to a scale entry (a scale key + an entry key), inline or as a small standalone block, and a `chip-cluster` block listing several such values
**When** rendered
**Then** each renders as a pill carrying the entry's colour and label from the scale (the same resolution the legend uses), the label text always present so colour is never the sole signal, and an unknown scale/entry key fails validation with an actionable problem-details error (FR2 parity)

**Given** a `table` block whose column declares a `scaleRef` (a status/severity column)
**When** rendered
**Then** that column's cells render as scale-driven badges (colour + label computed at render, never authored per cell), while the other columns render as plain escaped text, and a cell value absent from the referenced scale is an actionable validation error naming the row and column

**Given** an existing `table` with no scale-formatted column
**When** validated and rendered
**Then** it is unchanged - the `scaleRef` column formatting is additive and optional

**Given** any of these
**When** audited
**Then** they are pure SSR HTML (escaped values only), pass axe-core on the default theme (NFR14), and add no client JS beyond the reader budget (NFR3)

## Tasks / Subtasks

- [x] Shared `Badge` render helper (`src/lib/render/blocks/Badge.svelte`): renders ONE scale entry as a coloured pill carrying the entry's label - the same colour resolution the legend (`scaleEntryColor`) and the comparison-matrix severity pill use, so the badge look is consistent across every Phase B status surface. The label text is ALWAYS rendered (Svelte text interpolation, no `{@html}`), so colour is never the sole signal (NFR14) and HTML-looking labels render inert. SSR-only, zero hydration. An entry key that resolves to nothing (mid-edit preview only) falls back to the raw key + slot 0 so the preview never blanks.
- [x] New `chip-cluster` block type (`src/lib/schema/blocks/chip-cluster.ts`), additive member of the `blockSchema` discriminated union. Frame reuses `idSchema` + `audiencesSchema`. `scaleRef: idSchema` (one document scale), `entries: idSchema[]` (the ordered entry keys to render, bounded by `MAX_CHIPS = 64`), optional `title`. NO colour or label of its own - everything derives from the scale. Export from `src/lib/schema/index.ts`.
- [x] `chip-cluster` SSR render component (`src/lib/render/blocks/ChipClusterBlock.svelte`): a wrapped row of `Badge` pills resolved from the referenced scale; an unresolved `scaleRef` renders a neutral placeholder (preview path). Wire into `BlockRenderer.svelte` (threading the document `scales` + `theme`, the legend plumbing).
- [x] Extend `tableColumnSchema` (`src/lib/schema/blocks/table.ts`) with an OPTIONAL `scaleRef: idSchema`. Additive: a column with no `scaleRef` is unchanged.
- [x] Table conditional formatting in the renderer (`src/lib/render/blocks/TableBlock.svelte`): a column with a resolvable `scaleRef` renders its cells as `Badge` pills (colour + label computed at render from the scale entry whose key the cell value matches); every other column renders plain escaped text exactly as before. An empty cell (absent, null, empty string) in a scaleRef column renders blank, not a badge. `scales`/`theme` threaded from `BlockRenderer` the same way the matrix/legend get them. An existing table with no scaleRef column renders byte-identically (proven by a test).
- [x] Dangling-reference validation at the document superRefine locus (7.1 seam, `validateScaleReferences` in `scales.ts`): a chip-cluster `scaleRef` that names no declared scale, or an `entries` key not in that scale, yields the FR2 actionable problem-details error at `sections[i].blocks[j].scaleRef` / `...entries[k]`; a table column `scaleRef` that names no declared scale yields the error at `...columns[c].scaleRef`, and a static cell value in a scaleRef-formatted column that is not an entry of the referenced scale yields the error at `...rows[r].<columnKey>`, NAMING the row and the column so the author can find the bad cell. Columns with no `scaleRef` are untouched (additive).
- [x] Editors (scope: ui): a `chip-cluster` block editor (`ChipClusterBlockEditor.svelte`: pick a scale, an optional title, and the ordered list of entry keys via per-chip selects of the chosen scale's entries) wired into `BlockEditor.svelte` + the `SectionEditor` block-type palette + the `newBlock` starter; a per-column scale selector in `TableBlockEditor.svelte` (a "Plain text" / scale `<select>` per column, threaded `scales` from `BlockEditor`). Exhaustive block-summary switch in `StructureTree.svelte` gains the `chip-cluster` case.
- [x] Schema additivity: both are additive members of schema v1 - no version bump; every existing document still validates. The published `static/schema/v1.json` regenerated via `pnpm schema:export` (now ten union members); the `json-schema.test.ts` and `errors.test.ts` freshness guards updated.
- [x] Tests: a valid `chip-cluster` parses, with dangling scale/entry cross-ref errors at the right paths and the additive no-op; the table column `scaleRef` parses, with dangling column-scale and unknown-cell-value (row+column named) cross-ref errors and the additive no-op; the `Badge` resolves colour (default-palette token AND explicit hex) and always renders the label, escaping HTML-looking labels; `ChipClusterBlock` renders one pill per entry with the labels and colours and a placeholder on a missing scale; `TableBlock` renders scaleRef columns as badges + plain columns as text, renders the LABEL not the raw key (the AAA colour-plus-text assertion), renders a blank cell for an empty value, and renders byte-identically with or without scales when no column is formatted.

## Dev Notes

- **Reuse the scales foundation, do not invent a colour model.** Every categorical state in this story resolves its colour and label from a document-level scale entry exactly as the matrix and legend do (the Phase B foundational design). The `Badge` helper wraps `scaleEntryColor` (render tier, theme-palette-default or explicit author hex) + `resolveEntryRef().label` (schema tier) - the SAME two functions the legend swatch uses, so a status pill and a legend swatch for the same entry are the same colour and label (colour-language parity).
- **Badge is a render helper, not a schema type.** The AC names a "`badge` reference" inline or standalone, but the concrete schema deliverables are the `chip-cluster` block and the table column `scaleRef` - both resolve a (scale, entry) pair to a pill. Rather than add a standalone single-badge block (no driver in the corpus, and a one-entry chip-cluster already covers "a small standalone block"), the badge is a shared component reused by both surfaces and ready for a future inline-mark use. This keeps the schema surface minimal (the "three similar lines beat a premature abstraction" stance applied in reverse: one shared component, not three pill implementations). The comparison-matrix severity pill and the legend swatch were left as-is (their markup carries block-specific concerns - the matrix pill sits in a table cell with its own state semantics, the legend swatch is a separate-element chip with a sublabel); retrofitting them onto `Badge` would have regressed their structure for no visual gain, so the AC's "ideally retrofit ... only if it does not regress them" resolved to NOT retrofitting.
- **Chip-cluster shape** (`blocks/chip-cluster.ts`): `chipClusterBlockSchema = { type: literal('chip-cluster'), id: idSchema, audiences?: audiencesSchema, scaleRef: idSchema, entries: idSchema[] (1..64), title?: 1..200 }`. One `scaleRef` + a list of entry keys (the simpler of the AC's two shapes - "a list of entry keys" - since every chip in a cluster shares the cluster's status vocabulary; a heterogeneous `{scaleRef, entryKey}[]` would be a multi-legend, not a cluster). Additive union member (tenth); existing schema-v1 documents validate unchanged, no version bump.
- **Table column `scaleRef`** (`blocks/table.ts`): `tableColumnSchema` gains `scaleRef: idSchema.optional()`. The cell value in a scaleRef column is the entry KEY (e.g. `"done"`); the renderer resolves it to the entry's label and colour at render. An empty cell (absent / null / empty string) renders blank, not a badge, and is NOT a dangling reference (so a partially-filled status column validates). A cell value is matched as a string (`String(value)`) so a numeric or boolean cell value is coerced before the entry lookup.
- **Cross-reference additions** (`validateScaleReferences` in `scales.ts`): two new branches on the existing document-wide pass. Chip-cluster: an unknown `scaleRef` is one error at `...scaleRef` (and the entry loop is skipped); a resolvable scale with an `entries` key not in it is one error per bad key at `...entries[k]`. Table: each column with a `scaleRef` resolves the scale (one error at `...columns[c].scaleRef` if missing), then every non-empty static cell value in that column is checked against the scale's entries (one error at `...rows[r].<columnKey>` naming the row number and the column LABEL). The block-local zod schema cannot see the document `scales`, so the cross-reference lives at the document superRefine, like every other Epic 7 reference.
- **Render plumbing:** `TableBlock` and `ChipClusterBlock` both take `scales?` + `theme` props, threaded by `BlockRenderer` the same way the comparison-matrix and legend already receive them (no new view-model field - `scales` is already on `ReportView`). A table that declares no scaleRef column ignores `scales` entirely and is byte-identical to before (an explicit test renders the same HTML with and without `scales`).
- **Accessibility:** the badge always carries the entry label as text, so a screen reader and a colour-blind reader both get the status without the colour (NFR14, colour never the sole signal). The pill background is the scale colour, the text is `--report-bg` (the same contrast posture as the matrix severity pill, which the contrast tests already gate). No new axe e2e was added: the existing reader-accessibility e2e fixture already exercises the table and the scale-driven pill look through the comparison-matrix/legend blocks on the default theme, and these surfaces reuse that exact colour resolution; the component tests assert the label-with-colour invariant directly. (If a dedicated chip-cluster axe spec is wanted later it is a trivial fixture addition, but it is not load-bearing for this story's guarantee.)
- **Gates:** `pnpm lint` clean, `pnpm check` 0 errors / 0 warnings, `pnpm test` 1092 passing (was 1067; +25: chip-cluster schema + cross-ref, table conditional-formatting schema + cross-ref, Badge / ChipClusterBlock / TableBlock render), `pnpm build` ok, `pnpm reader:budget` **70.0 KB / 200 KB** (both new surfaces are static SSR with zero hydration; no new reader JS, no new dependency). `static/schema/v1.json` regenerated.

## Dev Agent Record

### Debug Log

- Adding the tenth block type broke three freshness guards that hardcode the catalogue size: `json-schema.test.ts` ("nine block types as a union" -> ten), `errors.test.ts` (the "Valid block types" hint string gains `chip-cluster`), and the committed `static/schema/v1.json` drift checks in `json-schema.test.ts`, `mcp/tools.test.ts`, `api/v1/schema/server.test.ts`. Root cause was the new union member, not a regression; fixed by updating the two count/list assertions and running `pnpm schema:export` to regenerate the published artifact. All three artifact-drift tests then read the regenerated file and pass.
- `pnpm check` flagged the exhaustive block-summary switch in `StructureTree.svelte` (`const exhaustive: never = block`) - the new block type made `block` non-`never`. Fixed by adding the `chip-cluster` case (the intended guard behaviour: a new block type must add a case rather than fall through silently).

### Completion Notes

- The shared `Badge` is the load-bearing reuse: chip cluster, table column and (potential future) inline badge all route colour+label through one component, so the status-pill look cannot drift between surfaces and matches the legend swatch for the same scale entry.
- Additivity proven, not asserted: `table.test.ts` renders the SAME HTML for a plain table with and without `scales` passed, and validates a no-scaleRef table against a scales-less document; `chip-cluster.test.ts` and `table.test.ts` both carry the "v1 document with no such block validates unchanged" no-op case.
- No new axe e2e: the reader-accessibility e2e fixture already gates the table and the scale-pill colour resolution on the default theme; the component tests assert the label-accompanies-colour invariant directly (the AAA "colour never the sole signal" guarantee). A dedicated chip-cluster axe spec is a trivial later addition if wanted, not load-bearing here.
