# Story 4.3: Data Push & Published Schema Endpoint

Status: Approved

## Story

As an agent or script,
I want to push data onto reports or skeletons and fetch the document schema,
So that the inject-and-render cycle runs unattended.

## Acceptance Criteria

**Given** a valid PAT
**When** I push a data set onto a report or skeleton via `/api/v1/data-sets`
**Then** parsing, binding, and rebinding behave exactly as the upload flow, including diagnostics (FR13, FR14/15 parity)

**Given** any client (no auth required)
**When** `/api/v1/schema` is fetched
**Then** the published JSON Schema of the current document version is returned with its examples (AR2; FR31 groundwork)

## Tasks / Subtasks

- [ ] `/api/v1/data-sets` push endpoint as a THIN ADAPTER over the EXACT ingestion + binding services the upload form uses (the 4.2 workspace-parity contract, applied to ingestion). An API entry instead of a multipart form, but the SAME pipeline behind it: parse -> store on the uploads volume -> inspect fields -> resolve binding -> auto-rebind -> diagnostics. Endpoint (architecture tree `api/v1/data-sets/`, "upload + push (FR12-13)"):
  - `POST /api/v1/data-sets` with a target (a report id or a skeleton id) and the data payload (decide transport: multipart file vs an inline JSON/CSV body - see Dev Notes); calls the same ingestion service `2.4` exposes (parse + the 50 MB cap BEFORE full parse + `data_sets` row + field inspection), then the same binding resolution (`applyBinding` / the binding-slot contract from 2.4) and the `2.5` auto-rebind (`rebindReport`) so an existing report's bound blocks re-resolve with the fresh data, no manual remap (FR14).
  - The response carries the SAME diagnostics the workspace refill surfaces (FR15): per-block `BlockDiagnostic` (block, expected field, closest candidate) + the `BindingSummary` aggregate - serialized as problem-details-consistent JSON, NOT a UI payload. A drifted/unresolved binding is reported in the response body, not hidden.
  - PAT-authenticated (4.1 `event.locals.apiIdentity`); errors flow through the 4.1 `/api/*` boundary. A parse failure is the existing 4xx problem+json (encoding/format/size, never silent - the 2.4 contract); an oversize body is the 2.4 413.
  - A target that is a published report follows the SAME rule as the workspace refill: `rebindReport` persists via `updateReportDocument`, which refuses a published report with 409 (2.5 Completion Note) - so an API push onto a published report is a clean conflict, not a silent skip. Document whether the push targets the draft.
- [ ] Skeleton target parity (2.2): pushing onto a skeleton routes through the same skeleton/instantiate path the workspace uses (`instantiateReport` / the skeleton ingestion scope). Decide and document the exact semantics (push onto a skeleton = instantiate a report then bind, vs bind into a skeleton-scoped data set) - mirror whatever the workspace skeleton flow does, no new behavior.
- [ ] `/api/v1/schema` published-schema endpoint (`api/v1/schema/+server.ts` in the architecture tree) - NO auth required (PUBLIC; a discovery surface for agents, leaks no report data, consistent with the 4.2 public `/api/v1/openapi.json`). Returns the published JSON Schema of the CURRENT document version WITH its examples (AR2; FR31 groundwork - the read surface MCP consumes in Epic 5). Reuse the 1.2 schema export: serve `static/schema/v1.json` (the committed `z.toJSONSchema()` draft-2020-12 artifact) plus the `minimal`/`full` example documents (1.2 `examples/`), bundled as `{ version, schema, examples }`. The version comes from the 1.2 `schemaRegistry` / `SUPPORTED_VERSIONS` (current = the registry head). Cacheable (this is public, immutable per version - set a sane `Cache-Control`, unlike the reader's `no-store`).
- [ ] No new tables, no new migration: this story is pure surface over existing services. `data_sets` (2.4) and the document storage (1.5) already exist; the schema endpoint serves committed static artifacts.
- [ ] Tests: a data-set push parses + stores + inspects identically to the upload flow (assert it calls the SAME 2.4 ingestion service, not a reimplementation); auto-rebind re-resolves bound blocks on matching fresh data (FR14); a renamed/missing field returns the FR15 diagnostic (block + expected + closest candidate) in the response body; a parse failure / oversize returns the 2.4 problem+json (4xx/413); a push onto a published report returns the 409 (no silent skip); the skeleton target routes through the 2.2 path; an unauthenticated push is the 4.1 401; `/api/v1/schema` returns `{version, schema, examples}` with the current version, the draft-2020-12 schema matching `static/schema/v1.json`, and the 1.2 examples, with NO PAT required and a cache header; the served schema does not drift from the committed artifact (reuse the 1.2 drift test discipline).

## Dev Notes

- Authority: AC verbatim from epics.md Epic 4 Story 4.3 (FR13 data ingestion via API, FR14 auto-rebind parity, FR15 diagnostics parity, AR2 published schema, FR31 groundwork). Architecture tree `api/v1/data-sets/` and `api/v1/schema/+server.ts` (lines 290, 292), line 299 (three surfaces / one service layer), line 254 (`src/lib/schema/` is the published contract, FR31), line 313 (FR30-33 = `routes/api/v1/` + the schema as the agent read surface). The closing note in epics.md: "*MVP complete after Story 4.3 - dogfooding gate begins.*" Scopes: `api` (the two routes), `ingest` (the push reuses ingestion), `schema` (the published-schema endpoint reuses the export), `docs`.
- DEPENDS ON 4.1 (PAT auth + the `/api/*` error boundary). REUSES 2.4 (ingestion: parsers, 50 MB cap, `data_sets`, field inspection, `applyBinding`, the binding-slot contract) and 2.5 (auto-rebind `rebindReport`, the `BlockDiagnostic`/`FieldDrift`/`BindingSummary` diagnostics, `recoverSlotMapping`, the closest-match algorithm). Independent of 4.2 (4.2 before 4.3 is natural ordering but they share only the 4.1 seam).
- Seam reuse - the EXACT upload-flow services, "just an API entry instead of a form":
  - Ingestion (2.4, `src/lib/server/ingestion/`): the parse + store + inspect service (CSV/JSON; Excel still parked per the 2.4 backlog item - the API push returns the SAME honest "Excel ingestion not yet enabled" problem-details until a package is approved), `readDataSetTable(dataSetId)`, `applyBinding(block, dataSetId, fields, slotMapping, rows)`, the 50 MB cap enforced before full parse, the UPLOADS_DIR storage under a UUIDv7 name (never the client filename - the 2.4 path-traversal defence).
  - Rebind + diagnostics (2.5, `src/lib/server/ingestion/`): `rebindReport` (persists only when >= 1 block re-resolved), `recoverSlotMapping(binding)`, the `diagnostics.ts` `BlockDiagnostic { blockId, blockType, label, state, drifts }` + `FieldDrift { expected, closest, distance? }` + `BindingSummary { total, bound, drifted, unresolved, allGreen }`, `remapField` (a programmatic remap may be a follow-up; the push reports drift, the agent re-pushes corrected data or calls a remap variant - decide, see ambiguity).
  - Skeletons (2.2, `src/lib/server/skeletons/`): `instantiateReport(skeletonId)` / the skeleton path for the skeleton target.
  - Schema export (1.2, `src/lib/schema/`): `static/schema/v1.json` (committed draft-2020-12 export), `examples/minimal.*` + `examples/full.*`, `schemaRegistry` / `getSchema(version)` / `SUPPORTED_VERSIONS` (`versions/index.ts`). The endpoint composes these; it adds no schema logic.
- The diagnostics on the API are the SAME data the workspace `RefillPanel` renders (2.5), serialized as JSON instead of mounted into `BindingChip`/`BindingSummary` components. The diagnostic objects live in `src/lib/server/ingestion/` (server domain), so the API serializes them directly - no UI coupling, the renderer/UI boundary holds (line 301).
- `/api/v1/schema` is PUBLIC by AC ("any client - no auth required"). It is the one unauthenticated `/api/v1` surface alongside 4.2's `/api/v1/openapi.json`; both are discovery surfaces that leak nothing (the schema is the published contract, already shipped in `/static/`). It is cacheable per version (immutable), unlike the reader's `no-store` neutral pages. This is the FR31 read groundwork Epic 5's MCP discovery surface (Story 5.1) consumes.
- MVP gate: epics.md marks the MVP complete after this story; the dogfooding gate begins after 4.3. This is the last V1 story - the inject-and-render cycle now runs unattended (create via 4.2, push data via 4.3, publish via 4.2, read via the Epic 3 reader surface), all PAT-driven.
- AMBIGUITY for the product owner (do not invent): (a) the data-payload transport on `POST /api/v1/data-sets` - multipart file upload (matches the workspace form exactly, reuses the 2.4 50 MB multipart cap) vs an inline JSON/CSV body in the request (more ergonomic for agents pushing generated data, but a second ingestion entry shape) - recommend multipart to keep ONE ingestion entry and inherit the 2.4 cap unchanged, but confirm; (b) whether the API exposes a programmatic remap (an equivalent of the 2.5 `?/remap` action) or only reports drift and expects a corrected re-push - recommend report-drift-only for V1 (the agent owns the data, re-pushing corrected fields is cleaner than a remap-by-API round trip), but flag it; (c) skeleton-target semantics (instantiate-then-bind vs skeleton-scoped data set) - recommend mirroring the exact workspace skeleton flow (2.2) with no new behavior, but confirm which the workspace actually does before wiring it.
