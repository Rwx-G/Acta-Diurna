# Story 4.3: Data Push & Published Schema Endpoint

Status: Done

## Story

As an agent or script,
I want to push data onto reports or skeletons and fetch the document schema,
So that the inject-and-render cycle runs unattended.

## Acceptance Criteria

**Given** a valid PAT
**When** I push a data set onto a report or skeleton via `/api/v1/data-sets`
**Then** parsing, binding, and rebinding behave exactly as the upload flow, including diagnostics (FR13, FR14/15 parity)

**Given** any client (no auth required)
**When** `/api/v1/schema` is fetched
**Then** the published JSON Schema of the current document version is returned with its examples (AR2; FR31 groundwork)

## Tasks / Subtasks

- [x] `/api/v1/data-sets` push endpoint as a THIN ADAPTER over the EXACT ingestion + binding services the upload form uses (the 4.2 workspace-parity contract, applied to ingestion). An API entry instead of a multipart form, but the SAME pipeline behind it: parse -> store on the uploads volume -> inspect fields -> resolve binding -> auto-rebind -> diagnostics. Endpoint (architecture tree `api/v1/data-sets/`, "upload + push (FR12-13)"):
  - `POST /api/v1/data-sets` with a target (a report id or a skeleton id) and the data payload (decide transport: multipart file vs an inline JSON/CSV body - see Dev Notes); calls the same ingestion service `2.4` exposes (parse + the 50 MB cap BEFORE full parse + `data_sets` row + field inspection), then the same binding resolution (`applyBinding` / the binding-slot contract from 2.4) and the `2.5` auto-rebind (`rebindReport`) so an existing report's bound blocks re-resolve with the fresh data, no manual remap (FR14).
  - The response carries the SAME diagnostics the workspace refill surfaces (FR15): per-block `BlockDiagnostic` (block, expected field, closest candidate) + the `BindingSummary` aggregate - serialized as problem-details-consistent JSON, NOT a UI payload. A drifted/unresolved binding is reported in the response body, not hidden.
  - PAT-authenticated (4.1 `event.locals.apiIdentity`); errors flow through the 4.1 `/api/*` boundary. A parse failure is the existing 4xx problem+json (encoding/format/size, never silent - the 2.4 contract); an oversize body is the 2.4 413.
  - A target that is a published report follows the SAME rule as the workspace refill: `rebindReport` persists via `updateReportDocument`, which refuses a published report with 409 (2.5 Completion Note) - so an API push onto a published report is a clean conflict, not a silent skip. Document whether the push targets the draft.
- [x] Skeleton target parity (2.2): pushing onto a skeleton routes through the same skeleton/instantiate path the workspace uses (`instantiateReport` / the skeleton ingestion scope). Decide and document the exact semantics (push onto a skeleton = instantiate a report then bind, vs bind into a skeleton-scoped data set) - mirror whatever the workspace skeleton flow does, no new behavior. **Resolved per the backlog Epic 4 decision: the data push targets a REPORT, exact parity with the upload flow. The workspace has no bind-data-to-a-skeleton flow (skeletons are structure-only), so "push onto a skeleton" is satisfied by instantiate-then-push (4.2 `POST /reports` instantiates, then push onto the resulting draft). No skeleton-binding path is invented; a skeleton-scoped data set is a future product decision.**
- [x] `/api/v1/schema` published-schema endpoint (`api/v1/schema/+server.ts` in the architecture tree) - NO auth required (PUBLIC; a discovery surface for agents, leaks no report data, consistent with the 4.2 public `/api/v1/openapi.json`). Returns the published JSON Schema of the CURRENT document version WITH its examples (AR2; FR31 groundwork - the read surface MCP consumes in Epic 5). Reuse the 1.2 schema export: serve `static/schema/v1.json` (the committed `z.toJSONSchema()` draft-2020-12 artifact) plus the `minimal`/`full` example documents (1.2 `examples/`), bundled as `{ version, schema, examples }`. The version comes from the 1.2 `schemaRegistry` / `SUPPORTED_VERSIONS` (current = the registry head). Cacheable (this is public, immutable per version - set a sane `Cache-Control`, unlike the reader's `no-store`).
- [x] No new tables, no new migration: this story is pure surface over existing services. `data_sets` (2.4) and the document storage (1.5) already exist; the schema endpoint serves committed static artifacts.
- [x] Tests: a data-set push parses + stores + inspects identically to the upload flow (assert it calls the SAME 2.4 ingestion service, not a reimplementation); auto-rebind re-resolves bound blocks on matching fresh data (FR14); a renamed/missing field returns the FR15 diagnostic (block + expected + closest candidate) in the response body; a parse failure / oversize returns the 2.4 problem+json (4xx/413); a push onto a published report returns the 409 (no silent skip); the skeleton target routes through the 2.2 path; an unauthenticated push is the 4.1 401; `/api/v1/schema` returns `{version, schema, examples}` with the current version, the draft-2020-12 schema matching `static/schema/v1.json`, and the 1.2 examples, with NO PAT required and a cache header; the served schema does not drift from the committed artifact (reuse the 1.2 drift test discipline).

## Dev Agent Record

### Debug Log

- `pnpm check` flagged `new File([bytes], ...)` / `new Blob([bytes], ...)` as a `BlobPart` type error under strict lib types: a plain `Uint8Array`'s backing buffer is `ArrayBufferLike` (potentially a `SharedArrayBuffer`), not the `ArrayBuffer` a `BlobPart` requires. Fixed in `ingestBytes` by copying to a fresh buffer via `bytes.slice().buffer` (a one-time copy at the API boundary) and passing the `ArrayBuffer` to `new File`.
- `pnpm test` initially failed one assertion in `hooks.server.test.ts` left as a 4.2 placeholder (`isPublicApiPath('/api/v1/schema')` expected `false` "not wired yet"). 4.3 wires it public, so the assertion was flipped to `true`.
- **QA iteration 1 (2026-06-12)**: the original `pnpm lint` was NOT clean. Prettier reported style issues in `e2e/data-push-api.e2e.ts` (three `post(url, {...})` call sites wanted the collapsed form); prettier short-circuits the `prettier --check && eslint` chain, so eslint never ran and the dev's "all gates green" claim was wrong. Fixed with `prettier --write`; both prettier and eslint now pass.
- **QA iteration 1 - streaming size cap**: the original `readBodyBytes` checked `Content-Length` (a client-supplied, omittable header) then called `await request.arrayBuffer()`, which buffers the WHOLE body before the real cap fires - a chunked request with no/false `Content-Length` bypassed the pre-check and buffered unboundedly (bounded only by adapter-node's `BODY_SIZE_LIMIT`, which was unset). Replaced with a streaming read over `request.body.getReader()`: chunks are pulled one at a time, the cumulative byte count is checked after each, and the instant it exceeds `MAX_UPLOAD_BYTES` the reader is cancelled and a 413 thrown - so an oversized body is never fully buffered. The `Content-Length` pre-check is kept as a cheap fast-path early rejection. `ingestBytes` re-checks the assembled length as the second line. New test in `body.test.ts` asserts the stream aborts at the cap (the reader is cancelled, pull count stays near the cap, 413).
- **QA iteration 1 - BODY_SIZE_LIMIT alignment**: adapter-node reads `BODY_SIZE_LIMIT` directly from `process.env` at startup (not the app env schema), defaulting to 512K - below the 50 MB push cap, so a legitimate 512K-50MB push was rejected at the transport with a generic error and the app cap was unreachable. Set `BODY_SIZE_LIMIT: ${BODY_SIZE_LIMIT:-52428800}` in `docker-compose.yml` (aligned with `MAX_UPLOAD_BYTES`, with a comment). No env.ts change needed (the app does not read it). Backlog note added that the 2.4 upload-form path keeps the same post-buffer pattern and should get the same streaming treatment for parity (the API push is fixed here; the upload form remains on the `BODY_SIZE_LIMIT` bound).

### Completion Notes

- **Route shape**: `POST /api/v1/data-sets?reportId=<uuid>` (the data set is a first-class resource that TARGETS a report via the query param, not nested under `/reports/:id`). This matches the AC's named path `/api/v1/data-sets`, the architecture tree `api/v1/data-sets/`, and the backlog "4.3 data transport" decision ("target report id in the path/query"). It also mirrors the workspace, where data sets are uploaded as an independent resource (the `data-sets` page) and then bound to a report - a data set can exist unbound, so a path that does not force a report parent is the honest model. With no `?reportId`, the push stores an unbound data set (201, no diagnostics); with `?reportId`, it auto-rebinds the draft and returns the diagnostics.
- **Transport**: raw file bytes in the request BODY; format from `Content-Type` (`text/csv` -> csv, `application/json` -> json; an Excel content-type -> the honest 415 `excelNotEnabled`, parity with the parked upload-flow Excel branch; anything else -> 415 unsupported-format). Optional `X-Filename` header labels the set (metadata only - the service stores bytes under a UUIDv7 name, never the client value, the 2.4 path-traversal defence). The 50 MB cap is enforced by a STREAMING read in `readBodyBytes` that aborts (cancels the reader, throws 413) the instant cumulative bytes exceed `MAX_UPLOAD_BYTES`, so an oversized body is never fully buffered; a declared over-cap `Content-Length` is a cheap pre-read 413 fast path; and `ingestBytes` re-checks the assembled length as the second line. (Corrected in QA iter 1: the original implementation buffered the whole body via `arrayBuffer()` before the cap could fire - the "before buffer" guarantee was false for a chunked or omitted-`Content-Length` request.)
- **Ingestion + binding are REUSED, not reimplemented.** The push calls (1) `ingestBytes` - a thin new raw-body entry in `src/lib/server/ingestion/ingestion.ts` that wraps the bytes in a `File` and delegates to the EXACT `ingestFile` pipeline (same parser, same `inspectFields`, same UUIDv7 storage on `UPLOADS_DIR`, same `data_sets` row, same `MAX_UPLOAD_BYTES`); and (2) `rebindReport(reportId, dataSetId)` from `src/lib/server/ingestion/rebind.ts` - the SAME 2.5 auto-rebind the workspace `?/rebind` action calls, returning the SAME `BlockDiagnostic[]` + `BindingSummary` (green/drifted/unresolved, closest-match for drift). No parsing, no binding, no diagnostics logic was duplicated; the only new code is the raw-body adapter (`ingestBytes`) and the transport parsing (`body.ts`). The endpoint test asserts the push delegates to the SAME `ingestBytes` + `rebindReport` functions; `ingestion.test.ts` asserts `ingestBytes` runs the exact `ingestFile` pipeline (parse/inspect/store/row).
- **Published-report 409 guard**: `rebindReport` persists via `updateReportDocument`, which refuses a published report with a 409 (the same rule the workspace refill follows). So the push targets a DRAFT; a push onto a published report is a clean conflict, surfaced as problem+json by `runApi` (not a silent skip). Covered by the unit test and the e2e (publish, then push -> 409).
- **Skeleton target**: per the backlog decision, the data push targets a REPORT. The workspace has no bind-data-to-a-skeleton flow (skeletons are structure-only); "push onto a skeleton" is satisfied by instantiate-then-push (4.2 `POST /reports` instantiates from a skeleton, then push onto the draft). No skeleton-binding path was invented.
- **`/api/v1/schema` (public)**: response shape `{ version, schema, examples }`. `version` = `CURRENT_SCHEMA_VERSION` (the 1.2 registry head); `schema` = the live `toJsonSchema()` draft-2020-12 export (the 1.2 drift test proves it byte-equal to `static/schema/v1.json`, so the served schema cannot drift while keeping one source of truth - the endpoint test re-asserts the equality); `examples` = the 1.2 `minimal` + `full` example documents (the endpoint test asserts both validate against the schema). Added to `isPublicApiPath` in `hooks.server.ts` (no PAT), `Cache-Control: public, max-age=3600` (immutable per version, unlike the reader's `no-store`).
- **Both endpoints use `runApi`** (the 4.2 correction: the `/api/*` handle boundary does NOT catch endpoint throws, so an AppError would 500 without it). An AppError -> problem+json with the right status (415/413/422/409/400/401), verified by the endpoint tests (content-type `application/problem+json`).
- **OpenAPI**: `buildOpenApiDocument` extended with the `/data-sets` (POST) and `/schema` (GET) paths and the `DataSet` / `BlockDiagnostic` / `BindingSummary` / `DataPushResponse` / `SchemaResponse` component schemas; the `/schema` operation overrides the global security with `security: []` (public). The dangling-ref guard and the path-set test were updated.
- **MVP gate**: epics.md marks the MVP complete after this story; the dogfooding gate opens after 4.3. The inject-and-render cycle now runs unattended end to end: create + publish over the API (4.2), push data + auto-rebind (4.3), read over the public reader surface (Epic 3), all PAT-driven.
- **Gates (corrected after QA iter 1)**: the dev's original "all gates green" claim was WRONG - `pnpm lint` failed on prettier style in `e2e/data-push-api.e2e.ts` (and prettier short-circuited eslint). After the QA iter 1 fixes, all gates are GENUINELY green: `pnpm lint` (prettier AND eslint clean), `pnpm check` (0 errors), `pnpm test` (736 unit tests, +1 streaming-abort test on the original +50), `pnpm build`, `pnpm reader:budget` (64.1 KB, well under the 200 KB NFR3 budget - the API is server-only, no reader JS added). `pnpm test:e2e` green (31 passed, 12 mobile-skipped workspace specs); the `data-push-api.e2e.ts` PAT-pushes a CSV onto a draft (green rebind diagnostics + the report shows the bound data), drifts a field (closest-match diagnostic), pushes onto a published report (409), and fetches `/api/v1/schema` with NO token (200, valid draft-2020-12 schema + examples).
