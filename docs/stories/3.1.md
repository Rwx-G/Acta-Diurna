# Story 3.1: SMTP Mail Service

Status: Approved

## Story

As an operator,
I want SMTP configured via environment with surfaced failures,
So that magic links reach readers through my existing mail infrastructure.

## Acceptance Criteria

**Given** SMTP env configuration (host, port, credentials, TLS mode)
**When** the app boots
**Then** the configuration is validated and a workspace test-send confirms delivery (FR36, NFR7/16)

**Given** a mail delivery failure
**When** it occurs
**Then** the author sees the failure in the workspace - never silent (NFR16)

## Tasks / Subtasks

- [ ] Extend the 1.3 Zod env validation (`src/lib/server/env.ts`) with the SMTP block: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_TLS_MODE` (`starttls | tls | none`). Validate SHAPE at boot, fail-fast on a malformed/contradictory config (e.g. non-numeric port, unknown TLS mode). Do NOT make boot depend on a live SMTP handshake - absent/unreachable relay must not crash the container (the operator may bring SMTP up after the app). Document the boot-vs-send split in Dev Notes. Add the SMTP keys to `.env.example` with safe placeholders (NEVER read or write any other `.env*` variant).
- [ ] `src/lib/server/mail/` domain (architecture structure pattern): a `mailer.ts` building the nodemailer transport from validated env (STARTTLS/TLS/none -> `secure`/`requireTLS` flags per D17), a `send.ts` exposing `sendMail({ to, subject, text, html })` returning a typed result, and a `templates/` home for the magic-link template (the actual magic-link body is authored in 3.3; this story ships the transport + a plain test-send template). Delivery errors throw a typed `AppError` (problem-details-shaped, surfaced - never swallowed, NFR16).
- [ ] Workspace test-send action in settings (`(workspace)/settings`): a `?/test-send` form action that calls `sendMail` to an operator-entered address and reports success or the exact failure (SMTP error code/message, sanitized) inline. Author-realm, under `workspaceGuard`. Uses the `lib/ui` StatusChip grammar (green sent / red failed + retry) per the UX "status chips with one-click repair" pattern.
- [ ] Surface delivery failures as a first-class state, never a silent drop (NFR16): a failed send returns a problem-details `AppError` that the calling surface renders; log the failure at `warn` via pino (the architecture logging-levels rule: SMTP retry/failure is `warn`). No credential ever logged (extend 1.3 pino redaction to `SMTP_PASSWORD`).
- [ ] NEW DEPENDENCY (needs the recorded pin + license, see Dev Notes): `nodemailer` - exact-pinned, Apache-2.0-compatible license verified and recorded in Completion Notes. Plus its `@types/nodemailer` dev dependency if not bundled.
- [ ] Tests: env validation accepts a well-formed SMTP block and rejects a malformed one (bad port, unknown TLS mode); `sendMail` success and failure paths against a mocked transport (no live SMTP in unit tests); the `?/test-send` action returns success and surfaces a transport failure as problem-details; pino does not emit the password.

## Dev Notes

- Authority: FR36 (SMTP env config + test-send), NFR7 (STARTTLS/TLS authenticated relay), NFR16 (no silent mail failure), architecture D17 (nodemailer over SMTP), structure pattern (`server/mail/` domain, routes thin), process pattern (env validated at boot fail-fast; `warn` log level for SMTP degradation). The `mail` git scope maps to `server/mail`.
- Seam reuse: the env module is `src/lib/server/env.ts` (1.3, Zod fail-fast). The error model is `src/lib/server/problem.ts` (1.4) - throw `AppError`, the single `handleError` hook maps it. pino redaction config is in place since 1.3; add `SMTP_PASSWORD` to the redact list.
- NEW DEPENDENCY decision: nodemailer is the architecture-named V1 SMTP library (D17), so it is pre-approved in spirit (SMTP is a named V1 capability); the implementing dev MUST still record the exact installed version pin and confirm the license is Apache-2.0-compatible (nodemailer is MIT - compatible) in Completion Notes, per the project "no new dependencies without recorded justification" rule. Pin exact, justify, run `pnpm audit`.
- BOOT vs SEND decision (recommended, document it): validate the SMTP config SHAPE at boot (fail-fast on a malformed config - the operator should know immediately their env is wrong), but do NOT perform a live SMTP connection at boot. A misconfigured-but-shaped relay (wrong host that is up later, transient outage) must surface at SEND time as a problem-details failure in the workspace, not block the container from starting. This honors the trivial-deploy promise (the app boots, the operator runs the test-send to confirm reachability) while still catching env typos early.
- This story is the prerequisite for 3.3 (reader magic-link verification consumes `sendMail` + the magic-link template). It ships the transport + a test-send; the magic-link template body and the verification flow land in 3.3.
- No third-party assets, no phone-home: the mailer talks only to the operator-configured relay. No external service.
