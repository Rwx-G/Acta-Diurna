# Story 3.1: SMTP Mail Service

Status: Done

## Story

As an operator,
I want SMTP configured via environment with surfaced failures,
So that magic links reach readers through my existing mail infrastructure.

## Acceptance Criteria

**Given** SMTP env configuration (host, port, credentials, TLS mode)
**When** the app boots
**Then** the configuration is validated and a workspace test-send confirms delivery (FR36, NFR7/16)

**Given** a mail delivery failure
**When** it occurs
**Then** the author sees the failure in the workspace - never silent (NFR16)

## Tasks / Subtasks

- [x] Extend the 1.3 Zod env validation (`src/lib/server/env.ts`) with the SMTP block: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_TLS_MODE` (`starttls | tls | none`). Validate SHAPE at boot, fail-fast on a malformed/contradictory config (e.g. non-numeric port, unknown TLS mode). Do NOT make boot depend on a live SMTP handshake - absent/unreachable relay must not crash the container (the operator may bring SMTP up after the app). Document the boot-vs-send split in Dev Notes. Add the SMTP keys to `.env.example` with safe placeholders (NEVER read or write any other `.env*` variant).
- [x] `src/lib/server/mail/` domain (architecture structure pattern): a `mailer.ts` building the nodemailer transport from validated env (STARTTLS/TLS/none -> `secure`/`requireTLS` flags per D17), a `send.ts` exposing `sendMail({ to, subject, text, html })` returning a typed result, and a `templates/` home for the magic-link template (the actual magic-link body is authored in 3.3; this story ships the transport + a plain test-send template). Delivery errors throw a typed `AppError` (problem-details-shaped, surfaced - never swallowed, NFR16).
- [x] Workspace test-send action in settings (`(workspace)/settings`): a `?/test-send` form action that calls `sendMail` to an operator-entered address and reports success or the exact failure (SMTP error code/message, sanitized) inline. Author-realm, under `workspaceGuard`. Uses the `lib/ui` StatusChip grammar (green sent / red failed + retry) per the UX "status chips with one-click repair" pattern.
- [x] Surface delivery failures as a first-class state, never a silent drop (NFR16): a failed send returns a problem-details `AppError` that the calling surface renders; log the failure at `warn` via pino (the architecture logging-levels rule: SMTP retry/failure is `warn`). No credential ever logged (extend 1.3 pino redaction to `SMTP_PASSWORD`).
- [x] NEW DEPENDENCY (needs the recorded pin + license, see Dev Notes): `nodemailer` - exact-pinned, Apache-2.0-compatible license verified and recorded in Completion Notes. Plus its `@types/nodemailer` dev dependency if not bundled.
- [x] Tests: env validation accepts a well-formed SMTP block and rejects a malformed one (bad port, unknown TLS mode); `sendMail` success and failure paths against a mocked transport (no live SMTP in unit tests); the `?/test-send` action returns success and surfaces a transport failure as problem-details; pino does not emit the password.

## Dev Notes

- Authority: FR36 (SMTP env config + test-send), NFR7 (STARTTLS/TLS authenticated relay), NFR16 (no silent mail failure), architecture D17 (nodemailer over SMTP), structure pattern (`server/mail/` domain, routes thin), process pattern (env validated at boot fail-fast; `warn` log level for SMTP degradation). The `mail` git scope maps to `server/mail`.
- Seam reuse: the env module is `src/lib/server/env.ts` (1.3, Zod fail-fast). The error model is `src/lib/server/problem.ts` (1.4) - throw `AppError`, the single `handleError` hook maps it. pino redaction config is in place since 1.3; add `SMTP_PASSWORD` to the redact list.
- NEW DEPENDENCY decision: nodemailer is the architecture-named V1 SMTP library (D17), so it is pre-approved in spirit (SMTP is a named V1 capability); the implementing dev MUST still record the exact installed version pin and confirm the license is Apache-2.0-compatible (nodemailer is MIT - compatible) in Completion Notes, per the project "no new dependencies without recorded justification" rule. Pin exact, justify, run `pnpm audit`.
- BOOT vs SEND decision (recommended, document it): validate the SMTP config SHAPE at boot (fail-fast on a malformed config - the operator should know immediately their env is wrong), but do NOT perform a live SMTP connection at boot. A misconfigured-but-shaped relay (wrong host that is up later, transient outage) must surface at SEND time as a problem-details failure in the workspace, not block the container from starting. This honors the trivial-deploy promise (the app boots, the operator runs the test-send to confirm reachability) while still catching env typos early.
- This story is the prerequisite for 3.3 (reader magic-link verification consumes `sendMail` + the magic-link template). It ships the transport + a test-send; the magic-link template body and the verification flow land in 3.3.
- No third-party assets, no phone-home: the mailer talks only to the operator-configured relay. No external service.

### Completion Notes

- **nodemailer 8.0.11 (MIT-0), @types/nodemailer 8.0.1 (MIT)** - both exact-pinned, lockfile committed. MIT-0 is Apache-2.0-compatible.
- **Boot-vs-send validation decision (as recommended in Dev Notes, implemented)**: `env.ts` validates the SMTP block SHAPE at boot - a malformed value (non-numeric `SMTP_PORT`, unknown `SMTP_TLS_MODE`) fails fast and names the variable, exactly like the rest of the env. It does NOT open any SMTP connection at boot. The whole SMTP block is OPTIONAL (an operator can deploy first and configure the relay later) but ALL-OR-NOTHING when present: if any `SMTP_*` var is set, a `superRefine` requires `SMTP_HOST`, `SMTP_PORT` and `SMTP_FROM` together so a half-configured relay is caught at boot, while `SMTP_USER`/`SMTP_PASSWORD` stay optional (unauthenticated localhost submission) and `SMTP_TLS_MODE` defaults to `starttls` at the mailer. Reachability and auth are exercised only at SEND time, where a failure becomes a problem-details `AppError` surfaced in the workspace. This honors the trivial-deploy promise (the container always boots; the operator confirms reachability via the test-send) and still catches env typos immediately.
- **TLS mapping (D17/NFR7)**: `tls` -> `{ secure: true }` (implicit TLS, port 465); `starttls` -> `{ secure: false, requireTLS: true }` (plaintext connect then MANDATORY STARTTLS upgrade - a relay without STARTTLS is rejected, never silently downgraded); `none` -> `{ secure: false, requireTLS: false }` (local/dev only).
- **Failure surfacing + redaction (NFR16/NFR8)**: `sendMail` throws a typed `AppError` on every failure - `/problems/mail-not-configured` (503) when SMTP is absent, `/problems/mail-delivery-failed` (502) on a transport error. The RAW error (which can carry the relay host, the auth response, connection internals) is logged server-side at `warn` via pino (architecture logging-levels: SMTP degradation is `warn`) and NEVER placed in the client-facing `detail`. The detail carries only the 3-digit SMTP response code when present (`The mail relay rejected the message (SMTP 535).`) or a generic unreachable hint - no host, no credentials, no raw response. The Settings `?/test-send` action renders that detail inline as a red "Failed" chip; a success renders a green "Sent" chip. Both are first-class returned states, never a silent drop.
- **Settings surface (FR36)**: new `(workspace)/settings` route (author-realm, covered by the existing `workspaceGuard`; NOT added to `isPublicPath`). `load` reports whether SMTP is configured (sender + TLS mode shown; password never read) so the page explains the absent case instead of offering a test-send that always 503s. The rail "Settings" entry was enabled (was a disabled placeholder).
- **Template seam for 3.3**: `src/lib/server/mail/templates/test-email.ts` is a pure function `(to) => MailMessage`. 3.3 adds a sibling magic-link template taking the verification URL and calls `sendMail(magicLinkEmail(to, url))` - no transport change needed.
- **For 3.3**: import `sendMail` from `$lib/server/mail/send`. Signature: `sendMail(message: { to, subject, text, html? }, requestId?: string): Promise<{ messageId }>`. It throws `AppError` on failure (catch it and surface via `problemResponse`/`fail`, never swallow). Build the body as a `templates/magic-link.ts` returning a `MailMessage`. The transport, TLS handling, env, and redaction are done; 3.3 owns only the template body and the verification flow.
