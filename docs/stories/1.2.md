# Story 1.2: Document Schema v1 - the Published Contract

Status: Approved

## Story

As an author (human or agent),
I want a versioned document schema with actionable validation,
So that any producer can create a valid report and know precisely why an invalid one fails.

## Acceptance Criteria

**Given** the `src/lib/schema/` package (Zod 4, AR2)
**When** a document with section + text/table/chart/kpi/image blocks is validated
**Then** it parses with full TypeScript types, and audience-tag fields are accepted (rendering deferred to P2)

**Given** an invalid document (missing field, wrong type, unknown block)
**When** validated
**Then** the error names the block path and field with a hint, in problem-details shape (FR2)

**Given** the schema
**When** the `z.toJSONSchema()` export runs
**Then** a valid JSON Schema (draft 2020-12) is produced with version identifier `1`
**And** example documents (minimal + full-featured) live beside the schema and validate in tests

## Tasks / Subtasks

- [ ] Define `src/lib/schema/` package: document root (version field = 1, title, theme ref, sections), section (id, title, audience tags optional, annex flag, blocks), and the five block types (text, table, chart, kpi, image) with data-binding declarations (expected fields) where applicable
- [ ] Audience tags: optional `audiences` array on sections and blocks (values: summary/full/technical) - accepted and typed, not yet rendered
- [ ] Actionable error layer (`errors.ts`): Zod error map producing `{path, message, hint}` entries; problem-details shaping helper
- [ ] `z.toJSONSchema()` export with version identifier; verify output is valid draft 2020-12
- [ ] Example documents: `examples/minimal.json` and `examples/full.json` beside the schema; co-located Vitest tests validating both plus a corpus of invalid documents asserting exact error paths/hints
- [ ] Version dispatch skeleton (`versions/`): registry mapping version -> schema, unsupported-version error with supported range (groundwork for FR7)

## Dev Notes

- THE load-bearing deliverable (architecture AR2). The schema is isomorphic: no imports from `server/` or `ui/`; it is the published artifact for agents (FR31 groundwork).
- Authority: architecture "Cross-Cutting Concerns" 1/2/5 (versioning, XSS-safe = narrative is data never HTML - no HTML-bearing field anywhere), patterns section ("schema is sacred"); PRD FR1/FR2/FR7; UX spec block list (TextBlock/TableBlock/ChartBlock/KpiBlock/ImageBlock).
- Image block: reference to an uploaded asset + required alt text (UX accessibility); no remote URLs (CSP/no-phone-home).
- Table/chart/kpi blocks: declare `binding` (expected field names + types) so ingestion (Epic 2) can resolve; static inline data also allowed for authoring without uploads.
- Zod 4 native `z.toJSONSchema()`; confirm exact API with the best-practices web agent if uncertain.
