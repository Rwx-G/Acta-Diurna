# Story 3.2: Share Links with Expiry

Status: Done

## Story

As the author,
I want to generate expiring share links on published reports,
So that distribution is one link with a bounded lifetime.

## Acceptance Criteria

**Given** a published report
**When** I create a share
**Then** a high-entropy link (>= 128 bits) is generated with an optional expiry I control (shares table created by this story's migration) (FR17, FR21, NFR6)

**Given** a draft report
**When** I attempt to share it
**Then** sharing is refused with a clear message (FR6 dependency)

## Tasks / Subtasks

- [x] `shares` table migration (drizzle-kit generate, next sequential number): `id` uuidv7 PK, `report_id` uuid FK -> reports, `token_hash` text (the raw token NEVER stored, only its SHA-256 hash at rest - see 1.4 session-token pattern), `mode` text with check `in ('restricted','open')` default `'restricted'` (column present now, driven in 3.4), `expires_at` timestamptz NULLABLE (no expiry = null), `created_at` timestamptz default now, `revoked_at` timestamptz NULLABLE (column present now, set in 3.5). Indexes: unique `shares_token_hash_idx`, `shares_report_id_idx`. Register in `src/lib/server/db/schema.ts`.
- [x] `src/lib/server/sharing/` domain (architecture structure pattern). Token service `tokens.ts`: generate a >= 128-bit (use 256-bit, matching the 1.4 session token strength) random token via `crypto`, return the RAW token to the caller (it goes only into the URL) and store only `sha256(token)`; a `hashToken`/`findShareByToken` lookup mirroring the 1.4 session hash-keyed lookup. `shares.ts`: `createShare(reportId, { mode?, expiresAt? })` and a `listShares(reportId)` / `getShareByToken(rawToken)` read side.
- [x] Only PUBLISHED reports are shareable: `createShare` calls `assertShareable(report)` from 1.7 (`src/lib/server/documents/reports.ts`) - a draft throws the existing 409 `/problems/report-not-published`, surfaced as a clear message in the share UI (FR6 dependency). Never generate a token for a non-published report.
- [x] Workspace share surface on a published report (`(workspace)/reports/[id]/share` route per the architecture tree): a `?/create-share` action (optional expiry input the author controls; mode selector present, restricted default - the recipient-list UX lands in 3.4) returning the RAW link copied in one gesture (UX Flow B end: "link copied in one gesture", ShareDialog component). Author-realm, under `workspaceGuard`. A draft report shows the refusal message, not a generate button.
- [x] Expiry semantics: `expires_at` is the author-chosen absolute instant (ISO 8601 UTC); a null `expires_at` means no time bound (FR21 "optional expiry"). Enforcement of expiry on the READER side (serving the neutral page) is 3.5; this story persists and surfaces the expiry, and the share read side exposes an `isExpired(share, now)` helper 3.3/3.5 consume.
- [x] Tests: `createShare` on a published report returns a raw token of >= 128 bits entropy and stores only the hash (raw never persisted); `createShare` on a draft throws 409 `/problems/report-not-published`; token lookup finds a share by raw token via its hash and misses on a wrong token; expiry persists and round-trips; `?/create-share` action success + draft-refusal problem-details; the mode column defaults to restricted.

## Dev Notes

- Authority: FR17 (generate share link), FR21 (optional expiry), FR6 (only published reports shareable), NFR6 (>= 128-bit token entropy, hashed at rest), architecture D2 (shares table around the JSONB document), D5 (tokens random + hashed at rest), structure pattern (`server/sharing/` domain). The `share` git scope maps to `server/sharing`; the migration is a `db`-scoped concern but ships with this story.
- Seam reuse: `assertShareable(report)` and `getPublishedDocument(id)` are the 1.7 sharing gates (`src/lib/server/documents/reports.ts`) - a share is always against the published snapshot, never the draft `document`. The token hash-at-rest + hash-keyed lookup pattern is the 1.4 session model (`src/lib/server/auth/sessions.ts`, SHA-256, `timingSafeEqual`, UUIDv7 ids via `src/lib/server/db/ids.ts`). Migration generation follows the 1.4/1.7 recipe (`MSYS_NO_PATHCONV=1 DATABASE_URL=postgres://x pnpm exec drizzle-kit generate --name shares`, no live DB).
- The `mode` and `revoked_at` columns are created NOW but exercised later (3.4 drives mode, 3.5 sets revoked_at) - same forward-schema discipline the 1.4 `sessions.realm` column used for the reader realm. Do not split into a second migration.
- This story is the prerequisite for 3.3 (the reader verification gate resolves a share by its token before prompting for email) and 3.5 (revocation/expiry serve a neutral page). It depends on nothing from 3.1 - it can be implemented in parallel with 3.1, but 3.3 needs BOTH.
- `/r/[token]` already exists from 1.6/1.7 as the reader render route; this story does NOT add the verification gate (that is 3.3). It produces the token that route will consume.

### Completion Notes

- **Migration (0006)**: `shares` table - `id` uuid PK, `report_id` uuid NOT NULL FK -> reports **ON DELETE CASCADE**, `token_hash` text, `mode` text NOT NULL default 'restricted' (CHECK in ('restricted','open')), `expires_at` timestamptz nullable, `created_at` timestamptz default now, `revoked_at` timestamptz nullable. Unique index on `token_hash`, plain index on `report_id`. **Cascade vs SET NULL**: a share is meaningless without its report (it serves that report's published snapshot and nothing else), so a deleted report's shares must vanish with it - a dangling share would resolve to no report. Contrast `data_sets.report_id` (SET NULL): a data set can legitimately outlive or precede a report. **Forward-schema columns**: `mode` and `revoked_at` are created NOW but exercised later (3.4 drives mode, 3.5 sets revoked_at), the same discipline as the sessions `realm` column - so 3.3/3.4/3.5 do not re-migrate.
- **Token service** (`src/lib/server/sharing/tokens.ts`): `SHARE_TOKEN_BYTES = 32` (256 bits, well above the NFR6 >= 128-bit floor, matching the 1.4 session token strength). `generateShareToken()` returns 32 random bytes base64url-encoded (43 URL-safe chars, fits `/r/[token]`). `hashShareToken()` is SHA-256 hex - the **exact same hash-at-rest function the 1.4 session model uses** (`createHash('sha256')`), so a share token (a bearer credential resolved on every reader request) is stored and looked up identically. The raw token reaches the caller once; only the hash is persisted.
- **Sharing service** (`src/lib/server/sharing/shares.ts`): `createShare(reportId, { mode?, expiresAt? }) -> { token, share }` reuses 1.7 `getReport` + `assertShareable` to refuse a draft (409 `/problems/report-not-published`) **before** minting any token; rejects a past expiry (422 `/problems/share-expiry-past`); mints the token, stores hash + metadata, returns the raw token once. `listShares(reportId) -> ShareSummary[]` (id/mode/expiresAt/createdAt/revokedAt/status, newest first, **never the raw token**). `getShareByToken(rawToken) -> ResolvedShare | null` hashes then matches on `token_hash`, returning the share + its status. `shareStatus(share, now)` / `isExpired(share, now)` are the status helpers 3.3/3.5 consume: **revocation wins over expiry** (revoked even past its window), an elapsed `expiresAt` is expired, a null `expiresAt` never expires, else active. `shareUrl(origin, token)` is the single point composing `/r/[token]`. A barrel `index.ts` exposes the domain (ingestion-style convention).
- **Workspace UI** (`(workspace)/reports/[id]/share`): under `workspaceGuard` (author realm). A **draft** report shows an EmptyState refusal ("Publish this report before sharing") with a link back to the editor, no generate button. A **published** report shows the create form (optional `datetime-local` expiry labelled UTC + a restricted/open mode selector, restricted default) and, on success, the raw link **once** in a highlighted block with one-gesture copy-to-clipboard (the raw token lives only there and only on the action result - reloading loses it, by design). Below, the existing shares list each row's status chip (active/expired/revoked), mode, creation, and expiry - never the token. "Share" entry points added to the reports list (published rows only) and the editor toolbar (published only).
- **Security (NFR6)**: 256-bit entropy documented via the `SHARE_TOKEN_BYTES` constant; only the SHA-256 hash at rest; the raw token is shown once, never logged (pino lines in `hooks.server.ts` log method/path/status only, never bodies or the token), never re-fetched, never stored. The share URL is the only place the raw token exists. Tests assert the persisted row carries the token on no column and the summary/listing never contain it.
- **For 3.3**: `getShareByToken(rawToken)` is the resolution seam for the reader gate - hash the URL token, look up by `token_hash`. It returns `{ id, reportId, mode, expiresAt, createdAt, revokedAt, status }` with `status` already computed (active/expired/revoked); this story does NOT enforce that status at a route. The reader route `/r/[token]` must be created by 3.3 (it is already whitelisted in `isPublicPath`/`isNoindexReportPath`); per the Epic 3 backlog decision, a revoked/expired/unknown token must all serve one identical neutral 404 (3.5), and an active share serves the verify gate. `reportId` on the resolved share points the reader at `getPublishedDocument(reportId)` (the frozen snapshot, 1.7). The `mode` column is `'restricted'` by default - 3.4 drives the recipient-list flow off it.
