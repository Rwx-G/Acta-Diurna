# Story 9.1: Series Lineage Model

## Status

Review

## Story

As the author,
I want each "next issue" I start to be linked to the one it came from,
So that consecutive editions of a recurring report form a series I can diff and navigate instead of a pile of unrelated reports.

## Acceptance Criteria

**Given** the series model
**When** the schema is migrated
**Then** a `report_series` table identifies a lineage, the `reports` row carries a `series_id` (the lineage it belongs to) and a `predecessor_id` (the issue it was duplicated from, null for the first issue), both owner-scoped, and an optional author-set `issue_label`; pre-existing reports get a fresh single-issue `series_id` and a null predecessor (one-time, idempotent backfill), so no report is left without a series

**Given** an author duplicating a report to start the next issue (`duplicateReport`, FR10)
**When** the new draft is minted
**Then** it inherits the source's `series_id` and sets its `predecessor_id` to the source, while keeping the existing duplicate semantics unchanged (deep copy, forced draft, cleared publish snapshot, owner = the duplicating author) - the lineage edge is the only addition

**Given** a report that was created fresh (not by duplication)
**When** it is stored
**Then** it starts its own series (fresh `series_id`, null `predecessor_id`), so a never-duplicated report is a one-issue series, not a null

**Given** an authenticated author in multi mode
**When** they read a series or its issues
**Then** the service filters by `owner_id`: a series and its predecessor edges are visible only to the owning author, and a cross-author series id returns the same neutral 404 the rest of the tenancy layer uses (no existence oracle); single mode preserves today's semantics (the implicit author owns every series)

**Given** the ordered issues of a series
**When** they are listed
**Then** order follows the `predecessor_id` chain (issue N's predecessor is issue N-1), NOT `published_at`, so a back-dated or out-of-order republish never reshuffles the series; `issue_label` and `published_at` are display labels only

## Dev Notes

### Model shape (the decision)

- **`report_series` carries almost nothing.** A series is identified by its id; the issues point back via `reports.series_id`, and the order is the predecessor chain on `reports.predecessor_id`. The only column beyond `id`/`created_at` is `owner_id` (FK -> authors, ON DELETE RESTRICT) - a series belongs to exactly one author and NEVER spans authors.
- **`reports` gains three additive nullable columns.** `series_id` (FK -> report_series, RESTRICT), `predecessor_id` (a SELF-FK -> reports, RESTRICT, null for the first issue), `issue_label` (optional, cosmetic). All nullable so the migration is safe against pre-existing rows; the boot backfill then assigns every report a series.
- **Lineage is DB metadata, not a document-schema change (epic resolved).** The series edge lives entirely in the relational tier - no `DocumentV1` field, no schema-version bump. `pnpm schema:export` produces a byte-identical `static/schema/v1.json` (confirmed: no git diff).

### Establishing the edge

- **A fresh report starts its own series.** `createReport` / `createReportWithDocument` mint a `report_series` row (owned by the creating author) and stamp it on the report with a null predecessor - so a never-duplicated report is a one-issue series, never a null (AC3).
- **A duplicate joins the source's series.** `duplicateReport` (the "start next issue" motion) sets `predecessor_id = source.id` and `series_id = source.series_id`. If the source carries no series yet (only a legacy pre-backfill row would, since every live report gets one on create), `duplicateReport` mints a series, assigns it to the SOURCE first, then to the copy, so the predecessor and its issue always share a lineage.
- **Owner-consistency is by construction.** The scoped `getRow` in `duplicateReport` already proved the source belongs to the duplicating author; the new series and report carry `ownerForInsert(scope)`. In single mode the implicit author owns everything (a no-op).

### Backfill (AC1)

- **A per-report sweep, not a single series.** `backfillReportSeries` gives EACH series-less report its OWN distinct series (a series groups a lineage, not all legacy reports), carrying the report's own owner. It runs at boot AFTER `inheritLegacyOwnership` (so every report already has an owner to copy onto its series) and BEFORE traffic. Idempotent: the `series_id IS NULL` guard matches zero rows on a second boot. It is fatal-on-failure with the rest of the ownership-ready boot step. The backfill is REQUIRED by the AC (pre-existing reports must not be left series-less), so it is not purely forward-looking.

### Ordered-lineage read (AC5)

- **Order is the predecessor chain, never `published_at`.** `listSeriesIssues` loads the series' issues (metadata projection, owner-scoped via the series lookup) and rebuilds the chain in memory: the head is the issue with a null (or out-of-series) predecessor, then each successor is the issue pointing back at the current one. A back-dated or out-of-order republish never reshuffles the order. The walk is bounded by the issue count and stops on a repeat, so a corrupted edge degrades to a truncated list, never a hang; any issue the chain did not reach is appended (never silently dropped). `issue_label` and `published_at` are carried for display only.
- **Owner-scoping at the series lookup.** The owner predicate ANDs into the series id lookup (the series is the lineage's owner of record; every issue of an owner-consistent series shares that owner). A cross-author, unknown, or malformed series id is the same neutral 404. Single mode: the predicate is a no-op.

### Tenancy guard

- `report_series` carries `owner_id`, so the schema-discovered tenancy guard (`tenancy-guard.test.ts`) picks it up automatically. `documents/reports.ts` uses `ownerFilter` on the series read and is already on the sanctioned allowlist for the reader path; `authors/inheritance.ts` is the sanctioned boot backfill. No allowlist edit needed.

### QA remediation (2026-06-14)

A 3-agent QA audit converged on seven findings; all fixed (no behaviour change on the success path):

1. **Fork misorders/drops a branch (high).** `orderByPredecessorChain` keyed `successorOf` as `Map<key, SeriesIssue>`, so two issues sharing a predecessor (a fork) overwrote each other and one branch silently fell into the orphan-append - a plausible-but-wrong order. Now `Map<key, SeriesIssue[]>` with a deterministic depth-first walk (siblings in input order, the issues query orders by `created_at, id`), a `logger.warn` on the collision (a corrupted edge is observable), and the existing cycle guard / no-loss append retained. Unit test added for a forked series asserting complete, deterministic order + the warn.
2. **Issues query not owner-scoped (medium, tenancy).** `listSeriesIssues` applied the owner predicate only to the `report_series` lookup. The issues `SELECT` now ALSO ANDs `ownerFilter(scope, reports.ownerId)` (belt-and-braces; single mode is a no-op, byte-identical). Tenancy test added: a foreign-owned issue carrying the owner's series id does not leak.
3. **Non-atomic create/duplicate (medium, integrity).** `createReport`, `createReportWithDocument`, and `duplicateReport` ran series INSERT + report INSERT (+ source UPDATE) as separate statements. Each sequence is now wrapped in `db.transaction`, so a crash mid-sequence leaves no dangling `report_series` row or half-formed lineage.
4. **Boot backfill O(2N) round-trips (medium, perf).** `backfillReportSeries` awaited an INSERT then an UPDATE per orphan. Now ONE multi-row `insert(reportSeries)` then `Promise.all` over the per-report stamps (mirrors `inheritLegacyOwnership`'s parallel E6 pattern); idempotency (`series_id IS NULL`) and per-row owner preserved. Multi-mode e2e (boot backfill on a fresh container) stays green.
5. **No LIMIT on the issues read (medium).** `listSeriesIssues` now caps at `.limit(1000)` (a longer series is pathological; the chain walk already tolerates truncation - an unreached issue is appended, never dropped).
6. **`report_series.owner_id` nullable contradicted the invariant (medium).** A series always has an owner (app-inserted by backfill or `createSeries`), so `ownerId` is now `.notNull()`. Migration `0017` regenerated cleanly (the column is `NOT NULL` on `CREATE TABLE`); the `0017` snapshot's `notNull` flag flipped to match (journal/snapshot consistent, no separate 0018 ALTER). Migration applies on the e2e boot. Migration DDL test extended to assert `"owner_id" uuid NOT NULL`.
7. **Clarity (info).** `backfillReportSeries` now has its own try/catch at the boot call site with a distinct "report series backfill failed" fatal message (no longer logged as "ownership inheritance failed"); the discarded `.orderBy()` in the issues query carries a comment that ordering is deferred to the in-memory chain walk.

Deferred as debt (measure-first / out of scope, NOT implemented):

- The single-JOIN optimization for the two-step series-check + issues-fetch in `listSeriesIssues` (measure-first; two indexed point reads are not a proven bottleneck).
- Parallelizing the create/duplicate round-trips (measure-first; the writes now share one transaction and are not on a hot path).
- The pre-existing `postForm` / `tableName` e2e + test-helper duplication (not 9.1's responsibility; a cross-cutting cleanup).
