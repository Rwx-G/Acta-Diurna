# Story 10.2: Block Palette and Structural Editing (Blocks and Sections)

## Status

Review

## Story

As the author,
I want to add, reorder, and delete blocks and sections by direct manipulation,
So that I build and restructure a report visually instead of through one big form.

## Acceptance Criteria

**Given** the block palette
**When** the author picks a block type
**Then** the palette offers exactly one entry per member of the block discriminated union (text, table, chart, kpi, image, comparison-matrix, set-membership, field-grid, legend, callout, code, card-grid, chip-cluster, list, timeline), and inserting one seeds it from the `newBlock` factory so the new block is at most one keystroke from valid (errors are guidance, the author is never blocked from adding a block)

**Given** a section with several blocks
**When** the author reorders or deletes a block
**Then** the change applies in the in-edit document and the live preview reflects it; reorder offers a keyboard-accessible move-up / move-down baseline (`moveItem`), with drag as a layered enhancement, never the only affordance (NFR15)

**Given** the section structure
**When** the author adds, reorders, or deletes a section
**Then** a new section seeds from `newSection` (one empty text block, one keystroke from valid), reorder and delete behave like the block case, and the preview's section navigation updates

**Given** a structural edit that leaves the document invalid (e.g. an emptied section)
**When** saved
**Then** the save returns the actionable 422 inline at the offending element - structural edits never silently drop content or save an invalid document

## Tasks / Subtasks

- [x] **Block palette catalogue (ui).**
  - [x] A single source of truth `blockPaletteEntries` (`editor-state.ts`) maps ONE entry per member of the block discriminated union to a `{ type, label, description }`. The backing `BLOCK_CATALOGUE` is `satisfies Record<BlockType, ...>`, so a new/removed/renamed block type is a COMPILE error here - the palette can never silently omit or stale-list a type.
  - [x] The palette adds NO new block type and NO new block shape: each entry's insertion is seeded from the existing `newBlock(type)` factory (carried from 1.5), so it exposes the existing catalogue. (The meta-strip is the field-grid `layout: 'strip'` variant - not a separate union member - reached through the field-grid editor, so it is not a separate palette entry.)
- [x] **Block palette component (ui).** `BlockPalette.svelte` renders the entries as a labelled group (NFR15): the group carries an `aria-label` ("Add a block to <section>"), each entry button an explicit `aria-label` ("Add a <label> block") and a visible one-line description. It reports the chosen type via `onInsert(type)`; the caller seeds and inserts. Replaces the flat "Add {type}" button row from 1.5.
- [x] **Structural editing through the working copy (ui).**
  - [x] Blocks: add (palette `onInsert` -> `newBlock` -> push), reorder (keyboard move up/down via `moveItem`), delete (splice) - all in `SectionEditor`, mutating the bound in-edit section `$state`.
  - [x] Sections: add (`newSection` -> push), reorder (`moveItem`), delete (splice) - in `ReportEditor`, mutating `doc.sections`.
  - [x] Every change goes through `onEdit()` -> the SAME debounced-preview + validated-save path 10.1 established (no parallel model). The debounced live preview re-renders the structural change; the validated save persists it; optimistic concurrency holds.
- [x] **Focus management on add / delete / move (ui, NFR15).**
  - [x] A structural change rebuilds the keyed `{#each}`, so the control the author activated is gone; the editor records a focus INTENT (a stable id) and moves focus to the affected element once the DOM settles (`tick()`): a moved block/section keeps focus (repeated up/down keep working), an added one is focused, and after a delete focus lands on the neighbour that took its place (or the palette / "Add section" button when the list empties).
  - [x] The block card (`BlockEditor`) and section card (`SectionEditor`) are `tabindex="-1"` scripted focus targets (out of the tab order) carrying `data-block-id` / `data-section-id`, with a visible `:focus-visible` ring.
  - [x] `Button` gains a bindable `ref` (for the "Add section" focus fallback) and merges a caller `class` (for the palette entry layout) - additive, no behaviour change for existing callers.
- [x] **Invalid-structure save (covered by 10.1's path).** An emptied section (or any invalid structural state) is the actionable 422 inline at the offending element on save - the server validate-on-write (10.1) stays the authority; no structural edit has a side path.
- [x] **Reader-budget isolation (ops).** The palette + structural editing is workspace-only: `pnpm reader:budget` confirms the reader path is byte-identical at 75.8 KB / 200 KB, and `pnpm schema:export` is unchanged (no new block types).
- [x] **Tests.**
  - [x] Unit (`editor-state.test.ts`): `blockPaletteEntries` offers exactly one entry per union member (no extras, no duplicates), each entry carries a non-empty label/description, and each inserts a block of the chosen type via `newBlock`.
  - [x] Component (`block-palette.svelte.test.ts`): the palette renders one labelled insert control per union member inside a labelled group, and activating an entry reports the chosen type.
  - [x] Component (`structural-editing.svelte.test.ts`, `SectionEditor`): add a block of the chosen type from the palette (working copy updates, an edit signals), reorder via the keyboard-accessible move-down, delete a block and focus lands on the neighbour, and a structural edit does not reach back into the loaded section object (no mutation leak).
  - [x] Component (`report-editor.svelte.test.ts`): add/delete a section through the working copy from the single validated path.
  - [x] e2e (`editor-structural.e2e.ts`, desktop): add a block from the palette, reorder it, delete a block, save, reload, see the structure persisted; add/delete a section, save, reload, persisted; a keyboard-only block move reorders the structure; the editor surface (the editing form) is axe-clean.
  - [x] The exhaustiveness backstop (`BlockRenderer.exhaustiveness.test.ts`) now reads the palette catalogue (`editor-state.ts`) instead of the removed SectionEditor menu, asserting every schema block type appears as a catalogue entry.

## Dev Notes

### This EXTENDS the 1.5 structure editor and the 10.1 shell - it is not a from-scratch build

The 1.5 form editor already carried per-section structural editing (a flat row of "Add {type}" buttons seeded from `newBlock`, block move/remove via `moveItem`/splice) and `ReportEditor` already added/moved/removed sections. Story 10.1 added the authoritative live preview, the validated save, and optimistic concurrency over that surface. Story 10.2's job was to turn the flat structural affordances into a proper BLOCK PALETTE and to add the accessibility/focus polish the epic calls for, all on the SAME working-copy + validated-save path - not to invent a new model.

What changed:

1. **A real block palette.** The flat "Add {type}" button row (an exhaustive `BLOCK_MENU` map inside `SectionEditor`) is replaced by `BlockPalette.svelte` fed `blockPaletteEntries` (the catalogue moved to `editor-state.ts`, the cross-editor home, as the single source of truth). Each entry carries a human label + a one-line description, lives in a labelled group, and seeds insertion from `newBlock`. The catalogue's `satisfies Record<BlockType, ...>` is the same compile-time exhaustiveness guarantee the old menu had.

2. **Focus management on every structural op.** A keyed `{#each}` rebuild on add/move/delete drops the activated control; the editor now records a stable-id focus intent and moves focus to the affected element after `tick()`. The cards are `tabindex="-1"` scripted focus targets with a visible focus ring. This is the NFR15 keyboard/screen-reader baseline the 1.5 affordances did not have.

3. **Section structural ops routed through named helpers.** `ReportEditor` gained `insertSection`/`removeSection`/`moveSection` (mirroring the block helpers in `SectionEditor`) so the focus management is consistent and the inline arrow-function handlers are gone.

### Drag vs keyboard move - the decision

The epic names a keyboard-accessible move-up/move-down as the NFR15 baseline and drag-and-drop as an OPTIONAL layered enhancement, "only if it stays accessible and within budget and does not add a dependency". I shipped the keyboard move as the baseline and DEFERRED drag, deliberately:

- A correct, accessible HTML drag-and-drop (pointer + keyboard parity, live-region announcements, focus management across the drop) is a non-trivial amount of bespoke code, and a library would add a dependency (forbidden without approval) and reader-budget risk if it leaked into a shared chunk.
- The keyboard move already satisfies the AC (a keyboard-accessible reorder that is never the only affordance gap - it IS the affordance) and NFR15. Drag would be pure enhancement on top.

So drag is a clean follow-up (a later story or a 10.7 polish pass): it would layer onto the SAME `moveItem` reorder and the SAME working copy, with the keyboard move staying as the guaranteed-accessible path. Nothing here blocks it.

### How it reuses 10.1's working-copy / validated-save path

Every structural edit mutates the in-edit `$state` document (`doc.sections` / `section.blocks`) and calls `onEdit()`. `onEdit()` is 10.1's single seam: it marks dirty and `scheduleSave()`s (the debounced autosave), and the 200 ms-debounced `settledSnapshot` `$effect` re-renders the live preview AND re-runs the optimistic validation off the same settled snapshot. The save posts the snapshot through `updateReportDocument` (validate-on-write) with the optimistic-concurrency token. There is NO second model and NO second write path: the palette/structural edits are just more producers of mutations on the one working copy. An invalid structural state (an emptied section) is the same inline 422 the shell renders at the offending element on save.

### Reader-budget isolation

The palette, the catalogue, and the focus management are all in the workspace edit route (`src/routes/(workspace)/reports/[id]/edit/`) and `$lib/ui/Button.svelte`; none is imported by the reader path (`/r/[token]`). `pnpm reader:budget` is byte-identical at 75.8 KB / 200 KB, and the reader-purity boundary test (10.1) still passes (no version-registry/migration fingerprints in any reader chunk). `pnpm schema:export` is unchanged: this story adds NO block type and NO schema field.

### Scope and the seams left for 10.3-10.7

- **10.3 / 10.4 (per-block-type field editing):** OUT of scope here. A newly-added block is a default shape; the per-block-type editors (`TextBlockEditor`, ... `TimelineBlockEditor`) already exist and are mounted by `BlockEditor`, so 10.3/10.4 refine THOSE as direct-manipulation affordances. The inline-error placement (`groupErrorsByLocation` -> per-block `IssueList`) is the seam they hang on.
- **Drag enhancement:** layers onto `moveItem` and the working copy, keyboard move staying the accessible baseline (see the decision above).
- **10.5 / 10.6 / 10.7:** unchanged from the 10.1 seams (binding from the block, audience-aware preview + notes/tags, autosave/undo-redo/conflict/publish).

### Non-goals confirmed (foundational design)

No new block types (the palette exposes the EXISTING union; the meta-strip is the field-grid `strip` layout, not a new member). No CRDT / real-time co-editing (concurrency is 10.1's optimistic-conflict detection). No freeform HTML. The editor stays a desktop workspace surface. None are touched here.

### QA remediation (2026-06-15)

A three-agent QA audit on the Review story surfaced six items, all addressed on the same workspace-only surface (reader budget byte-identical, schema unchanged):

- **(HIGH) Palette derivation soundness.** `blockPaletteEntries` derived via `Object.keys(BLOCK_CATALOGUE) as BlockType[]` - the cast discarded the compile-time exhaustiveness the `satisfies Record<BlockType>` design rests on. Now derived from the TYPED public Zod API: `blockSchema.options.map((o) => o.shape.type.value)` for the TYPES (sound `BlockType`, no cast) and `BLOCK_CATALOGUE[type]` for the LABEL/DESCRIPTION (still `satisfies`-exhaustive, so the lookup is total). The schema union order matches the catalogue order, so the palette still lists all 15 types in the intended order.
- **(Medium) Exhaustiveness backstop aligned to the public Zod API.** `BlockRenderer.exhaustiveness.test.ts` read the discriminant through a defensive internal chain (`.def.shape.type.def.values`) that could degrade to `''` and still pass the count check. Now uses the SAME `blockSchema.options[].shape.type.value` path as the palette derivation and the palette unit test - one canonical introspection. (The schema import is test-only; it never enters the built reader chunk, so the reader-purity boundary is unaffected.)
- **(Medium) Empty-section focus fallback is ref-anchored.** `removeBlock`'s emptied-list fallback walked the DOM (`closest('section').querySelector('[data-block-palette] button')`). `BlockPalette` now exposes a bindable `firstEntry` ref (its first entry button); `SectionEditor.removeBlock` focuses it directly, mirroring the `addSectionButton` ref fallback in `ReportEditor`. The `data-block-palette` wrapper (only there for the walk) is gone.
- **(Medium, perf) Structural derivations off the hot path + single-swap reorder.** `bindableBlocks` and `matrixBlocks` derive off the debounced `settledSnapshot` (structural, fine to lag the 200 ms settle) instead of the live `doc`, taking those flatMaps off the keystroke path; `moveItem` is a single in-place adjacent swap (`[a[i], a[t]] = [a[t], a[i]]`) instead of two splices (the move is always adjacent).
- **(Medium, test gaps)** Added: a component test for SECTION reorder (move-down on the first of two swaps them in the working copy and focus follows); a component test for the emptied-section inline 422 (deleting the last block surfaces "A section must contain at least one block." at THAT section's IssueList, not document-level - pinning AC4 at the 10.2 surface); an e2e for keyboard-only section move (mirrors the block keyboard-move spec). Both new component tests scope their `data-section-id` queries to `.editor-form` because the embedded live preview renders the same sections with their own `data-section-id`.
- **(Medium) e2e helper duplication removed.** `createDraft` and `FORM_HEADERS` (identical in `editor-structural.e2e.ts` and `editor-shell.e2e.ts`) are extracted to `e2e/helpers.ts` and imported from one source.

DEFERRED as noted debt (intentional, not regressions): the `{#key document}` keying on object identity (minor given the 200 ms debounce; revisit only if rapid identity-only settles are observed); the `previewSnapshot = settledSnapshot` alias (10.6 may add transformation there); the `BlockEditor` raw-type-key header label (10.3/10.4 territory).
