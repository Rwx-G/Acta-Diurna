# Story 9.2: Snapshot Diff Engine

## Status

Review

## Story

As the platform,
I want a pure server function that diffs two published snapshots into a structured result,
So that "what changed since last issue" has one authoritative, testable source feeding both the workspace and the reader.

## Acceptance Criteria

**Given** an issue with a published predecessor in the same series
**When** the diff engine runs
**Then** it compares the issue's frozen `published_document` against the predecessor's `published_document` (never drafts) and returns a typed `SeriesDiff` of per-section, per-block verdicts; both snapshots are immutable, so the result is reproducible and cacheable by the `(new, old)` snapshot pair

**Given** two snapshots whose sections and blocks share ids (the normal duplicate lineage)
**When** the structural diff runs
**Then** blocks are matched BY ID: an id in both is `kept`, only in the new is `added`, only in the old is `removed`, and a changed parent section or position is `moved` - no fuzzy text matching, so a rename is never fabricated

**Given** an id-matched data-bound block
**When** the data and content diff runs
**Then** the engine flags a DATA change when the resolved bound values differ between snapshots and a CONTENT change when escaped text/field values differ, reading both from the snapshot documents themselves (which already carry resolved data) - it never re-reads data sets or touches the uploads volume

**Given** two snapshots that share NO block ids (a series link to an unrelated report, or a fully rebuilt issue)
**When** the diff runs
**Then** it returns a neutral "structure changed substantially, per-block comparison unavailable" verdict rather than a misleading wall of adds and removes, and never throws

**Given** an issue with no published predecessor (first issue, or the predecessor is unpublished)
**When** the diff is requested
**Then** the engine returns a neutral "no prior issue to compare" result, not an error

**Given** the diff function
**When** it is invoked from any surface
**Then** it is a PURE server function (no `$lib/server` DB calls inside the comparison itself - snapshots are passed in), owner-scoping is enforced by the caller resolving both snapshots under one `AuthorScope`, and the function is covered by unit tests over add / remove / move / data-change / content-change / total-drift / no-predecessor fixtures

## Dev Notes

### Placement (the decision)

- **The engine is ISOMORPHIC and pure (`src/lib/schema/series-diff.ts`).** It imports nothing from `$lib/server` or `$lib/ui` (the same boundary `internal-links.ts` and `section-ids.ts` hold), so the workspace view (9.3) and any later reader use (9.5) can both call it without dragging the server in. It reads two validated documents passed in, has no DB access and no side effects, and returns a derived result that is never persisted - reproducible and cacheable by the immutable `(new, old)` snapshot pair (AC1, AC6).
- **The owner-scoped wiring lives in the service (`diffSeriesIssue`), separate from the engine.** The engine compares two documents; the service resolves the two published snapshots under one `AuthorScope` and feeds them in. This keeps 9.2 to the engine + the typed result + the fetch; the workspace VIEW is 9.3.

### The `SeriesDiff` shape

- A discriminated union on `kind`: `{ kind: 'no-predecessor' }`, `{ kind: 'substantial-drift', overlap }`, and `{ kind: 'diff', sections }`. A consumer switches on `kind` and renders the neutral state or the changelog.
- A `diff` carries `SectionDiff[]` in new-snapshot order (then sections removed entirely). Each `SectionDiff` has `{ id, title, change, blocks }`; each `BlockDiff` has `{ id, type, change, dataChanged, contentChanged }`, where `change` is `added | removed | moved | kept`.
- `dataChanged` / `contentChanged` are independent booleans, so a block changed in more than one dimension surfaces every verdict (the 9.3 AC "every applicable verdict is shown").

### Matching by id

- **Block matching is strictly by stable id.** Every block is indexed by id with its section and position (`placeBlocks`). An id in both snapshots is `kept`, or `moved` when its parent section id OR its index within the section changed; only-new is `added`, only-old is `removed`. A block that moved from section A to section B is reported ONCE, under its new section, as `moved` (the old-section removed-walk skips any block still present in the new snapshot), never double-counted as removed+added.
- **No fuzzy text matching.** A manually rebuilt block (new id) reads as a clean add/remove pair, never a fabricated rename - exactly the epic's "the diff never fabricates a false rename".

### DATA vs CONTENT

- **DATA** is the bound block's data-bearing field: `rows` (table), `series` (chart), `items` (kpi) - the canonical `StaticDataKey` trio, read straight off the snapshot (it already carries resolved data, so no data set is re-read, no uploads volume touched - AC3).
- **CONTENT** is every OTHER own field of the block except `id` and `type` (and, for a bound block, except the data field): text paragraphs, column labels, titles, axis labels, options, the binding's declared fields. Comparing the remainder catches a content edit without re-flagging a data edit as content.
- Equality is a canonical `JSON.stringify` compare (the same strategy `structural-equality.ts` uses): the snapshot fields are plain JSON produced by one serializer, so key order is stable and the compare is deep and deterministic.

### Drift threshold (the value + rationale)

- **`SUBSTANTIAL_DRIFT_THRESHOLD = 0.1` (10%).** The overlap ratio is `shared block ids / min(old block count, new block count)`: "of the smaller snapshot, what fraction of blocks survived by id?". Below 0.1, almost nothing lines up, so a per-block comparison is a noisy false diff (a wall of adds and removes plus a stray coincidental match) - the engine returns the neutral `substantial-drift` verdict instead.
- **`min`, not the union, is the denominator** so a heavy ADD is not mistaken for a rebuild: if every old block survives into a much larger new issue, the overlap is still 1.0 (a heavy add, not a structural break). The zero-overlap unrelated-report case (the AC's "share NO block ids") is always 0 < 0.1, so it is always drift. A pair with no blocks on either side is treated as fully drifted (nothing to compare), never a divide-by-zero. A normal refill (ids inherited) sits at ~1.0 and never trips it.

### Owner-scoped wiring (`diffSeriesIssue`)

- **Both snapshots are resolved under one `AuthorScope` via the scoped `getRow`** (the same owner-predicate path every author read uses), so a cross-author, unknown, or malformed id is the same neutral 404 the tenancy layer uses - a diff NEVER spans authors. The predecessor is re-resolved independently, so even a hand-corrupted `predecessor_id` pointing at a foreign report 404s rather than leaking it. In single mode the implicit author owns everything (a no-op).
- **The issue must be published** (a diff compares two frozen editions; an unpublished issue has no edition) -> the same 409 not-published `getPublishedDocument` raises. The predecessor being absent (null edge -> the first issue) or unpublished (no snapshot) is the neutral `no-predecessor` result, handed to the engine as a null old snapshot - never an error (AC5).
- Each snapshot goes through `validateStoredDocument` with the injectable `migrations` (the FR7 version-tolerance contract), so a snapshot frozen under an earlier schema version is lifted before the diff runs - identical to `getPublishedDocument`.

### Leak safety

- The diff never ships prior-issue data to a reader: 9.2 delivers the engine + the owner-scoped service only. Any reader exposure is a later opt-in story (9.5), which builds its summary from the leak-safe reader-served snapshot. The service's `publishedSnapshotOf` does NOT strip speaker notes because it is an AUTHOR-owned read (the diff verdicts carry no note text; a block's `notes` lives on the section, not in a `BlockDiff`).

### QA remediation (2026-06-14)

A three-agent QA audit converged on eight findings; all fixed, gates re-run green.

- **(HIGH) deepEqual key-order sensitivity.** `deepEqual` used raw `JSON.stringify`, correct only because both snapshots happened to share a key order; a future reader/MCP/cache path with a different key order would have produced a phantom data/content change. Canonicalization is now a property of the engine: a recursive, object-key-sorted `stableStringify` (arrays preserved in order - order is meaningful for sections/rows) backs `deepEqual` for both the data field and the content view, so equality is correct-by-construction regardless of caller. New test: same data, reordered keys, asserts no false change.
- **(Med) DATA_FIELD_BY_TYPE drift.** The hand-maintained mirror is now pinned to the real schema with a type-only `satisfies DataFieldByType` over `BindableBlock` (each type's value must be a key of that block variant). A schema data-field rename, or a new bindable block without an entry, is now a compile error. `import type` keeps the module isomorphic (`pnpm check` confirms the pin holds and stays erased).
- **(Med) diff used the sharing 409 message.** Added a `notPublished()` factory (same 409 `/problems/report-not-published`, diff-appropriate detail) and used it in the diff path; `notShareable()` and the sharing flow are unchanged.
- **(Med) diff pulled full rows.** Added a narrow `diffSnapshotProjection` / `getDiffSnapshotRow` (id, status, published snapshot, predecessor edge) mirroring the existing reader/meta/seriesIssue projections; both diff reads route through it, so the draft `document` column is no longer transferred. Owner-scoping preserved on BOTH reads (issue and predecessor).
- **(Med) SectionDiff.change typed as BlockChange.** Renamed `BlockChange` -> `ChangeVerdict`, a shared type used by both `BlockDiff.change` and `SectionDiff.change`; index export and consumers updated.
- **(Low) no-predecessor collapsed two states.** `NoPredecessorDiff` now carries `reason: 'first-issue' | 'predecessor-unpublished'`; `diffSnapshots` takes the reason (default `first-issue`) and `diffSeriesIssue` sets it at the two call sites. Engine and service tests updated.
- **(Med, test gap) substantial-drift through the service.** Added a service test seeding two published snapshots with disjoint block ids, asserting `kind === 'substantial-drift'` and `overlap === 0`.
- **(Cheap) blockOverlap + JSDoc + test ordering.** `blockOverlap` now iterates the placed-block Maps directly (no intermediate Sets); a `@throws` JSDoc note (404 / 409 / 422) was added to `diffSeriesIssue`; the engine test's `range` helper moved above its first use.

Deferred debt (recorded, NOT changed, both measure-first): the `validateStoredDocument` double-parse on each diff (a by-design FR7 migration contract, a no-op while only schema v1 exists) and the bounded both-documents-in-memory peak. Neither warrants a change before a measured need.
