## Dev Notes

**The new theme identities.** Two new light themes give report series distinct identities beyond the existing pair (`default` "Modern Gazette", `midnight`):

- **Cool Aurora (`aurora`)** - cool paper (`#eef3f4`), slate-teal ink (`#15232b`), a deep teal accent (`#08526a`). Reads calm and analytical; suits data-led reports.
- **Warm Meridian (`meridian`)** - warm cream paper (`#faf4ec`), sepia ink (`#2a2018`), a terracotta accent (`#922d13`). Reads inviting and editorial; suits narrative-led reports.

Both accents are deliberately darkened from their "vivid" form because the contrast contract treats the accent as inline/link text, which must hold AAA (7:1) on the paper. The categorical `chart-1` swatch matches the accent on each theme for brand coherence (the same stance the default takes).

**One registry, three consumers.** `lib/render/theme/index.ts` holds the single source of truth (`BUILT_IN_THEMES` + `THEME_OPTIONS`). The schema (`theme: idSchema.optional()`) does not enumerate themes deliberately (see the fallback note); the editor picker renders `THEME_OPTIONS`; the renderer resolves through `resolveTheme`. A registry test asserts the palette, categorical and tone tables in `palette.ts` are in lockstep with `BUILT_IN_THEMES`, so a half-skinned theme (a name with no token set) fails before render.

**Fallback path is exactly one place (AC2).** `resolveTheme(slug)` is total: a known slug resolves to itself, anything else (absent, unknown, removed) resolves to `default`. The renderer sets `data-theme` only for a non-default result, so the reader always gets a clean theme - a stale `theme` reference never throws and never produces a broken page. The schema stays soft on `theme` (a slug, not an enum) precisely so a stored/published document carrying a since-removed theme still validates and renders (in default), instead of becoming un-loadable. A NEW author selection can only ever be a known theme because the picker offers a closed `THEME_OPTIONS` list.

**Warning surface (AC2).** `themeFallbackWarning(slug)` returns `null` for an absent selection (the default applies silently, FR39) and for a known slug; for an unknown slug it returns `{ requested, applied: 'default', message }`. The editor renders this as an amber advisory next to the theme picker - amber, not the danger red used for validation errors, because the report still renders cleanly; the warning is informational ("why is this showing the default?"). It is distinct from the existing scale `scaleContrastWarnings` surface (Epic 7), which gates explicit author hexes below AAA.

**Applied fully, zero JS (AC1).** A theme is purely a block of `--report-*` overrides under `[data-theme='<name>']` in `app.css`. Every render component already reads only the semantic tokens, so the theme re-skins the whole report - cover, sections, every block, the chrome, the TOC scrim - with no component change. The `data-theme` attribute on the report root is set in `Report.svelte` from `resolveTheme(view.theme)`; the embedded editor preview uses the same root, so author preview and reader cannot drift. Reader budget is unchanged (72.8 KB): themes add CSS, not JS.

**Accessibility floor proven by the contrast tests (AC3).** Each new theme is asserted to the SAME contract axe-core gates for the default: report content (body/muted/heading text, accent-as-link, text on surface) holds AAA (7:1); decorative surfaces (accent fill, the six categorical swatches, the five callout tones, the two trend tints) hold the AA floor (4.5:1) on the theme's own report background. These are the machine-checkable proof; the reader axe e2e additionally now runs on `aurora` (the `full` fixture selects it), so a non-default theme is gated end to end under axe-core, while the matrix and Phase B fixtures stay on the default theme.

Measured ratios (rounded), all clearing their target:

- Aurora: text/bg 14.4, muted/bg 7.0, heading/bg 14.3, accent/bg 7.7, text/surface 16.1; charts 5.3-7.7; tones 5.3-7.0; trend-up 5.8, trend-down 5.8.
- Meridian: text/bg 14.6, muted/bg 8.1, heading/bg 15.6, accent/bg 7.4, text/surface 15.7; charts 5.8-8.3; tones 5.8-8.1; trend-up 5.8, trend-down 6.0.

**The `full` fixture's `theme: 'aurora'` is now coherent.** It previously named a theme that did not exist (an implicit fallback probe). With `aurora` promoted to a real built-in, the fixture exercises a non-default theme; the explicit unknown-theme fallback is now covered directly by unit tests against `resolveTheme`/`themeFallbackWarning` and a `Report.svelte` render test (`theme = 'removed-theme'` -> no `data-theme`).

## Dev Agent Record

### Debug Log

- `Report.svelte.test.ts` had a test "omits data-theme for the default theme" that rendered the `full` fixture and asserted no `data-theme`. That test was implicitly relying on `aurora` being an unknown theme (falling back to default). Promoting `aurora` to a built-in made the root carry `data-theme="aurora"`, failing the assertion. Fixed by making the test explicit (set `view.theme = undefined`) and added a dedicated unknown-theme fallback test (`view.theme = 'removed-theme'`), so the fallback is asserted directly instead of via a fixture coincidence.
