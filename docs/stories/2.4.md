# Story 2.4: Upload Data Files & Bind Blocks

Status: Review

## Story

As the author,
I want to upload data files and bind their contents to report blocks,
So that my exported tool data becomes charts and tables without manual re-entry.

## Acceptance Criteria

**Given** a CSV, JSON, or Excel file up to 50 MB
**When** uploaded
**Then** it is parsed and stored (uploads volume + data_sets table - created by this story's migration, carrying the injection timestamp and an optional data-as-of field), and its fields/columns are inspectable, with visible progress (FR12, NFR4, FR16 groundwork)

**Given** a parsed data set
**When** I bind a table/chart/KPI block to its fields
**Then** the block renders the bound data and the binding persists in the document

**Given** an unparseable file
**When** uploaded
**Then** a problem-details error states what failed (encoding, format, size) - never a silent failure

## Dev Agent Record

### Debug Log

- The binder UI's `slotMapping` is author input crossing a trust boundary; it is JSON-parsed and each slot re-validated through `bindingSlotSchema` in `bind-form.ts` before reaching the service (malformed -> 400). Never trusted raw.
- `bindBlock` writes through `updateReportDocument`, which refuses a published report with 409. The e2e therefore binds against a FRESH draft report, not the shared published fixture (read-only). The fixture's table block id was not reused.
- Svelte renders table cells as `<input>` with the value set as a DOM property, not an HTML attribute - `input[value="X"]` selectors miss. The e2e reads `(node as HTMLInputElement).value` via `evaluateAll` + `expect.poll`.
- `new File([content], ...)` rejects a `Uint8Array` typed as `string | Uint8Array` under strict TS (SharedArrayBuffer union). The test helper takes `BlobPart`.
- Resolver `ParseError` (incoherent slot mapping for the block type) is mapped to 422 in `bindBlock` so an author mistake surfaces as a problem-details, not a 500.
- QA iter 1: a leading UTF-8 BOM is NOT stripped by `TextDecoder('utf-8', { fatal: true })`, so the strip lives in `tokenize` (csv.ts) before any field accumulates - otherwise `columns[0]` carries the BOM and binding resolution fails silently.
- QA iter 1: `Number()` accepts hex/binary/octal literals and zero-padded integers, so numeric inference was tightened to a decimal/scientific regex plus an explicit leading-zero-integer guard. `"007"`/`"00"` -> string (padded id/zip), single `"0"` -> number, `"2026"` -> number, `"0x1F"`/`"0b101"`/`"0o17"` -> string.
- QA iter 1: the document-size budget now lives at the single write chokepoint (`writeDocument`, reports.ts) AFTER `validateOrThrow`, so bind/title/save are all bounded, not just the save action's pre-parse guard. Over-budget -> 413 `/problems/document-too-large`.
- QA iter 1: `readDataSetTable` is awaited BEFORE `bindBlock`'s try block, so a corrupted stored file or an over-cap row count must surface as problem-details inside the read itself: a re-parse `ParseError` -> 422 `/problems/data-set-unreadable`, an over-10000-row data set -> 422 `unparseable`.

### Completion Notes

**Scope: Review (CSV/JSON). Excel sub-task deferred to backlog.** CSV + JSON ingestion and the full binding-to-slot contract ship here with NO new dependency. The Excel branch returns an honest 415, parked for the product owner.

**Canonical binding-slot contract (the load-bearing 2.5 reference).** Each `binding.fields[]` entry gains an OPTIONAL `slot` descriptor (`src/lib/schema/blocks/shared.ts`, `bindingSlotSchema`). Additive: a v1 document with no `slot` on its fields still validates (proven by a test). Exact shape:

```
slot?: {
  role: 'column' | 'x' | 'y' | 'value' | 'label',
  key?: string,        // table column key (role 'column'); defaults to field name
  order?: number,      // table column order (role 'column'); lower comes first
  seriesName?: string  // chart series label (role 'y'); defaults to field name
}
```

Per-block consumption (the resolver in `src/lib/server/ingestion/resolve.ts`):
- **table**: every field with `role: 'column'` becomes a column. Column key = `slot.key ?? field.name`; column order = `slot.order` then declaration order. Rows are the data set rows projected onto those keys.
- **chart**: exactly ONE field with `role: 'x'` is the category/time axis (throws otherwise). Each `role: 'y'` field is one series; series name = `slot.seriesName ?? field.name`; points pair the x value with the y value per row (y must be numeric).
- **kpi**: one `role: 'value'` field feeds the value; one optional `role: 'label'` field feeds the label (defaults to the value field name). The FIRST row supplies them (a KPI is a single figure).

`applyBinding` (`bind.ts`) writes BOTH the `binding` (fields + slots, persisted in the document so the binding survives) AND the resolved static data (`rows`/`series`/`items`) so the block renders now. **2.5 auto-rebind builds on this**: re-run `readDataSetTable(dataSetId)` -> `applyBinding(block, dataSetId, fields, slotMapping, rows)` with the slot mapping read back from `block.binding.fields[].slot`. The mapping is fully recoverable from the persisted binding, so a refill needs no extra state. Diagnostics (FR15, 2.5) hang off the resolver's `ParseError` (already mapped to 422 problem-details) and the `inspect.ts` field types (compare expected `binding.fields[].type` vs the new data set's inferred type to flag a drift).

**Migration**: `drizzle/0005_data_sets.sql` (generated `MSYS_NO_PATHCONV=1 DATABASE_URL=postgres://x pnpm exec drizzle-kit generate --name data_sets`, no DB connection). `data_sets`: `id` uuid PK, `report_id` uuid FK -> reports (ON DELETE SET NULL, nullable), `filename` text, `source_format` text + check `in ('csv','json','xlsx')`, `fields` jsonb (`DataSetField[]`), `injected_at` tz default now, `data_as_of` tz nullable (FR16), `storage_path` text. Added to `schema.ts`; the drizzle client picks it up via `import * as schema`.

**CSV parser approach** (`csv.ts`, hand-written RFC 4180, no dependency): a single-pass tokenizer over the text. A field is quoted iff it opens with `"`; inside quotes a doubled `""` is a literal quote and commas/newlines are data; CRLF and LF both terminate a record. Rejects an unterminated quote, an empty/duplicate header column, and an empty file. Short rows pad missing trailing columns with `''`. First record is the header; rows become objects keyed by header name.

**JSON parser** (`json.ts`, stdlib `JSON.parse`): the only accepted shape is an array of flat objects. Columns = union of keys in first-seen order. Rejects (clear `ParseError`): malformed JSON, a bare object, an array of scalars, an array of arrays, a nested/non-scalar field value, an empty array.

**Type-inference precedence** (`inspect.ts`, deterministic). Per VALUE, most specific first: (1) **boolean** - `true`/`false` any case, or a JS boolean; (2) **number** - a finite JS number or finite numeric string (so a bare `2026` is a number, not a date); (3) **date** - an ISO-8601 date/date-time parseable by `Date`; (4) **string** - everything else, including empty. Per COLUMN: the single non-string type every non-empty value agrees on, else `string`; empty values are ignored and never promote; an all-empty column is `string`. (Guards the `Number('')===0` footgun.)

**Excel deferral handling (NOT a placeholder, a real response).** `detectFormat` maps `.xlsx`/`.xls` and the spreadsheet MIME types to `'xlsx'`; `ingestFile` then throws `excelNotEnabled()` -> 415 `/problems/excel-not-enabled`, detail "Excel ingestion is not yet enabled on this instance." Nothing is parsed or stored. Tested. Wiring an approved parser later is a small change: add a branch in `parseByFormat` and drop the `xlsx` guard. See backlog "Excel parser dependency choice".

**Size cap (NFR4)** enforced on `file.size` BEFORE `arrayBuffer()` buffers the bytes (413 `/problems/upload-too-large`), with a post-buffer re-check for honesty. The route also pre-checks `file.size` so a grossly oversized upload is refused before the service. `MAX_UPLOAD_BYTES = 50_000_000`.

**Storage**: the file is written to `UPLOADS_DIR` under a UUIDv7 name (`<id>.<format>`), NEVER the user filename - path traversal defence. Only the ingestion domain touches the uploads volume and the `data_sets` table.

**Workspace UI**: a new `/data-sets` route (rail link added) with an upload control (XHR upload for a visible progress bar; no-JS baseline is the same `?/upload` form action) and a per-data-set inspector (fields + inferred types). The report editor gained a `BlockBinder` panel (pick a data-bindable block + a data set, map each field to a slot, `?/bind`). Workspace-only: `/data-sets` and the editor `?/bind` action are author-realm (NOT in `isPublicPath`), covered by `workspaceGuard`. Reader budget unchanged at 63.4 KB (< 200 KB) - ingestion never enters the reader closure.

**QA iteration 1 (2026-06-12).** Six findings fixed; two intentionally deferred to backlog.

Fixed:
1. (High) CSV UTF-8 BOM. A leading BOM was glued onto the first header name (`columns[0]` carried it), silently breaking binding resolution for the most common real-world CSV (Excel/Windows UTF-8 export). `TextDecoder('utf-8', { fatal: true })` does NOT strip the BOM, so `tokenize` (csv.ts) now strips a single leading U+FEFF before parsing. Test: a BOM-prefixed CSV yields clean column names and resolves a first-column binding.
2. (Medium) Numeric inference. `Number()` misclassified hex/binary/octal literals and zero-padded integers as numbers. Tightened to `/^[+-]?(\d+\.?\d*|\.\d+)([eE][+-]?\d+)?$/` plus a leading-zero-integer guard `/^[+-]?0\d+$/`. Classifications: `"007"`->string, `"00"`->string, `"0"`->number, `"2026"`->number, `"+5"`->number, `"1e3"`->number, `"0x1F"`/`"0b101"`/`"0o17"`->string. `Number('')===0` guard preserved.
3. (Medium) Document-size budget on bind. The bind path wrote resolved data into the document via `writeDocument`/`updateReportDocument` without the save action's `MAX_DOCUMENT_BYTES` check, a 1 MB DoS-budget bypass straight into JSONB. Now enforced at the single write chokepoint (`writeDocument`, reports.ts) AFTER `validateOrThrow`: `JSON.stringify(document).length > MAX_DOCUMENT_BYTES` throws a 413 `/problems/document-too-large` AppError - closing it for EVERY writer (bind, title, save) at one place. Also capped rows materialized during resolution: `readDataSetTable` rejects an over-10000-row data set with a 422 (`Data set exceeds 10000 rows for binding.`) so a huge upload fails fast instead of building a giant array. Tests: over-budget write rejected with nothing persisted; over-cap data set rejected 422.
4. (Low) `toDataSet` was a byte-identical clone in ingestion.ts and queries.ts. Exported once from ingestion.ts (the write-side home of the `DataSet` type), imported in queries.ts; duplicate removed.
5. (Low) `readDataSetTable` threw a raw `ParseError` that `bindBlock` does not catch (awaited before its try block), so a corrupted stored file would surface as a 500. Now wrapped: a re-parse `ParseError` maps to 422 `/problems/data-set-unreadable` ("Stored data set could not be read."). 2.5 auto-rebind re-reads on every refill, so this is the clean failure it inherits. Test added.
6. (Low) Prototype-pollution defense in `resolveTable` (resolve.ts): a JSON upload field literally named `__proto__` could become a computed column key. The projected row is now a `Object.create(null)` object and `__proto__`/`constructor`/`prototype` keys are skipped. Test with a `__proto__`-named field asserts no pollution.

Deferred to backlog (NOT fixed here):
- (a) Orphan data sets / unbounded uploads-volume growth from the `ON DELETE SET NULL` FK: deleting a report leaves its data sets (and their files) behind with no GC. Needs a cleanup policy.
- (b) HTTP-boundary body-size limit (`BODY_SIZE_LIMIT`) BEFORE multipart parsing: the 50 MB cap is enforced on `file.size` inside the service, but the framework buffers the multipart body before that. A transport-level limit belongs at the boundary.
