# Story 3.5: Revocation & Leak-Free Posture

Status: Done

## Story

As the author,
I want one-click revocation and zero information leakage on closed links,
So that a mis-sent link is a non-event.

## Acceptance Criteria

**Given** an active share
**When** I revoke it
**Then** the link immediately serves a neutral page leaking nothing - not even the report title (FR20)

**Given** an expired share
**When** opened
**Then** the same neutral page is served

**Given** any report route
**When** served
**Then** `noindex/nofollow`, no-cache on sensitive responses, neutral link-preview metadata, and strict CSP with zero third-party assets are applied (NFR10)

## Tasks / Subtasks

- [x] One-click revocation: a `revokeShare(shareId)` service in `src/lib/server/sharing/` setting `shares.revoked_at = now` (the column exists from 3.2); idempotent (revoking a revoked share is a no-op, no error). Workspace `?/revoke-share` action on the share list/ShareDialog (author-realm, under `workspaceGuard`), one click, status flips to revoked in the UI (StatusChip grammar).
- [x] Neutral page for a closed link: the `/r/[token]` gate (3.3) serves a SINGLE neutral page - identical for revoked, expired, AND nonexistent token - leaking NOTHING (not the report title, not whether the token ever existed, not why it is closed). Same page, same status, same body for all three closed states (enumeration-safety, NFR9/NFR10). The live-share check is `revoked_at IS NULL AND (expires_at IS NULL OR expires_at > now)` AND the token resolves; anything else -> the neutral page. A revoked share takes effect IMMEDIATELY (next request, no cache).
- [x] Reader session invalidation on revoke: an existing `acta_reader` session bound to a now-revoked or expired share must stop serving the report (FR23 "while the session and share remain valid" - the share is no longer valid). The gate re-checks share liveness on every reader request, not only at verification, so a persistent session cannot outlive its share.
- [x] Audit + harden the whole sharing/reader surface (this story is the hardening pass, NFR10): confirm `noindex/nofollow` on every report route (1.6 groundwork - audit it is actually emitted on `/r/[token]`, the VerifyCard pages, and the neutral page); add `Cache-Control: no-store` (no-cache) on sensitive responses (the served report, verification, the neutral page) so a revoked link is never served from a cache; neutral link-preview metadata (NO OpenGraph/Twitter title or description that leaks the report title - emit neutral or no `og:`/`twitter:` tags on reader routes so a pasted link in chat/email previews nothing); confirm the strict CSP (D7, already present) applies with zero third-party assets on the reader surface.
- [x] Tests: revoke flips `revoked_at` and the link immediately serves the neutral page; an expired share serves the SAME neutral page; a nonexistent token serves the SAME neutral page (byte-identical to revoked/expired - the enumeration-safety assertion); revoke is idempotent; a live `acta_reader` session stops serving once its share is revoked/expired (per-request liveness check); the neutral page leaks no report title; `noindex/nofollow` present on report/verify/neutral routes; `Cache-Control: no-store` on the sensitive responses; no leaking `og:`/`twitter:` title in the reader-route HTML head; CSP header present with no third-party origins. E2e (Playwright, desktop): create + verify-read a share, revoke it, reload -> neutral page (the leak-free assertion through the live page).

## Dev Notes

- Authority: FR20 (one-click revoke + neutral leak-free page, not even the report title), FR21 (expiry serves the same neutral page), NFR10 (noindex/nofollow, no-cache on sensitive responses, neutral link-preview metadata, strict CSP zero third-party assets), NFR9 (revoked/expired/nonexistent indistinguishable). Architecture D7 (strict CSP, self-hosted fonts), the sharing domain. Scopes: `share` (revoke service), `security`/`ops` (the hardening audit - CSP/cache/meta), `render` (neutral page + meta on reader routes).
- DEPENDS ON 3.2 (the `shares` table + `revoked_at`/`expires_at` columns + `isExpired`), 3.3 (the `/r/[token]` gate, the reader session, the VerifyCard neutral states), and 3.4 (the mode-aware gate). Implement 3.2 -> 3.3 -> 3.4 first; this is the closing hardening pass over the whole sharing surface.
- Seam reuse: the `/r/[token]` gate is 3.3's `r/[token]/+page.server.ts`; the neutral-page states already exist as VerifyCard's "expired/used" state (3.3) - extend to the revoked/nonexistent case so ALL closed states render the one neutral page. CSP + security headers are emitted in `hooks.server.ts` (the 1.4 `securityHeaders` handle) - audit and extend there for `Cache-Control: no-store` on sensitive routes. `noindex/nofollow` is 1.6 groundwork on report routes - this story verifies and closes any gap on the verify/neutral routes. `getPublishedDocument` (1.7) is only ever reached AFTER the live-share check passes.
- The neutral page is the single most security-sensitive surface in the epic: it MUST be byte-identical across revoked / expired / nonexistent. A separate "this link was revoked" vs "this link expired" vs a 404 would each leak (the report existed, the link was real, etc.). One page, one status, no distinguishing detail. This realizes "a mis-sent link is a non-event".
- Reader-path JS budget (200 KB) unaffected - the neutral page is minimal SSR, no hydration.
- AMBIGUITY for the product owner (do not invent): the exact HTTP status for the neutral page is unspecified - a 404 leaks "no such token" semantics, a 200 with a neutral body is the most enumeration-safe but unconventional, a 410 implies "existed and gone" (a leak for revoked/expired, wrong for nonexistent). Recommend a uniform 200 (or 404) neutral page for ALL closed states - confirm the chosen status before implementing, since it is the crux of the leak-free contract.

- Idempotency is enforced in SQL, not in app logic: `UPDATE shares SET revoked_at = now() WHERE id = ? AND revoked_at IS NULL`. A second revoke matches zero rows (the `IS NULL` guard) and preserves the original revocation instant. The session sweep runs unconditionally on every call (itself idempotent, a no-op when no sessions remain). A dedicated `revoke.test.ts` mock decodes the `and(eq(id), isNull(revoked_at))` filter and asserts both the matched-row count (1 then 0 on double-revoke) and that the filter references both `id` and `revoked_at` (a regression dropping the guard fails).
- Neutral-page test gotcha: the SvelteKit `error()` body uses a problem-details `title` FIELD ("Not Found"), so a naive "body contains no 'title'" leak assertion false-positives on the structural key. Narrowed the leak regex to the actual leak words (revoked/expired/reportid/token_hash/recipient). Same for the `+error.svelte` component test: generic English in the help copy ("if someone shared it with you") is not a leak; the assertion targets the reason words and identifiers only.

### Completion Notes

- **One-click revocation (FR20)**: `revokeShare(shareId)` in `sharing/shares.ts` sets `revoked_at = now()` (idempotent via the `revoked_at IS NULL` SQL guard - a double-revoke is a verified no-op, never an error, and the original instant is preserved) and then calls `destroyReaderSessionsForShare(shareId)` to sweep every already-verified reader session bound to the share. Defense in depth: the gate's per-load liveness check alone already stops serving a revoked share, but dropping the session rows cuts a mid-session reader immediately and frees the rows. The workspace `?/revoke-share` action (author-realm, under `workspaceGuard`) is a two-click destructive confirm mirroring the reports-list delete pattern (`confirmRevoke` enhance: first click arms "Confirm revoke?", second within 5s submits). The Revoke button shows only on `active` shares; the status chip flips to `revoked` after.
- **Leak-free neutral page (FR20/NFR9)**: the single closed-share exit `serveNeutralClosed` (3.3) is unchanged in behavior - one byte-for-byte `404` + `Cache-Control: no-store` for revoked / expired / unknown alike. 3.5 themes its BODY by adding a root `src/routes/+error.svelte`: a branded card ("This link is not available", reader `--report-*` tokens, the ACTA DIURNA wordmark) that interpolates NO per-error status or message, so the three closed states render an identical body. It leaks nothing - not the report title, not the reason, not whether the token ever matched a share. (The page doubles as the app-wide error fallback; a generic "not available" is correct for an unauthenticated reader and harmless elsewhere.)
- **Byte-identical revoked == expired == unknown (the enumeration-safety crux, HOW TESTED)**: three layers. (1) `reader/neutral.test.ts` asserts `serveNeutralClosed` emits the identical `{status:404, body, headers:{cache-control:no-store}}` across three independent calls standing in for the three reasons - by construction it takes no reason argument, so it cannot branch. (2) `r/[token]/page.server.test.ts` asserts the gate routes revoked, expired, AND unknown tokens (and a 409 unpublished-after-share) all through the same `serveNeutralClosed`, throwing the identical neutral marker with the same `no-store` header. (3) The revocation e2e asserts the real HTTP response after revoke is `404`, contains "This link is not available", does NOT contain the fixture report title ("Quarterly"), and carries `cache-control: no-store` - the live byte-level proof.
- **Immediate effect, no cache window**: the gate re-checks `share.status !== 'active'` on EVERY load BEFORE it reads the reader session cookie, so a revoked/expired share short-circuits to the neutral page even for a reader holding a live `acta_reader` session - the session validator is never consulted. Combined with `Cache-Control: no-store` on every reader response, revocation takes effect on the very next request with no intermediary-cache window. Tests assert the live session is cut off (gate liveness) for both revoked and expired, with `getPublishedDocument` never reached.
- **Leak-free HTTP posture audit (NFR10)** - results:
  - **noindex/nofollow**: confirmed on the WHOLE reader surface. The `hooks.server.ts` `securityHeaders` handle emits `X-Robots-Tag: noindex, nofollow` for `/r` and any `/r/*` path (covers the gate `/r/[token]`, the VerifyCard prompt, the magic-link `/r/[token]/verify` server route, and the neutral 404 - all under `/r/*`). The in-page `<meta robots>` is present on the reader `+page.svelte` AND the new `+error.svelte` (the header covers header-only crawlers, the meta covers JS crawlers). No gap.
  - **no-store**: confirmed on every sensitive response. The served report and the email prompt (`serveReport` + the prompt branch of the gate load) set `cache-control: no-store`; `serveNeutralClosed` sets it; the magic-link landing `/r/[token]/verify` now sets it before any branch (added this story) so every exit (neutral 404, expired bounce, success redirect) carries it. A revoked link's previously-served content is therefore never replayed from a cache.
  - **OG/meta-title leak audit - was there a leak? NO, but verified and documented**. There are ZERO `og:`/`twitter:` tags anywhere in the reader surface (grep-confirmed across `r/`, `VerifyCard.svelte`, `+error.svelte`). The reader `<title>` resolves to the report title ONLY for a verified reader (when `view` is non-null); an unauthenticated link-unfurler (Slack/Teams/iMessage) never has a reader session, so it hits the VerifyCard or the neutral page where the title falls back to the generic "Acta Diurna". The report title therefore never reaches a preview unfurl. Added an explicit documenting comment on the reader head ("Do not add og:/twitter: metadata here") and a test asserting the report title is absent from the served neutral-page HTML.
  - **CSP decision - WIRED FULLY (already present, confirmed, no change)**. The 3.3 audit note that "CSP is not wired" was inaccurate: a strict CSP is wired the architecturally-correct way (D7: "via SvelteKit configuration") in `vite.config.ts` via SvelteKit's native `csp` block - `mode: 'auto'` (SvelteKit hashes its own inline hydration scripts/styles, no `unsafe-eval`), `default-src 'self'`, `script-src 'self'`, `style-src 'self' 'unsafe-inline'` (Svelte scoped styles + SSR inline `style` attributes), `font-src 'self'` (self-hosted Fontsource, zero third-party), `img-src 'self' data:`, `connect-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'self'`. SvelteKit emits this policy (as a `<meta http-equiv>` plus the hashes) into every SSR page including the reader surface; verified present in the built `index.js`. The renderer ships zero third-party assets (SSR charts are inline SVG, tokens are CSS custom props, fonts bundled), so the policy holds with no violation. The lone `style-src 'unsafe-inline'` is unavoidable for Svelte's scoped/SSR inline styles and was accepted at 1.6; no inline SCRIPT is unsafe (script-src is `'self'` only, hashed). No new header added in `hooks.server.ts`: duplicating the policy as a header risks a conflicting double-policy; the SvelteKit-managed CSP is canonical. NOT parked - the full strict CSP is in effect.
- **Reader budget**: unchanged at 64.1 KB. The neutral page is minimal SSR with no hydration; `+error.svelte` adds nothing to the reader client closure (the budget script anchors on the report shell + VerifyCard).
- **Epic 3 complete end to end**: secure sharing now works fully - share links with expiry (3.2), reader verification by magic link (3.3), restricted vs open modes (3.4), and one-click revocation with a leak-free neutral page + hardened HTTP posture (3.5). The whole closed-share surface (revoked, expired, unknown, unpublished-after-share) funnels through one byte-identical neutral 404; a mis-sent link is a non-event.
