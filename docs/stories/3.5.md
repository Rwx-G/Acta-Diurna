# Story 3.5: Revocation & Leak-Free Posture

Status: Approved

## Story

As the author,
I want one-click revocation and zero information leakage on closed links,
So that a mis-sent link is a non-event.

## Acceptance Criteria

**Given** an active share
**When** I revoke it
**Then** the link immediately serves a neutral page leaking nothing - not even the report title (FR20)

**Given** an expired share
**When** opened
**Then** the same neutral page is served

**Given** any report route
**When** served
**Then** `noindex/nofollow`, no-cache on sensitive responses, neutral link-preview metadata, and strict CSP with zero third-party assets are applied (NFR10)

## Tasks / Subtasks

- [ ] One-click revocation: a `revokeShare(shareId)` service in `src/lib/server/sharing/` setting `shares.revoked_at = now` (the column exists from 3.2); idempotent (revoking a revoked share is a no-op, no error). Workspace `?/revoke-share` action on the share list/ShareDialog (author-realm, under `workspaceGuard`), one click, status flips to revoked in the UI (StatusChip grammar).
- [ ] Neutral page for a closed link: the `/r/[token]` gate (3.3) serves a SINGLE neutral page - identical for revoked, expired, AND nonexistent token - leaking NOTHING (not the report title, not whether the token ever existed, not why it is closed). Same page, same status, same body for all three closed states (enumeration-safety, NFR9/NFR10). The live-share check is `revoked_at IS NULL AND (expires_at IS NULL OR expires_at > now)` AND the token resolves; anything else -> the neutral page. A revoked share takes effect IMMEDIATELY (next request, no cache).
- [ ] Reader session invalidation on revoke: an existing `acta_reader` session bound to a now-revoked or expired share must stop serving the report (FR23 "while the session and share remain valid" - the share is no longer valid). The gate re-checks share liveness on every reader request, not only at verification, so a persistent session cannot outlive its share.
- [ ] Audit + harden the whole sharing/reader surface (this story is the hardening pass, NFR10): confirm `noindex/nofollow` on every report route (1.6 groundwork - audit it is actually emitted on `/r/[token]`, the VerifyCard pages, and the neutral page); add `Cache-Control: no-store` (no-cache) on sensitive responses (the served report, verification, the neutral page) so a revoked link is never served from a cache; neutral link-preview metadata (NO OpenGraph/Twitter title or description that leaks the report title - emit neutral or no `og:`/`twitter:` tags on reader routes so a pasted link in chat/email previews nothing); confirm the strict CSP (D7, already present) applies with zero third-party assets on the reader surface.
- [ ] Tests: revoke flips `revoked_at` and the link immediately serves the neutral page; an expired share serves the SAME neutral page; a nonexistent token serves the SAME neutral page (byte-identical to revoked/expired - the enumeration-safety assertion); revoke is idempotent; a live `acta_reader` session stops serving once its share is revoked/expired (per-request liveness check); the neutral page leaks no report title; `noindex/nofollow` present on report/verify/neutral routes; `Cache-Control: no-store` on the sensitive responses; no leaking `og:`/`twitter:` title in the reader-route HTML head; CSP header present with no third-party origins. E2e (Playwright, desktop): create + verify-read a share, revoke it, reload -> neutral page (the leak-free assertion through the live page).

## Dev Notes

- Authority: FR20 (one-click revoke + neutral leak-free page, not even the report title), FR21 (expiry serves the same neutral page), NFR10 (noindex/nofollow, no-cache on sensitive responses, neutral link-preview metadata, strict CSP zero third-party assets), NFR9 (revoked/expired/nonexistent indistinguishable). Architecture D7 (strict CSP, self-hosted fonts), the sharing domain. Scopes: `share` (revoke service), `security`/`ops` (the hardening audit - CSP/cache/meta), `render` (neutral page + meta on reader routes).
- DEPENDS ON 3.2 (the `shares` table + `revoked_at`/`expires_at` columns + `isExpired`), 3.3 (the `/r/[token]` gate, the reader session, the VerifyCard neutral states), and 3.4 (the mode-aware gate). Implement 3.2 -> 3.3 -> 3.4 first; this is the closing hardening pass over the whole sharing surface.
- Seam reuse: the `/r/[token]` gate is 3.3's `r/[token]/+page.server.ts`; the neutral-page states already exist as VerifyCard's "expired/used" state (3.3) - extend to the revoked/nonexistent case so ALL closed states render the one neutral page. CSP + security headers are emitted in `hooks.server.ts` (the 1.4 `securityHeaders` handle) - audit and extend there for `Cache-Control: no-store` on sensitive routes. `noindex/nofollow` is 1.6 groundwork on report routes - this story verifies and closes any gap on the verify/neutral routes. `getPublishedDocument` (1.7) is only ever reached AFTER the live-share check passes.
- The neutral page is the single most security-sensitive surface in the epic: it MUST be byte-identical across revoked / expired / nonexistent. A separate "this link was revoked" vs "this link expired" vs a 404 would each leak (the report existed, the link was real, etc.). One page, one status, no distinguishing detail. This realizes "a mis-sent link is a non-event".
- Reader-path JS budget (200 KB) unaffected - the neutral page is minimal SSR, no hydration.
- AMBIGUITY for the product owner (do not invent): the exact HTTP status for the neutral page is unspecified - a 404 leaks "no such token" semantics, a 200 with a neutral body is the most enumeration-safe but unconventional, a 410 implies "existed and gone" (a leak for revoked/expired, wrong for nonexistent). Recommend a uniform 200 (or 404) neutral page for ALL closed states - confirm the chosen status before implementing, since it is the crux of the leak-free contract.
