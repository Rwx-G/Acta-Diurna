# Story 11.5: Drill-Down Authoring Across Producers

Status: Review

## Story

As an author or agent,
I want to create a detail page and wire an internal link to it from the document editor, the REST API, and MCP,
So that drill-down is authorable by hand and by agent today, before the Epic 10 WYSIWYG editor adds a friendlier gesture.

## Acceptance Criteria

**Given** any producer (document editor, REST API, MCP)
**When** a detail section (`kind: 'detail'`) and a `linkTo` reference are authored
**Then** the same schema, the same document-level cross-reference validation, and the same actionable problem-details errors apply across all three - no producer-specific authoring path (FR30 / FR31 parity)

**Given** the workspace editor preview (`toPreviewView`)
**When** an author is mid-edit with a not-yet-existing `linkTo` target
**Then** the preview surfaces the dangling reference as a gentle, actionable notice rather than throwing (consistent with the per-block preview tolerance), so the author sees the problem and fixes it before publish

**Given** the published JSON Schema and its examples
**When** fetched (`/api/v1/schema`)
**Then** the v2 schema describes `kind: 'detail'` and the `linkTo` carriers, and at least one example document includes a detail page reached by an internal link (so agents discover the shape)

**Given** the Epic 10 WYSIWYG editor (later)
**When** it ships
**Then** it surfaces a "link to a detail page" gesture over this same schema - this epic delivers the authorable model now and the editor builds on it, with no schema change required for the editor gesture (confirm scope at the Epic 10 kickoff)

There is no producer-specific authoring or validation path: the workspace edit form, REST, and MCP converge on the same chokepoint. Proved by e2e (below), not assumed.

The reader path (`toReportView`) sets `danglingLinks: []` (a validated document has no dangling link), so the parity test (`toPreviewView(valid) === toReportView(valid)`) still holds. ## Dev Notes

- Authority: `docs/prd/epic-11.md` Story 11.5 AC verbatim above. This is the LAST Epic 11 story; 11.1 (detail-section schema), 11.2 (validated `linkTo` + the no-dangling cross-ref pass), 11.3 (reader render/navigation), and 11.4 (audience + deep-link edges) all landed. 11.5 CONFIRMS producer parity (it was already true by construction - one validated service), adds the preview leniency, and ships the discoverable example. Renderer-pure: `src/lib/render` + `src/lib/schema` import no `$lib/server`, no `{@html}`, escaped output, internal anchors only. Scopes: `api` (parity confirmation, no code change there), `ui` (preview tolerance + notice), `schema`/`docs` (the example), `qa` (e2e + unit), `docs` (this story + CHANGELOG).
- PRODUCER PARITY (AC1) is a property of the architecture, not a feature this story adds: every producer (workspace edit form, REST `POST/PATCH /reports`, MCP `create_report`/`update_report`) writes through `writeDocument`/`createReportWithDocument`, which call `validateOrThrow(input)` -> `validateDocument` -> the v1 `documentSchemaV1` superRefine that runs `validateInternalLinks` and the `annex`/`kind` mutual-exclusion refine. So the schema, the cross-reference validation, and the RFC 9457 `problem+json` (`toProblemDetails`, status 422, `errors[]` with `path`/`message`/`hint`) are identical across producers. The e2e proves it end-to-end: the dangling-`linkTo` error from REST and from MCP both name `linkTo` in the path and the missing target in the message; the annex+detail error is the same "mutually exclusive" message from both. No gap was found - nothing to fix, only to confirm and lock with tests.
- PREVIEW TOLERANCE (AC2) - leniency is preview-only, save stays strict. The validate-on-write path (11.2) REJECTS a dangling `linkTo` at save/publish; that is unchanged. The live preview must let an author keep editing while a target is half-authored, so `toPreviewView` runs the same `validateInternalLinks` over the raw snapshot and surfaces the danglers as `ReportView.danglingLinks` (a gentle, named, actionable notice the workspace `LivePreview` renders), rather than throwing or blanking. `validateInternalLinks` is isomorphic and structural (it ignores blocks it does not recognize), so a transiently-invalid sibling block does not break the pass - consistent with the existing per-block preview tolerance. The reader path carries `danglingLinks: []` (a validated document has none), so the existing "valid snapshot renders identically to the reader path" parity test still passes byte-for-byte.
- EXAMPLE (AC3) - a NEW example, not a mutation. The `full` example is asserted by tests (title, section count, json sync), so the drill-down shape ships as a separate `drilldown` example rather than perturbing `full`. It is published as a third key from `getPublishedSchema` (`minimal`/`full`/`drilldown`); the schema route, the MCP `get_schema` tool, and the static artifact all flow from there. The JSON Schema itself already describes `kind: 'detail'` and the three `linkTo` carriers (the const-`detail` literal, the inline-run/`rowLinks`/finding `linkTo` fields) - confirmed in `static/schema/v1.json`, and `pnpm schema:export` produced no diff, so this story made no schema-shape change.
- EPIC 10 FORWARD NOTE (AC4) - documentation only, no code. The Epic 10 WYSIWYG editor will surface a friendlier "link to a detail page" gesture (e.g. select prose, pick a target detail section from a list) over this SAME schema: a detail section is `kind: 'detail'`, an internal link is a `linkTo` section id on a run/table-row/matrix-finding. The editor gesture needs NO schema change - it writes the same `linkTo`/`kind` fields this epic already validates through the same service. Confirm the exact gesture scope at the Epic 10 kickoff; this story delivers the authorable model the editor builds on.
- BUDGET: reader JS 74.6 KB / 200 KB (NFR3), +0.2 over 11.4's 74.4. The `validateInternalLinks` import is reached only via `toPreviewView` (a workspace-only path); the reader `/r/[token]` closure does not call it, so the bump is incidental module-graph cost, well within budget.
- VERIFIED vs REASONED: every gate below was RUN (unit, lint, check, build, reader:budget, single + multi e2e, schema:export). Producer parity is verified by the new REST + MCP e2e (the dangling/annex+detail errors round-trip through the real service + DB), not reasoned from code reading alone.
