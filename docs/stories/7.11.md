# Story 7.11: Timeline / Roadmap Block

**Epic:** 7 (Report Brick Library, Phase B)
**Status:** Done

## Story

As an author or agent,
I want a milestone timeline with per-milestone date and status,
So that an action plan or roadmap reads as a sequence rather than a status table.

## Acceptance Criteria

**Given** a `timeline` block with ordered `milestones` (each: a `label`, optional `date`/phase sub-label, optional rich-text `detail`, and a `status` referencing a scale entry)
**When** rendered
**Then** it renders as an ordered SSR timeline (a connector with one node per milestone) where each node shows the label, the optional date sub-label, the detail, and a status badge (colour + label from the referenced scale - reusing 7.5)

**Given** a milestone `status` value absent from the referenced scale
**When** validated
**Then** an actionable problem-details error names the offending milestone and value (FR2 parity)

**Given** the block
**When** audited
**Then** it is SSR (HTML or SSR SVG connector, zero hydration), Zod-validated, AAA on the default theme, colour never the sole signal (the status label is always present), within the reader budget

## Dev Notes

- The milestone `status` is a `{ scaleRef, entry }` PAIR carried per milestone, not one scale named once for the whole block (the chip-cluster's model): two milestones may carry statuses from different scales (e.g. a delivery scale and a risk scale). Each pair is cross-referenced against the document `scales` in the document-level pass; the shared `Badge` (7.5) resolves the entry's colour and label.
- The cross-reference lives in `validateScaleReferences` (`scales.ts`), the seam 7.1 established and 7.2-7.5 extend: a block cannot see the document `scales` from inside the discriminated union, so the reference check is wired at the document superRefine. `validateTimelineRefs` reports a dangling `status.scaleRef` at `...milestones[m].status.scaleRef` and a dangling `status.entry` at `...milestones[m].status.entry`, each message naming the offending milestone by its label (AC2).
- The connector is a pure-CSS vertical line down the node markers, NOT an SSR SVG: the milestones already live in a real `<ol>`, so the list IS the accessible structure and the connector is decorative (`aria-hidden` node markers). This avoids the UpSet block's `<title>`/`<desc>` text-alternative machinery, which is only needed when the SVG itself carries the data; here the data is HTML text. Colour is never the sole signal - every milestone carries its status label (the Badge) and its visible heading.
- The `detail` reuses the text block's `paragraphSchema` (paragraphs of inline runs) verbatim, so it renders escaped through the SAME marked-run snippet the callout (7.7), code (7.8) and list (7.10) blocks use - bold/italic, the inline-code chip, and http(s) links all work. No new inline vocabulary.
- `milestones` capped at `MAX_MILESTONES = 50` (a roadmap past 50 milestones is a structural smell - split it into phases), `detail` capped at `MAX_MILESTONE_DETAIL_PARAGRAPHS = 50` (the callout body / list-item ceiling). `label` bounded at 300, `date` at 120, `title` at 200.
- The `date` is FREE-FORM text, not a parsed date: a roadmap mixes calendar dates ("2026-06-12") and phase names ("Q3 2026", "Phase 1"), so the renderer shows it verbatim as a sub-label. No date parsing, no locale formatting.
- Timeline text uses `--report-*` theme tokens (AAA report content on the default theme); no raw hex in the component. Zero hydration: the timeline ships no client JS.
- The editor edits the detail as plain-text paragraphs (the callout / list flatten-on-edit pattern); switching the status scale clears the entry (the old entry would dangle against the new scale). The renderer drops only the badge (keeping the label) when a milestone's scale cannot resolve on the preview path; the cross-reference pass flags it at save/API time.
