# Story 11.4: Audience Levels and Deep-Link Interaction on Detail Pages

Status: Done

## Story

As a reader,
I want audience levels and deep links to behave correctly on detail pages,
So that a detail page respects my chosen depth and a shared link to it lands on the right content.

## Acceptance Criteria

**Given** a detail section (or its blocks) carrying audience tags
**When** the reader switches level
**Then** the detail page's blocks show/hide by the same `data-level` CSS the flow uses - content stays SSR, only visibility toggles (FR28 parity), and an untagged detail section appears at every level

**Given** a deep link to a detail section that is audience-tagged out of the reader's current level
**When** the report loads
**Then** the level is promoted to one that reveals the detail page before navigating (reusing the existing Report.svelte reveal-on-deep-link behavior), so the shared link lands on its content rather than on an empty hidden box

**Given** a report whose only audience tags live on detail sections
**When** rendered
**Then** the level switcher behaves consistently with the flow rule (shown when the document carries any tags, hidden when it carries none) - confirm at kickoff whether detail-only tags alone surface the switcher; the planning default is yes, they count

**Given** an internal link whose target detail section is hidden at the reader's current level
**When** the link is activated (not via a load-time deep link)
**Then** activation promotes the level the same way the deep link does, so an in-report drill-down never dead-ends on a hidden target

## Tasks / Subtasks

- [x] Confirm the audience CSS already reaches into detail content (AC1). The global `data-level` rule (`.report[data-level=...] :global([data-audiences]:not(...))`) is a descendant selector under `.report`; detail hosts and their blocks are descendants and already carry `data-audiences` (the host via `audiencesAttr(section.audiences)`, blocks via `BlockRenderer`). No detail-host overlay markup or `:has` scoping blocks its reach - verified by a render unit test, not assumed.
- [x] Make the `:target` reveal compose with `data-level` hiding for the both-targeted-and-hidden case. The audience hide rule out-specifies the `:target` reveal (4 vs 2 selector components on the same `.detail-host`), so an audience-excluded detail stays `display: none` even when targeted; the fix is to PROMOTE the level (so the hide rule no longer matches) before the reveal, not to fight specificity. The flow-hide and reveal rules already compose once promoted.
- [x] Add `levelRevealingDetail(section, currentLevel)` to `audience.ts`: returns the level to promote to so a detail page lands on its CONTENT (the section frame visible AND at least one block visible), or the current level when it already reveals it / nothing can. Covers BOTH a section-level tag (whole host hidden) AND a block-level tag (host shows, content an empty box) - AC4's block-level edge.
- [x] Wire `promoteLevelForDetail(section)` in `Report.svelte` on BOTH the load-time detail deep-link path AND the click-time activation path, replacing the section-audiences-only `promoteLevelFor` for detail targets (it still serves flow deep links). One rule, two entry points, block-aware.
- [x] Confirm + test that detail-only audience tags surface the switcher (AC3). `hasAudienceTags` already walks every section including detail (story 11.1 / `toReportView` counts detail-section tags); add a render + view-model assertion that a document whose tags live only on detail sections sets `hasAudiences` true and renders the switcher.
- [x] Harden the "back" affordance against a reactive-href race (surfaced by the new audience rendering). `handleBack` read the origin then cleared `detailOrigin`, which flipped the reactive `href` to the first-flow fallback and could race the browser's native anchor navigation, landing the reader on the cover. `handleBack` now `preventDefault`s and drives `window.location.hash = origin` (a real hash change re-evaluates `:target`, closing the overlay), so back is deterministic; the no-JS native anchor path is unchanged.
- [x] Tests: unit (`levelRevealingDetail` - untagged keeps level, section-tag promotion, block-tag promotion, no-visible-block promotion, first-canonical-level, unreachable fallback; the detail-only-tags `hasAudiences` view assertion; the tagged-detail-host render assertion); e2e (`reader-detail-audience.e2e.ts`, desktop + mobile) - detail blocks show/hide by `data-level`; deep link to a technical-only detail promotes + lands on content; click to a hidden technical-only detail promotes + reveals; click to a block-level-tagged detail promotes so content is not an empty box; detail-only tags surface the switcher; SSR floor (tagged detail content in the served HTML); axe with an open audience-tagged detail page.
- [x] Extend the existing detail fixture (`e2e/fixtures/detail.ts`, same id `...000000000007`) with two audience-tagged detail pages (`detail-technical-only` section-level `['technical']`; `detail-mixed-levels` untagged section, sole block `['technical']`) reached by inline `linkTo` from a dedicated `drilldowns` flow section, so `summary`/`findings` stay byte-stable for the 11.3 navigation geometry. No snapshot depends on this fixture, so the id stays.

## Dev Notes

- Authority: `docs/prd/epic-11.md` Story 11.4 AC verbatim above + the "Foundational design" audience bullet ("Audience levels apply to detail sections unchanged, and the deep-link-reveals-hidden behavior carries over ... promotes the level to one that reveals it before navigating ... so a shared link to a technical-only detail page lands on it"). Builds on 11.1 (`hasAudienceTags` counting detail-section tags), 11.3 (the CSS `:target` reveal, `promoteLevelFor`, `detailIdForFragment`, the load-time + click-time detail paths). Renderer-pure: `src/lib/render` + `src/lib/schema` import no `$lib/server`, no `{@html}`, escaped output, internal anchors only. Scopes: `render` (the compose + promotion), `qa` (fixture + e2e), `docs` (this story + CHANGELOG).
- KICKOFF CONFIRMATIONS (answered YES, per the planning default): detail-only audience tags count toward `hasAudiences` and surface the switcher (AC3). The deep-link / click both promote the level before revealing an audience-hidden detail (AC2/AC4). Verified, not assumed.
- THE LOAD-BEARING CSS EDGE (did the audience CSS reach into detail? + the both-targeted-and-hidden case): the audience CSS ALREADY reaches into detail content unchanged - the `data-level` rule is a `.report` descendant selector and detail hosts/blocks are descendants carrying `data-audiences`, so AC1 needed NO CSS change (confirmed by a render unit test asserting a `['technical']` detail host is `display:none` at the default `full` level). The interaction bug is specificity, not reach: the audience hide rule (`.report[data-level] [data-audiences]:not(~level)`, 4 components) OUT-SPECIFIES the `:target` reveal (`.detail-host:has(:target)`, 2 components) on the same `.detail-host`. So a detail that is BOTH `:target` AND audience-excluded stays hidden. The right composition is NOT to escalate the reveal's specificity (that would force-show content the reader's level excludes, breaking FR28) but to PROMOTE the level so the hide rule stops matching - then the reveal applies cleanly. Promotion is the single mechanism that makes "audience-allowed + targeted shows; audience-hidden + targeted promotes-then-shows" both hold.
- BLOCK-LEVEL vs SECTION-LEVEL (AC4's edge): `promoteLevelFor(audiences)` (11.3) only knew section-level tags, so a detail whose SECTION is untagged but whose only BLOCK is `['technical']` would reveal the host at `full` onto an empty box. `levelRevealingDetail(section, level)` fixes this: "reveals" means the section frame is visible AND at least one block is visible at the level. It promotes for a section tag, a block tag, or a section that is visible but has no visible block; it returns the current level when already adequate, and falls back to the current level when an over-constrained authoring mistake leaves nothing revealable (the reader stays put rather than jumping nowhere). `promoteLevelForDetail` calls it on both detail paths.
- THE BACK-AFFORDANCE RACE (a real 11.3 latent bug this story surfaced and fixed): turning the detail fixture audience-tagged made `hasAudiences` true, which renders `data-level` + the switcher and perturbed reactive timing enough to expose a race. The back link's `href` is the reactive `#${detailOrigin ?? firstFlow}`; `handleBack` cleared `detailOrigin` BEFORE the browser's native anchor navigation, flipping the href to the first-flow fallback and landing the reader on the cover (`#summary`) instead of the origin (`#findings`) - intermittently, mobile-first. Fix: `handleBack` now `preventDefault`s and sets `window.location.hash = origin` from the captured origin (a real hash change re-evaluates `:target`, so the overlay closes), making back deterministic regardless of reactive href timing. The no-JS path keeps the native anchor jump unchanged.
- REUSE / NO-DRIFT: `levelRevealingDetail` lives in `audience.ts` next to `isVisibleAtLevel` / `hasAudienceTags`, the single isomorphic source the reader switcher, the workspace preview, and any no-JS fallback share. It is pure (no DOM, no Svelte), unit-tested in isolation, and consumed by `Report.svelte` only - so the promotion rule cannot drift from the visibility rule.
- BUDGET: reader JS 74.4 KB / 200 KB (NFR3), +0.1 KB over 11.3's 74.3 - the `levelRevealingDetail` helper + the `handleBack` change are the only additions, deliberately minimal; the reveal stays pure CSS.
- DEFERRED TO 11.5 (flagged, not in 11.4 scope): drill-down authoring parity across producers (document editor / REST API / MCP), the `toPreviewView` gentle dangling-`linkTo` notice, and the published JSON Schema example document carrying a detail page reached by an internal link. 11.4 hardens the reader-side audience/deep-link edges only.
