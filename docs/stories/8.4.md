# Story 8.4: Mode-Aware Reader Sharing

## Status

Done

## Story

As an author,
I want sharing to match the instance mode,
So that a no-SMTP instance can still share (consultation token) and an SMTP instance keeps verified reader access.

## Acceptance Criteria

**Given** SINGLE mode
**When** an author shares a published report
**Then** the share is an unverified CONSULTATION TOKEN: opening the link grants read access directly (no email, no verification gate); the restricted/recipient-allow-list mode is unavailable and the UI says so; expiry, one-click revocation, and the leak-free neutral page for revoked/expired/unknown links all still apply

**Given** MULTI mode
**When** an author shares a published report
**Then** the verified magic-link reader flow (Epic 3) applies unchanged (restricted or open mode, per-recipient verification)

**Given** either mode
**When** the reader gate handles a request
**Then** it branches on the resolved mode (consultation-token validation vs verified-session validation) and the enumeration-safe / no-store / noindex posture holds in both

**Given** a share created in one mode
**When** the instance mode later changes
**Then** the behavior is documented and safe (a consultation share under newly-enabled SMTP, and vice versa) - define and test the transition so a stale share never escalates access

## Dev Notes

### The mode branch

The reader gate (`src/routes/r/[token]/+page.server.ts`) resolves the share, then branches on the CURRENT operating mode (`isMultiAuthor()` / the `servesConsultation` predicate). The closed-share check (`status !== 'active'` -> neutral 404) runs BEFORE the branch, so the leak-free posture is byte-identical in both modes - a prober cannot tell a single-mode instance from a multi-mode one off a dead link.

- SINGLE mode: a live `open` share is a consultation token - `servesConsultation` is true and `serveReport` returns the published snapshot directly, with no reader cookie read and no session validated. The token IS the grant.
- MULTI mode: `servesConsultation` is false, so the Epic 3 flow runs untouched (FR23 session re-use, else the email-prompt VerifyCard; the `request-verification` action and the `/verify` magic-link landing as before).

### The transition rule (the safe, documented behavior)

The gate always honors the CURRENT mode, never the mode a share was minted in. `servesConsultation(share)` (in `sharing/shares.ts`) is the one place the rule lives:

- MULTI mode: always false. A SINGLE-era consultation share is `open`, so under newly-enabled SMTP it becomes open-with-verification - a STRICTER gate, never an escalation. The `/verify` landing and the verify card both apply.
- SINGLE mode + `open` share: true. Both the consultation tokens single mode mints and any MULTI-era open share serve directly.
- SINGLE mode + `restricted` share: FALSE. A restricted share is a MULTI-era artifact whose recipient list cannot be enforced without email. Serving it directly would broaden a recipient-gated link to anyone holding it, so it is treated as CLOSED (the gate serves the neutral 404) until the instance runs multi mode again. **Closed-not-opened** is the safe transition: a mode downgrade never opens a previously-restricted link.

Both transition directions therefore tighten or hold access; neither escalates. This is tested in `shares.test.ts` (the predicate), `r/[token]/page.server.test.ts` (restricted-under-single -> neutral 404; consultation-under-multi -> verify prompt), and `r/[token]/verify/server.test.ts` (the landing opens no session in single mode).

### Leak-free posture in SINGLE mode

- The `/r/*` X-Robots-Tag (`hooks.server.ts` `isNoindexReportPath`) and the in-page `<meta robots>` are route-scoped, not mode-scoped, so `noindex, nofollow` holds in both modes with no change.
- Every serving exit (consultation direct-serve, verified serve, the neutral 404) sets `cache-control: no-store`; the consultation path goes through the same `serveReport` helper that sets it.
- Revocation and expiry are unchanged by mode: a revoked or expired consultation link hits the same `status !== 'active'` check and serves the same neutral 404. The session sweep on revoke (`destroyReaderSessionsForShare`) still runs (a no-op in single mode, where consultation grants no session); the per-load liveness re-check is what cuts off a consultation read the instant the share is revoked or expires.
- The strict CSP (vite.config.ts) and the leak-free link-preview stance (no og:/twitter: tags on `/r/*`) are route-level and unaffected.

### Why store consultation shares as `open`

Single mode mints `mode = 'open'` (not a new enum value) so the existing `ShareStatus` / `getShareByToken` / revoke / expiry machinery is reused unchanged, and the `restricted` value stays meaningful only as the MULTI-era artifact the transition rule closes. A new `consultation` mode value would have rippled through the schema and every status path for no functional gain.

## Dev Agent Record

### Debug Log

- The reader-route and share-route test suites import the route modules, which now call `isMultiAuthor()` / `servesConsultation()`. `$lib/server/mode` is parsed from `process.env` and throws without a full env, so each affected suite gained a `$lib/server/mode` mock (defaulting to the mode that suite asserts) rather than relying on a real env. This mirrors the 8.1-8.3 pattern (`vi.mock('$lib/server/mode', ...)`).
- `shares.test.ts` previously asserted `createShare` "defaults to restricted" under a single-mode mock - that encoded the OLD single-mode behavior. Replaced with the 8.4 rule (single -> consultation/open, restricted refused) plus the multi-mode default-restricted case, using a hoisted `modeState` so both modes are exercised in one file.
- `recipients.test.ts` mocked single mode but every `setShareRecipients` call expects success; recipient lists are a MULTI-mode concept, so the suite now runs under multi mode with one dedicated single-mode refusal test.
- The reader-gate `request-verification` action and the `/verify` landing each gained a single-mode early return; the existing multi-mode tests default `isMultiAuthor` to true so they are unaffected, and a single-mode inert/bounce test was added to each.

### Completion Notes

- All four gates green (verbatim in the session report): `pnpm lint`, `pnpm check`, `pnpm test`, `pnpm build`.
- No schema change, no migration: consultation shares reuse the existing `shares.mode = 'open'` value and all the 3.x status/revoke/expiry machinery.
- The mode branch lives in two route files (the gate + the magic-link landing) and four service functions (`createShare`, `setShareMode`, `setShareRecipients`, the new `servesConsultation`); the UI reads one `multi` flag from the share-management load.

### Unverified / could not run end to end

- The full single-mode browser flow (no SMTP -> create a consultation link -> open it in a fresh browser -> read directly with no verify card) needs an e2e harness with a real DB and is not run here. The paths are unit-tested by FORCING single mode (mocking `isMultiAuthor` / `operatingMode`), not against a live no-SMTP instance.
- The live mode-transition (boot single, mint a consultation share, add SMTP, restart, open the same link and land on the verify card; and the reverse) was not exercised against a real database. The transition rule is unit-tested through `servesConsultation` and the gate wiring, but the on-instance bascule is unverified end to end.
- Multi-mode parity is asserted by the unchanged existing reader/verify suites (they default to multi mode and still pass), not by two real logged-in readers against a live SMTP relay.
