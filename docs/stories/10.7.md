# Story 10.7: Persistence UX - Autosave, Undo/Redo, Conflict Handling, and Publish

## Status

Review

## Story

As the author,
I want autosave, undo/redo, concurrency conflict handling, and publish from the editor,
So that editing is safe and fluid without manual save discipline or fear of losing work to a concurrent write.

## Acceptance Criteria

**Given** an ongoing editing session
**When** the author makes changes
**Then** changes autosave to the server through the validated write path on a debounced interval (and an explicit save remains available), each save passing the loaded `updatedAt` for optimistic concurrency - autosave never bypasses validation

**Given** a concurrent write between load and save (a second editor tab, an API push, an MCP write)
**When** a save runs with a stale `expectedUpdatedAt`
**Then** the service returns the 409 `/problems/report-conflict` and the editor surfaces the conflict and the resolve path (reload and reapply) - never a silent last-writer-wins overwrite

**Given** an editing session
**When** the author undoes or redoes
**Then** undo/redo steps through the in-edit document history client-side, the preview and inline validation follow, and the next save persists the current state through the same validated path - undo/redo is an in-tab convenience, not a server-versioned history (a non-goal to clarify at kickoff)

**Given** a draft being edited
**When** the author publishes from the editor
**Then** the existing `publish` action runs (validate-on-write: an invalid draft is the 422 `errors[]` rendered inline at the failing blocks), publishing is idempotent, only a published report is shareable, and the author can unpublish to return to editing (the existing lifecycle, surfaced in the editor)

## Dev Notes

### The undo/redo model

`EditHistory<T>` (`editor-history.ts`) is a small, pure, framework-free class (no DOM, no Svelte, no Drizzle) so the coalescing, the bounded depth, and the baseline/reseed semantics are unit-testable in isolation; `ReportEditor` owns one instance and applies the restored snapshot onto the working copy.

- **Snapshot stack.** The stack holds `structuredClone`d document snapshots. `entries[index]` is always the current state; `index > 0` means undo is available, `index < length - 1` means redo is available. `current()` returns a fresh deep clone, so a restored document never aliases a stored entry the next edit would mutate.
- **Coalescing.** `record` coalesces a burst into ONE step: when two records fall inside the coalescing window (default 500 ms, on an injectable clock so the unit test is deterministic), the second REPLACES the top entry rather than pushing. `ReportEditor` records off the same ~200 ms settle the preview / validation share, so continuous typing produces one settle -> one record, and rapid successive settles within 500 ms also merge. The first edit after load is always a fresh step (the clock is seeded at `-Infinity`).
- **Fork on edit after undo.** Recording when the cursor is not at the top discards the redo tail ahead of it - a new edit after an undo forks history and the stale redo future is dropped.
- **Bounded depth.** At most `maxDepth` entries (default 50); a push past it evicts the oldest (the cursor follows).
- **Undo is just another edit.** `applyRestored` reassigns `doc` to the restored snapshot, marks it dirty and rearms the autosave through `onEdit`, so the restored state persists through the SAME validate-on-write seam. It sets a one-shot `skipHistoryRecord` flag so the settle that follows does not re-record the restore (the cursor already moved inside `EditHistory`).

### The baseline / reseed interaction (the key correctness point)

A SERVER reseed establishes a new authoritative baseline the author must not step PAST into stale state. `EditHistory.reseed(baseline)` replaces the whole history with a single entry, clearing BOTH stacks. It fires on:

- **A binding reconcile (10.5).** `reconcileBinding` already replaced the working copy with the server-derived re-resolved document and advanced the token; it now also reseeds the history to that document. The 10.5 Dev Notes are explicit that a binding reseed is a new baseline, not an undo step - this honours it: undo can never resurrect the pre-bind document.
- **Publish / unpublish.** On a successful publish or unpublish, the history is reseeded to the current `doc`, so a later unpublish-then-edit cannot undo across the publish/unpublish boundary into a document the server has already snapshotted.
- **A 409-resolved reload.** The conflict banner's "Reload latest" is an `invalidateAll`, which remounts `ReportEditor` (the page wraps it in `{#key report.id}`/refreshes the prop), giving a FRESH history seeded from the reloaded document - no explicit reseed needed, and no stale pre-reload step survives.

In every case the settle that follows the reseed is told to skip its record (`skipHistoryRecord = true`), so the reseed baseline is the floor and the first edit over it is a clean fresh step.

### previewLevel is excluded from the history by construction

The previewed audience level (`previewLevel` in `LivePreview`, Story 10.6) is a VIEW concern: it is not part of `doc`, not snapshotted, and never wired through `onEdit`. So it is excluded from the undo history by construction - the 10.6 Dev Notes called this out as the 10.7 seam, and 10.7 simply does not touch it. Switching the preview level (or the preview viewport toggle, also a `LivePreview`-owned view control) is not an undoable edit; the component test pins that a view-only interaction does not enable undo while a real document edit does.

### The autosave status indicator

A `saveStatus` derived collapses the existing save signals into one announced label: `saving` wins (the live truth), then a retry-able `saveFailed`, otherwise the last saved-at confirmation. A new `saveFailed` flag is the distinguishing piece - it is set on `result.type === 'error'` (server unreachable) and on a non-409 failure with NO inline errors (a 413 / 400 / 5xx), and is NOT set on a validation failure (which carries inline `errors[]` rendered at the block) or on a 409 (which owns the conflict banner). A fresh edit or a successful save clears it; the error state offers an explicit Retry that rearms the single save seam. `role="status"` + `aria-live="polite"` announces each transition without stealing focus.

### Conflict composes with undo

The 10.1 409 path is unchanged: on a stale-token save it sets `conflict = true`, preserves the in-memory edits, surfaces the amber reload-and-reapply banner, and crucially does NOT advance `expectedUpdatedAt`. So an undo after a conflict reverts the working copy through `applyRestored` -> `onEdit` and the follow-up autosave re-asserts the SAME (still stale) token, which 409s again - correct: the author must reload to reconcile, and the token is never corrupted by the undo. The e2e drives a real concurrent writer, confirms the banner + the preserved edit, then undoes and confirms the revert with the reload path still offered.

### What EXISTED vs what was ADDED

EXISTED (from 10.1 - 10.6, reused unchanged or only wired):

- The 800 ms debounced autosave, the explicit Save button (no-JS baseline), the `saving` / `pendingSave` in-flight state machine, the `expectedUpdatedAt` optimistic-concurrency token and the 409 conflict banner with the reload path (10.1).
- Publish / unpublish from the editor (the morphing primary action), the dirty/saving guard before publish, and the token reconcile from the action result (10.1).
- `reconcileBinding` replacing the working copy + advancing the token on a bind / rebind / remap (10.5).
- `previewLevel` as a `LivePreview`-owned view concern (10.6).

ADDED by this story:

- `EditHistory` (`editor-history.ts`) and its unit suite - the in-tab undo/redo model.
- The undo/redo wiring in `ReportEditor`: recording off the settle, `applyRestored`, the keyboard handler, the visible Undo / Redo controls, and the `skipHistoryRecord` one-shot.
- The history `reseed` calls on `reconcileBinding`, publish, and unpublish (the baseline interaction).
- The autosave status indicator: the `saveFailed` flag, the `saveStatus` derived, the `role="status"` region, and the Retry control.
