# Story 3.4: Restricted & Open Share Modes

Status: Review

## Story

As the author,
I want to choose between a restricted recipient list and open-with-verification per share,
So that confidential reports reach only intended recipients while routine ones can be forwarded.

## Acceptance Criteria

**Given** a share in restricted mode with listed emails
**When** an unlisted email requests verification
**Then** access is refused without revealing whether the email was known (FR19, NFR9)

**Given** a share in open-with-verification mode
**When** any holder of the link verifies their email
**Then** they can read, and their identity is recorded (FR19, FR22)

## Tasks / Subtasks

- [x] `share_recipients` table migration (recommended over an emails column - normalized, queryable, indexable): `id` uuidv7 PK, `share_id` uuid FK -> shares, `email` text (normalized lowercase/trim), `created_at` timestamptz, unique `share_recipients_share_id_email_idx` (one row per email per share). Register in `schema.ts`. The `shares.mode` column already exists from 3.2 (`restricted | open`, restricted default).
- [x] Sharing service: `setShareRecipients(shareId, emails[])` / `listShareRecipients(shareId)` in `src/lib/server/sharing/`; an `isAuthorizedReader(share, email)` predicate - in `restricted` mode true iff the normalized email is in `share_recipients`; in `open` mode true for any verified email. Email normalization shared with 3.3's identity normalization (one helper).
- [x] Wire the mode into 3.3's verification gate WITHOUT a leak: `?/request-verification` checks `isAuthorizedReader` AFTER computing the response shape, so a restricted unlisted email and an authorized email return the IDENTICAL neutral "check your email" confirmation (NFR9). The magic link is only actually SENT to an authorized email; an unlisted email gets the same neutral confirmation but no email and no token. The refusal is invisible - never a distinct "not authorized" message, never a different status code, never a timing tell (do the same work shape on both paths).
- [x] Open mode (FR19): any holder of the link who verifies their email may read; their identity is recorded in `access_records` (3.3 lifecycle) exactly as restricted readers are. Open mode has no recipient list - `isAuthorizedReader` short-circuits true on a verified email.
- [x] Workspace share UI (3.2's `(workspace)/reports/[id]/share` + ShareDialog): a mode selector (restricted / open-with-verification) and, in restricted mode, a recipient-email list editor (add/remove). Author-realm, under `workspaceGuard`. Persist via a `?/set-mode` / `?/set-recipients` action.
- [x] Tests: restricted mode - a listed email is sent a link, an unlisted email gets the SAME neutral confirmation with no link sent and no token created (the enumeration-safety assertion: identical response body/status, and a timing-shape check or a same-work-path assertion); open mode - any verified email reads and is recorded; `isAuthorizedReader` truth table for both modes; recipient normalization (case/whitespace) dedupes; set-recipients/set-mode actions persist; switching restricted -> open and back behaves.

## Dev Notes

- Authority: FR19 (restricted recipient list vs open-with-verification per share), FR22 (identity recorded), NFR9 (refusal reveals nothing about whether an email is known - enumeration-safety). Architecture: the sharing domain (`server/sharing`), the two-realm reader access from 3.3. Scope `share` (+ a `db` migration shipped with it).
- DEPENDS ON 3.3 (the verification gate, the neutral-confirmation response, `access_records`/`reader_identities`, the email-normalization helper). Implement 3.3 first. Builds directly on 3.2's `shares.mode` column.
- Seam reuse: 3.3's `?/request-verification` action and its neutral confirmation are the hook point - this story inserts `isAuthorizedReader` BEHIND the neutral response, not in front of it. 3.2's `getShareByToken` resolves the share. Email normalization is the single helper 3.3 introduced for `reader_identities.email`.
- The enumeration-safety contract is the load-bearing part: the response to an unlisted restricted email MUST be byte-indistinguishable from the response to a listed one (same status, same body, same headers), and the work performed should not branch in a timing-observable way. This mirrors the 1.4 uniform-login-failure pattern (every attempt runs the same shape of work, returns the same `fail`). Document the chosen anti-timing approach in Completion Notes.
- Recommended `share_recipients` table over an `emails` jsonb/array column on `shares`: normalized rows index cleanly, dedupe via the unique constraint, and scale past a handful of recipients without rewriting a blob. If the dev picks the column instead, justify it and keep normalization+dedupe.
- AMBIGUITY for the product owner (do not invent): FR19 does not specify whether, in restricted mode, an authorized reader may FORWARD their working magic link to an unlisted third party who then reads within the link's validity (the verification binds the session to the clicking browser, but the magic link itself is bearer until clicked). Recommend binding the magic-link token to the requested email so a forwarded raw link verifies only that email - confirm before implementing.

### Completion Notes

- **`share_recipients` schema (migration 0008)**: `id` uuidv7 PK, `share_id` uuid NOT NULL FK -> shares ON DELETE CASCADE, `email` text (normalized lowercase/trim before insert), `created_at` timestamptz default now. Unique index `share_recipients_share_id_email_idx` on (share_id, email) - one row per email per share, the dedup guard. A restricted share's allow-list; an open share simply has no rows (and even if rows exist, `isAuthorizedReader` ignores them while mode is `open`). CASCADE because an allow-list is meaningless without its share.
- **Sharing service signatures** (`src/lib/server/sharing/recipients.ts`): `setShareRecipients(shareId: string, emails: string[]): Promise<void>` (normalize + dedup + drop malformed, then delete-then-insert in one transaction so the list is exactly the submitted set); `listShareRecipients(shareId: string): Promise<string[]>` (normalized emails, ascending); `isAuthorizedReader(share: { id; mode }, normalizedEmail: string): Promise<boolean>` (open -> always true with NO DB read; restricted -> true iff the normalized email has a row). Plus `setShareMode(shareId, mode): Promise<number>` in `shares.ts` (returns rows updated; 0 = unknown share -> 404) to flip a share restricted<->open without touching its list. Email normalization is the SAME 3.3 boundary helper (`reader/email.ts` `normalizeEmail`/`isPlausibleEmail`), reused, not reimplemented - so a `Foo@X.com` list entry authorizes a `foo@x.com` request.
- **Gate wiring (FR19, behind the neutral return)**: `requestVerification` (`reader/gate.ts`) now takes the resolved share and calls `isAuthorizedReader(share, email)` FIRST. Off-list (restricted, not on the list) -> returns the same `void` immediately, no token, no mail. On-list / open -> the unchanged 3.3 path (dedup, issue, send). The route maps the void to the neutral `{state:'sent'}` identically on both paths. No route/response-shape change: the only branch is inside the service, behind the neutral return.
- **Timing-equivalence (NFR9, the parked 3.4 constant-work constraint - HOW)**: the magic-link send is FIRE-AND-FORGET on the authorized path (`void sendMail(...).catch(log)`), so the function returns WITHOUT awaiting the SMTP round-trip. The slow, attacker-observable, network-dependent cost (SMTP latency, and SMTP reachability) is therefore OFF the response path on BOTH the on-list and off-list paths. What remains is fast, bounded, local DB work (the off-list path: one allow-list read; the on-list path: allow-list read + dedup read + token insert). The two paths are NOT strictly identical work, so the claim is NOT "constant-work / same timing class": it is that they are indistinguishable in practice over the network - the SMTP round-trip (the only network-scale separator) is removed from both paths, the residual on-list-vs-off-list delta is sub-millisecond local DB work below the network noise floor, the same residual band NFR9 already accepts from the 3.3 dedup-suppressed-vs-sent split. A dummy-write constant-time mitigation is not required for V1 (the residual is not, on its own, an observable separator). Removing the SMTP variable is what closes the timing oracle that a synchronous send would have opened (an off-list short-circuit returning in microseconds vs an on-list path waiting hundreds of ms on the relay). The fire-and-forget rejection is caught and logged at `warn` (NFR16) so it is never an unhandled rejection and never reaches the reader. **Tests proving it**: gate.test.ts "timing: neither path awaits SMTP - returns before sendMail settles" (a send Promise that never resolves does not hang the call - if the response awaited the send this would time out); "enumeration-safety: off-list and on-list return the IDENTICAL void result"; "a fire-and-forget send failure is logged, never thrown to the caller". The e2e additionally asserts the on-list and off-list `request-verification` responses are deep-equal (`expect(onResult).toEqual(offResult)`: same 200 status, same `success` type) while only the on-list path created a `verification_tokens` row.
- **Forwarded-magic-link restricted bypass is CLOSED (confirmed)**: the verification token is email-and-share bound (3.3, `consumeVerificationToken` matches on the token hash AND verifies the bound email at consume). A restricted reader cannot forward their raw magic link to an unlisted third party to verify that third party: the link verifies only the address it was issued to. And an off-list address never gets a token issued in the first place (the allow-list check precedes issuance). Two independent barriers. No new code needed beyond the allow-list gate; the binding was already in place and is left intact.
- **Enumeration-safety on all paths (preserved)**: off-list restricted -> neutral `{state:'sent'}`, no token, no mail. On-list restricted / open -> neutral `{state:'sent'}`, token + (fire-and-forget) mail. Malformed email -> `{state:'invalid'}` (a form-shape signal, not an auth signal - unchanged from 3.3). Closed/unknown share -> the one neutral 404. Dedup-suppressed -> the same neutral `{state:'sent'}`. Throttled -> `{state:'throttled'}` (rate-limit signal, not auth). Every path that an attacker can drive with a plausible email returns the byte-identical `sent`, and timing no longer separates them.
- **Workspace UI**: the create form gained a recipients textarea shown only when `restricted` is selected (and an "open: anyone with the link" note for `open`); an initial list can be set in the create gesture. Each existing share row gained a "Switch to open/restricted" toggle (`?/set-mode`) and, for restricted shares, an inline recipient-list editor (`?/set-recipients`) pre-filled with the current list. All under `workspaceGuard` (author realm). The list editor accepts newline/comma/semicolon-separated emails, normalized and deduped server-side.
- **For 3.5 (revocation / leak-free, the final Epic 3 story)**: removing an email from a restricted share's allow-list stops FUTURE verifications for that email, but does NOT by itself end an already-verified reader session - 3.5's `destroyReaderSessionsForShare(shareId)` (the 3.3 revoke seam) is the lever to sweep live sessions when a share is revoked; consider whether removing a single recipient should also sweep that identity's sessions for the share (a per-recipient revoke), which would need a session lookup by (share, identity). The neutral 404 (`serveNeutralClosed`) is still the single closed-share exit; 3.5 themes its body. `share_recipients` rows CASCADE on share delete, so no orphan cleanup is owed.

### QA iteration 1 (2026-06-12)

- **Fix 1 (Medium) - unbounded recipient list**: `setShareRecipients` now caps the effective list at `MAX_SHARE_RECIPIENTS = 500` (a single distribution-list ceiling, well past realistic use while bounding the one-transaction insert). The cap is counted AFTER normalization+dedup (the real row count), and an over-cap list throws an `AppError(422, /problems/share-recipients-limit)` with "A share allow-list is limited to 500 recipients." BEFORE any write. Enforced in the service so it holds for every caller; the `set-recipients` route action wraps the call in a try/catch mapping the AppError to `fail(422, ...)`, and the `create-share` action's existing AppError catch covers the initial-list path. Tests: a list at the cap succeeds (500 rows inserted), a list over the cap rejects with 422 and writes nothing, a MAX+1 raw list that dedups to MAX succeeds (proves post-normalization counting), plus the route-level 422 fail.
- **Fix 2 (Low) - set-recipients 500 on stale/garbage shareId**: `setShareRecipients` now verifies the share exists before writing (a `select id from shares where id = ?` after a `UUID_PATTERN` shape check mirroring `reports.ts`/`skeletons.ts`), throwing `AppError(404, /problems/share-not-found)` for an unknown or malformed id - so the FK-violation/cast-error 500 path is gone. The route action returns the clean 404 via its AppError catch. Tests: unknown shareId rejects 404 and writes nothing, a non-UUID id rejects with an AppError (no DB cast), and the route action returns `{status:404}` (not 500) when the service rejects.
- **Fix 3 (Low, doc accuracy) - softened the timing claim**: the prior wording overstated the two paths as "same timing class / constant-work". Corrected here, in the Completion Notes timing bullet above, and in `reader/gate.ts`'s doc comment to the accurate claim: the paths are NOT strictly identical work (off-list = one allow-list read; on-list = allow-list read + dedup read + token insert), but they are indistinguishable in practice over the network - the SMTP round-trip (the only network-scale separator) is removed from both paths via fire-and-forget, and the residual on-list-vs-off-list delta is sub-millisecond local DB work below the network noise floor, the same residual band NFR9 accepts from 3.3's dedup-suppressed-vs-sent split. No behavior change; a dummy-write constant-time mitigation is explicitly not required for V1.
