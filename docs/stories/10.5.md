# Story 10.5: Data Binding from the Editor

## Status

Review

## Story

As the author,
I want to bind, rebind, and remap data from inside the editor at the block I am editing,
So that turning uploaded data into a chart or table never sends me to a separate screen.

## Acceptance Criteria

**Given** a bindable block (table / chart / kpi) selected in the editor
**When** the author binds it to an uploaded data set
**Then** the editor calls the EXISTING `bind` action and binding service (no re-implementation), the binding persists in the document through validate-on-write, and the preview re-renders the bound block (FR12)

**Given** a fresh data set injected
**When** the author rebinds
**Then** the existing `rebind` action runs and the per-block diagnostic chips (green / amber / red) and the summary surface at the affected blocks exactly as today (FR14), the preview reflecting the re-resolved data

**Given** a binding diagnostic naming a drifted or missing field
**When** the author acts on it
**Then** the remap affordance (the existing `remap` action: point an expected field at an available one) is reachable from the diagnostic at the block, and the block re-resolves after remap (FR15) - the editor surfaces the existing diagnostics, it does not invent a new binding model

**Given** a bind / rebind / remap that would exceed the document size budget
**When** written
**Then** it is rejected at the single write chokepoint (`MAX_DOCUMENT_BYTES`, 413) like any other oversized write - the editor inherits the budget guard

## Tasks / Subtasks

- [x] **Surface binding at the bindable block, reusing the existing engine (ui).** The bind / refill panels already mount on the edit route and call the EXISTING `?/bind` / `?/rebind` / `?/remap` actions (which call `bindBlock` / `rebindReport` / `remapField`). This story brings the diagnostics + the remap affordance INTO the editor at the block: `BlockEditor` (the per-block chrome) renders, for a bindable block, the bound-vs-static state, and - when the last rebind produced a drift for that block - the existing `BindingChip` plus the inline `DiagnosticPanel` with a `?/remap` form. No new binding engine, no new diagnostics: the same `BlockDiagnostic` shape the refill panel uses, threaded down by block id.
- [x] **Bound-vs-static state shown clearly (ui).** A bindable block whose `binding.dataSetId` is resolved shows "Bound to data set" (with the FR16 `dataAsOf` freshness instant when present); otherwise "Static data". The static shape (10.3 / 10.4 authored rows / series / items) and the bound shape coexist per the schema's existing `requireStaticDataOrBinding` rule - no change to the binding / static schema contract.
- [x] **Bind from the editor re-renders the preview bound (ui, FR12).** A successful bind reseeds the editor's in-edit working copy from the re-resolved document the action returns, so the authoritative live preview (the pure `$lib/render` tier) re-renders the bound block without a reload.
- [x] **Rebind surfaces diagnostics at the affected blocks (ui, FR14).** A rebind returns the per-block diagnostics + the summary (unchanged); the editor stores them and threads each block's diagnostic to its `BlockEditor`, so the green / amber / red chip appears at the block (and the refill panel summary, exactly as today).
- [x] **Remap from the block re-resolves it (ui, FR15).** The inline remap at the block posts the existing `?/remap` action (point an expected field at an available one); on success the block re-resolves, the editor reseeds the working copy, and the now-green block's diagnostic is dropped so its chip clears.
- [x] **Concurrency-token reconciliation after a binding action (the key correctness point).** A bind / rebind / remap is a server mutation that advances the report's `updatedAt`. Each action now returns the re-resolved `document` alongside its new timestamp, and the editor's `reconcileBinding` reseeds the working copy and advances `expectedUpdatedAt` from THAT result - the same self-contained reconciliation publish / unpublish use, plus the document reseed. The binding panels no longer `invalidateAll` (which would clobber in-flight edits and leave the token stale); they report their result UP to the editor. So a subsequent document save asserts the post-binding state instead of spuriously 409-ing.
- [x] **Budget guard inherited (ops).** The binding write goes through the same `updateReportDocument` chokepoint, so an oversized bind / rebind / remap is the 413 (`MAX_DOCUMENT_BYTES`) like any other write - no new path, no new guard.
- [x] **Accessibility (ui, NFR15 / WCAG 2.5.3).** The binding-state row carries an accessible label; the chip is a real button with `aria-pressed`; the inline remap has labelled controls. The shared `BindingChip` amber state, composited over the block-card background, dropped to 4.46:1 contrast inside the card; the binding-state row gives the chips an opaque state surface so they are AA-clean (the refill panel's own chips are untouched).
- [x] **Reader-budget isolation (ops).** Everything is workspace-only behind the author cookie: `pnpm reader:budget` is byte-identical at 75.9 KB / 200 KB, and `pnpm schema:export` is unchanged (no schema change). The `BlockDiagnostic` import is type-only and erases at build, so no `$lib/server` code enters the reader closure; the 10.1 reader-purity boundary (scoped to `src/lib/render/**`) is not touched.
- [x] **Tests.**
  - [x] Server actions (`page.server.test.ts`): the `bind` / `rebind` / `remap` actions return the re-resolved `document` alongside their timestamp (the reconciliation payload the editor needs).
  - [x] Component (`block-editor.svelte.test.ts`): the bound-vs-static state renders (bound badge + `dataAsOf`, or static), a non-bindable block shows no binding-state row, a drift diagnostic surfaces the chip + opens the inline `?/remap` form naming the expected field and its closest match, and a clean block shows no chip.
  - [x] Component (`data-binding.svelte.test.ts`): on a synthetic bind / rebind result the editor advances its token (the displayed saved-at moves off the loaded timestamp) and reseeds the working copy (the preview renders the bound rows); a rebind drift surfaces at the block. `$app/forms` is mocked so the enhance result callback runs without a live server.
  - [x] e2e (`editor-data-binding.e2e.ts`, desktop): seed a bound table, upload data sets, bind from the editor, see it render bound in the preview, refill with a drifted set, remap from the block, save, reload, the binding persists; a save AFTER a bind succeeds (200, not 409) proving the token reconciliation; axe-clean.

## Dev Notes

### What EXISTED vs what was WIRED into the editor

The binding ENGINE and most of the UI already existed and are reused unchanged:

- **Services** (`src/lib/server/ingestion/`): `bindBlock`, `rebindReport`, `remapField`, and the diagnostics (`diagnoseDocument` / `diagnoseBlock`, the `closestField` / `levenshtein` hint, the green/amber/red `BindingState`, the `BlockDiagnostic` / `BindingSummary` shapes). Untouched.
- **Actions** (`+page.server.ts`): the `bind` / `rebind` / `remap` form actions already called those services, owner-scoped, through validate-on-write. The ONLY change here: each now returns the re-resolved `report.document` alongside its existing timestamp, for the editor's token reconciliation (see below). The `rebind` already returned the diagnostics + summary.
- **UI components** (`$lib/ui`): `BindingChip`, `DiagnosticPanel`, `BindingSummary` reused verbatim. `BlockBinder` / `RefillPanel` (the bind / refill panels) kept; their success handlers changed from `invalidateAll` to reporting the result UP.

What was WIRED in by this story:

- **The diagnostics + remap AT the block.** `BlockEditor` now renders, for a bindable block, the bound-vs-static badge and (when the last rebind drifted that block) the `BindingChip` + the inline `DiagnosticPanel` with a `?/remap` form. `ReportEditor` holds the last rebind's diagnostics, indexes them by block id (`diagnosticsByBlock`, drifted/unresolved only), and threads each block's diagnostic + the rebind source's available fields + data set id + the `onRemapped` callback down through `SectionEditor` -> `BlockEditor`.
- **The bound-vs-static state.** Derived in `BlockEditor` from `block.binding?.dataSetId` (bound) vs absent (static), plus the `dataAsOf` instant - so the author always knows where a bindable block's values come from.

### The concurrency-token reconciliation (the key correctness point)

A bind / rebind / remap mutates the report through the same validate-on-write path a save uses, so it advances the row's `updatedAt`. The 10.1 editor seeds `expectedUpdatedAt` from the loaded row and advances it only on a successful save (and on publish / unpublish, self-contained from the action result). Before this story the binding panels were siblings that called the actions and then `invalidateAll`; the editor's `expectedUpdatedAt` was never advanced, so the FIRST document save after any bind would assert the stale pre-bind timestamp and 409 spuriously (and `invalidateAll` would also clobber in-flight edits).

The fix mirrors publish / unpublish exactly, plus a document reseed (a bind changes the document, not just the timestamp): the bind / rebind / remap actions return the re-resolved `document` + the new `updatedAt`, the binding panels report that UP via `onBound` / `onRebound` / `onRemapped`, and `ReportEditor.reconcileBinding` reseeds `doc` (deep-copied, never aliasing the payload), sets `savedAt` and advances `expectedUpdatedAt` to the new timestamp, clears `dirty` / `conflict`, and drops any pending save (the binding write already carried the latest document forward). So the next document save asserts the post-binding state and lands cleanly. The e2e proves it end to end (a save after a bind returns 200, and the title edit persists), and a component test proves the token advances and the working copy reseeds on a synthetic action result.

The 200 ms `settledSnapshot` debounce means the preview / bindable-block list re-settle ~200 ms after the reseed (the same debounce every edit rides); block ids are stable across the settle, so the diagnostics land on the right block.

### Why type-only `BlockDiagnostic` imports are safe

`BlockEditor` / `SectionEditor` / `ReportEditor` import `BlockDiagnostic` from `$lib/server/ingestion` as a TYPE only (the established pattern `RefillPanel` already used). Type imports erase at build, so no server code enters any chunk. These are edit-route components (workspace-only, behind the author cookie); the reader path (`/r/[token]`) never imports the edit route. `pnpm reader:budget` confirms the reader closure is byte-identical at 75.9 KB. The 10.1 reader-purity ESLint rule is scoped to `src/lib/render/**` and is not in play here.

### Accessibility note - the amber chip contrast

The shared `BindingChip` composites its translucent state background over whatever element sits behind it. Inside the block card that element is `--color-stone`, where the amber chip's 12%-over-stone background dropped the amber text to 4.46:1 (just under the WCAG AA 4.5:1 floor) - a marginal pre-existing contrast the refill panel's own axe scan never covered (it sits outside `.editor-form`). The block-level binding-state row gives its chips an OPAQUE state surface (the state colour mixed with white, not transparent) so the contrast is deterministic and AA-clean regardless of the card background; the override is scoped to `.binding-state`, so the refill panel's chips are untouched. The new editor binding surface is axe-clean (desktop e2e, scoped to `.editor-form`).

### Seams for 10.6 and 10.7

- **10.6 (audience-aware preview, tags, speaker notes):** untouched. The binding surface sits inside the per-block `BlockEditor` chrome alongside the existing `AudiencePicker`; 10.6 adds the level-switched preview and the section speaker notes. The bound-vs-static state and the binding diagnostics are orthogonal to audience filtering.
- **10.7 (autosave / undo / redo / conflict / publish):** a binding action is a server mutation that advances `updatedAt`. `reconcileBinding` already advances `expectedUpdatedAt` and drops the pending save, so it composes with the 10.7 autosave debounce and the conflict path (a binding reseed clears `conflict`, since the action wrote through the same validated chokepoint and the editor now holds the latest state). For undo / redo, note that a binding action REPLACES the working copy from the server (a reseed), so it is a history checkpoint, not an in-tab mutation undo / redo should step past blindly - 10.7 should treat a binding reseed as a new baseline, the same way it treats a publish / unpublish reconcile.

## Dev Agent Record

### Debug Log

- The bind / rebind / remap actions return shapes were `{ boundAt }` / `{ reboundAt, diagnostics, summary, rebound }` / `{ remappedAt }`; added `document: report.document` to each (the `rebind` reads `result.report.document`). The existing action tests asserted the return with `toEqual` (bind / remap) and `toMatchObject` (rebind); updated the two `toEqual` assertions to include `document` and added the `document` field to the rebind `toMatchObject`, so the reconciliation payload is pinned.
- `reconcileBinding` reassigns `doc` (the reseed). `doc` was previously only ever MUTATED in place, never reassigned, so the reassignment newly tripped `state_referenced_locally` on the init-time `let settledSnapshot = $state($state.snapshot(doc))`. Added a `// svelte-ignore state_referenced_locally` with the WHY (the init read is intentionally the loaded value; the settle `$effect` re-captures on every doc change including a reseed). `pnpm check` is 0 errors / 0 warnings.
- A `BlockDiagnostic` typed `onRemapped` initially took `(savedAt, document)`; a remap re-resolves ONE block, so the now-green block's chip would linger because `bindingDiagnostics` still listed it. Threaded the `blockId` through `onRemapped` (from the remap form's `blockId` field) so `reconcileBinding`'s caller drops that block's diagnostic; both the block-level remap and the refill-panel remap pass it.
- Component-test seam: `$app/forms` `enhance` is mocked in `data-binding.svelte.test.ts` to capture each form's submit handler and let the test drive its result callback with a synthetic `ActionResult` (there is no server in the component runner). This exercises the editor's reconciliation logic - the token advance + the working-copy reseed - without a live action.
- e2e seam: data sets are uploaded BEFORE navigating to the editor so they appear in the server-loaded data-set list (the binding actions no longer `invalidateAll`, so the list is what the page loaded - matching how the binder reads it).

### QA remediation (2026-06-15)

A three-agent QA audit ran against the Review state. The findings below were fixed; one is logged as deferred debt with the rationale.

- **(HIGH, data loss) A binding action while the editor was dirty silently destroyed unsaved edits.** A bind / rebind / remap reads the SERVER's last-saved document (the services call `getReport`, not the in-memory `doc`); its result drives `reconcileBinding`, which reseeds `doc`, cancels the pending autosave and clears `dirty`. So unsaved edits in flight (a typed title, an added section the 800 ms autosave had not yet posted) were overwritten with the server-derived document, no conflict surfaced. Fixed by mirroring the publish guard: a new `bindingGuard(cancel)` in `ReportEditor` (returns false + cancels + re-arms the autosave + surfaces "Saving your latest edits..." while `dirty || saving`) is threaded to `BlockBinder` (`submitBind`), `RefillPanel` (`submitRebind` / `submitRemap`), and `BlockEditor` (`submitRemap`); each calls it before submitting. This also closes the saving-in-flight reconcile race. New component test: a bind while dirty is gated and the unsaved title survives.
- **(HIGH) `onBound` left stale per-block diagnostics.** `onRebound` / `onRemapped` mutate `bindingDiagnostics`, but `onBound` did not, so a bind after a rebind left a stale drift chip. `onBound` now clears `bindingDiagnostics` + `diagnosticDataSetId` (a bind re-resolves the block's state). New component test: bind-after-rebind clears the chip.
- **(Medium) Extracted the duplicated remap form** (the ~20-line near-copy in `BlockEditor` and `RefillPanel`) into a shared `RemapForm.svelte` (blockId / dataSetId / expectedField / suggested / fields / disabled / submit). Both call sites use it, so an a11y/label change is one edit.
- **(Medium) Collapsed the three diagnostic props into one `DiagnosticContext`** (`{ byBlock, fields, dataSetId }`, in a new co-located `editor-types.ts`). `ReportEditor` builds one derived object; `SectionEditor` is now a clean single-object pass-through.
- **(Medium) `dataAsOf` formatting** moved off the ad-hoc `.slice(0, 10)` to a new `formatUtcDate` helper (the date-portion twin of the project's `formatUtcTime`).
- **(Medium) Replaced the `as unknown` / ad-hoc payload casts** on the bind / rebind / remap results with shared `BindActionResult` / `RebindActionResult` / `RemapActionResult` types (in `editor-types.ts`), used by BOTH the action return (`satisfies ...`) AND the client cast - so an action-shape change is a compile error, not a silently skipped reconcile.
- **(Medium) `remapOpen` not reset on diagnostic change** in `BlockEditor`: a `$effect` now resets `remapOpen = false` when the `diagnostic` prop changes (a rebind replaces the diagnostic but the panel kept its prior expand state).
- **(Cheap fold-ins)** strengthened the token-advance test with a positive `toContain('11:00')` assertion; fixed the `onRemapped as never` cast in the block-editor test helper to the real 3-arg signature; prettier-fixed the `rebind` action return indentation; `boundDataSetId` / `dataAsOf` keep the `isBindable(block)` inline call (it is the schema TYPE GUARD that narrows the block union, which a precomputed boolean cannot do - a comment records this); replaced the e2e `waitForLoadState('networkidle')` before navigation with an explicit save-response wait (and dropped the now-redundant one after the remap reconcile).

### Deferred debt: binding writes bypass optimistic concurrency (cross-producer case)

NOT fixed in 10.5, recorded as a candidate for the Epic 10 solidification / a hardening story. `bindBlock` / `rebindReport` / `remapField` call `updateReportDocument` WITHOUT `expectedUpdatedAt`, so a binding action can silently stomp a CONCURRENT edit from ANOTHER producer (a second tab, an MCP / API push) made between the action's `getReport` and its write. This is PRE-EXISTING (10.5 did not introduce it) and a medium-effort change (thread the token into the binding chokepoint so all write paths share one concurrency invariant). It is distinct from the data-loss finding above: that guard addresses the EDITOR's OWN unsaved edits (a same-tab race); this debt is the separate cross-producer case the binding services do not yet assert against.
