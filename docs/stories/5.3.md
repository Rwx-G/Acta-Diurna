# Story 5.3: LLM Endpoint Configuration

Status: Review

## Story

As an operator,
I want to configure an OpenAI-compatible LLM endpoint with explicit opt-in,
So that AI generation is available without data leaving my control unknowingly.

## Acceptance Criteria

**Given** instance settings
**When** I configure endpoint, model, and key (env or settings)
**Then** no LLM call is made anywhere before explicit opt-in, and the endpoint can be any OpenAI-compatible URL - cloud or local (FR33, NFR18)

**Given** no endpoint configured or opt-in absent
**When** generation is requested
**Then** a problem-details error states that AI generation is disabled and how an operator enables it

## Tasks / Subtasks

- [x] NO NEW DEPENDENCY: the LLM connector is built over the platform `fetch` to the configured OpenAI-compatible endpoint (Chat Completions shape). No OpenAI SDK, no Anthropic SDK, no HTTP client - `fetch` only (Node 22 has it native). State this explicitly in Completion Notes (the Epic 5 single approved dependency is `@modelcontextprotocol/sdk` from 5.1; 5.3/5.4 add none).
- [x] Extend the 1.3 Zod env validation (`src/lib/server/env.ts`) with an OPTIONAL, ALL-OR-NOTHING LLM block, shape-validated at boot exactly like the 3.1 SMTP block: `LLM_BASE_URL` (any OpenAI-compatible URL - cloud or local, validated as a URL), `LLM_API_KEY` (the bearer key for the endpoint), `LLM_MODEL` (the model id). The whole block is OPTIONAL (the app MUST boot without it - 3.1's pattern), but ALL-OR-NOTHING when present (a `superRefine`: if any `LLM_*` is set, require `LLM_BASE_URL` + `LLM_MODEL` together; `LLM_API_KEY` may be optional for an unauthenticated local endpoint like a localhost Ollama/llama.cpp - decide and document, recommend optional-key for local-endpoint parity). Validate SHAPE at boot, fail-fast on a malformed config (non-URL base, contradictory block); do NOT make boot depend on a live LLM handshake (a misconfigured-but-shaped endpoint surfaces at GENERATION time, not boot - the 3.1 boot-vs-send split applied to LLM). Add the `LLM_*` keys to `.env.example` with safe placeholders (NEVER read/write any other `.env*` variant).
- [x] Secret discipline (NFR8, the 3.1 SMTP_PASSWORD pattern): extend the 1.3 pino redaction list to `LLM_API_KEY` (`llmApiKey`/`llm_api_key`/`LLM_API_KEY`). The key is NEVER logged, NEVER placed in a client-facing `detail`, NEVER returned by any settings `load` (the 3.1 "password never read by load" rule - the settings surface reports whether the LLM is configured, the model, and the base URL, but never the key).
- [x] Explicit OPT-IN gate (the load-bearing AC: "no LLM call is made anywhere before explicit opt-in"): a configured endpoint is necessary but NOT sufficient - generation also requires an explicit opt-in flag, so an operator who sets the env still consciously enables AI. Decide and document the opt-in storage: a settings flag (an `instance_settings`-style row or a dedicated `LLM_ENABLED`/opt-in env) - recommend an explicit `AI_GENERATION_ENABLED` boolean (env or a settings row) SEPARATE from the connection config, so "configured" and "enabled" are two distinct gates; the connector refuses to issue ANY `fetch` unless BOTH (configured AND opted-in) hold. This is the FR33/NFR18 "opt-in per instance, no call without explicit opt-in" contract.
- [x] `src/lib/server/ai/` domain (mirrors the 3.1 `server/mail/` shape): a `connector.ts` building the request to `${LLM_BASE_URL}/chat/completions` with the bearer key, the configured model, and the caller's messages, over `fetch`; a typed result; and a single `isAiEnabled()` / `assertAiEnabled()` guard that checks BOTH configured + opted-in and throws the disabled `AppError` otherwise. The connector is the ONE place a `fetch` to the LLM happens - 5.4 calls it, never `fetch`es directly. Talks ONLY to the operator-configured endpoint (no phone-home, the 3.1 posture): no hardcoded provider URL, no default cloud endpoint.
- [x] Disabled-state `AppError` (the second AC): when generation is requested with no endpoint configured OR opt-in absent, throw a typed `AppError` (`/problems/ai-generation-disabled`, recommend 503 - the capability is unavailable, mirroring the 3.1 `/problems/mail-not-configured` 503) whose `detail` states AI generation is disabled and HOW an operator enables it (set the `LLM_*` env + flip the opt-in), WITHOUT leaking config internals. This is the SAME problem-details model (D9) every surface returns; the REST/MCP/workspace generation triggers (5.4) surface it unchanged.
- [x] Generation failure surfacing (NFR16-style, no silent drop; groundwork the 5.4 third AC consumes): a transport/endpoint failure from the connector (`fetch` reject, non-2xx from the endpoint, an unreachable base URL) becomes a typed `AppError` (`/problems/ai-generation-failed`, recommend 502 - an upstream/bad-gateway failure, mirroring the 3.1 `/problems/mail-delivery-failed` 502) logged server-side at `warn` via pino (the LLM endpoint is a degradable external dependency, like SMTP), with the RAW upstream error (which can carry the endpoint host or response body) kept in the SERVER log ONLY and a sanitized `detail` (no key, no host, no raw body) client-facing.
- [x] Settings surface (FR33): the `(workspace)/settings` page (author-realm, under `workspaceGuard`) reports whether the LLM is configured (base URL + model shown, key NEVER) and whether generation is opted-in, and - IF the AC's "or settings" path is taken (see ambiguity) - lets the operator flip the opt-in and optionally a connectivity test (a minimal probe call through the connector, surfacing success or the sanitized failure as a green/red chip, the 3.1 test-send pattern). Decide whether config is env-only or also editable in settings (see ambiguity).
- [x] Tests: env validation accepts a well-formed `LLM_*` block and rejects a malformed one (non-URL base, half-configured block); the app boots with NO `LLM_*` block (optional); `isAiEnabled()` is false when unconfigured OR not opted-in, true only when BOTH hold; `assertAiEnabled()` throws the `/problems/ai-generation-disabled` 503 with the actionable detail when disabled; the connector issues NO `fetch` when disabled (assert the `fetch` mock is never called - the "no call before opt-in" AC, proven, not asserted by inspection); a configured + opted-in connector calls `fetch` to `${LLM_BASE_URL}/chat/completions` with the bearer key + model and returns the parsed result; an endpoint failure (non-2xx / reject) throws `/problems/ai-generation-failed` 502 and pino does NOT emit the key; the settings `load` never returns the key.

## Dev Agent Record

### Debug Log

- Two-gate design (the load-bearing AC): the connector guards every call with TWO distinct, deliberately separate gates. (1) CONFIGURED - `aiConfig()` reads `LLM_BASE_URL` + `LLM_MODEL` from the validated env (the all-or-nothing refine guarantees they come together; `LLM_API_KEY` optional). (2) OPTED-IN - `AI_GENERATION_ENABLED` is true. `assertAiEnabled()` checks BOTH and throws `/problems/ai-generation-disabled` (503) when either is missing, and `chatComplete` calls it as the very first statement, BEFORE constructing any `fetch`. So setting the env alone never enables an outbound call. Proven by test, not inspection: `connector.test.ts` has two tests asserting `fetchMock` is never called (`.not.toHaveBeenCalled()`) when unconfigured and when configured-but-not-opted-in.
- Boot-vs-call split (the 3.1 SMTP pattern applied to the LLM): `env.ts` validates the LLM block SHAPE at boot - a non-`http(s)` `LLM_BASE_URL` and a half-configured block (e.g. `LLM_API_KEY` set without `LLM_BASE_URL`/`LLM_MODEL`) fail fast and name the variable. It opens NO connection at boot. An unreachable-but-shaped endpoint surfaces only at generation time as `/problems/ai-generation-failed` (502). The container always boots so the trivial-deploy promise holds.
- All-or-nothing refine placement: the LLM refine block was first written nested inside the `if (anySmtp)` SMTP block; moved to the superRefine top level so an LLM-configured-but-no-SMTP instance is validated. The env LLM tests deliberately set no SMTP, which is what caught the placement.
- `AI_GENERATION_ENABLED` is a `z.enum(['true','false']).default('false').transform(v => v === 'true')` so the env carries a string but the validated `Env` exposes a boolean; default false means configuration alone never opts in.
- Redaction: `LLM_API_KEY` added to the pino redaction list in `logger.ts` (`llmApiKey`/`llm_api_key`/`LLM_API_KEY`), the SMTP_PASSWORD treatment. The `generationFailed` mapper logs only `{ requestId, err }` at `warn` and returns a fixed client detail that never carries the host, the response body, or the key. `connector.test.ts` asserts the thrown detail excludes the key and the host, and the load test asserts the settings `load` payload never contains the key.
- Settings probe: the `?/test-ai` action makes a REAL outbound call, so it is gated by `chatComplete`'s `assertAiEnabled()` (a disabled connector returns the 503 disabled detail, no call) and is an explicit operator action shown only when enabled. The probe message carries only the trimmed reply, never the host or key.
- env.ts was hand-edited with a node script for exact tab indentation, then `prettier --write` normalized it; the regex `//` inside `LLM_BASE_URL` needed `\/\/` escaping (a `//` literal started a line comment and broke the parse - caught by `pnpm check`).
- Gates (final): `pnpm lint` clean (prettier + eslint); `pnpm check` 1103 files, 0 errors, 0 warnings; `pnpm test` 972 unit tests passed (94 files); `pnpm build` adapter-node done; `pnpm reader:budget` 68.9 KB < 200 KB (unchanged).
- Client-bundle isolation verified empirically after build: `grep -rl "chat/completions|chatComplete|ai-generation" .svelte-kit/output/client` = 0; the connector resolves only in `.svelte-kit/output/server/entries/pages/(workspace)/settings/_page.server.ts.js`. The `$lib/server/` boundary keeps it server-only.
- `pnpm test:e2e` (Docker stack up): 39 passed, 14 skipped (pre-existing data-dependent / mobile specs from prior epics, unrelated to this story). No AI e2e was added: a real LLM call needs a live endpoint absent from CI (and the no-phone-home posture argues against one); the disabled-path and the status panel are fully covered by mock-based unit tests, and 5.4 exercises the real call.

### Completion Notes

- **NO new dependency.** The connector is built over the platform `fetch` (Node 22 native) - no OpenAI SDK, no Anthropic SDK, no HTTP client. The Epic 5 single approved dependency remains `@modelcontextprotocol/sdk` (5.1); 5.3 adds none.
- **Ambiguities resolved (as recommended in Dev Notes):** (a) OpenAI-compatible Chat Completions ONLY - an operator points `LLM_BASE_URL` at OpenAI, a local runtime, or an Anthropic-compatible proxy; no native Anthropic shape. (b) Config is ENV-ONLY (the connection secrets stay in the operator's env, never persisted to the DB); the opt-in is also env (`AI_GENERATION_ENABLED`) for a single source of truth and trivial-deploy parity - no DB settings table. (c) One instance-wide opt-in for V1. (d) `LLM_API_KEY` OPTIONAL so an unauthenticated local endpoint (Ollama, llama.cpp) works without a bearer token.
- **Env block:** `LLM_BASE_URL` (http(s) URL shape), `LLM_API_KEY` (optional, redacted), `LLM_MODEL`, all-or-nothing (`LLM_BASE_URL` + `LLM_MODEL` required together when any `LLM_*` is set), plus the SEPARATE opt-in `AI_GENERATION_ENABLED` (boolean, default false). Shape-validated at boot, never reachability-tested.
- **Connector signature (for 5.4):** `chatComplete(messages: ChatMessage[], options?: { temperature?, timeoutMs?, requestId? }): Promise<{ content: string; model?: string }>` from `$lib/server/ai/connector`. It asserts BOTH gates first (503 `/problems/ai-generation-disabled` when disabled, BEFORE any fetch), POSTs the OpenAI Chat Completions shape (`{ model, messages, temperature? }`) to `${LLM_BASE_URL}/chat/completions` with a `Bearer` key when set (omitted otherwise), a 60s `AbortController` timeout, and returns the first choice's message content. A transport/HTTP/abort/parse failure throws `/problems/ai-generation-failed` (502) with a redacted detail; the full error is logged server-side at `warn`. `isAiEnabled()` and `assertAiEnabled()` are exported for callers that want to gate UI or fail early. 5.4 calls `chatComplete`, never `fetch`es directly, and catches the `AppError` to surface it (the disabled 503 and the failed 502 flow through `problemResponse`/`fail` unchanged on every surface - REST, MCP, workspace).
- **Failure -> status mapping:** disabled (unconfigured OR not opted-in) -> `/problems/ai-generation-disabled` 503 with an actionable detail (set `LLM_BASE_URL`/`LLM_MODEL`, set `AI_GENERATION_ENABLED=true`, restart). Transport/HTTP/timeout/parse -> `/problems/ai-generation-failed` 502 with a host/body/key-redacted detail.
- **Settings panel (FR33):** three states - "AI generation not configured" (env names shown inline as code), "Configured, disabled" (model + base URL shown, hint to set `AI_GENERATION_ENABLED=true`), "Enabled" (model + base URL + a "Test connection" probe). The API key is never read by `load` and never rendered.
- **Reader budget:** the connector is server-only (`$lib/server/ai/`), absent from the client bundle, reader budget unchanged at 68.9 KB / 200 KB.
