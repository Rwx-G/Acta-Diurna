# Story 5.3: LLM Endpoint Configuration

Status: Approved

## Story

As an operator,
I want to configure an OpenAI-compatible LLM endpoint with explicit opt-in,
So that AI generation is available without data leaving my control unknowingly.

## Acceptance Criteria

**Given** instance settings
**When** I configure endpoint, model, and key (env or settings)
**Then** no LLM call is made anywhere before explicit opt-in, and the endpoint can be any OpenAI-compatible URL - cloud or local (FR33, NFR18)

**Given** no endpoint configured or opt-in absent
**When** generation is requested
**Then** a problem-details error states that AI generation is disabled and how an operator enables it

## Tasks / Subtasks

- [ ] NO NEW DEPENDENCY: the LLM connector is built over the platform `fetch` to the configured OpenAI-compatible endpoint (Chat Completions shape). No OpenAI SDK, no Anthropic SDK, no HTTP client - `fetch` only (Node 22 has it native). State this explicitly in Completion Notes (the Epic 5 single approved dependency is `@modelcontextprotocol/sdk` from 5.1; 5.3/5.4 add none).
- [ ] Extend the 1.3 Zod env validation (`src/lib/server/env.ts`) with an OPTIONAL, ALL-OR-NOTHING LLM block, shape-validated at boot exactly like the 3.1 SMTP block: `LLM_BASE_URL` (any OpenAI-compatible URL - cloud or local, validated as a URL), `LLM_API_KEY` (the bearer key for the endpoint), `LLM_MODEL` (the model id). The whole block is OPTIONAL (the app MUST boot without it - 3.1's pattern), but ALL-OR-NOTHING when present (a `superRefine`: if any `LLM_*` is set, require `LLM_BASE_URL` + `LLM_MODEL` together; `LLM_API_KEY` may be optional for an unauthenticated local endpoint like a localhost Ollama/llama.cpp - decide and document, recommend optional-key for local-endpoint parity). Validate SHAPE at boot, fail-fast on a malformed config (non-URL base, contradictory block); do NOT make boot depend on a live LLM handshake (a misconfigured-but-shaped endpoint surfaces at GENERATION time, not boot - the 3.1 boot-vs-send split applied to LLM). Add the `LLM_*` keys to `.env.example` with safe placeholders (NEVER read/write any other `.env*` variant).
- [ ] Secret discipline (NFR8, the 3.1 SMTP_PASSWORD pattern): extend the 1.3 pino redaction list to `LLM_API_KEY` (`llmApiKey`/`llm_api_key`/`LLM_API_KEY`). The key is NEVER logged, NEVER placed in a client-facing `detail`, NEVER returned by any settings `load` (the 3.1 "password never read by load" rule - the settings surface reports whether the LLM is configured, the model, and the base URL, but never the key).
- [ ] Explicit OPT-IN gate (the load-bearing AC: "no LLM call is made anywhere before explicit opt-in"): a configured endpoint is necessary but NOT sufficient - generation also requires an explicit opt-in flag, so an operator who sets the env still consciously enables AI. Decide and document the opt-in storage: a settings flag (an `instance_settings`-style row or a dedicated `LLM_ENABLED`/opt-in env) - recommend an explicit `AI_GENERATION_ENABLED` boolean (env or a settings row) SEPARATE from the connection config, so "configured" and "enabled" are two distinct gates; the connector refuses to issue ANY `fetch` unless BOTH (configured AND opted-in) hold. This is the FR33/NFR18 "opt-in per instance, no call without explicit opt-in" contract.
- [ ] `src/lib/server/ai/` domain (mirrors the 3.1 `server/mail/` shape): a `connector.ts` building the request to `${LLM_BASE_URL}/chat/completions` with the bearer key, the configured model, and the caller's messages, over `fetch`; a typed result; and a single `isAiEnabled()` / `assertAiEnabled()` guard that checks BOTH configured + opted-in and throws the disabled `AppError` otherwise. The connector is the ONE place a `fetch` to the LLM happens - 5.4 calls it, never `fetch`es directly. Talks ONLY to the operator-configured endpoint (no phone-home, the 3.1 posture): no hardcoded provider URL, no default cloud endpoint.
- [ ] Disabled-state `AppError` (the second AC): when generation is requested with no endpoint configured OR opt-in absent, throw a typed `AppError` (`/problems/ai-generation-disabled`, recommend 503 - the capability is unavailable, mirroring the 3.1 `/problems/mail-not-configured` 503) whose `detail` states AI generation is disabled and HOW an operator enables it (set the `LLM_*` env + flip the opt-in), WITHOUT leaking config internals. This is the SAME problem-details model (D9) every surface returns; the REST/MCP/workspace generation triggers (5.4) surface it unchanged.
- [ ] Generation failure surfacing (NFR16-style, no silent drop; groundwork the 5.4 third AC consumes): a transport/endpoint failure from the connector (`fetch` reject, non-2xx from the endpoint, an unreachable base URL) becomes a typed `AppError` (`/problems/ai-generation-failed`, recommend 502 - an upstream/bad-gateway failure, mirroring the 3.1 `/problems/mail-delivery-failed` 502) logged server-side at `warn` via pino (the LLM endpoint is a degradable external dependency, like SMTP), with the RAW upstream error (which can carry the endpoint host or response body) kept in the SERVER log ONLY and a sanitized `detail` (no key, no host, no raw body) client-facing.
- [ ] Settings surface (FR33): the `(workspace)/settings` page (author-realm, under `workspaceGuard`) reports whether the LLM is configured (base URL + model shown, key NEVER) and whether generation is opted-in, and - IF the AC's "or settings" path is taken (see ambiguity) - lets the operator flip the opt-in and optionally a connectivity test (a minimal probe call through the connector, surfacing success or the sanitized failure as a green/red chip, the 3.1 test-send pattern). Decide whether config is env-only or also editable in settings (see ambiguity).
- [ ] Tests: env validation accepts a well-formed `LLM_*` block and rejects a malformed one (non-URL base, half-configured block); the app boots with NO `LLM_*` block (optional); `isAiEnabled()` is false when unconfigured OR not opted-in, true only when BOTH hold; `assertAiEnabled()` throws the `/problems/ai-generation-disabled` 503 with the actionable detail when disabled; the connector issues NO `fetch` when disabled (assert the `fetch` mock is never called - the "no call before opt-in" AC, proven, not asserted by inspection); a configured + opted-in connector calls `fetch` to `${LLM_BASE_URL}/chat/completions` with the bearer key + model and returns the parsed result; an endpoint failure (non-2xx / reject) throws `/problems/ai-generation-failed` 502 and pino does NOT emit the key; the settings `load` never returns the key.

## Dev Notes

- Authority: AC verbatim from epics.md Epic 5 Story 5.3 (FR33 OpenAI-compatible endpoint, cloud or local, opt-in per instance; NFR18 OpenAI-compatible contract, no call without explicit opt-in; the disabled-state problem-details error). Architecture line 52 (optional OpenAI-compatible LLM endpoints, P2), line 107 (Deferred: LLM connector layer), the FR30-33 mapping (line 313), D9 (problem+json), the process pattern (env validated at boot fail-fast; `warn` for a degradable external dependency), NFR8 (secrets never logged). Scopes: `ops` (the env block + opt-in + settings config), `api` (the connector + the disabled/failed `AppError`), `docs`. (No `mcp` here - 5.3/5.4 are the LLM track, independent of the MCP track.)
- DECIDED architecture (bake in): **LLM connector over `fetch` (NO new dependency).** Configure an OpenAI-compatible endpoint via env (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`), shape-validated at boot like the SMTP block (the 1.3/3.1 pattern), the block OPTIONAL so the app boots without it, failures surfaced not silent. Built over `fetch` to the configured endpoint - no OpenAI/Anthropic SDK. Keep `LLM_API_KEY` redacted/never-logged like `SMTP_PASSWORD`.
- Seam reuse - this is the 3.1 SMTP story's shape applied to an LLM endpoint, NOT new infrastructure:
  - Env: `src/lib/server/env.ts` (1.3 Zod fail-fast), the 3.1 all-or-nothing `superRefine` pattern for an optional block, `.env.example` placeholders.
  - Redaction: the 1.3 pino redaction list (extended to `SMTP_PASSWORD` in 3.1; extend again to `LLM_API_KEY`).
  - Error model: `AppError` + `problemResponse`/`toProblemDetails` (`src/lib/server/problem.ts`, 1.2/1.4); the 3.1 `/problems/mail-not-configured` (503) + `/problems/mail-delivery-failed` (502) are the templates for `/problems/ai-generation-disabled` (503) + `/problems/ai-generation-failed` (502).
  - Settings: the `(workspace)/settings` route + the 3.1 `?/test-send` green/red chip pattern (the LLM connectivity test, if taken, is the same shape).
  - Domain layout: `src/lib/server/ai/` mirrors `src/lib/server/mail/` (architecture structure pattern: one feature-domain dir, routes thin).
- The "no call before opt-in" AC is load-bearing and PROVEN by test, not by inspection: the connector's `assertAiEnabled()` gate runs BEFORE any `fetch`, and a test asserts the `fetch` mock is never called when the connector is disabled. Two distinct gates (configured AND opted-in) so setting the env alone never enables generation.
- This story is the PREREQUISITE for 5.4 (outline-first generation consumes this connector + the opt-in gate + the disabled/failed `AppError`s). Implement 5.3 first; 5.4 builds the generation logic on top. 5.3/5.4 are INDEPENDENT of 5.1/5.2 (the MCP track): different transport (outbound `fetch` to an LLM vs inbound MCP-over-HTTP), different dependency (none vs the MCP SDK), no shared seam beyond the common env + problem + settings modules. The two pairs can be built in parallel; each pair has an internal order (5.1->5.2, 5.3->5.4).
- No third-party assets, no phone-home (the 3.1 posture): the connector talks ONLY to the operator-configured `LLM_BASE_URL`. No default cloud endpoint, no hardcoded provider, no call unless the operator configured AND opted in.
- Reader JS budget (NFR3): the connector is server-only (`src/lib/server/ai/`, SvelteKit-enforced), ZERO reader JS - confirm `pnpm reader:budget` unchanged and the connector is absent from the client bundle (the 3.1 grep discipline).
- AMBIGUITY for the product owner (do not invent): (a) whether the LLM connector targets OpenAI-compatible Chat Completions ONLY (the FR33/NFR18 contract names "OpenAI-compatible", and Anthropic's API is NOT OpenAI-compatible) or also a NATIVE Anthropic shape - recommend OpenAI-compatible ONLY for V1 (it is exactly what the FR/NFR specify, and many gateways - including Anthropic-via-a-proxy and local runtimes - speak the OpenAI shape), but FLAG that native Anthropic would be a second connector shape if wanted; (b) config transport - env-only (`LLM_*` vars, the trivial-deploy/ops-config promise FR34) vs ALSO editable in workspace settings (the AC says "env or settings") - recommend env for the connection secrets (key/base URL stay in the operator's env, never persisted in the DB) and a settings-stored OPT-IN flag + connectivity test (so the operator enables consciously without re-deploying), but confirm which the product owner wants persisted where; (c) whether the opt-in is a single instance-wide flag or per-capability (e.g. enable outline generation but not full content generation) - recommend one instance-wide opt-in for V1 (the simplest honest gate), but flag a future per-capability split; (d) the `LLM_API_KEY` optionality for an unauthenticated local endpoint (localhost Ollama/llama.cpp) - recommend the key OPTIONAL so a local no-auth endpoint works, but confirm.
