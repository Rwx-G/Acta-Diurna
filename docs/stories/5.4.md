# Story 5.4: Outline-First Generation

Status: Approved

## Story

As the author,
I want the AI to propose an outline I approve before it writes content,
So that generated reports follow my narrative, not the model's.

## Acceptance Criteria

**Given** a skeleton and a data set
**When** I request generation
**Then** the connector produces a bounded outline draft (sections + key points) for review (FR32)

**Given** the outline
**When** I edit and approve it
**Then** content generation fills the document only after approval, and the result is schema-validated before save
**And** regeneration after outline changes requires re-approval
**And** the approval interaction follows UX Flow D in `ux-design-specification.md`

**Given** a generation failure (endpoint unreachable, invalid model output)
**When** it occurs
**Then** the draft document is left untouched and the error names the failing stage with a retry action

## Tasks / Subtasks

- [ ] Outline-first generation over the 5.3 connector (NO new dependency - all `fetch`, all via `src/lib/server/ai/`): a two-stage pipeline in `src/lib/server/ai/generate.ts`. Stage 1 (OUTLINE) produces a BOUNDED outline draft - sections + key points - from a skeleton + a data set (FR32); it is a structural skeleton (the sections/blocks shape), NOT filled content. Stage 2 (CONTENT) fills the document only AFTER explicit approval, producing a complete document. Both stages call the 5.3 `connector` (`assertAiEnabled()` first - a generation request when disabled is the 5.3 `/problems/ai-generation-disabled` 503, surfaced unchanged); the connector is the ONLY `fetch` path.
- [ ] Bounded outline (the first AC): the outline is explicitly BOUNDED - cap the number of sections and key-points-per-section (reuse the 1.2 schema DoS bounds as the ceiling: sections <= 100, etc.) so a runaway model cannot produce an unbounded outline. The outline is a reviewable artifact (sections + key points), held for the author to edit/approve BEFORE any content is written - never auto-promoted to a saved document.
- [ ] Approval gate -> content fill -> schema-validate-before-save (the second AC): content generation runs ONLY after the author edits and approves the outline. The generated document then goes through the SAME service-layer write + validation path as every other surface (NO bypass): `validateDocument` / `updateReportDocument` (1.5) - a model that emits an invalid document is REJECTED by the existing validator with the FR2 actionable `errors[]`, exactly as a bad API/MCP write is, and is NEVER saved. Re-approval discipline (the AC's "regeneration after outline changes requires re-approval"): editing the approved outline INVALIDATES the approval - a changed outline must be re-approved before content is (re)generated; track the approval against the outline content (e.g. a hash/version of the approved outline) so a stale approval cannot fill content from an edited outline.
- [ ] Generation goes through the service-layer write, NO bypass (the load-bearing parity rule, AR5): the filled document is persisted via the SAME `updateReportDocument(id, document, expectedUpdatedAt?)` the workspace/REST/MCP use - validated on write, draft/publish lifecycle respected (a published report is the existing 409), optimistic-concurrency honored. AI generation is a PRODUCER of a document that the existing write path accepts or rejects; it is not a privileged path. The generation orchestration (outline -> approve -> fill) lives in `server/ai/`, but the WRITE is the documents service.
- [ ] Failure leaves the draft untouched + names the stage (the third AC): a failure at EITHER stage (endpoint unreachable -> the 5.3 `/problems/ai-generation-failed` 502; invalid model output -> a parse/validation failure naming the stage) leaves the existing draft document UNCHANGED - generation writes only on a fully successful, schema-valid fill (no partial write, no half-filled document persisted). The error names the failing STAGE (outline vs content-fill vs validation) and carries a RETRY action (re-run the failed stage), as a problem-details `AppError` the triggering surface renders. The outline stage failing never touches the document; the content stage failing rolls back to the pre-generation draft.
- [ ] Generation trigger surface (decide and document - see ambiguity): wire the outline-request -> approve -> fill flow to a triggering surface. The AC + UX Flow D (`ux-design-specification.md`) imply a WORKSPACE-triggered author interaction (the author requests generation, reviews/edits/approves the outline, then content fills). Decide whether generation is ALSO exposed over the API/MCP (an agent-triggered variant) or workspace-only for V1. The orchestration service (`server/ai/generate.ts`) is surface-agnostic (it takes a skeleton id + data set id, returns an outline, accepts an approved outline, returns/writes a document); the workspace route is the V1 trigger. Follow UX Flow D for the approval interaction (the outline review/edit/approve card) - this is the one UX-spec'd interaction in the story.
- [ ] No new tables UNLESS the approval/outline state needs persistence (decide): if the outline + approval round-trip is held in the workspace form/session (the outline returned to the client, edited, posted back with the approval), no migration is needed - recommend this stateless round-trip (the outline travels client-side between request and approval, the server validates the approved outline against the requested skeleton/data set on fill) to avoid an outline-storage table for V1; if a persisted outline-draft is wanted (resume-later), that is a migration + a backlog decision - flag it. Document the chosen approach.
- [ ] Tests: stage 1 produces a BOUNDED outline (sections + key points) from a skeleton + data set, capped at the schema bounds (a runaway model output is truncated/rejected, not passed through); content generation does NOT run before approval (assert the content-stage `connector` call never fires until the approved-outline path runs - the "only after approval" AC, proven by the mock); a filled document goes through `updateReportDocument`/`validateDocument` and an INVALID model document is rejected with the FR2 `errors[]` and NEVER saved (the no-bypass rule, asserted); editing the approved outline invalidates the approval and a re-approval is required before re-fill (stale-approval rejected); a generation request when AI is disabled is the 5.3 `/problems/ai-generation-disabled` 503; an endpoint-unreachable failure is the 5.3 `/problems/ai-generation-failed` 502 with the failing stage named + a retry action, and the existing draft is UNCHANGED (assert the document row is not written on failure); an invalid-model-output failure names the content/validation stage and leaves the draft untouched. An e2e (gated on a configured + opted-in LLM, or a mocked connector in the e2e stack) drives request-outline -> edit -> approve -> fill -> schema-valid draft saved, plus a failure path leaving the draft intact.

## Dev Notes

- Authority: AC verbatim from epics.md Epic 5 Story 5.4 (FR32 outline-first generation, human approval before content; schema-validated before save; re-approval after outline change; UX Flow D; failure leaves the draft untouched and names the stage with a retry). Architecture line 34 (AI connectors a bounded abstraction; outline-first generation), line 107 (Deferred: LLM connector layer), the FR30-33 mapping (line 313), AR5 (one service layer, no privileged write path), D9 (problem+json), the process pattern (validation on write; `warn` for a degradable external dependency). Scopes: `api` (the generation orchestration + the document write), `ui` (the workspace outline-approval surface, UX Flow D), `ops` (reuses the 5.3 opt-in/config), `docs`. (No `mcp`/`schema` here unless generation is exposed over MCP - see ambiguity.)
- DECIDED architecture (bake in): **outline-first generation = the connector generates a report OUTLINE/structure first (sections/blocks skeleton), then fills content, producing a valid document the existing `validateDocument` accepts; built over `fetch` to the configured endpoint (NO OpenAI/Anthropic SDK). The generated document goes through the SAME service-layer write + validation path (NO bypass).** Built on 5.3's connector + opt-in gate + disabled/failed `AppError`s.
- DEPENDS ON 5.3: every LLM call goes through the 5.3 `connector` (`assertAiEnabled()` gate + `fetch` to `${LLM_BASE_URL}/chat/completions` + the sanitized `/problems/ai-generation-disabled`/`-failed` errors). Implement 5.3 first. INDEPENDENT of 5.1/5.2 (the MCP track) - 5.4 shares nothing risky with the MCP surface; it reuses the common documents service (1.5) + problem model, but no MCP code. The two pairs (5.1->5.2, 5.3->5.4) can be built in parallel.
- Seam reuse - the generated document is just ANOTHER producer feeding the existing write path, NOT a new write path:
  - LLM connector + opt-in: the 5.3 `src/lib/server/ai/connector.ts` + `assertAiEnabled()` + the disabled/failed `AppError`s. 5.4 adds the OUTLINE + FILL orchestration (`generate.ts`); it never `fetch`es directly.
  - Documents write + validation: `validateDocument` / `updateReportDocument(id, document, expectedUpdatedAt?)` (1.5), `createReport`/`createReportWithDocument` (1.5) if generation seeds a new report. The 1.2 `errors.ts` actionable layer rejects an invalid model document with the FR2 `errors[]` - the SAME rejection a bad API/MCP write gets (4.2/5.2 parity). The 1.2 schema DoS bounds are the outline ceiling.
  - Skeletons + data sets: the generation INPUT - `instantiateReport(skeletonId)` / the skeleton path (2.2) and the `data_sets` + `readDataSetTable` ingestion (2.4) provide the skeleton structure + the data the outline/content is grounded in. Generation reads them; it does not re-ingest.
  - Error model: `AppError` + `problemResponse`/`toProblemDetails` (`src/lib/server/problem.ts`); the failing-stage + retry detail is a problem-details payload (D9).
  - UX: UX Flow D in `ux-design-specification.md` for the outline review/edit/approve interaction (the one UX-spec'd surface in this story), the StatusChip grammar for the generation states.
- The "no bypass" rule is the load-bearing architectural contract: AI generation is a PRODUCER of a document, never a privileged write. The filled document is accepted or rejected by the EXACT `validateDocument`/`updateReportDocument` path every other surface uses - so a hallucinated invalid document is rejected with actionable errors and never saved, and the draft/publish lifecycle + optimistic-concurrency guards apply unchanged. The test asserts an invalid model document is rejected by the validator, not by a generation-specific check.
- The "failure leaves the draft untouched" rule (third AC): generation writes the document ONLY on a fully successful, schema-valid content fill - never a partial/half-filled write. A failure at any stage rolls back to the pre-generation draft and surfaces a problem-details error naming the stage (outline / content-fill / validation) with a retry action. The test asserts the document row is unchanged on a failure path.
- This story COMPLETES the LLM track (5.3 config + 5.4 generation): the "3-minute report" the epic promises - request, approve an outline, fill, read - over any operator-configured OpenAI-compatible endpoint, with the human-approval gate front and center (the report follows the author's narrative, not the model's).
- Reader JS budget (NFR3): the generation orchestration is server-only (`src/lib/server/ai/`); the only reader-path concern is the workspace outline-approval UI, which is author-surface (not in the reader closure) - confirm `pnpm reader:budget` unchanged.
- AMBIGUITY for the product owner (do not invent): (a) the outline-first UX trigger - WORKSPACE-triggered (the author requests/reviews/approves in the workspace, what UX Flow D implies) vs ALSO API/MCP-triggered (an agent requests an outline, a human approves elsewhere, content fills) - recommend WORKSPACE-ONLY for V1 (the AC is author-centric, the human-approval gate is the whole point, and UX Flow D specifies the workspace interaction) and defer an agent-triggered generation API to a follow-up, but FLAG it (an agent that can author via MCP (5.2) may want to drive generation too); (b) outline/approval persistence - a stateless client round-trip (the outline travels to the client, is edited, posted back with the approval; no table) vs a persisted outline-draft (resume-later, an `ai_outlines`-style table + migration) - recommend the stateless round-trip for V1 (no new storage, the approval is validated server-side on fill), but flag the persistence option; (c) how the approval is bound to the outline so a stale approval cannot fill from an edited outline - recommend a content hash/version of the approved outline checked at fill time, but confirm the mechanism; (d) whether generation SEEDS a new draft or fills an EXISTING draft created from the skeleton - recommend filling the draft instantiated from the skeleton (2.2 `instantiateReport`) so the structural-consistency promise (FR11) holds and the write is a normal `updateReportDocument`, but confirm; (e) whether the data set grounding is mandatory or optional (the AC says "a skeleton AND a data set") - recommend requiring both as the AC states for V1, but flag whether outline-from-skeleton-alone (no data) is a wanted variant.
