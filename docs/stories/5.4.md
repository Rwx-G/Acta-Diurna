# Story 5.4: Outline-First Generation

Status: Review

## Story

As the author,
I want the AI to propose an outline I approve before it writes content,
So that generated reports follow my narrative, not the model's.

## Acceptance Criteria

**Given** a skeleton and a data set
**When** I request generation
**Then** the connector produces a bounded outline draft (sections + key points) for review (FR32)

**Given** the outline
**When** I edit and approve it
**Then** content generation fills the document only after approval, and the result is schema-validated before save
**And** regeneration after outline changes requires re-approval
**And** the approval interaction follows UX Flow D in `ux-design-specification.md`

**Given** a generation failure (endpoint unreachable, invalid model output)
**When** it occurs
**Then** the draft document is left untouched and the error names the failing stage with a retry action

## Tasks / Subtasks

- [x] Outline-first generation over the 5.3 connector (NO new dependency - all `fetch`, all via `src/lib/server/ai/`): a two-stage pipeline in `src/lib/server/ai/generate.ts`. Stage 1 (OUTLINE) produces a BOUNDED outline draft - sections + key points - from a skeleton + a data set (FR32); it is a structural skeleton (the sections/blocks shape), NOT filled content. Stage 2 (CONTENT) fills the document only AFTER explicit approval, producing a complete document. Both stages call the 5.3 `connector` (`assertAiEnabled()` first - a generation request when disabled is the 5.3 `/problems/ai-generation-disabled` 503, surfaced unchanged); the connector is the ONLY `fetch` path.
- [x] Bounded outline (the first AC): the outline is explicitly BOUNDED - cap the number of sections and key-points-per-section (reuse the 1.2 schema DoS bounds as the ceiling: sections <= 100, etc.) so a runaway model cannot produce an unbounded outline. The outline is a reviewable artifact (sections + key points), held for the author to edit/approve BEFORE any content is written - never auto-promoted to a saved document.
- [x] Approval gate -> content fill -> schema-validate-before-save (the second AC): content generation runs ONLY after the author edits and approves the outline. The generated document then goes through the SAME service-layer write + validation path as every other surface (NO bypass): `validateDocument` / `updateReportDocument` (1.5) - a model that emits an invalid document is REJECTED by the existing validator with the FR2 actionable `errors[]`, exactly as a bad API/MCP write is, and is NEVER saved. Re-approval discipline (the AC's "regeneration after outline changes requires re-approval"): editing the approved outline INVALIDATES the approval - a changed outline must be re-approved before content is (re)generated; track the approval against the outline content (e.g. a hash/version of the approved outline) so a stale approval cannot fill content from an edited outline.
- [x] Generation goes through the service-layer write, NO bypass (the load-bearing parity rule, AR5): the filled document is persisted via the SAME `updateReportDocument(id, document, expectedUpdatedAt?)` the workspace/REST/MCP use - validated on write, draft/publish lifecycle respected (a published report is the existing 409), optimistic-concurrency honored. AI generation is a PRODUCER of a document that the existing write path accepts or rejects; it is not a privileged path. The generation orchestration (outline -> approve -> fill) lives in `server/ai/`, but the WRITE is the documents service.
- [x] Failure leaves the draft untouched + names the stage (the third AC): a failure at EITHER stage (endpoint unreachable -> the 5.3 `/problems/ai-generation-failed` 502; invalid model output -> a parse/validation failure naming the stage) leaves the existing draft document UNCHANGED - generation writes only on a fully successful, schema-valid fill (no partial write, no half-filled document persisted). The error names the failing STAGE (outline vs content-fill vs validation) and carries a RETRY action (re-run the failed stage), as a problem-details `AppError` the triggering surface renders. The outline stage failing never touches the document; the content stage failing rolls back to the pre-generation draft.
- [x] Generation trigger surface (decide and document - see ambiguity): wire the outline-request -> approve -> fill flow to a triggering surface. The AC + UX Flow D (`ux-design-specification.md`) imply a WORKSPACE-triggered author interaction (the author requests generation, reviews/edits/approves the outline, then content fills). Decide whether generation is ALSO exposed over the API/MCP (an agent-triggered variant) or workspace-only for V1. The orchestration service (`server/ai/generate.ts`) is surface-agnostic (it takes a skeleton id + data set id, returns an outline, accepts an approved outline, returns/writes a document); the workspace route is the V1 trigger. Follow UX Flow D for the approval interaction (the outline review/edit/approve card) - this is the one UX-spec'd interaction in the story.
- [x] No new tables UNLESS the approval/outline state needs persistence (decide): if the outline + approval round-trip is held in the workspace form/session (the outline returned to the client, edited, posted back with the approval), no migration is needed - recommend this stateless round-trip (the outline travels client-side between request and approval, the server validates the approved outline against the requested skeleton/data set on fill) to avoid an outline-storage table for V1; if a persisted outline-draft is wanted (resume-later), that is a migration + a backlog decision - flag it. Document the chosen approach.
- [x] Tests: stage 1 produces a BOUNDED outline (sections + key points) from a skeleton + data set, capped at the schema bounds (a runaway model output is truncated/rejected, not passed through); content generation does NOT run before approval (assert the content-stage `connector` call never fires until the approved-outline path runs - the "only after approval" AC, proven by the mock); a filled document goes through `updateReportDocument`/`validateDocument` and an INVALID model document is rejected with the FR2 `errors[]` and NEVER saved (the no-bypass rule, asserted); editing the approved outline invalidates the approval and a re-approval is required before re-fill (stale-approval rejected); a generation request when AI is disabled is the 5.3 `/problems/ai-generation-disabled` 503; an endpoint-unreachable failure is the 5.3 `/problems/ai-generation-failed` 502 with the failing stage named + a retry action, and the existing draft is UNCHANGED (assert the document row is not written on failure); an invalid-model-output failure names the content/validation stage and leaves the draft untouched. An e2e (gated on a configured + opted-in LLM, or a mocked connector in the e2e stack) drives request-outline -> edit -> approve -> fill -> schema-valid draft saved, plus a failure path leaving the draft intact.

## Dev Agent Record

### Debug Log

- Two-stage design (the whole story): `src/lib/server/ai/generate.ts` is surface-agnostic. `generateOutline(input)` -> a bounded `Outline` (sections + per-block intents). `hashOutline(outline)` -> a SHA-256 of the canonicalized outline. `fillFromOutline({ outline, approvedHash, ... }, reportId?)` -> a persisted `Report`. The workspace route is the V1 trigger; the service takes ids + an intent and returns/writes, so an agent-triggered variant later reuses it unchanged.
- Untrusted-LLM handling (the critical contract): the connector returns only `{ content }`, an UNTRUSTED string. `parseModelJson` extracts the outermost `{ ... }` span (handles prose/fence wrapping) and JSON.parses it inside a try, returning null on anything malformed or over `MAX_MODEL_OUTPUT_CHARS` (200k) - never a throw to the caller. `parseOutline` and `assembleDocument`/`assembleBlock` read every field through `asRecord`/`asArray`/`clampText`, clamp to the schema DoS ceilings (100 sections, 200 blocks/section, 10000 rows/points), and IGNORE the model's `type` in favor of the OUTLINE's approved type. A block that yields no usable content falls back to a one-line text block, so the assembled document is always well-formed BEFORE it reaches the validator. The model's ids are NEVER used: every section/block gets a server-generated slug (`section-N`, `block-N-M`) so `idSchema` passes regardless of model output. The final write goes through `updateReportDocument`/`createReportWithDocument` - the SAME validate-on-write (and the same `MAX_DOCUMENT_BYTES` DoS cap) every surface uses; `validateDocument` is the ONLY gate, so a hallucinated invalid document is rejected with the FR2 `errors[]` and the draft is left untouched (test: an invalid model document -> the service 422, `updateReportDocument` never reached or rejecting, the row never written). No prompt-injection sink: the output is data assembled into a validated document, never executed.
- Content-hash approval binding (the stale-approval guard, AC2's re-approval rule): the approval is bound to the EXACT approved outline by `hashOutline` - a canonical JSON (stable key order, the meaningful fields only) hashed with `node:crypto` `createHash('sha256')` (no new dependency). The hash travels client-side with the fill request (stateless round-trip, NO new table - the recommended ambiguity-(b) resolution). `fillFromOutline` re-hashes the posted outline and compares to `approvedHash` as its FIRST statement, BEFORE `chatComplete`; a mismatch is `/problems/ai-outline-stale` 409 and no LLM call is made (test asserts `chatComplete` and `updateReportDocument` are never called on a stale hash). The workspace UI clears the held hash on any inline outline edit, forcing a re-request to obtain a fresh server-minted hash.
- Two distinct `ai-generation-failed` 502 sources, same type/status so a surface renders them identically: the connector's (endpoint unreachable / non-2xx / abort) and the orchestration's own (unparseable/empty model output). The orchestration one names the STAGE in the detail (`... at the outline stage: ... Retry the outline stage.` / `... content-fill stage ...`), satisfying AC3's "names the failing stage with a retry action". The disabled 503 flows straight through from `chatComplete` unchanged.
- Workspace UX (UX Flow D, workspace-triggered only per ambiguity-(a)): the entry point lives in the report editor as `GeneratePanel.svelte`, rendered by `ReportEditor` ONLY when `data.aiEnabled` (the `load` calls `isAiEnabled()`); AI off -> the panel is absent (no offer of a 503ing capability). Three client stages: request (intent + optional skeleton + optional data set) -> review (the outline, every line inline-editable, edit clears the approval hash) -> done (the draft filled, `invalidateAll()` reloads the editor to show it). Two server actions `generate-outline` (returns the outline + its hash) and `generate-fill` (re-checks the hash, fills via the service); both map an `AppError` to a `fail()` carrying the staged message / the 422 `errors[]`, the established editor pattern. The panel is `disabled` on a published report (generation replaces the draft document).
- Prompt bounding: the author intent is capped at 2000 chars, each intent/key-point at 500, the data-set fields at 100 (each `name (type)`), the sample rows at 20, before anything enters a prompt (test asserts a 50k-char intent yields a <3k-char user message). The schema block types are injected into the system prompt so the model targets the document contract; the model is told to return ONLY JSON.
- Default fills `fillFromOutline(input, reportId)` (the recommended ambiguity-(d): fill the EXISTING draft instantiated from the skeleton, a normal `updateReportDocument`); `reportId` omitted seeds a new draft via `createReportWithDocument`. Data-set grounding is OPTIONAL in the service (ambiguity-(e)) - the workspace makes the skeleton and the data set optional pickers and requires only an intent, which is the most usable reading of "a skeleton AND a data set" without forcing an upload before any generation.
- Gates (final): `pnpm lint` clean (prettier + eslint; the new files needed a `prettier --write` pass, and `generate-outline` dropped an unused `params` destructure caught by eslint); `pnpm check` 1106 files, 0 errors, 0 warnings; `pnpm test` 997 unit tests passed (95 files) - 25 new (15 in `generate.test.ts`, 10 added to the edit `page.server.test.ts`); `pnpm build` adapter-node done; `pnpm reader:budget` 69.2 KB / 200 KB (was 68.9 at 5.3; the +0.3 is shared-chunk drift, the generate UI is workspace-only, not in the reader closure). Client-bundle isolation verified: `grep -rl "chatComplete|generateOutline|fillFromOutline|chat/completions" .svelte-kit/output/client` = 0.
- `pnpm test:e2e` (Docker stack up): 40 passed, 15 skipped (pre-existing mobile/data-dependent specs). The new `e2e/ai-generate.e2e.ts` is the AI-DISABLED path: the e2e stack configures no `LLM_*`/`AI_GENERATION_ENABLED`, so the connector is disabled - the test creates a draft, opens the editor, asserts the "Generate with AI" heading is absent (entry point hidden), and asserts a direct POST to `?/generate-outline` carries the disabled signal. A real-LLM happy-path e2e is impractical in CI (no endpoint, no phone-home posture) and is fully covered by the mock-based unit tests; the disabled-path e2e is the contract that matters at the integration boundary.

#### QA follow-up (2026-06-12)

- **QA Medium - rate-limit the generation actions (cost/DoS):** both `generate-outline` and `generate-fill` issued an unmetered `chatComplete` per call, so an authenticated author could drive unlimited paid LLM calls. Added `aiGenerationLimiter` in `rate-limit.ts` (a new `TokenBucketLimiter`, the same class the login/api-auth brakes use): capacity 10, refill 1 token / 30s (sustained ~2/min, a burst of 10 for outline iteration). Keyed PER AUTHOR SESSION (`${locals.authorSession!.id}:/generate`) - the workspace guard guarantees a live session reaches the action, and per-session keying means one author's burst never starves another. Consumed at the TOP of BOTH actions, BEFORE `request.formData()` and any `chatComplete`/service call; on deny the action returns `fail(429, { generate: { message } })` carrying the shared `rateLimited()` detail (the same 429 problem shape the login limiter surfaces), and makes no LLM call. Three new tests in `page.server.test.ts`: outline throttled past the cap -> 429 + `generateOutline` never called; fill throttled past the cap -> 429 + `fillFromOutline` never called; session isolation (a drained session does not throttle a fresh one). The `generateEvent` test helper now mints a fresh session id per event by default so the shared module-level limiter does not bleed state across the existing generate tests.
- **QA Low - dead `validateAssembled` export:** `validateAssembled` was exported "for callers and tests" but had NO production caller and NO test reference (the only test mention was `assembleDocument`, a different private function exercised through the public fill path). Removed it. No coverage lost: the no-persist-invalid guarantee is enforced by `validateDocument` inside `updateReportDocument`/`createReportWithDocument` (the service write path `fillFromOutline` already uses), which the existing invalid-document tests cover. With it gone, `validateDocument` and the `DocumentV1` type were no longer referenced in `generate.ts`, so both were dropped from the `$lib/schema` import (only `DocumentV1Input` remains).
- **Gates (QA follow-up):** `pnpm lint`, `pnpm check` (1106 files, 0 errors), `pnpm test` (1000 unit tests, 95 files - 3 new rate-limit tests), `pnpm build`, `pnpm reader:budget` (69.2 KB / 200 KB, unchanged - the limiter is server-only) all green. `pnpm test:e2e` not re-run: the change is server-side with no route/action contract change (same actions, same problem shape, an added 429 branch on an authenticated path); the existing AI-disabled-path e2e still covers the integration boundary.

### Completion Notes

- **NO new dependency.** The orchestration uses `node:crypto` `createHash` (native) for the approval hash and the 5.3 `chatComplete` for every LLM call. The Epic 5 single approved dependency remains `@modelcontextprotocol/sdk` (5.1); 5.3 and 5.4 add none.
- **Ambiguities resolved (as recommended in Dev Notes):** (a) WORKSPACE-triggered ONLY for V1 - the report editor's Generate panel; an agent-triggered generation API is deferred (the service is surface-agnostic so it is a thin future addition). (b) STATELESS outline round-trip - the outline + a content hash travel client-side between request and approval; NO `ai_outlines` table, no migration. (c) The approval is bound by a SHA-256 content hash re-checked at fill time before any LLM call. (d) Generation fills the EXISTING draft via `updateReportDocument` (a normal write); `createReportWithDocument` seeds a new draft when no report id is given. (e) The skeleton and data set are OPTIONAL pickers; only an intent is required (the most usable reading; outline-from-skeleton-alone and content-from-data-alone both work).
- **The two-stage design:** Stage 1 `generateOutline` -> a bounded `Outline` (sections + per-block intents, clamped to the schema ceilings). Author approval -> `hashOutline` mints the binding hash. Stage 2 `fillFromOutline` re-checks the hash (409 on mismatch, no call), calls `chatComplete`, assembles a `DocumentV1Input` with server-owned slug ids, and persists through the service write. The model only ever supplies CONTENT; the structure (which blocks, in what order) is the author-approved outline, and the ids + write path are server-owned.
- **The no-bypass rule (proven):** the filled document is accepted or rejected by the EXACT `validateDocument`/`updateReportDocument` path every other surface uses. A test routes the service mock to throw the validator's 422 for an empty-title document and asserts generation surfaces it unchanged; another asserts a valid filled document reaches `updateReportDocument` with server slug ids (`section-1`, `block-1-1`) and passes the REAL validator. An invalid generated document is NEVER persisted.
- **Failure leaves the draft untouched (proven):** generation writes ONLY on a fully valid fill. Tests assert that an outline-stage garbage output, a content-fill unparseable output, a stale approval hash, and a 503-disabled connector each result in NO write (`updateReportDocument`/`createReportWithDocument` never called), the error naming the failing stage with a retry action.
- **Untrusted-output handling (proven):** a prose-wrapped outline parses; a garbage outline -> the outline-stage 502; a runaway 500-section outline clamps to <=100; a wrong-shape object fill assembles defensively to a valid document (fallback text); an oversized output (300k chars) fails cleanly with the content-fill 502, never crashing, never persisting.
- **Reader budget:** the generation orchestration is server-only (`$lib/server/ai/`), absent from the client bundle; the Generate panel is workspace-only (not in the reader closure). Reader budget 69.2 KB / 200 KB.
- **Epic 5 is complete end to end:** MCP discovery (5.1) + MCP authoring (5.2) + LLM endpoint configuration (5.3) + outline-first generation (5.4). An operator points `LLM_BASE_URL` at any OpenAI-compatible endpoint, opts in with `AI_GENERATION_ENABLED=true`, and an author requests an outline, approves it, and fills a schema-valid draft - the "3-minute report" the epic promises, with the human-approval gate front and center and every model output validated on write like any other surface.
