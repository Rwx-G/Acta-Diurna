# Story 4.1: API Tokens

Status: Approved

## Story

As the author,
I want to create and revoke personal access tokens,
So that my scripts and agents can authenticate to the API.

## Acceptance Criteria

**Given** the workspace settings
**When** I create a token
**Then** it is shown once, stored hashed (api_tokens table), and revocable from the same screen (D10)

**Given** an API request with a missing, invalid, or revoked token
**When** received
**Then** a problem+json 401 is returned, and authentication endpoints are rate-limited (AR4, AR12)

## Tasks / Subtasks

- [ ] `api_tokens` table migration (drizzle-kit generate, next sequential number): `id` uuidv7 PK; `name` text (an author-chosen label so the list is legible); `token_hash` text (the raw token is NEVER stored, only its at-rest hash via the shared `hashToken` helper - see the 1.4/3.3 session-token pattern); `created_at` timestamptz default now; `last_used_at` timestamptz NULLABLE (stamped on each successful authentication, null until first use); `revoked_at` timestamptz NULLABLE (set on revoke, never deleted - an audit trail). The token is author-scoped (single-author MVP, so no owner column yet - mirror the 1.5 "Multi-author IDOR prep" backlog note: add owner/tenant when tenancy lands). Indexes: unique `api_tokens_token_hash_idx`, `api_tokens_revoked_at_idx` (list filtering). Register in `src/lib/server/db/schema.ts`.
- [ ] API token service `src/lib/server/auth/api-tokens.ts`: `createApiToken(name) -> { token, row }` generates a >= 128-bit random token (use 256-bit, matching the 1.4 session / 3.2 share token strength), returns the RAW token to the caller ONCE and stores only `hashToken(raw)`; `listApiTokens() -> ApiTokenSummary[]` (id/name/createdAt/lastUsedAt/revokedAt/status, newest first, NEVER the raw token); `revokeApiToken(id)` sets `revoked_at` (idempotent: revoking an already-revoked token is a no-op success, not an error); `resolveApiToken(rawToken) -> AuthorIdentity | null` hashes then matches on `token_hash`, returns null for unknown/revoked, and stamps `last_used_at` on a live match. A token prefix convention (e.g. `acta_pat_<base64url>`) so a leaked token is greppable and the bearer parser can reject obviously-malformed values cheaply before any DB lookup.
- [ ] THIRD auth path - the PAT bearer authenticator: a new realm distinct from `acta_author` and `acta_reader`. An `apiRealm` handle (or an `authenticatePat(request)` helper invoked by the `/api/*` error boundary below) reads `Authorization: Bearer <token>`, calls `resolveApiToken`, and populates `event.locals.apiIdentity` (typed in `app.d.ts`, `ApiIdentity | null`). STRICT SEPARATION (NFR12 discipline extended to the API): the API path MUST NOT accept cookies (no `acta_author`/`acta_reader` fallback - a browser session never authorizes `/api/v1`), and the cookie realms MUST NOT accept PATs (the workspace/reader handles ignore `Authorization`). A missing/invalid/revoked/malformed token yields `401` problem+json with `WWW-Authenticate: Bearer` (the 1.4 `problemResponse` header allow-list already passes `www-authenticate`).
- [ ] `/api/*` error boundary handle (backlog "Epic 4 prep - API error boundary"): a SvelteKit `handle` segment scoped to `/api/*` that wraps `resolve(event)` in try/catch and maps any thrown `AppError` to `problemResponse(error)` (RFC 9457). This removes the per-endpoint catch discipline the 1.4 note flagged (`handleError` cannot change the status of unexpected errors, so endpoints would otherwise each catch). Ordering in `sequence(...)`: the boundary wraps the API auth + endpoints; a genuine unexpected error still falls through to the opaque 500. This handle is the shared seam 4.2 and 4.3 build every endpoint on.
- [ ] Rate-limit the API auth (AR12, D6): reuse `src/lib/server/auth/rate-limit.ts` (`TokenBucketLimiter`) keyed per-IP on the `/api/*` auth attempt, plus the global failure brake (the 1.4 second line behind a proxy, same reverse-proxy `ADDRESS_HEADER` contract as 3.3). A throttled request returns `429` problem+json with `Retry-After`, routed through the `/api/*` error boundary.
- [ ] Token management UI in workspace settings (D10): under `workspaceGuard` (author realm) at `(workspace)/settings` (the settings route is in the architecture tree). Create form (name input) showing the raw token ONCE in a highlighted copy-in-one-gesture block (the raw token lives only on the action result - reloading loses it, by design, mirroring 3.2's share-link one-time reveal); a list of tokens (name, created, last used, status chip active/revoked) with a revoke button per row; the raw token is never re-fetchable, never logged.
- [ ] Tests: `createApiToken` returns a raw token of >= 128-bit entropy and stores only the hash (raw never persisted on any column); `resolveApiToken` finds a live token by raw token via its hash, misses on a wrong/unknown token, returns null for a revoked token, stamps `last_used_at`; `revokeApiToken` is idempotent; the bearer authenticator returns 401 problem+json (with `WWW-Authenticate`) for missing/malformed/invalid/revoked, and rejects a cookie on `/api/*` (no session fallback); the cookie realms ignore `Authorization` (a PAT never opens a workspace session); the `/api/*` error boundary maps a thrown `AppError` to problem+json (and a non-AppError to the opaque 500); rate limiting engages on repeated auth attempts (per-IP + global brake); settings UI create shows the token once + list + revoke action.

## Dev Notes

- Authority: AC verbatim from epics.md Epic 4 Story 4.1 (D10 PAT-style bearer tokens hashed in DB; AR4 problem+json everywhere; AR12 rate-limited auth). Architecture D10 (`api_tokens` table in the tables list, line 170), D9 (RFC 9457 problem+json), the "three entry surfaces, one service layer" boundary (line 299: reader cookie / author cookie / programmatic PAT bearer). Scopes touched: `auth` (the PAT realm + service), `db` (the migration ships with this story), `api`/`ops` (the `/api/*` error-boundary handle in `hooks.server.ts`), `ui` (settings surface).
- Seam reuse: the at-rest hash helper is the shared `hashToken` extracted in 3.3 at `src/lib/server/crypto/hash-token.ts` (SHA-256, the SAME function the session and share tokens use) - a PAT is a bearer credential resolved on every API request, stored and looked up identically. The random-token generation + hash-keyed lookup pattern is the 1.4 session / 3.2 share model (256-bit via `crypto`, `db/ids.ts` for UUIDv7). The rate limiter is `auth/rate-limit.ts` `TokenBucketLimiter` + the 1.4 global failure brake. The error model is `AppError` + `problemResponse` from `src/lib/server/problem.ts`; the 1.4 Completion Note explicitly anticipated this: "`problemResponse()` ... used by the rate-limit hook and by future /api/v1 endpoints" and "API endpoints must catch AppError and return `problemResponse(error)` themselves (or via a thin wrapper)" - this story builds that wrapper as the `/api/*` boundary handle so endpoints stay thin. Realm handles live in `hooks.server.ts` (the 1.4 `authorRealm` and 3.3 `readerRealm` are the templates for `apiRealm`); `event.locals` typing is in `app.d.ts`.
- The PAT realm is a THIRD path, not a cookie realm. Argon2 (the author password) is NOT used here: a PAT is a high-entropy random token like a session/share token, so SHA-256-at-rest + constant-time hash-keyed lookup is correct (argon2 is for low-entropy human passwords only). Strict separation is the NFR12 principle extended to the API surface: cookies never reach `/api/v1`, PATs never open a workspace/reader session.
- Forward-schema discipline (the 3.2 `mode`/`revoked_at` pattern): `last_used_at` and `revoked_at` are created NOW and exercised now (unlike 3.2's deferred columns). No second migration.
- This story is the PREREQUISITE for BOTH 4.2 and 4.3: they consume `event.locals.apiIdentity` (PAT auth) and build every endpoint on the `/api/*` error boundary. Implement 4.1 first; 4.2 and 4.3 are then largely independent of each other (4.2 before 4.3 is natural but not required).
- Migration generation follows the 1.4/3.2/3.3 recipe (`MSYS_NO_PATHCONV=1 DATABASE_URL=postgres://x pnpm exec drizzle-kit generate --name api_tokens`, dummy URL, no live DB).
- AMBIGUITY for the product owner (do not invent): (a) the PAT prefix string and whether to surface a non-secret display fragment (e.g. last 4 chars) in the token list so an author can tell two tokens apart without re-revealing - recommend a `acta_pat_` prefix + a stored non-secret short fragment, but confirm before the migration freezes the columns; (b) whether PATs carry an optional expiry (the FRs/D10 do not specify one - the share model has optional expiry, the session model a fixed lifetime; recommend non-expiring + revocable-only for V1, since the author owns revocation, but flag it); (c) whether `/api/v1` 401s should be timing-flat against the enumeration concern NFR9 raised for the reader realm (a PAT is high-entropy so enumeration is not a practical threat, unlike low-entropy emails - recommend the standard 401 without the constant-work machinery, but note the divergence from the reader path).
