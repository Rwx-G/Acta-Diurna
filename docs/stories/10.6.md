# Story 10.6: Live Audience-Aware Preview, Speaker Notes, and Audience Tags

## Status

Review

## Story

As the author,
I want the preview to show exactly what each audience level sees and to edit audience tags and speaker notes in place,
So that I author the summary / full / technical experience and the presenter notes against the real render.

## Acceptance Criteria

**Given** the live preview
**When** the author switches the previewed audience level (summary / full / technical)
**Then** the preview re-renders to that level using the same level filtering the reader uses (Epic 6.1) - tagged blocks appear/disappear per level, untagged blocks appear at every level, default is full - so the author sees each audience's exact view

**Given** a block selected in the editor
**When** the author sets its audience tags
**Then** the existing `AudiencePicker` writes the tags into the in-edit document, the level-switched preview reflects them immediately, and the tags persist through validate-on-write

**Given** a section
**When** the author edits its speaker notes
**Then** the notes are edited in place and persist in the draft, and the preview reflects that notes are author-only - the reader-serving chokepoint already strips notes (Story 6.2), so the editor never makes notes reader-visible

**Given** the audience-aware preview
**When** measured
**Then** the level-switching preview is a workspace-bundle concern only; the reader's own level switcher and the reader budget are unaffected (NFR3)

## Tasks / Subtasks

- [x] **Live audience-aware preview, reusing Epic 6.1's level filtering (ui, AC1).** The embedded `Report` (the same pure renderer the reader uses) already renders its reader `LevelSwitcher` when `embedded && view.hasAudiences`, driving `data-level` on the report root while `toPreviewView` emits `data-audiences` on every section / block - so the audience CSS shows / hides tagged content per level in the editor preview exactly as the reader does. No second renderer, no re-implemented level logic; default is `full` (FR28), untagged content shows at every level. This story wires the level CHOICE to PERSIST across the editor's settled-snapshot remount (see below) so the author keeps authoring against the level they picked.
- [x] **Persist the picked level across the `{#key document}` remount (ui).** `LivePreview` remounts the `Report` tree on every settled edit (`{#key document}`), which reset the embedded switcher's in-component `activeLevel` to `full` on every keystroke-settle. `LivePreview` now OWNS `previewLevel` and passes it down as `Report`'s `level` (re-seeded on every remount), and a new `onlevelchange` callback on `Report` reports the embedded switch UP so the owner holds it across remounts. The reader passes no `onlevelchange`, so it tree-shakes out of the reader path (budget byte-identical).
- [x] **Audience tags reflected in the level-switched preview (ui, AC2).** The existing `AudiencePicker` is already mounted at the section level (`SectionEditor`) and the block level (`BlockEditor`); it writes the `audiences` tag onto the in-edit working copy through the same `onEdit` -> debounced-settle -> validated-save seam. Once the settled snapshot renders, `toPreviewView` flips `hasAudiences` true (surfacing the embedded switcher) and the tagged element carries the `data-audiences` attribute the reader CSS reads, so the level-switched preview reflects the tag immediately. Tags persist through validate-on-write (no schema change - the field already exists).
- [x] **Speaker notes edited in place (ui, AC3).** A new `SectionNotesEditor` edits the author-only section `notes` field (the Story 6.2 schema field) in a disclosure beside the `AudiencePicker`, on the working copy through the same validated-save seam. The optional field is omitted when empty (undefined, never stored `""`, the document format rule). A privacy hint states the contract to the author: "Author-only. Readers never see speaker notes."
- [x] **Notes never reach the reader (the load-bearing privacy guard, AC3).** Not weakened: the reader-serving chokepoint already strips notes (`stripSpeakerNotes` at `getPublishedDocument`, Story 6.2), and the render tier (`toPreviewView` / `toReportView`) never reads the `notes` field - so notes never appear in the reader render or the reader-facing preview output. The editor edits notes on the working copy and saves them in the DRAFT (where the presenter view reads them); they are stripped only on the reader serve. The editor cannot make them reader-visible.
- [x] **Reader-budget isolation (ops, AC4).** Everything is workspace-only behind the author cookie: `pnpm reader:budget` is byte-identical at 75.9 KB / 200 KB, and `pnpm schema:export` is unchanged (no schema change). The `onlevelchange` callback added to `Report` is reader-shared render code but tree-shakes (the reader passes no callback) - the budget confirms zero impact. The 10.1 reader-purity boundary (scoped to `src/lib/render/**`) is not touched.
- [x] **Accessibility (ui, NFR15 / WCAG).** The notes editor's textarea carries an explicit `aria-label`; the level switcher reuses the reader's labelled, operable visually-hidden radio group; the `AudiencePicker` checkboxes are labelled. The editor surface with the audience and notes disclosures open is axe-clean (desktop e2e, scoped to `.editor-form`).
- [x] **Tests.**
  - [x] Component (`audience-notes.svelte.test.ts`): the embedded reader switcher appears only when the draft carries tags; switching the preview to Technical flips `data-level` and reveals the tagged block (the same filtering the reader uses); setting a tag through the section `AudiencePicker` surfaces the switcher and the `data-audiences` attribute in the preview; the notes editor edits the section `notes` on the working copy; an emptied note drops to undefined; the privacy hint renders.
  - [x] Render-tier tripwire (`document-view.test.ts`): `toPreviewView` carries no `notes` onto the editor preview view-model (no property, no value anywhere in the serialized view) - the NO-LEAK guard on the editor's reader-facing surface (parallel to the existing `toReportView` guard).
  - [x] e2e (`editor-audience-notes.e2e.ts`, desktop): tag a block technical and switch the preview level to see it hide / show; edit a speaker note, save, reload, the note persists for the author; the notes-never-leak guard (mint a real reader share for the published report and assert the note is absent from the served DOM and the SSR HTML); axe-clean.

## Dev Notes

### What EXISTED vs what was WIRED

Most of the AUDIENCE machinery already existed and is reused unchanged - this story is mostly a confirm-and-test plus the speaker-notes gap:

- **The level filtering and the embedded preview switcher (Epic 6.1)** already shipped: `Report.svelte` renders its reader `LevelSwitcher` in embedded mode when the document carries tags (`embedded && view.hasAudiences`), driving `data-level` on the report root; the audience CSS (`.report[data-level=...] [data-audiences]:not(...)`) hides mismatched elements; `toPreviewView` sets `hasAudiences` and emits `data-audiences` via `audiencesAttr`. So the editor's live preview was ALREADY level-switchable by the same mechanism as the reader. The isomorphic predicate (`isVisibleAtLevel`, `audiencesAttr`, `hasAudienceTags`, `DEFAULT_AUDIENCE`) in `src/lib/schema/audience.ts` is the single source of truth the reader, the workspace preview and the no-JS fallback share.
- **The `AudiencePicker`** already existed and was already mounted at both the section level (`SectionEditor`) and the block level (`BlockEditor`), writing the optional `audiences` field onto the working copy through `onEdit`. Reused verbatim.
- **The `notes` schema field** already existed on sections (Story 6.2) with its 20,000-char cap, and the reader-serving `stripSpeakerNotes` chokepoint already stripped it. The render tier never read it.

What was WIRED in by this story:

- **The picked level now persists across the preview remount.** `LivePreview` owns `previewLevel` (default `full`) and passes it as `Report`'s `level`, re-seeded on every `{#key document}` remount; `Report` gains an `onlevelchange` callback the embedded switcher fires, so the owner holds the chosen level. Before this, switching to Technical and then typing snapped the preview back to `full` on the next ~200 ms settle (the remount reset the in-component `activeLevel`). This is the one author-facing defect in the existing AC1 machinery, and the fix is minimal (reuse the reader switcher, lift its state).
- **The speaker-notes editor.** A new `SectionNotesEditor` (a disclosure with a labelled textarea + the privacy hint), mounted in `SectionEditor` beside the `AudiencePicker`, edits `section.notes` on the working copy through the same validated-save seam. This is the genuine gap - the field existed, the strip existed, but the editor had no UI to author notes.

### The notes-privacy chokepoint (not weakened)

Speaker notes are author-only. The single privacy boundary is `stripSpeakerNotes` at `getPublishedDocument` (`src/lib/server/documents/reports.ts`): every reader path (`/r/[token]`) funnels through it, so the served document - the rendered HTML and the hydration payload - carries no notes. This story does NOT touch that chokepoint. Two independent reasons notes cannot leak through the editor:

1. The render tier (`toPreviewView` / `toReportView` in `src/lib/render/document-view.ts`) never reads the `notes` field, so the reader-facing render output (including the editor's own live preview) is note-free by construction - the `SectionView` view-model has no `notes` property. A new render-tier tripwire pins this for `toPreviewView` (the editor preview path), parallel to the existing `toReportView` guard.
2. The reader serve strips notes server-side. The existing `reports.test.ts` unit test and the `presenter-view.e2e.ts` guard already pin this; this story adds an editor-authored e2e that mints a real reader share for a note-bearing published report and asserts the note is absent from the served DOM and the SSR HTML.

The notes live in the DRAFT (where the presenter view reads them) and only the reader serve strips them - so the author's note persists across a reload (the e2e proves it) while a reader never sees it.

### Why `onlevelchange` on the render tier is reader-safe

`onlevelchange` is an optional callback prop on `Report.svelte` (the reader-shared render component). The reader render passes no callback, so the branch that fires it is tree-shaken out of the reader closure; `pnpm reader:budget` confirms the reader path is byte-identical at 75.9 KB. The prop adds no import, no server reference, and does not touch the 10.1 reader-purity ESLint boundary (scoped to `src/lib/render/**` and concerned with `$lib/server` / validation-machinery imports, not callback props).

### Seam for 10.7 (autosave / undo / publish)

- A tag edit and a notes edit are ordinary in-edit mutations through `onEdit` -> `scheduleSave`, so they ride the existing autosave debounce and the validate-on-write path; 10.7's autosave / undo-redo / conflict handling composes with them with no special case (a tagged-or-noted document is just a document).
- The preview level (`previewLevel` in `LivePreview`) is a VIEW concern, not document state: it is not part of the working copy, not saved, and not subject to undo / redo. 10.7 should leave it out of the document-history stack - switching the preview level is not an edit.

### QA remediation (2026-06-15)

A 3-agent QA audit (security clean) raised quality/architecture findings; all addressed:

- **(HIGH) `Report.level` one-time-seed caller contract was undocumented.** `activeLevel = $state(level)` captures `level` only at construction; it works today only because `LivePreview` remounts `Report` on every settle (`{#key document}`) and reseeds, and `previewLevel` has a single writer. Documented the contract in the `level` prop JSDoc on `Report.svelte` (seeds once per mount; the preview reseeds via remount, not prop reactivity; a caller needing live changes must remount or own the level via `onlevelchange`) and added an inline `WHY` reason on each `state_referenced_locally` ignore. Additionally hardened the notes-privacy invariant at the TYPE level: `SectionView.notes?: never` in `document-view.ts` so a render-tier `notes` field is now a compile error, converting the load-bearing privacy guarantee from discipline to type-enforcement. The existing `toReportView` and `toPreviewView` no-leak tripwires still pass.
- **(Medium) Reader deep-link level promotion ran in embedded mode.** The `onMount` deep-link / hash-reading block read `window.location.hash` even in the embedded preview, where an editor URL section fragment could transiently promote `activeLevel` and diverge from the author's `previewLevel`. Guarded the whole block with `if (!embedded)`; the LevelSwitcher + `level` prop fully cover the embedded case.
- **(Medium) FALSE POSITIVE - SectionNotesEditor disclosure collapse on settle remount.** VERIFIED: the editor FORM (`SectionEditor` / `SectionNotesEditor` / `AudiencePicker`) lives in the LEFT pane (`.editor-form` in `ReportEditor.svelte`), bound to `doc` directly via `bind:section`, and is NOT inside any `{#key}` boundary. Only the RIGHT pane (`.editor-preview` -> `LivePreview`) is keyed (`{#key document}`). So the editor form does NOT remount on settle, and the `<details>` disclosure open-state and textarea focus are stable across edits. No change made; finding dismissed. (Had the form been remounted, ALL typing would lose focus every ~200 ms, which the e2e would have caught - it does not.)
- **(Medium) Misleading dead CSS fallback removed.** `LivePreview` dangling-links `background: var(--color-amber-12, color-mix(... purple ...))` - the purple fallback for an amber warning was dead (the token always exists) and semantically wrong. Now `var(--color-amber-12)` directly.
- **(Low) Level-persistence regression test added.** `audience-notes.svelte.test.ts`: switch the embedded preview to Technical, change the `document` prop (the `{#key document}` remount the editor performs on every settle), assert `data-level` is still `technical`. Pins the exact regression the `onlevelchange` + reseed fix addressed.
- **(Fold-in) Naming + discoverability.** Renamed `SectionNotesEditor`'s `onInput` helper to `commitValue` (it takes a string, not an Event - the `on`-prefix was misleading) and surfaced the notes-privacy contract as an "Author-only" badge on the COLLAPSED `<summary>`, not only inside the open body.
- **Debt deferred (noted, not done):** a `<Disclosure>` / `EditorDisclosure` extraction for the AudiencePicker + SectionNotesEditor shared `<details>` markup. The two are diverging (the badge is notes-only, the state labels differ), so a shared component would need a snippet-heavy API for two thin call sites - a premature abstraction. Left as-is. Also deferred (per QA scope): the notes `stateLabel` binary present/none -> a snippet preview (minor UX).

Gates re-run after remediation (local, no CI; pnpm off PATH on Node 25, run via `node_modules/.bin`): `pnpm check` 0 errors / 0 warnings; `pnpm lint` clean; `pnpm test` 2007 passed / 172 files, 0 failed (was 2006, +1 the level-persistence test); `pnpm build && pnpm test:e2e` 148 passed / 47 skipped / 0 failed (desktop + mobile); `pnpm build && pnpm test:e2e:multi` 11 passed / 0 failed; `pnpm reader:budget` 75.9 KB / 200 KB (unchanged); `pnpm schema:export` no diff (`notes?: never` is a render-tier TS type, not the document schema).
