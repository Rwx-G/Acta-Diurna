# Story 7.2: Comparison Matrix Block

Status: Done

## Story

As an author or agent,
I want a findings-by-sources matrix with formatting computed from the scales,
So that a multi-source audit reads as a single coverage table without hand-colouring cells.

## Acceptance Criteria

**Given** a Comparison Matrix block carrying findings (each: `category`, `label`, `severity` key, per-source `{ state: found|missing|none, text? }`, `treatment: { before, after, status: action|deferred }`) and referencing the severity + sources scales
**When** rendered
**Then** rows are grouped by `category` (a banner row), each finding shows a severity pill (colour+label from the severity scale) and a row of typed cells: one per source (source tint when `found`, hatched grey when `missing`, a neutral dash when `none`, with the optional `text`), then treatment-before and treatment-after cells tinted by `status` (FR41)

**Given** the findings
**When** any cell's `state` / `severity` / `treatment.status` changes
**Then** the cell formatting is recomputed at render from the scales - no colour is authored per cell

**Given** invalid findings (unknown `severity` key, unknown source key, malformed `state`)
**When** validated
**Then** an actionable problem-details error names the offending finding and field (FR2 parity)

**Given** the rendered block
**When** audited
**Then** it is a pure SSR HTML table (no raw HTML, escaped values only), passes axe-core on the default theme (NFR14), and ships no per-block client JS beyond the reader budget (NFR3)

- DEPENDS ON 7.1 (the document `scales` field + the `resolveScaleRef`/`scaleEntryColor`/`validateScaleReferences` seams). Build 7.1 first. This story is ~80% of the report's value (epic build-order note); 7.4 depends on THIS block (references it by id).
- Proposed `comparison-matrix` Zod shape (the load-bearing contract; `blocks/comparison-matrix.ts`):

```
export const sourceStateSchema = z.enum(['found', 'missing', 'none']);

export const sourceCellSchema = z.object({
  state: sourceStateSchema,
  text: z.string().max(2000, 'Source cell text too long: 2000 characters maximum.').optional()
});

export const treatmentStatusSchema = z.enum(['action', 'deferred']);

export const treatmentSchema = z.object({
  before: z.string().max(2000, 'Treatment-before too long: 2000 characters maximum.'),
  after: z.string().max(2000, 'Treatment-after too long: 2000 characters maximum.'),
  status: treatmentStatusSchema
});

export const findingSchema = z.object({
  category: z.string().min(1).max(300, 'Finding category too long: 300 characters maximum.'),
  label: z.string().min(1).max(300, 'Finding label too long: 300 characters maximum.'),
  severity: idSchema,                                   // an entry key in the severity scale
  sources: z.record(idSchema, sourceCellSchema),        // key = an entry key in the sources scale
  treatment: treatmentSchema,
  tag: z.string().min(1).max(100, 'Finding tag too long: 100 characters maximum.').optional()  // short label, used by 7.4 pills
});

export const comparisonMatrixBlockSchema = z.object({
  type: z.literal('comparison-matrix'),
  id: idSchema,
  audiences: audiencesSchema.optional(),
  severityScale: idSchema,                              // document scales key
  sourceScale: idSchema,                                // document scales key
  findings: z.array(findingSchema).min(1).max(MAX_FINDINGS, 'Too many findings: 500 maximum.')
});
```

- DoS bounds: `MAX_FINDINGS = 500` (a finding row is bounded; 500 rows is well under the table 10000-row cap and keeps SSR within NFR1). The source count is bounded by the sources scale entries (7.1 `MAX_SCALE_ENTRIES = 24`), so the matrix is at most 500 x 24 source cells. Text caps at 2000 chars (cell prose is richer than a 300-char id but bounded). Confirm `MAX_FINDINGS` against the real audit report at kickoff.
- `tag` is carried on the finding now (optional) because 7.4 renders each finding as a short pill beside its intersection ("their short tag/label"). Defining it here means 7.4 reads it without a schema change; absent, 7.4 falls back to `label`. Document this forward-dependency in the finding's doc comment.
- The `sources` record is keyed by source-scale entry key, so a finding need NOT carry a cell for every source (a missing record key renders as `none`/absent at render). Render ALWAYS iterates the sources-scale entry order for columns (not the record's own key order) so every finding row aligns to the same columns - the load-bearing render rule for a readable matrix AND the precondition 7.4 relies on (it derives intersections over the same source set). Document it.
- Treatment status tint is NOT a scale (decision): `status` is a closed two-value enum (`action`/`deferred`) with a fixed semantic meaning, unlike severity/source which are author-defined open sets. Tinting it from theme tokens (e.g. a "due" accent vs a muted "deferred" tone) keeps it a render concern and avoids forcing authors to declare a third scale. The hatched-`missing` and neutral-`none` fills are likewise fixed neutral tokens, not scale colours (epic: "hatched grey when missing, a neutral dash when none"). Only `found` source tint and the severity pill pull from a scale.
- Renderer purity + escaping: follow `TableBlock.svelte` exactly - Svelte text interpolation escapes every value, NO `{@html}` anywhere (epic: "no raw HTML, escaped values only"). The component is SSR-only and ships zero hydration like the other block components, so the reader budget (NFR3, currently ~64 KB) is unaffected - verify with `pnpm reader:budget`. AAA: a colour-coded cell must also carry text (the source `text`, a visually-hidden state name, the severity entry label) so colour is never the only signal; axe-core in e2e gates it (NFR14).
- AMBIGUITY for the product owner (do not invent): (a) whether `category` grouping should also be VALIDATED for contiguity or sorted at render - recommend render-time first-seen grouping (an author lists findings in any order, render groups them; no validation constraint), but a banner appears once per distinct category, so two non-adjacent findings of the same category land under ONE banner - confirm that is the wanted behaviour vs. preserving authored order with repeated banners. (b) the `missing` vs `none` semantics in the report's real vocabulary - the epic fixes the render (hatched grey vs neutral dash) but the dev should confirm the author-facing labels in the editor select match the audit's meaning ("the source looked and did not find it" vs "the source was not run for this finding"). (c) whether a finding with an empty `sources` record (no source covers it) is valid - recommend yes (it renders all-`none`, and 7.4 treats it as the empty intersection), but confirm it is not an authoring mistake worth flagging.

### Debug Log

- **`scales` not previously threaded to the renderer.** `BlockRenderer` received only `view.block`; the comparison-matrix needs the document `scales` to resolve colours. Added `scales` to `ReportView` (`document-view.ts`, both `toReportView` and `toPreviewView`), and passed `scales` + the resolved `theme` down `Report.svelte -> SectionSlide.svelte -> BlockRenderer.svelte -> ComparisonMatrixBlock.svelte` as props. `Report.svelte` already derives `theme` via `resolveTheme(view.theme)`; the matrix needs it because `scaleEntryColor(scale, index, theme)` resolves the categorical palette per theme. The preview path parses `snapshot.scales` permissively with `scalesSchema.safeParse` (a mid-edit snapshot can carry a malformed scales array; the matrix tolerates `undefined` and falls back to a placeholder).
- **Brick scale references cannot live on a section.** A `comparison-matrix` block references `severityScale`/`sourceScale` document-level keys, but a `Brick.factory()` returns only a `SkeletonSection`. The document-level cross-reference pass (7.1) flags dangling refs, so a matrix brick assembled alone into a document fails validation. Added an optional `Brick.scales: () => Scales` companion factory; `appendBrick` now takes the whole draft document and merges the companion scales by key (deduping so re-adding the brick reuses the existing scales). Three existing tests that assembled all bricks without scales (`bricks/index.test.ts`, `skeletons/structural-equality.test.ts`, `server/skeletons/skeletons.test.ts`) were updated to seed `brick.scales()`.
- **Isomorphic cross-ref without importing the block schema.** `validateScaleReferences` (in `scales.ts`) must narrow on `block.type === 'comparison-matrix'` and read the block's ref fields, but importing the block schema there would create an import cycle (section -> scales -> block). Typed the block structurally (`ComparisonMatrixRefView`) inside `scales.ts`; the block has already passed its own shape validation before this pass runs, so the fields are present. Paths use `['sections', i, 'blocks', j, ...]`, formatted by `formatIssuePath` to `sections[i].blocks[j].field`.
- **axe `scrollable-region-focusable` (mobile).** The `.matrix-scroll` wrapper overflows horizontally on a narrow viewport but was not keyboard-reachable. Added `role="region"`, `aria-label`, and `tabindex="0"` (with a `svelte-ignore a11y_no_noninteractive_tabindex` - a scroll container is the recognized exception, same as `SectionSlide`'s in-card scroll). The table's accessible name moved from a `<table aria-label>` to the region label + the `<caption>`. axe clean after the fix.
- **Generated hints update automatically.** The "Valid block types" hint (`errors.ts`) is derived from the union options, so it auto-listed `comparison-matrix`; only the test expectation needed updating. The published JSON Schema (`static/schema/v1.json`) was regenerated via `pnpm schema:export` (the `json-schema.test.ts` freshness guard now expects six union members).

### Completion Notes

- **Final Zod shape** (`blocks/comparison-matrix.ts`): `sourceStateSchema = enum('found'|'missing'|'none')`; `sourceCellSchema = { state, text?: max 2000 }`; `treatmentStatusSchema = enum('action'|'deferred')`; `treatmentSchema = { before: max 2000, after: max 2000, status }`; `findingSchema = { category: 1..300, label: 1..300, severity: idSchema, sources: record(idSchema, sourceCellSchema), treatment, tag?: 1..100 }`; `comparisonMatrixBlockSchema = { type: literal('comparison-matrix'), id: idSchema, audiences?, severityScale: idSchema, sourceScale: idSchema, findings: array(findingSchema).min(1).max(MAX_FINDINGS=500) }`. Additive union member; existing docs validate unchanged.
- **How `scales` reaches the render tier:** `document.scales` -> `ReportView.scales` (`toReportView`/`toPreviewView`) -> prop down `Report -> SectionSlide -> BlockRenderer -> ComparisonMatrixBlock`, alongside the resolved `theme`. The component resolves the severity + source scales with `resolveScaleRef(scales, key)` and colours with the render-tier `scaleEntryColor(scale, entryIndex, theme)` (explicit author hex, else the categorical `--report-chart-N` twin by index). When a referenced scale is absent it renders a neutral placeholder rather than throwing. No `$lib/server` import (renderer-purity boundary held).
- **Cell-formatting rules (state -> visual):** columns iterate the SOURCE-SCALE entry order, not the per-finding record order, so every row aligns (the load-bearing rule 7.4 relies on). `found` -> cell tinted with `color-mix(... var(--source-color) 18% ...)` where `--source-color` is the source entry's resolved scale colour, plus the optional escaped `text`. `missing` -> a fixed neutral `repeating-linear-gradient` hatch on `--report-text` (NOT a scale colour). `none` (including an absent record key) -> a neutral dash. Severity pill: label + `--pill-color` from the severity scale. Treatment tint (status -> tint): `action` -> a `--report-trend-down` wash, `deferred` -> a muted `--report-text-muted` wash (a fixed two-state semantic tint, never a scale; status is a closed enum). Every colour-coded cell carries a visually-hidden state name (`Found`/`Missed`/`Not covered`, the treatment status) so colour is never the sole signal (AAA).
- **Category grouping decision (AMBIGUITY (a)):** banner-on-change preserving AUTHORED order - a banner appears each time the category differs from the previous finding, so two non-adjacent same-category findings produce TWO banners (no reordering). Applied per the prompt's decision #3.
- **Editor vocabulary (AMBIGUITY (b)):** source states surface as "Found" / "Missed" / "Not covered" in the editor select. Applied per decision #4.
- **Empty sources record (AMBIGUITY (c)):** valid - it renders all-`none`, and 7.4 treats it as the empty intersection. The schema allows `sources: {}`.
- **Cross-reference additions** (`validateScaleReferences` in `scales.ts`): for each `comparison-matrix` block, resolve `severityScale` + `sourceScale` against `document.scales` (dangling -> FR2 error at `sections[i].blocks[j].severityScale` / `.sourceScale`); for each finding, the `severity` must be an entry of the severity scale (-> `...findings[k].severity`) and each `sources` record key must be an entry of the sources scale (-> `...findings[k].sources.<key>`). Each issue carries an actionable hint naming the missing scale/entry.
- **Brick + scales:** the `comparisonMatrix` brick's `factory()` produces a schema-valid section (valid standalone at section level - the scale-ref pass runs only at document level); its `scales()` companion seeds the `severity` (ordinal, default colours) + `sources` (nominal) scales the block references. The composer's `appendBrick(draft, brick)` merges them by key. A test proves the brick + its scales validate, and that without the scales the document-level pass flags the dangling refs.
- **Gates:** `pnpm lint` clean, `pnpm check` 0 errors/0 warnings, `pnpm test` 815 passing (was 786; +29 net: schema block, cross-ref, render-component, brick, compose-state, editor-state cases), `pnpm build` ok, `pnpm reader:budget` **66.5 KB / 200 KB** (was 64.5; the matrix is a static SSR table with zero hydration, the delta is shared-chunk shift). `pnpm test:e2e` (Docker): 33 passed / 12 skipped, including the new matrix axe spec on the DEFAULT theme (seeded as a second fixture report so the full example's snapshots stay untouched).
- **For 7.4 (Set-Membership / UpSet):** read this block's findings off the `comparison-matrix` block, referenced BY ITS BLOCK `id` (the epic's "references it by id"). For each finding: `finding.severity` is the severity-scale entry key (resolve colour/label via the same `severity` scale the matrix uses), and `finding.tag ?? finding.label` is the short pill text (the optional `tag` is carried for exactly this; falls back to `label`). Intersections are derived over the `found` sources per finding: a finding's source set is `{ key | sources[key].state === 'found' }`, iterated over the SAME sources-scale entry order this block uses for columns (the precondition for aligned intersections). `missing`/`none`/absent keys are NOT in the found set.
