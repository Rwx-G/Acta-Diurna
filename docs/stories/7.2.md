# Story 7.2: Comparison Matrix Block

Status: Approved

## Story

As an author or agent,
I want a findings-by-sources matrix with formatting computed from the scales,
So that a multi-source audit reads as a single coverage table without hand-colouring cells.

## Acceptance Criteria

**Given** a Comparison Matrix block carrying findings (each: `category`, `label`, `severity` key, per-source `{ state: found|missing|none, text? }`, `treatment: { before, after, status: action|deferred }`) and referencing the severity + sources scales
**When** rendered
**Then** rows are grouped by `category` (a banner row), each finding shows a severity pill (colour+label from the severity scale) and a row of typed cells: one per source (source tint when `found`, hatched grey when `missing`, a neutral dash when `none`, with the optional `text`), then treatment-before and treatment-after cells tinted by `status` (FR41)

**Given** the findings
**When** any cell's `state` / `severity` / `treatment.status` changes
**Then** the cell formatting is recomputed at render from the scales - no colour is authored per cell

**Given** invalid findings (unknown `severity` key, unknown source key, malformed `state`)
**When** validated
**Then** an actionable problem-details error names the offending finding and field (FR2 parity)

**Given** the rendered block
**When** audited
**Then** it is a pure SSR HTML table (no raw HTML, escaped values only), passes axe-core on the default theme (NFR14), and ships no per-block client JS beyond the reader budget (NFR3)

## Tasks / Subtasks

- [ ] New block type `comparison-matrix` (`src/lib/schema/blocks/comparison-matrix.ts`), an ADDITIVE member of the `blockSchema` discriminated union (`blocks/section.ts`): add the import + union member, export the schema/types from `src/lib/schema/index.ts`. Reuse `idSchema` + `audiencesSchema` on the block frame exactly as the five existing blocks do. The findings live ON the block (its content) - NOT a document-level registry (epic decision: "author once, two views; the findings live on the Comparison Matrix block; the Set-Membership block references it by id"). See Dev Notes for the exact Zod shape and bounds.
- [ ] The block references the two scales by key: `severityScale: idSchema` (the severity scale key) and `sourceScale: idSchema` (the sources scale key). Each finding's `severity` is an entry key in the severity scale; each `sources` record key is an entry key in the sources scale. Validation that those keys resolve against the document `scales` uses the 7.1 cross-reference seam (`validateScaleReferences` / `resolveScaleRef`) at the document superRefine locus 7.1 establishes - a dangling severity key, an unknown source key, or a source record key not in the sources scale each yields the FR2 actionable error naming the offending finding index + field (e.g. `sections[2].blocks[1].findings[3].severity`).
- [ ] Render component `src/lib/render/blocks/ComparisonMatrixBlock.svelte` (pure SSR, zero hydration, the renderer-purity boundary - imports schema types + the 7.1 colour helpers only, no `$lib/server`). A pure HTML `<table>`: a category banner row (`<th scope="rowgroup">` / a full-width grouping row) per distinct `category` in first-seen order, then one row per finding under it. Each finding row: a severity pill cell (`scaleEntryColor` from the severity scale + the entry label), one cell per source-scale entry (column order = the sources scale entry order, NOT the per-finding record order, so columns align across findings), then treatment-before and treatment-after cells. ALL values escaped (Svelte text interpolation, as `TableBlock.svelte` does - no `{@html}`). Wire it into `BlockRenderer.svelte` (`{:else if view.block.type === 'comparison-matrix'}`) and the `document-view.ts` block flow (no change needed there - it passes `Block` through).
- [ ] Cell formatting computed at render from the scales, never authored per cell (the AC): source cell tint when `state === 'found'` (the source entry's resolved colour at a low tint via `color-mix`, like the table even-row rule), a hatched grey fill when `state === 'missing'` (a CSS `repeating-linear-gradient` on a neutral token, NOT a colour from a scale), a neutral dash glyph when `state === 'none'`; the optional per-source `text` renders inside the cell, escaped. Treatment cells tinted by `treatment.status` (`action` vs `deferred`) - a fixed two-state semantic tint from theme tokens (NOT a scale; status is a closed enum, see Dev Notes decision). A cell carries `aria-label`/visually-hidden text naming the state so the colour is never the sole signal (AAA, mirrors the chart accessible-title pattern).
- [ ] Editor component (workspace, `src/routes/(workspace)/reports/[id]/edit/`): a `comparison-matrix` block editor for adding/removing findings, picking the `category`/`label`/`severity` (a select bound to the severity scale entries), setting each source's `state` + `text`, and the `treatment` before/after/status. Structured-JSON authoring (epic: findings are authored as JSON in the document, NOT the 2.4 flat-CSV upload/binding path - do NOT route findings through `bindingSchema`/`BlockBinder`). Follow the existing per-block editor shape in the ReportEditor; the block has NO `binding` field at all.
- [ ] A brick (`src/lib/bricks/index.ts`): a `comparisonMatrix` brick factory producing a fresh schema-valid `comparison-matrix` section with a small placeholder findings set referencing placeholder scale keys, plus the matching `scales` so a freshly composed skeleton validates and renders as guidance (the brick must seed BOTH the block and the document `scales` it references, or reference scale keys a companion brick seeds - document the choice). Add it to the `BRICKS` registry + the `BrickId` union.
- [ ] Tests: a valid `comparison-matrix` block parses with full types; findings group by category in render order; columns align to the sources-scale order regardless of per-finding record order; an unknown `severity` key / unknown `sourceScale` key / a source record key absent from the sources scale / a malformed `state` each fail with the FR2 actionable error naming the finding + field; the render emits a pure escaped HTML table (a finding `label` containing `<script>` renders inert text); cell tint/hatch/dash derive from `state` and treatment tint from `status` with no authored cell colour; an axe-core pass on a rendered matrix; the brick factory yields a validating section.

## Dev Notes

- Authority: epics.md Epic 7 Story 7.2 AC verbatim (findings shape, category grouping, severity pill, typed source cells found/missing/none, treatment before/after tinted by status, formatting computed-not-authored, FR2 errors, pure SSR escaped table, axe-core AAA, reader budget) + the "Foundational design" decisions (author once on the block; scales referenced by key; no per-cell colour; SSR renderer-pure). FR2 parity (1.2 `errors.ts`). NFR3 (reader budget), NFR14 (AAA). Scopes touched: `schema` (new block), `render` (new component), `ui` (editor + brick).
- DEPENDS ON 7.1 (the document `scales` field + the `resolveScaleRef`/`scaleEntryColor`/`validateScaleReferences` seams). Build 7.1 first. This story is ~80% of the report's value (epic build-order note); 7.4 depends on THIS block (references it by id).
- Proposed `comparison-matrix` Zod shape (the load-bearing contract; `blocks/comparison-matrix.ts`):

```
export const sourceStateSchema = z.enum(['found', 'missing', 'none']);

export const sourceCellSchema = z.object({
  state: sourceStateSchema,
  text: z.string().max(2000, 'Source cell text too long: 2000 characters maximum.').optional()
});

export const treatmentStatusSchema = z.enum(['action', 'deferred']);

export const treatmentSchema = z.object({
  before: z.string().max(2000, 'Treatment-before too long: 2000 characters maximum.'),
  after: z.string().max(2000, 'Treatment-after too long: 2000 characters maximum.'),
  status: treatmentStatusSchema
});

export const findingSchema = z.object({
  category: z.string().min(1).max(300, 'Finding category too long: 300 characters maximum.'),
  label: z.string().min(1).max(300, 'Finding label too long: 300 characters maximum.'),
  severity: idSchema,                                   // an entry key in the severity scale
  sources: z.record(idSchema, sourceCellSchema),        // key = an entry key in the sources scale
  treatment: treatmentSchema,
  tag: z.string().min(1).max(100, 'Finding tag too long: 100 characters maximum.').optional()  // short label, used by 7.4 pills
});

export const comparisonMatrixBlockSchema = z.object({
  type: z.literal('comparison-matrix'),
  id: idSchema,
  audiences: audiencesSchema.optional(),
  severityScale: idSchema,                              // document scales key
  sourceScale: idSchema,                                // document scales key
  findings: z.array(findingSchema).min(1).max(MAX_FINDINGS, 'Too many findings: 500 maximum.')
});
```

- DoS bounds: `MAX_FINDINGS = 500` (a finding row is bounded; 500 rows is well under the table 10000-row cap and keeps SSR within NFR1). The source count is bounded by the sources scale entries (7.1 `MAX_SCALE_ENTRIES = 24`), so the matrix is at most 500 x 24 source cells. Text caps at 2000 chars (cell prose is richer than a 300-char id but bounded). Confirm `MAX_FINDINGS` against the real audit report at kickoff.
- `tag` is carried on the finding now (optional) because 7.4 renders each finding as a short pill beside its intersection ("their short tag/label"). Defining it here means 7.4 reads it without a schema change; absent, 7.4 falls back to `label`. Document this forward-dependency in the finding's doc comment.
- The `sources` record is keyed by source-scale entry key, so a finding need NOT carry a cell for every source (a missing record key renders as `none`/absent at render). Render ALWAYS iterates the sources-scale entry order for columns (not the record's own key order) so every finding row aligns to the same columns - the load-bearing render rule for a readable matrix AND the precondition 7.4 relies on (it derives intersections over the same source set). Document it.
- Treatment status tint is NOT a scale (decision): `status` is a closed two-value enum (`action`/`deferred`) with a fixed semantic meaning, unlike severity/source which are author-defined open sets. Tinting it from theme tokens (e.g. a "due" accent vs a muted "deferred" tone) keeps it a render concern and avoids forcing authors to declare a third scale. The hatched-`missing` and neutral-`none` fills are likewise fixed neutral tokens, not scale colours (epic: "hatched grey when missing, a neutral dash when none"). Only `found` source tint and the severity pill pull from a scale.
- Renderer purity + escaping: follow `TableBlock.svelte` exactly - Svelte text interpolation escapes every value, NO `{@html}` anywhere (epic: "no raw HTML, escaped values only"). The component is SSR-only and ships zero hydration like the other block components, so the reader budget (NFR3, currently ~64 KB) is unaffected - verify with `pnpm reader:budget`. AAA: a colour-coded cell must also carry text (the source `text`, a visually-hidden state name, the severity entry label) so colour is never the only signal; axe-core in e2e gates it (NFR14).
- AMBIGUITY for the product owner (do not invent): (a) whether `category` grouping should also be VALIDATED for contiguity or sorted at render - recommend render-time first-seen grouping (an author lists findings in any order, render groups them; no validation constraint), but a banner appears once per distinct category, so two non-adjacent findings of the same category land under ONE banner - confirm that is the wanted behaviour vs. preserving authored order with repeated banners. (b) the `missing` vs `none` semantics in the report's real vocabulary - the epic fixes the render (hatched grey vs neutral dash) but the dev should confirm the author-facing labels in the editor select match the audit's meaning ("the source looked and did not find it" vs "the source was not run for this finding"). (c) whether a finding with an empty `sources` record (no source covers it) is valid - recommend yes (it renders all-`none`, and 7.4 treats it as the empty intersection), but confirm it is not an authoring mistake worth flagging.
