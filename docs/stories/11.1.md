# Story 11.1: Detail-Section Schema (Hidden from Flow and TOC, Addressable)

Status: Review

## Story

As an author or agent,
I want a section I can mark as a detail page - rendered and addressable by a stable id, but kept out of the main flow and the table of contents,
So that deep detail can live in the report behind a link without cluttering the cover-to-close narrative.

## Acceptance Criteria

**Given** a section with `kind: 'detail'` (additive, optional; the default is a main-flow section)
**When** the document is validated
**Then** it parses with full TypeScript types, the section keeps its `id`, `title`, `audiences`, `notes`, and `blocks` exactly as a flow section, and `kind` defaults to the main-flow value when absent

**Given** a section that sets both `annex: true` and `kind: 'detail'`
**When** validated
**Then** an actionable problem-details error names the section and states the two placements are mutually exclusive (a section is either main-flow end-matter or a detail page, never both) (FR2 parity)

**Given** the document view model is built (`toReportView`)
**When** sections are shaped
**Then** detail sections are excluded from the main-flow section sequence AND from the `toc` entries, while remaining present and rendered (with their stable anchor id) so an internal link can reach them - the main-flow count the navigation reads excludes them

**Given** an existing document with no `kind` field on any section
**When** validated and rendered
**Then** it validates and renders byte-unchanged - `kind` is additive and optional, N/N-1 compatibility preserved

## Tasks / Subtasks

- [x] Add an additive, optional `kind: z.literal('detail').optional()` to `sectionSchema` (`src/lib/schema/blocks/section.ts`), placed alongside `annex` and before `notes`. Absent is a normal main-flow section; the field reuses the section's existing `id`/`title`/`audiences`/`notes`/`blocks` with no new block path. No schema-version bump (additive).
- [x] Add a section-level `superRefine` enforcing that `annex: true` and `kind: 'detail'` are mutually exclusive: a section setting both fails with an actionable problem-details error at `sections[i].kind`, naming the section by id and stating the two placements are mutually exclusive (FR2 parity, matching the existing schema-error style: offending path + actionable message + hint). The check is section-local (both fields live on the same section), so no document-level cross-reference pass is needed.
- [x] Thread `kind` through the view model (`src/lib/render/document-view.ts`): add a `detail: boolean` flag to `SectionView`, a `detailSections: SectionView[]` array to `ReportView`. In `toReportView`, map every document section to a `SectionView`, then PARTITION into `sections` (main-flow, `!detail`) and `detailSections` (`detail`); build `toc` from the main-flow `sections` only. `hasAudiences` keeps counting all document sections (detail tags count, kickoff default). Apply the same partition in `toPreviewView` (the workspace preview path).
- [x] Render detail sections out-of-sequence in `Report.svelte`: after the `{#each view.sections}` main-flow loop, render `{#each view.detailSections}` as plain section hosts WITHOUT the `sectionEls` binding (so they are not paged, observed by the IntersectionObserver, or counted by the navigation) and without a cover. They carry their `data-audiences` wrapper for the level CSS and their `id` anchor (via `SectionSlide`), so they are in the DOM and reachable by anchor; the link-driven reveal is story 11.3.
- [x] Fix the presenter notes-pairing (`present/presenter-sequence.ts`): `toPresenterSections` paired notes by positional index `view.sections[i] -> document.sections[i]`, which breaks now that `view.sections` excludes detail sections. Pair notes by section id instead. The presenter deck is the main-flow sections only - detail sections are not presented.
- [x] Regenerate the published JSON Schema artifact (`static/schema/v1.json`) via `pnpm schema:export` (the `json-schema.test.ts` freshness test guards it): the section node gains only the optional `kind` const-enum, additively.
- [x] Tests: `kind: 'detail'` parses with full types and keeps id/title/audiences/notes/blocks; a no-kind document validates with `kind === undefined` (additivity); the annex+detail mutual-exclusion error carries the right path/message/hint; `toReportView` excludes detail sections from `sections` and `toc`, keeps them in `detailSections` with their stable anchor, and the main-flow count excludes them; `hasAudiences` counts a detail-only-tagged document; a no-kind document maps byte-unchanged; `toPreviewView` partitions the same way; the presenter deck drops detail sections and pairs notes by id; the regenerated artifact is fresh.

## Dev Notes

- Authority: `docs/prd/epic-11.md` Epic 11 "Foundational design" (detail sections are a `kind` on the existing section, not a new top-level concept; `annex` and `detail` distinct and mutually exclusive; reader navigation counts only main-flow sections; deep-linkable like a flow section fragment; schema additivity) + Story 11.1 AC verbatim above. FR2 parity for the mutual-exclusion error (1.2 `errors.ts`). Architecture: schema is the Zod single source of truth, isomorphic (no `$lib/server` / `$lib/ui` imports in `src/lib/schema`); the renderer is pure (no `$lib/server`, no `{@html}`, escaped). Scopes touched: `schema` (the `kind` field + refine), `render` (the view-model partition + Report.svelte loop), `docs` (the published artifact). FOUNDATION story for Epic 11: 11.2 (the `linkTo` reference) reads these section ids; 11.3 (reader render + navigation to/from a detail page) reads the `detailSections` array.
- ADOPTED KICKOFF DEFAULTS (product owner confirmed): (a) `annex` and `detail` mutually exclusive - both set is a validation error; (b) detail-only audience tags DO count toward the level switcher (`hasAudiences` true); (c) a detail-section fragment is deep-linkable directly. 11.1 implements (a) and (b); (c) is the schema/anchor groundwork (the section renders with its `id` anchor in the DOM), with the on-mount fragment resolution and level promotion for a detail target hardened in 11.3/11.4.
- View-model shape chosen: a SEPARATE `view.detailSections` array, not a `skip` flag the renderer filters in place. The renderer already drives the main-flow sequence, the IntersectionObserver, the progress rail, the keyboard paging and the `sectionEls` binding ALL off `view.sections.length` and the `view.sections` iteration order - so the cleanest way to keep the navigation count correct is to make `view.sections` contain ONLY the main-flow sections (the navigation reads the array it iterates, with no per-element predicate to keep in sync). Detail sections then render from their own array after the flow, with no `sectionEls` binding, so they are in the DOM with their anchor but invisible to every navigation/progress/TOC computation. A flag would have forced every consumer (`view.sections.length`, the `{#each}` index keying the observer, `indexForFragment`) to filter consistently, a drift risk for no gain.
- The mutual-exclusion check is SECTION-LOCAL (a section-level `superRefine`), not the document-level cross-reference pass (`validateScaleReferences`): both `annex` and `kind` live on the same section, so the check needs no whole-document context, unlike a `linkTo` target (story 11.2) which must resolve against the document's section ids and DOES belong in the document-level pass. Keep them distinct.
- Presenter notes-pairing gotcha: `toPresenterSections` aligned `view.sections[i]` to `document.sections[i]` by position for notes. That alignment held only because `toReportView` previously never dropped a section. Now a detail section is dropped from `view.sections`, so a detail section before a flow section would mis-pair notes. Fixed by pairing notes by section id (a `Map<id, notes>`), which is correct regardless of how many sections the partition drops. The presenter deck is intentionally the main-flow sections only.
- Additivity proof is the load-bearing test (mirror 7.1's no-scales test): a document with NO `kind` must validate AND render byte-unchanged. No schema-version bump - `kind` is `z.literal('detail').optional()` on the section. The published `static/schema/v1.json` gains only the optional `kind` enum; `required` and the block union are untouched.
- Deferred to 11.3 (flagged, not in 11.1 scope): the actual link-driven reveal/navigation to a detail page, the "back to where you were" affordance, focus management into the detail page, and the on-mount/activation level-promotion for a detail target that is audience-hidden. 11.1 renders detail sections after the flow in the DOM (reachable by anchor, no-JS fallback intact) but adds NO new reveal JS; that is 11.3's contract.

## Dev Agent Record

### Debug Log

- `svelte-check` caught one downstream break: a presenter test helper constructed a `SectionView` literal that now misses the required `detail` flag (`presenter-sequence.test.ts`). Added `detail: false` to the literal. This surfaced the deeper presenter notes-pairing issue (see Completion Notes), fixed in `presenter-sequence.ts`.
- A first cut of the byte-unchanged view-model test asserted `JSON.parse(JSON.stringify(view))` equals `view`, which failed: the pre-existing view model carries explicit `audiences: undefined`, and `JSON.stringify` drops `undefined` keys, so a self-round-trip differs - a property of the existing model, not the Epic 11 change. Rewrote the test to assert the meaningful invariant (main-flow `sections` length and TOC unchanged, `detailSections` empty, every section `detail: false`) instead of a self-round-trip.

### Completion Notes

- **Schema:** `sectionSchema` gains `kind: z.literal('detail').optional()` and a section-level `superRefine` for the annex+detail mutual exclusion. The error is `code: 'custom'` at `path: ['kind']`, message naming the section by id and stating the placements are mutually exclusive, with a hint telling the author which field to drop - it flows through the existing `toValidationErrors` -> RFC 9457 `errors[]` pipeline (FR2 parity), surfacing at `sections[i].kind`.
- **View model:** `SectionView` gains `detail: boolean`; `ReportView` gains `detailSections: SectionView[]`. `toReportView` maps all sections then partitions main-flow (`sections`) from detail (`detailSections`); `toc` is built from `sections` only; `hasAudiences` still walks all `document.sections` (so detail-only tags count). `toPreviewView` applies the same partition over its per-section parse result. The reader navigation count is `view.sections.length`, which now excludes detail sections with no consumer change.
- **Renderer:** `Report.svelte` renders `view.detailSections` after the main-flow `{#each}`, as `.section-host.detail-host` divs with NO `sectionEls` binding and no cover - in the DOM with their anchor, out of the paging/observer/progress sequence. No new reader JS (budget unchanged at 73.2 KB / 200 KB).
- **Presenter fix:** `toPresenterSections` now pairs author-only notes by section id (`Map<id, notes>`) instead of positional index, correct now that `view.sections` is a subset of `document.sections`. The presenter deck is the main-flow sections only; detail sections are not presented (and their notes are never paired in, so never reach the deck).
- **Artifact:** `static/schema/v1.json` regenerated via `pnpm schema:export`; the section node gains only the optional `kind` const-enum (`{ type: 'string', const: 'detail' }`), additively. `required` and the fifteen-block union are unchanged.
- **Gates:** `pnpm test` (1714 passing, +9 new), `pnpm lint`, `pnpm check` (0 errors), `pnpm build`, `pnpm reader:budget` (73.2 KB / 200 KB, unchanged) all green. `pnpm build && pnpm test:e2e` for the reader/presenter specs (`reader-navigation`, `presenter-view`, `audience-levels`, `reader-accessibility`): 36 passed, 1 pre-existing conditional skip - no regression (the `full` fixture has no detail section, so the rendered output is byte-identical; the partition and detail-render loop are exercised by the unit tests).
