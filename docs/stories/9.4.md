# Story 9.4: Numeric Delta Annotations at Render

## Status

Review

## Story

As an author,
I want a KPI or status figure to show an up/down delta against the previous issue,
So that a reader sees "revenue 1.2M, up 8% vs last month" without me hand-typing the comparison every cycle.

## Acceptance Criteria

**Given** a data-bound KPI block (and, where it applies, a table cell) that opts into a delta
**When** the issue is published
**Then** the platform computes the delta SERVER-SIDE from the predecessor snapshot's id-matched block (prior value, direction up / down / flat, absolute and relative change) and bakes it onto the binding as a `delta` annotation, frozen into this issue's published snapshot - the same precompute-onto-the-binding pattern as `data_as_of` (Story 6.4)

**Given** a baked delta annotation
**When** the report renders
**Then** the renderer reads the delta straight off the validated document and shows the arrow + figure with the prior-issue baseline label, staying PURE (no `$lib/server`, no client compute, and the prior issue's data is never shipped to the reader - only the precomputed delta is)

**Given** a delta-enabled block with no usable predecessor value (first issue, no published predecessor, the prior block had no comparable value, or no id match)
**When** the issue is published and rendered
**Then** the delta annotation is omitted rather than showing a misleading or zero delta (the same "omit rather than mislead" rule as the `data_as_of` caption)

**Given** the `delta` annotation
**When** an existing schema-v1 document with no delta opt-in is validated and rendered
**Then** it is unchanged - `delta` is an additive, optional field on the binding, so every existing document validates and renders exactly as before (no version bump unless kickoff decides a breaking shape forces one)

**Given** a delta-enabled report
**When** the rendered block is audited
**Then** the delta is conveyed by more than colour (an explicit up/down glyph and the signed figure, never colour alone), holds AAA on the default theme (NFR14), and adds no client JS beyond the reader budget (NFR3)

## Dev Notes

### Scope decision (KPI-only; table-cell deltas deferred) - FLAGGED for Romain's kickoff confirmation

The AC reads "a data-bound KPI block **(and, where it applies, a table cell)** that opts into a delta". That parenthetical is PERMISSIVE, not a mandate, and epic-9's "Open questions for kickoff" lists, verbatim: "(1) whether the table-cell delta (9.4) is in v2 scope or KPI-only first". The contract is therefore genuinely undecided on table cells, with no default.

Per the conservative-floor rule, I implemented the unambiguous core - **KPI deltas** - and DID NOT silently pick the expansive interpretation. **Table-cell deltas are deferred and flagged here for Romain's kickoff confirmation.** The architecture is ready for the extension when the decision lands: the bake walks blocks by stable id (the diff engine already id-matches every block type), the schema's `delta` field lives on the shared `binding` object (tables already carry a `binding`), and the renderer pattern (`KpiDelta.svelte`) ports directly to a table-cell indicator. The KPI core is fully delivered and shippable on its own; nothing about adding table cells later reshapes it.

### Where the delta is computed and baked (the `data_as_of` precedent mirrored)

- **Bake at publish, not at bind.** `dataAsOf` is stamped at bind time because freshness is a property of the bound data set. A delta is a property of the SERIES relationship (this issue vs the predecessor's PUBLISHED edition), which only exists at publish. So `publishReport` is the bake site: it validates the draft, resolves the predecessor's published snapshot under the same `AuthorScope`, calls `bakeBindingDeltas`, re-validates, and freezes the result into `publishedDocument`. The draft `document` is untouched (the delta is a snapshot-only annotation), exactly as `publishReport` already leaves the draft alone.
- **Owner-scoped predecessor resolution reuses 9.1/9.2.** `predecessorSnapshot` calls the 9.2 `getDiffSnapshotRow` (the narrow owner-scoped projection: id, status, published snapshot, predecessor edge - no draft document column) and `publishedSnapshotOf` (the migrate-then-validate render-path contract). So a cross-author, unknown, or corrupted `predecessor_id` is the same neutral 404 the diff path raises, a delta is never computed across an ownership boundary, and a predecessor frozen under an earlier schema version is lifted before its values feed the delta. A first issue (null edge) or an unpublished predecessor (no snapshot) yields a null old snapshot and bakes nothing.
- **Id-matching, not value-matching.** The bake indexes the predecessor's bound KPI blocks by their stable id (the 9.1 precondition: `duplicateReport` keeps ids across issues) and compares the current value to the prior value of the SAME id. An unmatched id, a non-KPI predecessor block at that id, or a non-numeric value on either side bakes no delta.

### Pure render + omit-when-unstable

- `KpiDelta.svelte` is a pure presentational component (the `DataAsOf.svelte` shape): it reads `binding.delta` off the already-validated document and renders. No `$lib/server` import, no DB, no client compute - the renderer never recomputes the delta, it only displays the baked figure. So the prior issue's raw data is never shipped to the reader: only the computed `{ direction, priorValue, absolute, relative }` rides on the snapshot.
- **Omit rather than mislead.** When `binding.delta` is `undefined` the component renders nothing (no placeholder, no zero). The bake produces no `delta` for a first issue, an unpublished predecessor, an unmatched id, or a non-numeric value, and DROPS a previously-baked delta on a republish that no longer has a comparable prior value - so a stale figure is never frozen.
- **Flat is truthful, not an omission.** An unchanged numeric value bakes a `flat` delta (▬, "no change", +0) - a real "no movement" signal, distinct from a non-comparable pair that carries no delta at all. The two cases are intentionally different: the reader sees "no change" only when there genuinely was a comparable, unchanged value.

### Accessibility (NFR14) - never colour alone

- The indicator carries the direction THREE ways: an explicit glyph (▲ / ▼ / ▬), the signed figure itself (`signDisplay: 'always'`, so "+8" / "-30" lead with the sign), and a visually-hidden word ("up" / "down" / "no change") for assistive tech. Colour (`--report-trend-up` / `--report-trend-down`) is redundant reinforcement, never the sole signal. The e2e runs axe-core (WCAG 2 A/AA) over the rendered delta surface.

### Additivity / N-N1 (no version bump)

- `delta` is an optional field on the existing `binding` object, additive like `slot` and `dataAsOf`. Every existing schema-v1 document with no delta validates and renders byte-unchanged; the `bake-delta` "no-predecessor bake is deep-equal to the input" test pins this. epic-9 question (2) (does any annotation force a schema v2?) resolves NO for this story: the field is additive, so no `versions/v2.ts` and no migration step. `pnpm schema:export` reflects the additive node on each binding; the artifact is committed.

### Tenancy / privacy

- The delta computation is owner-scoped end to end: the predecessor is resolved through the same owner-filtered `getDiffSnapshotRow` the diff uses, so a delta never crosses authors. Only the numeric `delta` object reaches the reader - no prior-issue prose, no speaker notes (the reader-serving chokepoint `getPublishedDocument` still strips notes), no other author's data.

### QA remediation (2026-06-15)

A 3-agent QA audit converged on seven findings; all fixed, Status stays `Review`.

- **(HIGH) Non-finite delta fields.** `bindingDeltaSchema`'s `priorValue` / `absolute` / `relative` are now `.finite()` (relative stays `.finite().nullable()`), so a hand-authored / externally-produced `Infinity` or `NaN` is rejected at validation rather than rendering as "∞". No migration (the bake only writes finite values via `computeBindingDelta`). New schema test in `binding-delta.test.ts` asserts a non-finite delta is rejected. The `.finite()` constraint did NOT change `static/schema/v1.json` (the exporter emits no JSON-Schema node for it); re-ran `pnpm schema:export`, artifact byte-identical.
- **(Med) `baselineLabel` half-finished.** Removed the never-wired, schema-unbacked `baselineLabel` prop from `KpiDelta.svelte` and its two tests; the fixed "vs previous issue" label stays, the accessible direction word is unchanged. To be re-added only when a schema field backs it.
- **(Med) Multi-item KPI delta.** `kpiValue` now returns `undefined` for `items.length !== 1`, so a multi-item KPI bakes NO binding-level delta (omit-rather-than-mislead - a binding-level delta cannot say which item it annotates). The bound-KPI delta contract is single-item by construction. New bake test asserts omission for a 2-item KPI.
- **(Med) `indexKpiByIdOf` bound-vs-static asymmetry.** Documented in JSDoc that the index covers ALL predecessor KPI blocks (bound or static): the prior value is value-only, only the CURRENT block's binding gates eligibility. New bake test for the mixed case (current bound, predecessor unbound, same id, numeric -> bakes).
- **(Med, perf) Double validation on publish.** Dropped the second full `validateOrThrow` on the baked result in `publishReport`: `bakeBindingDeltas` is structure-preserving over an already-validated current-version document (only adds/removes the optional, finite `binding.delta`), so the baked result is frozen directly. Pinned by a new "baked doc equals the draft except for delta fields" bake test.
- **(Low, cross-engine) Id duplicate tie-break.** `indexKpiByIdOf` now uses FIRST-occurrence-wins (`if (!byId.has(id))`) to match the 9.2 diff engine's `placeBlocks`, so the two id-matching engines agree on a corrupted document. (Block-id uniqueness is still unvalidated - tracked as debt below.)
- **(Folded in) Cheap items.** Added `if (priorById.size === 0) return published;` early-exit in `bakeBindingDeltas` (no predecessor KPI -> no rebuild). Extracted the duplicated glyph map to `src/lib/render/blocks/direction.ts`, used by both `KpiDelta` and `KpiBlock` (distinct SR labels kept per-component). Added a bake test for a non-numeric predecessor value. Added a `down`-direction render case (a second KPI on the second-issue fixture) to the e2e, covered by the existing axe pass over both directions.

**Deferred debt (NOT 9.4 scope):**

- **BLOCK-ID UNIQUENESS VALIDATION** - a document-level `superRefine` mirroring `validateSectionIds`, which BOTH the 9.2 diff engine and the 9.4 bake currently assume but do not enforce. Both engines now degrade consistently (first-occurrence-wins) on a corrupted duplicate-id document, but neither rejects it. This is a candidate for the Epic 9 solidification phase, tracked separately.
- The `.sr-only` CSS duplication across `KpiDelta` / `KpiBlock` (forced by Svelte component scoping).
- A predecessor `validateStoredDocument` re-walk on the publish path - measure-first, not done here.
