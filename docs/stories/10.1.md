# Story 10.1: WYSIWYG Editor Shell - Load, Edit-in-Place, Validated Save

## Status

Review

## Story

As the author,
I want to open a report in a direct-manipulation editor with a live preview and save through the validated service,
So that I edit the document where I read it without leaving the one write contract.

## Acceptance Criteria

**Given** a draft report opened in the editor
**When** the editor loads
**Then** it deep-copies the loaded `DocumentV1` into in-edit state (no aliasing the loaded row), renders the authoritative live preview through `$lib/render` (the same tier the reader uses), and records the loaded `updatedAt` for concurrency

**Given** an in-place edit to any field
**When** the author changes it
**Then** the live preview re-renders from the in-edit document, and the client validates optimistically against the isomorphic Zod schema, placing any error inline at the failing block before any round-trip (guidance, never blocking the edit)

**Given** a save
**When** the in-edit document is posted
**Then** it goes through `updateReportDocument` (validate-on-write) with no parallel path, and an invalid document returns the 422 `errors[]` (block path, field, hint) rendered inline at the failing block - the server remains the authority even if the client validated clean

**Given** a published report
**When** it is opened in the editor
**Then** the read-only rule holds (a published report refuses document writes, 409) and the editor surfaces that the report must be unpublished to edit - the editor never bypasses the lifecycle guard

**Given** the editor bundle
**When** the reader route is measured
**Then** the reader path (`/r/[token]`) ships zero editor code and stays under the 200 KB compressed JS budget (NFR3) - the editor is a workspace-only bundle

## Dev Notes

### This EXTENDS the existing edit surface - it is not a from-scratch build

The workspace editor (`src/routes/(workspace)/reports/[id]/edit/`) already deep-copies the loaded document into `$state` on load, saves through the one validated PATCH service (`updateReportDocument`), and gates editing on draft status (a published report loads read-only with an unpublish affordance). Story 10.1's job was to close the three gaps the epic names against THAT surface, not to rebuild it:

1. **Authoritative live preview embedded in the editor.** Before, the editor only LINKED to a separate `/preview` route; the live preview was not in the editing surface. Now the editor embeds the SAME `LivePreview` component (the pure `$lib/render` tier the reader uses) fed the LIVE in-edit snapshot, so the preview re-renders on every edit. Reusing the existing embedded preview path is deliberate: there is no second renderer and no lookalike - the preview IS the reader render (`toPreviewView` -> `Report.svelte embedded`, which the `/preview` route already used over a static load; here it is fed the reactive `$state.snapshot(doc)`).

2. **Optimistic concurrency.** The service `writeDocument` / `updateReportDocument` ALREADY accepted `expectedUpdatedAt` and raised the 409 `/problems/report-conflict` on a zero-row update; the editor's save action simply never passed it (a documented gap in the epic: "the current editor save does NOT pass it"). The fix is the wiring, not the mechanism: the editor records the loaded `updatedAt`, posts it on every save, advances it to each save's result, and surfaces the 409 as a reload-to-reconcile banner.

3. **Client-side optimistic validation.** Before, the editor showed only SERVER save errors. Now it parses the live document against the isomorphic `documentSchemaV1` and places issues inline before a round-trip (guidance), with the server validate-on-write staying the authority on save.

### Reader-budget isolation - why `documentSchemaV1`, not `validateDocument` (the load-bearing decision)

The reader path (`/r/[token]`) must ship ZERO editor JS and stay byte-identical at 75.8 KB. The renderer tier IS shared between the reader and the workspace preview (both use `$lib/render`), so a careless client import in the editor can perturb the shared chunk and breach the budget.

The first attempt imported `validateDocument` from `$lib/schema` (the server's validate-on-write entry point). Measured: the reader chunk grew +0.8 KB to 76.6 KB. `validateDocument` lives in `src/lib/schema/errors.ts`, which pulls the version registry (`getSchema`), the migration chain (`migrateToVersion`, `MigrationPathError`), and the hint table - and Rollup co-located that graph into a chunk the reader statically imports. A dynamic import of the `$lib/schema` barrel did not isolate it (the barrel re-exports the render-shared schemas too, so the static edge stayed). Confirmed by grepping the built reader chunk: it contained "Supported document schema versions" / `validateDocument`.

The fix: import the schema OBJECT directly. `optimisticDocumentIssues` calls `documentSchemaV1.safeParse(snapshot)` - `documentSchemaV1` (`src/lib/schema/versions/v1.ts`) imports ONLY the per-block/section schemas (`sectionSchema`, `scalesSchema`, `validateInternalLinks`, `validateScaleReferences`, `validateSectionIds`, `changeSummarySchema`, `idSchema`) that the renderer ALREADY loads (`document-view.ts` uses `sectionSchema` / `blockSchema` / `scalesSchema` / `validateInternalLinks`). So it adds zero new modules to the client graph, and crucially never pulls `errors.ts` / the version registry / the migration chain (a server-and-load concern the live editor never needs - the in-edit document is always current-version). After the switch the reader budget is byte-identical at 75.8 KB, and the built chunks contain no version-registry code.

This is NOT a client-side schema fork (the foundational-design non-goal): `documentSchemaV1` IS the isomorphic schema the server validates with, including the same document-level cross-reference superRefine. The only editor-local code is `formatIssuePath` (a trivial Zod-issue-path -> `sections[i].blocks[j].field` formatter, a presentation helper, not a validation rule) - the `optimisticDocumentIssues` unit test pins that its paths match `validateDocument`'s output exactly, so the inline placement agrees before and after the round-trip.

### Optimistic concurrency token lifecycle

- Seeded from `report.updatedAt` on load, posted as `expectedUpdatedAt` on every JS save.
- A successful save advances the token to the returned `savedAt`, so a rapid second save asserts against the state the first one wrote (no spurious self-conflict).
- A 409 sets a `conflict` flag (an amber banner + a "Reload latest" button that `invalidateAll`s); the in-memory edits are kept and the token is NOT advanced - the author reloads to reconcile, never a silent last-writer-wins overwrite.
- Publish / unpublish write a new `updatedAt`; after their `invalidateAll` the handlers reconcile the token to the fresh `report.updatedAt`, so the first edit-and-save after returning to draft does not 409 against a stale pre-publish value.
- The no-JS narrative-save baseline posts no `expectedUpdatedAt`, so it stays on the single-writer path (the service treats undefined as no concurrency check) - its semantics are unchanged.

### Scope and the seams left for 10.2-10.7

This story is the SHELL only: load -> editable working copy -> authoritative live preview -> validated save -> optimistic concurrency -> published read-only. It deliberately does NOT build:

- **10.2 (block palette + structural editing):** add/reorder/delete blocks and sections via the palette and `moveItem` / `newSection` / `newBlock`. The seam: `editor-state.ts` already exports the `newBlock` / `newSection` factories and `moveItem`; `ReportEditor.svelte` already renders per-section editors with move/remove/add wired (carried from the 1.5 form editor). 10.2 layers the palette and drag on top.
- **10.3 / 10.4 (per-block editing):** the per-block-type editors (`TextBlockEditor`, `TableBlockEditor`, ...) already exist and are mounted by `SectionEditor` / `BlockEditor`; 10.3/10.4 refine them as direct-manipulation affordances against the live preview. The shell's inline-error placement (`groupErrorsByLocation` -> `errorsByKey` -> per-block `IssueList`) is the seam they hang on.
- **10.5 (data binding from the editor):** the `bind` / `rebind` / `remap` actions and `BlockBinder` / `RefillPanel` already exist; 10.5 reaches them from the block being edited.
- **10.6 (audience-aware preview, notes, tags):** `LivePreview` / `Report.svelte` already support `level` filtering (Epic 6.1) and `AudiencePicker` already writes tags; 10.6 adds a level switcher on the embedded preview and in-place notes/tags editing. The seam: the preview is already the pure renderer fed the live document, so a `level` prop is all 10.6 needs to thread.
- **10.7 (autosave, undo/redo, conflict-handling UX, publish):** the debounced autosave and the publish/unpublish lifecycle already run; 10.7 adds undo/redo history and a richer conflict-resolution flow. The seam: the optimistic-concurrency token and the `conflict` state this story introduces are exactly what 10.7's autosave + conflict UX build on.

### Non-goals confirmed (foundational design)

No real-time multi-cursor / CRDT co-editing (concurrency is the optimistic-conflict detection this story wires). No freeform-HTML rich text beyond the schema's inline marks. No new block types (Epic 7 owns the catalogue). No new asset-upload pipeline. No client-side document persistence beyond the in-tab save-to-server. The editor stays a desktop workspace surface (the reader is mobile-first). None of these are touched here.

### Tenancy unchanged

Every editor write still flows through the owner-scoped service (`resolveAuthorScope` -> `updateReportDocument` -> the scoped `getRow`): an author edits only their own reports, a cross-author id is the same neutral 404, and the author realm stays separate from the reader and PAT realms. The shell adds no new access path and no new realm.

### Debug Log

- **Reader-budget regression chased to root cause.** Importing `validateDocument` (client-side) pushed the reader chunk from 75.8 KB to 76.6 KB; a dynamic import of the `$lib/schema` barrel did not help (76.9 KB). Isolated it by grepping the built chunks: `errors.ts` (the version registry + migrations + hints) was co-located into a reader-static chunk. Switched to `documentSchemaV1.safeParse` (the schema object the renderer already ships, no `errors.ts`); reader budget returned byte-identical to 75.8 KB and the built chunks carry no version-registry code. Documented as the load-bearing decision in Dev Notes.
- **SvelteKit action `fail()` status is in the BODY, not the HTTP status.** The e2e first asserted `response.status() === 409` on a `?/save` POST; SvelteKit returns a 200 envelope carrying `{type:'failure', status:409, data}`. Fixed the e2e to assert the body's `type` / `status` (the same pattern the publish-lifecycle e2e uses for its action results).
