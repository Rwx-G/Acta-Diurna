# Story 7.8: Code Block and Inline Code

**Epic:** 7 - Rich Block Catalogue (Phase B)
**Status:** Done

## Story

As an author or agent,
I want a monospace code block and an inline-code mark,
So that commands, snippets, and literal identifiers render faithfully in technical reports.

## Acceptance Criteria

**Given** a `code` block with a `code` string and an optional `language` label and optional per-line annotations
**When** rendered
**Then** it renders as a static, selectable `<pre>` monospace block (escaped content, preserved whitespace/newlines), with the optional language label shown and any annotations rendered as adjacent escaped text - and NO copy-to-clipboard button (zero hydration; the reader budget holds)

**Given** prose containing an inline-code mark
**When** rendered
**Then** the marked run renders as a monospace chip (escaped), extending the text block's inline-formatting vocabulary, with no new block needed for inline code

**Given** code content containing HTML-like or script-like text
**When** rendered
**Then** it is fully escaped and inert (no raw HTML, no execution) - the renderer-purity guarantee holds for untrusted code content

**Given** the block and the mark
**When** audited
**Then** they are SSR, Zod-validated, pass axe-core on the default theme, and add no client JS

## Dev Notes

### Code-block shape decisions

The `code` block carries the LITERAL source in `code`, rendered escaped with whitespace and newlines
preserved (`white-space: pre`), never raw HTML and never executed - the renderer-purity guarantee for
untrusted content. The source is bounded TWICE for DoS, mirroring how other blocks bound their content:
a 20000-character ceiling AND a 500-line ceiling (a long single line is still bounded by the character
cap; the line cap stops a pathological many-newlines payload). Annotations are capped at 100 entries,
each note at 280 characters.

`language?` is a free-form short CAPTION label (e.g. `bash`, `sql`, `json`), deliberately NOT a
highlighter directive: there is NO syntax-highlighter library (that would be a new dependency and a
hydration cost), so the renderer shows the label as a small caption and does no highlighting. This keeps
the block plain escaped monospace, within the zero-hydration Phase B stance.

`annotations?` is an optional list of `{ line?, text }`: a required escaped note, and an optional 1-based
`line` tying it to a source line. A trailing or general note carries no line. The shape is intentionally
simple and additive - it can grow (e.g. a `severity`) without breaking existing documents.

NO copy-to-clipboard button: a copy affordance needs client JS and would move the reader JS budget
(NFR3). The Phase B foundational design note is explicit that the code block is a selectable static
`<pre>` only; a copy affordance is a later, budgeted enhancement if ever wanted, and is out of scope here.

### Inline-code mark

The inline-code mark is an ADDITIVE `code?: boolean` on `inlineRunSchema` (the text block's inline-run
vocabulary), the inline twin of the code block. A run without it validates and renders exactly as before,
proven by a render test. The renderer wraps the run text in a monospace `<code class="run-code">` chip;
the marks nest, so a bold inline-code run is `<strong><code>`. To avoid a combinatorial explosion of the
bold/italic/code/link branches, both `TextBlock.svelte` and `CalloutBlock.svelte` now render a run through
a shared `{#snippet markedRun}` that applies the code wrapper then the bold/italic marks, called both
inside and outside the link anchor.

Because the callout body (7.7) reuses the text block's `paragraphSchema` / `inlineRunSchema` verbatim,
inline code works in a callout body with no extra schema change - only the shared snippet was added to the
callout renderer.

### Monospace token

A new `--font-mono` token (a `ui-monospace` system stack) drives both the code block and the inline chip.
It is a SYSTEM font stack, not a self-hosted webfont: no network fetch, so it stays within the reader's
strict no-CDN CSP and adds no asset to the reader budget. The block surface reuses the existing report
tokens (`--report-surface`, `--report-rule-strong`, `--report-text`, `--report-text-muted`); the inline
chip tints with a low wash of `--report-text` over the surface, the same token language the rest of the
report uses.

### Block-type count fan-out

Adding the twelfth block type required two existing tests to roll forward (legitimate, not a contract
change): `errors.test.ts` (the unknown-block-type hint now ends with `code`) and `json-schema.test.ts`
(the block union is now twelve members). The `StructureTree.svelte` exhaustive `never` switch required a
`code` case (svelte-check gate). The document-level cross-reference pass (`scales.ts`) needed no change: a
code block carries no scale reference.
