# Story 7.1: Document-Level Categorical Scales

Status: Review

## Story

As an author or agent,
I want named scales of `{ key, label, colour }` entries (severity, source sets) declared once on the document,
So that every matrix and the legend share one colour and label source instead of redefining it per block.

## Acceptance Criteria

**Given** a document declaring `scales` (e.g. a severity scale and a sources scale, each a list of `{ key, label, color?, sublabel? }`)
**When** a block references a scale entry by key
**Then** its label and colour resolve from the scale, and a missing/typed-wrong scale or key fails validation with an actionable problem-details error naming the offending reference (FR2 parity)

**Given** a scale entry with no explicit colour
**When** rendered
**Then** a colour is assigned deterministically from the theme's categorical palette (stable by index, AAA-safe), so an author who supplies no colours still gets a legible report

**Given** a scale entry with an explicit hex colour below the contrast threshold on the report background
**When** rendered
**Then** it renders in that colour but the workspace surfaces a contrast warning on the report (consistent with FR39 / the "AAA default, author may degrade" stance)

**Given** the `scales` field is absent
**When** an existing document (schema v1, no scales) is validated and rendered
**Then** it validates and renders unchanged - `scales` is additive and optional

## Dev Notes

- Authority: epics.md Epic 7 "Foundational design" (categorical scales: `{ key, label, entries: [{ key, label, color?, sublabel? }] }`, authored once, referenced by key, never colours redefined per block; "AAA by default, author may degrade" with a workspace contrast warning; deterministic theme-palette default colour by index) + Story 7.1 AC verbatim above. FR2 parity for reference errors (1.2 `errors.ts`). NFR14 (AAA on the default theme; author customization may degrade with a surfaced warning) + FR39 stance. Architecture: schema is the Zod single source of truth (AR2/D3), additive version policy (epics.md "Schema additivity": add to v1, do NOT bump unless a breaking change is unavoidable - and document if so). Scopes touched: `schema` (the new `scales` field + module), `render` (palette + contrast helpers), `docs` (the published artifact/examples).
- FOUNDATION STORY for Epic 7. 7.2, 7.3 and 7.4 all depend on `scales` and on the `resolveScaleRef` / `scaleEntryColor` / `scaleContrastWarnings` seams defined here. Build first. Nothing in 7.1 depends on the later stories.
- Proposed `scales` Zod shape (the load-bearing contract; `scales.ts`):

```
export const hexColorSchema = z
  .string()
  .regex(/^#[0-9a-fA-F]{6}$/, 'Use a 6-digit hex colour, e.g. #66023c.');

export const scaleEntrySchema = z.object({
  key: idSchema,                                  // slug, reused from shared.ts
  label: z.string().min(1).max(300, 'Scale entry label too long: 300 characters maximum.'),
  color: hexColorSchema.optional(),               // absent -> palette colour by index
  sublabel: z.string().min(1).max(300, 'Scale entry sublabel too long: 300 characters maximum.').optional()
});

export const scaleSchema = z
  .object({
    key: idSchema,
    label: z.string().min(1).max(300, 'Scale label too long: 300 characters maximum.'),
    kind: z.enum(['ordinal', 'nominal']).optional(),   // ordinal = ranked (severity), nominal = unordered (sources)
    entries: z.array(scaleEntrySchema).min(1).max(MAX_SCALE_ENTRIES, 'Too many scale entries: 24 maximum.')
  })
  .superRefine(/* unique entry keys within the scale */);

export const scalesSchema = z
  .array(scaleSchema)
  .max(MAX_SCALES, 'Too many scales: 16 maximum.')
  .superRefine(/* unique scale keys at document level */);
```

  And on `documentSchemaV1` (`versions/v1.ts`), additive, after `theme`:

```
scales: scalesSchema.optional(),
```

- DoS bounds (consistent with the existing schema caps: 300-char strings, sections 100, blocks 200, table rows 10000, kpi items 50): `MAX_SCALES = 16`, `MAX_SCALE_ENTRIES = 24` per scale. These bound the combinatorial surface 7.4 derives over (an UpSet over N sources is 2^N intersections in the worst case - capping the sources scale entries keeps that bounded; see 7.4 Dev Notes). Strings reuse the 300-char cap. Confirm the two numbers at kickoff if the real audit report needs more.
- Why `kind` is optional metadata only: `ordinal` vs `nominal` lets a future renderer order a severity scale by declared rank and leave a source scale unordered, but V1 renders entries in declared order regardless. It is carried so authors can express intent and a later story can use it; it changes no V1 behaviour. Do not gate any V1 logic on it.
- Default-colour determinism: index the categorical palette by the entry's position in `scale.entries` (0-based), modulo the palette length (6 chart tokens). This is stable across renders for a fixed document and mirrors how `chart-geometry.ts` assigns `colorIndex = seriesIndex % MAX_COLORS`. Reuse that mental model exactly so severity pills and chart series share a colour language. The palette literals live in `palette.ts` (the test twin of the `--report-chart-*` CSS tokens), so the render component emits `var(--report-chart-N)` and the contrast test asserts the hex.
- Contrast warning is a WORKSPACE concern, never a render gate: a sub-threshold author hex still renders in that hex (FR39). The warning rides the same surface a 6.5 theme-contrast warning would (the workspace report list / editor), not the reader. Default-palette colours are AAA-safe by construction (the `--report-chart-*` tokens already pass the contrast tests), so only explicit author hex can warn. Keep the helper pure (in the render tier) so both the workspace check and a test consume it.
- Additivity proof is the load-bearing test (mirror 2.4's slotless-doc test): a document with NO `scales` must validate AND render byte-identically to before. Do NOT bump the schema version - `scales` is purely additive. If the dev finds an unavoidable reason to bump, STOP and surface it (the epic says document the bump; a version bump touches the N/N-1 migration chain `versions/migrations.ts` and the published artifact and is out of proportion to an optional field).
- AMBIGUITY for the product owner (do not invent): (a) the cross-reference validation LOCUS - a block carrying a scale ref (7.2 severity/source, 7.3 legend `scaleRef`) cannot see the document `scales` from inside its own block-level superRefine (Zod validates the block in isolation in the discriminated union); the choice is a document-level superRefine that walks blocks and checks refs against `scales` (centralized, one path-construction site) vs. deferring scale-ref resolution to the render/service layer (validation stays block-local, dangling refs surface at render). RECOMMEND the document-level superRefine so a dangling ref is an FR2 validation error at save/API time (matches the AC "fails validation"), and define the path-construction helper here for 7.2/7.3/7.4 to reuse - but confirm, because it is the one place Epic 7 adds a whole-document validation pass. (b) `MAX_SCALES`/`MAX_SCALE_ENTRIES` exact values (16/24 proposed) - confirm against the real audit report's source count and severity granularity. (c) whether `kind` should be REQUIRED (forcing authors to declare ordinal/nominal) rather than optional metadata - recommend optional (no V1 behaviour depends on it), but flag that making it required later is a breaking change.

### Debug Log

- The categorical `--report-chart-*` tokens are NOT all AAA on the report background, contrary to the task note that called them "already AAA-safe swatches". Measured: default `--report-chart-5` = 6.94:1, midnight `--report-chart-1` = 5.74:1 - both above the AA floor (4.5:1), below AAA (7:1). They are decorative swatch fills (severity pills, chart series), not prose, so AA is their real contract (same stance the existing `contrast.test.ts` applies to `accentContrast` on `accent`). The `categorical palette contrast` test asserts the AA floor, and the doc comments in `palette.ts`/`scales.ts` were corrected from "AAA-safe" to "AA floor, decorative". The functional guarantee the story relies on - a default-palette colour never raises a contrast warning - still holds, because `scaleContrastWarnings` only checks entries with an EXPLICIT `color`; defaults are never fed to it.
- Wrapping `documentSchemaV1` in `.superRefine` turns it from a `ZodObject` into a refined schema. Verified nothing accesses `documentSchemaV1.shape` (only `.safeParse` in `errors.ts`/tests), `z.toJSONSchema` still emits the same `required: ['version','title','sections']` and the five-block union, and `getSchema`/`schemaRegistry` still type-check. All 786 unit tests pass.

### Completion Notes

- **`validateScaleReferences` seam contract (for 7.2/7.3/7.4):** signature `validateScaleReferences(document: { scales?: Scales; sections: ReadonlyArray<{ blocks: ReadonlyArray<{ type: string }> }> }): ScaleReferenceIssue[]`, where `ScaleReferenceIssue = { path: PropertyKey[]; message: string; hint: string }`. It is the ONE document-level cross-reference pass (the agreed locus, AMBIGUITY (a) resolved to the document-level superRefine). It is wired into `documentSchemaV1.superRefine` in `versions/v1.ts`: each returned issue is re-emitted as a zod `custom` issue with `params.hint`, so it flows through the existing `toValidationErrors` pipeline into the RFC 9457 problem-details `errors[]` (FR2 parity) at save/API time. For 7.1 it returns `[]` (no v1 block references a scale). A 7.2+ block that carries a scale/entry ref plugs its check into the loop body: walk `document.sections[i].blocks[j]`, narrow on `block.type`, read the block's ref fields, resolve them against `document.scales` via `resolveScaleRef(scales, scaleKey)` then `resolveEntryRef(scale, entryKey)`, and push a `ScaleReferenceIssue` per dangling ref with `path: ['sections', i, 'blocks', j, <refField>]` and a hint naming the missing scale/entry key. Keep path-construction in this one function so every Epic 7 block shares it.
- **Colour resolution approach:** two layers. Isomorphic (`schema/scales.ts`): `resolveEntryColor(scale, entryKey, paletteIndex?)` returns a tagged union `{ kind: 'hex'; value } | { kind: 'token'; token }` - the token is a `--report-chart-N` CSS custom-property NAME (via `categoricalToken(index)`, `index mod 6`), never a hardcoded hex, so the schema package stays free of theme literals. Render tier (`render/theme/scales.ts`): `scaleEntryColor(scale, entryIndex, theme)` resolves to a concrete hex per theme from `CATEGORICAL_PALETTES` (the test twins of the CSS tokens in `palette.ts`) so the contrast math can run; the Svelte component emits `var(--report-chart-N)` the same way `ChartBlock.svelte` does. Determinism mirrors `chart-geometry.ts` `colorIndex = seriesIndex % MAX_COLORS`, so severity pills and chart series share one colour language.
- **Contrast helper:** reuses the existing `relativeLuminance`/`contrastRatio` in `render/theme/contrast.ts` (already pure WCAG 2.1 math, no DOM). Added `isBelowAA(ratio)`/`isBelowAAA(ratio)` thresholds there, and `scaleContrastWarnings(scales, theme)` in `render/theme/scales.ts` returning `[{ scaleKey, entryKey, ratio }]` for every EXPLICIT author hex below AAA on the resolved report background. Workspace surface, never a render gate (FR39).
- **Additivity:** no schema-version bump. `scales` is `scalesSchema.optional()` on `documentSchemaV1`. The additivity test (`document.test.ts` "validates a v1 document with no scales unchanged") asserts the parsed minimal document equals its input and that no `scales` key is introduced. `minimal.ts`/`minimal.json` stay scales-free; `full.ts`/`full.json` carry a severity (ordinal, mixed colours) + sources (nominal, all defaults) scale; `static/schema/v1.json` regenerated via `pnpm schema:export`.
- **Bounds:** `MAX_SCALES = 16`, `MAX_SCALE_ENTRIES = 24` (AMBIGUITY (b) applied as proposed). `kind` left OPTIONAL metadata, no V1 logic gated on it (AMBIGUITY (c) -> optional).
- **Gates:** `pnpm lint`, `pnpm check` (0 errors), `pnpm test` (786 passing), `pnpm build`, `pnpm reader:budget` (64.5 KB / 200 KB, unchanged - scales add no render path yet) all green. `pnpm test:e2e` not run: scales touch no rendered path in 7.1, so there is nothing for the browser suite to exercise.
