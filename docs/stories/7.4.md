# Story 7.4: Set-Membership (UpSet) Matrix Block

Status: Approved

## Story

As an author or agent,
I want an UpSet-style matrix derived from the same findings,
So that coverage by source-combination is visible at a glance, with zero extra data entry.

## Acceptance Criteria

**Given** a Set-Membership block referencing a Comparison Matrix block by id (`sourceBlockId`)
**When** rendered
**Then** it derives one row per present intersection - findings grouped by the exact set of sources where `state != none` - and renders each row as a dot pattern (one dot per source in the sources scale, filled when the source is in that set, with a line connecting the filled dots) (FR42)

**Given** an intersection row
**When** rendered
**Then** the findings in that intersection appear beside the pattern as severity-coloured pills (from the severity scale) carrying their short tag/label

**Given** the dot-and-line pattern
**When** rendered
**Then** it is SSR SVG built with d3-scale / d3-shape (zero hydration, no LayerChart), within the reader budget (NFR3), and passes axe-core (the SVG carries an accessible text alternative summarising each intersection)

**Given** a `sourceBlockId` that does not resolve to a Comparison Matrix block in the same document, or findings that are all `none`
**When** validated or rendered
**Then** validation flags the dangling reference (problem-details), and an all-`none` data set renders a neutral empty state rather than crashing

## Tasks / Subtasks

- [ ] New block type `set-membership` (`src/lib/schema/blocks/set-membership.ts`), additive member of the `blockSchema` discriminated union. Frame reuses `idSchema` + `audiencesSchema`. `sourceBlockId: idSchema` (the id of a `comparison-matrix` block IN THE SAME DOCUMENT). NO findings of its own - it derives everything from the referenced matrix (epic: "references that block by id; it never re-enters findings"). Optional render hints allowed (e.g. a `title`), but no data. Export from `src/lib/schema/index.ts`.
- [ ] Dangling-reference validation at the document superRefine locus (7.1 seam): `sourceBlockId` must resolve to a block of type `comparison-matrix` somewhere in the document's sections. A `sourceBlockId` that matches no block, or matches a block that is not a `comparison-matrix`, yields the FR2 actionable problem-details error naming the offending block + the missing/mismatched reference (the AC "validation flags the dangling reference"). This is the second whole-document cross-reference 7.1 establishes the locus for (the first being scale refs); reuse the same path-construction helper.
- [ ] Intersection-derivation algorithm as a PURE ISOMORPHIC function (`src/lib/render/blocks/upset-geometry.ts`, sibling to `chart-geometry.ts`, no DOM, no server): given the referenced matrix's findings + the sources-scale entry order, group findings by the EXACT set of sources where `state !== 'none'` (an intersection key = the sorted set of source-scale entry keys with a non-`none` state). Produce one row per PRESENT intersection (an intersection with zero findings is omitted), each row carrying: the membership set (which sources are in it), the findings in it (with their `severity` + `tag`/`label` for the pills), and a count. Order rows deterministically (recommend by descending finding count, then by membership size - the conventional UpSet ordering; document the chosen order). The function returns plain data (membership booleans per source, finding pill descriptors, dot/line pixel geometry via d3-scale/d3-shape) - NEVER the raw findings beyond what the SVG + pills need (mirrors `chart-geometry.ts`'s "only the path strings and positions" rule, NFR3).
- [ ] SSR SVG render component `src/lib/render/blocks/SetMembershipBlock.svelte` (pure SSR, zero hydration, the `ChartBlock.svelte` pattern exactly): a static `<svg>` built from the geometry - one dot per sources-scale entry per intersection row (filled when the source is in that intersection's set, hollow otherwise), a connecting line through the filled dots of each row (d3-shape `line`), and the severity-coloured finding pills beside each row (`scaleEntryColor` from the severity scale, 7.1). Reuse the chart colour-token approach (`var(--report-chart-N)`/explicit hex). `role="img"` + a `<title>`/`<desc>` accessible text alternative SUMMARISING each intersection ("3 findings covered by PingCastle and PurpleKnight but not Synacktiv", generalized - no domain vocabulary in the code) so the pattern is not the sole signal (AAA, the AC). Wire into `BlockRenderer.svelte`. Consumes the document `scales` + the referenced matrix via the render plumbing 7.2/7.3 established.
- [ ] All-`none` / empty intersection neutral state: when every finding in the referenced matrix is `none` across all sources (or the matrix has no findings), there are no present intersections - render a neutral empty state (a short escaped message, e.g. "No source coverage to chart yet."), NEVER a crash or an empty SVG (the AC). The derivation function returns an empty rows array; the component branches to the empty state (mirrors `BlockPlaceholder` usage in `ChartBlock`/`TableBlock`).
- [ ] Reader budget: the SVG is SSR-only with zero hydration and d3-scale/d3-shape are math-only (already in the reader-excluded chart path) - no new dependency, no client JS (epic: "no LayerChart, zero hydration"). Verify `pnpm reader:budget` stays under 200 KB (currently ~64 KB) and the SetMembership block adds nothing to the reader closure.
- [ ] Tests: a valid `set-membership` parses; a `sourceBlockId` resolving to no block / to a non-matrix block fails with the FR2 actionable error; the derivation groups findings by exact source set (a fixture with overlapping coverage yields the expected intersections + counts), omits empty intersections, and orders rows deterministically; an all-`none` matrix yields zero rows and the component renders the neutral empty state (no crash); the SVG is pure SSR with a `<title>`/`<desc>` summarising each intersection (axe-core pass); the pills carry the severity colour + the finding `tag`/`label`; `pnpm reader:budget` unchanged.

## Dev Notes

- Authority: epics.md Epic 7 Story 7.4 AC verbatim (references a comparison-matrix by `sourceBlockId`; derives one row per present intersection grouped by the exact set of sources where `state != none`; dot-per-source + connecting line; severity-coloured finding pills with short tag/label; SSR SVG via d3-scale/d3-shape, zero hydration, no LayerChart; accessible text alternative per intersection; dangling-ref problem-details; all-`none` neutral empty state) + the "Foundational design" (author once, two views: the UpSet REFERENCES the matrix by id and re-enters nothing; SVG via d3-scale/d3-shape since 1.6, LayerChart dropped - do not reintroduce). FR2 parity (1.2 `errors.ts`). NFR3 (reader budget, no raw dataset shipped), NFR14 (AAA / accessible alternative). Scopes: `schema` (new block), `render` (geometry + SVG component). The ONLY genuinely new visualization in Epic 7 (the bonus after the report is already useful post-7.3).
- DEPENDS ON 7.1 (scales + cross-ref seam) AND 7.2 (the `comparison-matrix` block it references by id, and the finding `severity`/`tag` fields it reads for the pills). Build LAST. Build order 7.1 -> 7.2 -> 7.3 -> 7.4.
- Proposed `set-membership` Zod shape (the load-bearing contract; `blocks/set-membership.ts`):

```
export const setMembershipBlockSchema = z.object({
  type: z.literal('set-membership'),
  id: idSchema,
  audiences: audiencesSchema.optional(),
  sourceBlockId: idSchema,                              // id of a comparison-matrix block in the same document
  title: z.string().min(1).max(300, 'Set-membership title too long: 300 characters maximum.').optional()
});
```

- Intersection-derivation contract (the load-bearing pure function, `upset-geometry.ts`):
  - Input: the referenced matrix's `findings` + the sources-scale entry keys in scale order.
  - For each finding, its membership set = `{ sourceKey | finding.sources[sourceKey]?.state !== 'none' }` (an ABSENT source record key counts as `none` - it is not in the set; consistent with 7.2's "a missing record key renders as none"). The intersection key is the membership set's source keys sorted in sources-scale order (a stable, canonical key).
  - Group findings by that key; emit one row per NON-EMPTY group (a present intersection). A finding whose membership set is empty (all-`none`) belongs to the empty intersection, which is OMITTED from rows (it has no dots to draw) - it is NOT a crash, it is just not charted. When EVERY finding is empty-set (the all-`none` AC), rows is empty and the component shows the neutral empty state.
  - Row order: descending finding count, then descending membership size, then the canonical key (deterministic, conventional UpSet). Document the exact tiebreak.
  - Output: per row { membership: boolean[] aligned to the sources-scale order, findingPills: [{ severity, tag/label }], count, dot/line pixel geometry }. Ship ONLY this, never the raw `text`/`treatment` of the findings (NFR3 "no raw dataset beyond what the SVG needs").
- Why a pure geometry module sibling to `chart-geometry.ts`: it keeps the math isomorphic and testable without a DOM, and keeps the SVG component a thin static emitter (the 1.6 D12 SSR-only chart pattern). d3-scale (a band/point scale over the sources for dot x-positions, over the intersection rows for y) + d3-shape (`line` for the connector) - the EXACT two packages already in `chart-geometry.ts`, no new dependency (CLAUDE.md "no new dependencies"; epic "no new dependency beyond the existing d3-scale/d3-shape").
- Combinatorial bound: an UpSet over N sources has up to 2^N possible intersections, but only PRESENT ones are emitted and the row count is bounded by the finding count (`MAX_FINDINGS = 500`, 7.2) - at most one row per distinct membership set actually present, never 2^N empty rows. The sources scale is capped at 24 entries (7.1), so a row's dot count is <= 24. SSR stays within NFR1. No unbounded surface.
- Dangling-ref + cross-document scope: `sourceBlockId` must resolve WITHIN THE SAME DOCUMENT (epic: "a comparison-matrix block in the same document"). The resolution walks the document's sections for a block with that id and `type === 'comparison-matrix'`. This is a whole-document concern (the referenced block can be in any section), so it lives at the 7.1 document superRefine locus, not the block-local superRefine. A `set-membership` pointing at a `table` block id, or at a non-existent id, is the dangling-ref FR2 error.
- AMBIGUITY for the product owner (do not invent): (a) the EXACT intersection row ordering (descending count then membership size proposed - the conventional UpSet sort) vs. a fixed author-meaningful order - recommend the conventional descending-count sort (it surfaces the biggest coverage gaps first), but confirm. (b) whether a source whose state is `missing` (the source looked, did not find) counts as IN the membership set or OUT - the AC says "where `state != none`", which puts `missing` IN the set alongside `found`; CONFIRM this is intended (UpSet conventionally charts "did this source have an opinion" which `missing` arguably is, vs "did this source cover it" which is only `found`) - this is the single most load-bearing semantic of the whole block and the epic's literal wording (`state != none`) is the current contract; flag it explicitly before implementing. (c) whether multiple `set-membership` blocks may reference the same matrix - recommend yes (no reason to forbid; each derives independently), no constraint needed, but confirm.
