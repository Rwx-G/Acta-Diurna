# Story 6.3: Access Audit Log & Retention

**Epic:** 6 - Multi-Audience Reading & Governance (Phase 2)
**Status:** Done

As the author,
I want a full access log with configurable retention,
So that I know who read what, within GDPR bounds.

## Acceptance Criteria

**AC1 - Access audit view (FR24)**
Given recorded accesses (since Epic 3)
When I open the audit view
Then I see who opened which report and when, filterable by report and reader.

**AC2 - Configurable auto-purge (FR38, NFR11)**
Given a configured retention period
When records age past it
Then they are purged automatically.

## Dev Notes

**No schema change.** The audit reads tables that already exist (`access_records`, `reader_identities`, `reports`, all since Epic 3 / Epic 8) and retention only DELETEs `access_records` rows. There is no new column or index, so no migration is generated and no version bump - the existing `access_records_report_id_idx` keys the report filter and `reports_owner_id_idx` keys the owner scope.

**Owner-scoped audit query (the tenancy seam).** `listAccessRecords` joins `access_records -> reports` and `access_records -> reader_identities`. Ownership is enforced on the join to `reports`: in multi mode `ownerFilter(scope, reports.ownerId)` ANDs `reports.owner_id = scope.authorId` into the WHERE, so a record whose report belongs to another author is invisible - a cross-owner `?report=` filter is the same empty result as an unknown id (no existence oracle, story 8.2 tenancy). In single mode `ownerFilter` returns `undefined` and no WHERE is added, so the query is byte-identical to an unscoped read (one implicit author owns everything). The report and reader filters AND on top. A malformed filter id is rejected by the UUID guard and returns `[]` WITHOUT touching the db (never a postgres cast error, never a 500). The result is capped at `MAX_ACCESS_RECORDS_LISTED` (500) and ordered `accessed_at DESC`, mirroring `listReports` / `listDataSets` - newest-first so the cap keeps the most recent accesses.

**Retention purge design.** `purgeAccessRecords(db, now, retentionDays)` is a pure function over its `db` argument (individually testable, like the sibling purges) that deletes `access_records` with `accessed_at < accessRecordCutoff(now, retentionDays)`. It NEVER reads the environment - the caller decides whether to run it. `runPurgeSweep` resolves `accessRecordRetentionDays()` (the env var, or `undefined`) and calls `purgeAccessRecords` ONLY when it is set; when unset the sweep skips access records entirely and the count logged is 0. This is the deliberate, configurable retention the 3.3 purge module explicitly deferred to 6.3 - it does not blindly delete audit history. The boot sweep registration in `hooks.server.ts` is unchanged: it already calls `runPurgeSweep(getDb())` on the `PURGE_INTERVAL_MINUTES` timer (off under `NODE_ENV=test`), and the new retention step rides inside it.

**`ACCESS_RECORD_RETENTION_DAYS` - the conservative no-default.** Unlike `DATA_SET_ORPHAN_RETENTION_DAYS` (default 30), this var has NO default. Unset means the audit trail is KEPT indefinitely. An audit trail is evidentiary: silently aging it out by default would destroy history an operator may be relying on, so opting INTO retention is a conscious act. When set, it bounds how long reader-access history lives (GDPR data minimization). It is bounded `1..3650` so a typo cannot delete fresh accesses (zero) or set an absurd window.

**GDPR framing.** The audit is the author's own readers' access to the author's own reports - owner-scoped both in the query and in the view's report-filter options (the dropdown never names another author's report). Retention bounds how long the rows are kept. The scope is kept minimal: who (reader email), which (report title), when (timestamp), nothing more.

**View is plain GET-form filtering (no-JS friendly).** The report dropdown, the per-row "filter by this reader" controls, and clear/reset are all GET form submissions, so the filter state lives in the URL and the page works without JavaScript. This also sidesteps hand-built query-string `href`s (the `svelte/no-navigation-without-resolve` lint rule). Reader ids are opaque in the URL; the active reader filter is surfaced as the matching row's email (falling back to the id when no row matches, e.g. the reader's accesses aged out of retention).
