# Story 8.3: Magic-Link Author Authentication

## Status

Review

## Story

As an author with an email in the allowed domain,
I want to sign in by clicking an emailed magic link,
So that multi-author access is by identified person, with no shared password.

## Acceptance Criteria

**Given** MULTI mode and an email within `AUTHOR_EMAIL_DOMAIN`
**When** the email is submitted at the author login
**Then** a single-use, TTL'd, hashed magic link is emailed (reusing the Epic 3 verification machinery); clicking it opens an author-realm session and, on first sign-in, mints the author record (self-service provisioning)

**Given** MULTI mode
**When** the password login is attempted
**Then** it is DISABLED (the password field is absent and the action refuses) - magic link is the only author path

**Given** an email NOT in `AUTHOR_EMAIL_DOMAIN` (or any unknown email)
**When** it is submitted
**Then** the response is the SAME neutral "check your email" as a valid one (enumeration-safe, NFR9) and no link is sent and no author is minted

**Given** SINGLE mode
**When** the login is shown
**Then** the password login applies unchanged (no magic link, no email field)

**Given** the author realm
**When** a session is issued
**Then** it stays strictly separate from the reader realm and the PAT realm (its own cookie, NFR12), reusing the realm-parameterized session core

## Dev Notes

### Token-reuse decision (a PARALLEL author-verification table, not the reader table)

The reader `verification_tokens` row is bound to BOTH a share and an email (NOT NULL `share_id`, CASCADE on the share). An author signs in to the whole workspace, not to one report, so it has no share to bind. Two options were on the table:

- **Reuse the reader table with a nullable `share_id` + a realm discriminator.** Rejected: it weakens the reader table's NOT NULL `share_id` guarantee (the load-bearing binding for 3.4 restricted mode), forces a realm column and a discriminator on every reader query, and risks a reader token ever being consumed by the author path (or vice versa) if a WHERE clause is mistyped - exactly the realm-blur NFR12 forbids.
- **A separate `author_verification_tokens` table (chosen).** Email-bound only, no `share_id`, no FK to authors (the author row does not exist yet on a FIRST sign-in - it is minted on consume). The two stores are physically separate, consumed by different functions: a reader token has a `share_id` the author consume never supplies, and an author token has no `share_id` the reader consume requires, so a token from one store can NEVER verify the other realm. The machinery (single-use atomic UPDATE ... WHERE consumed_at IS NULL RETURNING, 15-min TTL, SHA-256 hash-at-rest via the shared `hashToken`, dedup-before-issue) is the reader pattern reproduced, not the reader table reused. This keeps both realms' invariants intact at the cost of a small, near-identical store - the right trade for an auth-critical seam.

### Author-minting (self-service provisioning on first verified sign-in)

No author row is created on REQUEST (an unverified email never mints anything - so a request can never plant a row an attacker could later detect). The author is minted on a VERIFIED CONSUME inside `completeAuthorSignIn`, via 8.2's `ensureAuthor(email)` (idempotent, concurrency-safe on the unique email index): a first sign-in inserts the row, a returning author finds it. The minted author id is then passed to `createAuthorSession(authorId)` and stored on `sessions.author_id`.

### How the author id now flows into the tenancy scope (8.2 made real)

`sessions.author_id` -> `validateAuthorSession` surfaces it on `AuthorSession.authorId` -> the `authorRealm` hook resolves it into `locals.authorSession.authorId` -> every workspace route calls `resolveAuthorScope(locals.authorSession?.authorId)`. `resolveAuthorScope` now branches: in MULTI mode a non-null author id is the scope (the real logged-in author), so 8.2's `ownerFilter` predicate filters by THAT author; in SINGLE mode the argument is ignored and the implicit author is used (byte-identical to today, the session author id is null on a password session). The implicit-author fallback for a null id in multi mode is defensive - a live magic-link session always carries a real id. The PAT realm (`resolveApiAuthorScope`) is unchanged: it already reads the token owner from 8.2.

### Enumeration-safety (NFR9)

The login `request-sign-in` action NEVER branches on the address: it returns the neutral `{ state: 'sent' }` for an in-domain, an out-of-domain, or an unknown email. The only surfaced failure is a malformed email SHAPE (a form-validation error telling the author to fix their own typo, not an authorization signal), and a shape error does not consume the shared global brake. The domain check (`isAuthorEmailInDomain`, exact case-insensitive match on `AUTHOR_EMAIL_DOMAIN`) lives INSIDE `requestAuthorSignIn`, behind the neutral return: an off-domain email silently issues no token, mints no author, sends no mail. The mail send is FIRE-AND-FORGET (the response never awaits SMTP), so the attacker-observable SMTP round-trip is off the response path on every email - the residual local-DB delta between the off-domain and in-domain paths is sub-millisecond, below the network noise floor (the same stance the reader gate documents). A pre-send error (DB) is swallowed at the route so the author always sees the neutral state. The magic-link landing returns the IDENTICAL `?expired=1` bounce for a used / expired / forged / throttled token, never a distinct error, so the landing is no oracle either. Rate-limited per-IP plus an IP-independent global brake (the verification limiter pattern), the global brake charged only on a genuine attempt.

### Realm separation (NFR12)

The author session keeps its own `__Host-acta_author` cookie (the realm-parameterized session core, unchanged). The author-verification tokens are physically separate from the reader-verification tokens (different tables, different consume functions, different bindings), so an author link can never open a reader session and a reader link can never open an author session. The PAT realm is untouched.

- The login page Svelte test gained a required `data` prop (the load now returns `{ multi }`); added the multi-mode field-absence and neutral-confirmation cases.
