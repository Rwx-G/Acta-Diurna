# Story 9.5: Reader-Facing Change Summary (audience-aware, opt-in)

## Status

Review

## Story

As an author,
I want to optionally show readers a "what changed since the previous issue" summary,
So that a returning reader orients on the deltas instead of re-reading the whole report - without ever exposing anything they should not see.

## Acceptance Criteria

**Given** a published issue with a published predecessor and the change-summary opt-in enabled
**When** a verified reader opens it
**Then** they see a concise "changes since the previous issue" panel derived from the `SeriesDiff` - sections added/removed, headline data movements - rendered SSR and within the reader budget (NFR3)

**Given** the change summary
**When** it is built for a reader
**Then** it respects the reader's audience level (it never references a block hidden at that level) and is built from the SAME leak-safe snapshot the reader is served - speaker notes are already stripped server-side (`stripSpeakerNotes`), and no other author's data and no draft content ever enters the summary

**Given** the opt-in is off (the default), or there is no published predecessor, or the pair is substantial-drift
**When** the report renders for a reader
**Then** no change-summary panel appears and the report renders exactly as it does today - the opt-in is an additive, optional field, so every existing document is unaffected

**Given** the change summary
**When** it is audited
**Then** it is renderer-pure (no `$lib/server` in the render path, escaped values only, no raw HTML), owner data never crosses authors, passes axe-core on the default theme, and leaks nothing on the neutral/revoked/expired share path (the Epic 3 posture holds unchanged)

## Dev Notes

### Scope decision (field set) - the AC RESOLVES epic-9 open question 3; no kickoff park

epic-9's "Open questions for kickoff" lists, verbatim: "(3) the exact field set surfaced in the reader change summary (9.5) - sections only, or headline data deltas too." That is the open question. **Story 9.5's AC1 resolves it in text:** it reads "a concise 'changes since the previous issue' panel derived from the `SeriesDiff` - **sections added/removed, headline data movements**". So the field set is NOT undecided at the story level: AC1 names it as sections PLUS headline data movements. I implemented exactly that, verbatim. **This is the AC-states-it-clearly case, not the leave-it-undecided case** - I did not invoke the conservative floor, because the AC supplies the contract.

The leak-safe interpretation of "headline data movements" is the load-bearing refinement: the movements are NOT prior-issue raw values, they are the **already-baked `binding.delta` figures** (Story 9.4) the reader is ALREADY served on the KPI block. So surfacing a movement in the summary ships nothing new - it re-presents a figure already in the reader's DOM. A KPI whose data changed but that carries no baked delta (non-numeric, unmatched, multi-item) contributes no movement (omit-rather-than-mislead).

### Audience-aware interpretation (the leak-safe reading of AC2)

AC2: the summary "respects the reader's audience level (it never references a block hidden at that level)". Audience tags are a PRESENTATION filter, not a confidentiality boundary (the `audience.ts` / `shared.ts` audit invariant): every level ships to the authorized reader's DOM and is hidden only by CSS. So the leak-safe implementation is: each summary entry carries its SECTION's own audience tags on `data-audiences`, and the panel renders inside the `.report` root where `data-level` lives - so the SAME reader CSS that hides the section at the reader's level hides its summary line. The summary therefore never VISUALLY references a section the reader's level conceals, in lockstep with the section itself (promoting the level reveals both together). This is the audience model already used for sections, blocks, and detail hosts; the summary reuses it rather than inventing a second mechanism. Documented in `ChangeSummary.svelte` and `change-summary.ts`.

The entry is at SECTION granularity (AC1 is "sections added/removed"), so "never references a block hidden at that level" is satisfied at the coarser section grain: a section hidden at the level hides its whole entry. A summary entry never names an individual block.

### Where the summary is baked (the 9.4 delta precedent mirrored)

- **Bake at publish, after the delta bake.** Like the 9.4 `binding.delta`, the summary is a property of the SERIES relationship (this issue vs the predecessor's PUBLISHED edition), which only exists at publish. `publishReport` is the bake site: it validates the draft, bakes the KPI deltas (`bakeBindingDeltas`), THEN bakes the summary (`bakeChangeSummary`) over the delta-baked document - so the headline movements read the freshly-baked deltas - and freezes the result into `publishedDocument`. The draft `document` is untouched (it keeps the bare `{ enabled: true }` opt-in, no baked entries), exactly as `publishReport` leaves the draft alone for the delta.
- **Owner-scoped predecessor reuses 9.1/9.2/9.4.** The summary bake takes the SAME `predecessor` snapshot the delta bake resolved through `predecessorSnapshot` (the narrow owner-scoped `getDiffSnapshotRow` + `publishedSnapshotOf`). So a cross-author/unknown/corrupted `predecessor_id` is the same neutral 404 the diff path raises, a summary never spans authors, and a predecessor frozen under an earlier schema version is lifted before the diff runs. A first issue (null edge) or unpublished predecessor bakes no entries.
- **No second full validation.** `bakeChangeSummary` is structure-preserving over an already-validated document (it only sets the optional, schema-valid `changeSummary` from the schema-package `buildChangeSummaryEntries`), so `publishReport` freezes the result directly - the same reasoning that already drops the redundant re-validate for the delta bake.

### Pure render + leak-safety (AC2/AC4)

- `ChangeSummary.svelte` is a pure presentational component (the `KpiDelta.svelte` shape): it reads the baked entries off the already-validated document and renders. No `$lib/server`, no DB, no client compute, no `{@html}` - every value (section title, label, figure) is escaped text. So no prior-issue raw content reaches the reader: only the leak-safe facts ride on the snapshot (section ids/titles - already in the reader's TOC; the change verdict - a flag; audience tags - already on the section; the baked deltas - already on the binding).
- **Leak tripwires.** The `change-summary` builder test, the `bake-change-summary` test, and the `publishReport` test each assert the PREDECESSOR's prior prose is NEVER present in the baked summary; the component test asserts a section title is rendered as escaped text (no `<img>` from a script-y title). The reader-serving chokepoint `getPublishedDocument` still strips speaker notes; the summary never carries notes by construction (it only reads sections/verdicts/audiences/deltas).
- **Omit rather than mislead.** No panel renders when the opt-in is off (default), there is no published predecessor (first issue / unpublished), the pair drifted substantially, or a refill changed nothing - the `entries` key is omitted entirely so the renderer's "no panel" branch fires on absence.

### Accessibility (NFR14) - never colour alone, correct heading order

- The headline movement carries direction THREE ways (glyph ▲/▼/▬, the signed figure with `signDisplay: 'always'`, and a visually-hidden word), reusing the 9.4 `direction.ts` glyph + `formatDelta` so the summary and the inline KPI delta cannot drift. Colour is redundant reinforcement, never the sole signal.
- The panel leads the report (before the cover `h1` in DOM order), so its title is a STYLED `<p>` naming the region via `aria-labelledby`, NOT an `<h2>` - a real heading there would break the h1-first heading order (axe `heading-order`). The `<section aria-labelledby>` is a labelled landmark assistive tech announces. axe-core (WCAG 2 A/AA) runs over the rendered panel on both desktop and mobile.

### Additivity / N-N1 (no version bump)

- `changeSummary` is an optional document field, additive like `scales`. Every existing schema-v1 document with no change summary validates and renders byte-unchanged; the `document.test.ts` additivity test pins this (the full fixture has no `changeSummary` and still validates). epic-9 question (2) (does any annotation force a schema v2?) resolves NO for this story too: the field is additive, so no `versions/v2.ts` and no migration. `pnpm schema:export` reflects the additive node; the artifact is committed.

### Tenancy / privacy (AC2/AC4)

- The summary is owner-scoped end to end: the predecessor is resolved through the same owner-filtered `getDiffSnapshotRow` the diff/delta use, so a summary never crosses authors. The neutral/revoked/expired share path is unchanged - the summary lives on `publishedDocument`, served only through the existing share-gated `getPublishedDocument`, which already strips notes and serves one byte-identical neutral 404 on a closed share. This story adds no new reader route and no new serving exit, so the Epic 3 posture holds untouched.
