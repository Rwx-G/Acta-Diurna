# Story 3.3: Reader Verification by Magic Link

Status: Done

## Story

As a reader,
I want to verify my email once and then read freely,
So that access is secure without an account.

## Acceptance Criteria

**Given** a valid share link
**When** I open it
**Then** I am prompted for my email and receive a magic link (single-use token, hashed at rest, 15-minute TTL) (FR18, NFR6, AR6)

**Given** the magic link
**When** clicked
**Then** a reader-realm session opens (separate cookie realm), the report is served, and my verified identity is recorded for this access (reader_identities and access_records tables created by this story's migrations) (FR22, NFR12)
**And** the verification experience follows UX Flow C (themed VerifyCard) in `ux-design-specification.md`

**Given** my persistent reader session
**When** I revisit the report later or from the same device
**Then** no re-verification is required while the session and share remain valid (FR23)

**Given** verification attempts
**When** repeated or probing
**Then** rate limiting engages and responses never reveal whether an email is authorized (NFR9)

### Completion Notes

- **Realm-parameterized session core (NFR12)**: `sessions.ts` serves both realms. Author unchanged (7d fixed, `acta_author`). Reader: `createReaderSession({shareId, reportId, readerIdentityId})`/`validateReaderSession(token, shareId)`/`destroyReaderSession` + `destroyReaderSessionsForShare(shareId)` (the 3.5 revoke seam). Strict separation: distinct cookie names (both HMAC-signed via shared `cookies.ts` internals), distinct DB tables, distinct validators. `validateReaderSession` takes the shareId because the reader realm is PER-SHARE: a valid token for share A returns null against share B.
- **Design parameters applied (backlog "Decided autonomously during Epic 3")**: (1) reader TTL default 30 days, env-configurable via `READER_SESSION_TTL` (days, 1-365, coerced + bounded); author stays 7d. (2) `reader_identities` grain: one global row per normalized email; per-access audit in `access_records`. (3) reader session scope: per-share. (4) verification token bound to email+share - forwarding the raw link does not verify a different address (load-bearing for 3.4). (5) neutral page: `serveNeutralClosed` serves one byte-for-byte `404` + `Cache-Control: no-store` for revoked/expired/unknown alike (3.5 themes the body).
- **Verification token lifecycle (FR18/AR6)**: 256-bit random, SHA-256 at rest, 15-min TTL, single-use (atomic consumed_at claim), bound to (share, email). `issueVerificationToken(shareId, email)` / `consumeVerificationToken(rawToken, shareId)` returning the binding or null (used/expired/wrong-share all null, indistinguishable).
- **Enumeration-safety (NFR9)**: `request-verification` returns the SAME `{state:'sent'}` for any plausible email. The 3.4 restricted-list check goes INSIDE `requestVerification`, behind this neutral return. A mail-delivery failure is caught + swallowed at the route boundary (logged by `sendMail` at warn) so a real send attempt is never revealed. Only a malformed email shape returns a distinct `invalid` (a typo signal). The magic-link email body is report-agnostic and never states the recipient is allowed.
- **FR23 no-re-verify**: the gate load reads the `acta_reader` cookie and calls `validateReaderSession(token, share.id)`. A live session bound to THIS share serves `getPublishedDocument` directly - no VerifyCard, no new token. Per-share, so the same reader still verifies independently for another report's share.
- **Rate limiting + reverse-proxy second line**: per-(IP, share) `TokenBucketLimiter` (cap 5, 1/20s) keyed so probing one share does not starve another, PLUS an IP-independent global brake (cap 60, 1/5s) for proxy collapse. Both the email submission and the magic-link landing consume them. A throttled submission returns `{state:'throttled'}` (429), never an enumeration hint.
- **VerifyCard (UX Flow C)**: themed via `--report-*` tokens (branded gateway). States prompt / sent / expired (`?expired=1` from a dead link) / invalid / throttled. SSR-complete, plain progressively-enhanced POST form; reader budget held at 64.1 KB.
- **No token or email in logs**: zero `logger`/`console` calls in the reader domain/routes (grep-verified); pino redaction is the backstop.
- **For 3.4 (restricted vs open)**: the share's `mode` is already on the `ResolvedShare` the gate reads. 3.4 inserts the recipient-list check inside `requestVerification` (`reader/gate.ts`), BEHIND the neutral `{state:'sent'}` return - unauthorized email silently gets no link, reader sees the identical confirmation. Token is already email-bound, so a restricted-list email cannot be swapped by forwarding. No route/response change needed.
- **For 3.5 (revocation / leak-free)**: `serveNeutralClosed` is the single closed-share exit (404 + no-store) for revoked/expired/unknown - 3.5 themes its body and confirms uniformity. `destroyReaderSessionsForShare(shareId)` is ready so revoking a share invalidates already-verified reader sessions. The gate re-checks `share.status === 'active'` on every load, so a revoked share stops serving even before the sessions are swept.

- **QA iteration 1 (2026-06-12) - three fixes, all enumeration-safe**:
  - **Fix 1 (unpublished-after-share 409 leak)**: an active share whose report was later unpublished (or its snapshot cleared) made `getPublishedDocument` throw a 409 `/problems/report-not-published`, which escaped `serveReport`'s catch and rendered a distinguishable SvelteKit 409 page - an oracle vs the byte-identical neutral 404. `serveReport` now treats that problem type as a closed share and routes it through `serveNeutralClosed`. Before: `verified` session + unpublished report -> 409 error page. After: -> the same neutral 404 + `no-store` as a revoked/expired/unknown share. The FR7 render-version-error (`.errors`) branch is unchanged; only a genuine 5xx escapes.
  - **Fix 2 (verify rate limit not enforced)**: `/r/[token]/verify` consumed the limiter buckets but discarded the boolean, so the landing was throttled in bookkeeping only. It now checks both buckets via `withinVerificationLimit` (per-(IP, share) + global brake, same shape as the email-submit action) and short-circuits BEFORE consuming the verification token. Before: limiter tripped -> token still consumed, normal flow. After: limiter tripped -> `redirect(303, ?expired=1)`, no consume, IDENTICAL to a failed/expired verification (no distinct 429 page, no new oracle).
  - **Fix 3 (mail amplification via request-verification)**: one valid open-mode share link let an attacker POST arbitrary victim emails, each issuing a token + sending operator-branded mail. `requestVerification` now calls `hasLiveVerification(shareId, email)` first and returns early (no issue, no send) when an unconsumed, unexpired token already exists for that (share, email). Caps the pair to one pending verification per 15-min TTL (a victim address is emailed at most once per window per share). Before: N requests -> N tokens + N mails. After: N requests within TTL -> 1 token + 1 mail. The response is the SAME neutral `{state:'sent'}` whether mail was sent or suppressed (the dedup is never revealed); a request after the first token is consumed or expired issues a fresh one. Dedup query: `SELECT id FROM verification_tokens WHERE share_id = ? AND email = ? AND consumed_at IS NULL AND expires_at > now() LIMIT 1`. No weakening of the atomic single-use consume, no change to realm separation or per-share session binding.

- **PO decision (2026-06-12) - reader sessions no longer expire by default**: the reader TTL is no longer a 30-day default. `READER_SESSION_TTL` is now an OPTIONAL operator override; unset (the default) means reader sessions have NO time bound and access is governed entirely by the share (its optional expiry + revocation, re-checked by the gate on every load). Model is nullable-expiry: `reader_sessions.expires_at` is now NULLABLE (migration `0010_reader_session_no_expiry`, single `ALTER TABLE "reader_sessions" ALTER COLUMN "expires_at" DROP NOT NULL`). `readerSessionTtlMs()` returns `number | null` (null when unset; `READER_SESSION_DEFAULT_TTL_MS` removed). `createReaderSession` inserts `null` (no expiry) or a `Date` (override set) and returns the new `CreatedReaderSession` (`expiresAt: Date | null`); the author `CreatedSession` stays `expiresAt: Date`. `validateReaderSession` only sweeps a row whose `expires_at` is non-null and past - a null `expires_at` never expires. `setReaderCookie(cookies, token, expiresAt: Date | null)`: a null expiry still yields a persistent cookie capped at the browser's ~400-day cookie-lifetime maximum (`READER_COOKIE_MAX_DAYS = 400`), so a returning reader re-verifies at most every ~400 days while the share governs real access. Author sessions, per-share scope, realm separation, and the gate's per-load share-status recheck are all unchanged.
- **`.env.example` now updated** (the earlier-session deferral is resolved): `READER_SESSION_TTL` is commented out (`# READER_SESSION_TTL=30`) so the committed default is "no reader-session expiry", with the share governing access.
