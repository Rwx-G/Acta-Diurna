# Story 3.3: Reader Verification by Magic Link

Status: Approved

## Story

As a reader,
I want to verify my email once and then read freely,
So that access is secure without an account.

## Acceptance Criteria

**Given** a valid share link
**When** I open it
**Then** I am prompted for my email and receive a magic link (single-use token, hashed at rest, 15-minute TTL) (FR18, NFR6, AR6)

**Given** the magic link
**When** clicked
**Then** a reader-realm session opens (separate cookie realm), the report is served, and my verified identity is recorded for this access (reader_identities and access_records tables created by this story's migrations) (FR22, NFR12)
**And** the verification experience follows UX Flow C (themed VerifyCard) in `ux-design-specification.md`

**Given** my persistent reader session
**When** I revisit the report later or from the same device
**Then** no re-verification is required while the session and share remain valid (FR23)

**Given** verification attempts
**When** repeated or probing
**Then** rate limiting engages and responses never reveal whether an email is authorized (NFR9)

## Tasks / Subtasks

- [ ] PREREQUISITE REFACTOR (backlog "Epic 3 prep - realm-parameterized session core"): extract the 1.4 session core in `src/lib/server/auth/sessions.ts` to `createSession(realm, ...)` / `validateSession(realm, ...)` / `destroySession(realm, ...)`, parameterized by realm, before adding the reader realm. Author-realm callers (1.4 `acta_author`) keep their behavior unchanged. Add the reader realm: a separate cookie (`acta_reader`, distinct name, HttpOnly/SameSite/Secure-behind-proxy per 1.4 `cookies.ts`), a CONFIGURABLE TTL (reader lifetime is not the author's fixed 7 days - see Dev Notes for the open value), identity/share binding on the session row, and record-then-delete via `access_records` rather than the author realm's delete-on-sight. The `sessions.realm` check constraint already admits `reader` (1.4).
- [ ] `reader_identities` table migration: `id` uuidv7 PK, `email` text (the verified reader email; normalize lowercase/trim), `created_at` timestamptz. Decide and document the uniqueness grain (global unique email vs per-share identity - recommend a single global identity row per email, referenced by access records). `access_records` table migration: `id` uuidv7 PK, `share_id` uuid FK -> shares, `reader_identity_id` uuid FK -> reader_identities, `accessed_at` timestamptz, plus the binding the reader session points at. Indexes per the naming rule. Register both in `schema.ts`. (FR24 configurable-retention is groundwork here, swept in a later Epic.)
- [ ] Verification token store: a single-use, hashed-at-rest, 15-minute-TTL token for the email -> magic-link step. Reuse the 1.4/3.2 token pattern (256-bit random, SHA-256 at rest, hash-keyed lookup, single-use = deleted/marked on first valid click). Store the in-flight verification keyed to (share, email) so the clicked link binds back to the requested share. TTL 15 min per FR18/AR6.
- [ ] Verification gate in front of `/r/[token]` (the reader render route from 1.6/1.7): `r/[token]/+page.server.ts` resolves the share by token (3.2 `getShareByToken`); if the reader has a valid `acta_reader` session bound to this share, serve `getPublishedDocument` (1.7) directly (FR23, no re-verification); otherwise render the email-prompt VerifyCard. A `?/request-verification` action takes the email, sends the magic link via 3.1 `sendMail` + the magic-link template, and ALWAYS returns the same neutral "check your email" confirmation regardless of whether the email is authorized (NFR9 enumeration-safety; 3.4 adds the restricted-list check behind this same neutral response).
- [ ] Magic-link landing `r/[token]/verify/+server.ts` (architecture tree): validate the single-use 15-min token (expired/used -> the neutral "request a new link" page per Flow C), open the reader-realm session bound to (share, identity), record the access in `access_records` (record-then-delete lifecycle), and redirect to the cover. Record/find-or-create the `reader_identities` row for the verified email.
- [ ] Themed VerifyCard (UX Flow C, Component Strategy render tier): `lib/render/VerifyCard.svelte` - carries the REPORT THEME (branded gateway, never a generic auth wall), states: email prompt, sent (neutral confirmation), expired/used ("request a new link"), refused (neutral, indistinguishable from sent per NFR9). Tokens only, AAA on reader content. The verification pages are reader-surface, SSR-complete.
- [ ] Rate limiting on verification (D6 in-memory token bucket, the 1.4 `TokenBucketLimiter`): throttle `?/request-verification` and the magic-link landing per-IP with the global failure brake behind a proxy (1.4 QA pattern + backlog reverse-proxy contract: `ADDRESS_HEADER` only behind a trusted XFF-stripping proxy, global brake as the second line). Responses never reveal authorization status (NFR9).
- [ ] Tests: request-verification sends a magic link and returns the neutral confirmation; an authorized vs (in 3.4) unauthorized email yield IDENTICAL responses (enumeration-safety harness lands here); the magic-link token is single-use (second click -> neutral expired page), 15-min TTL expiry; clicking opens an `acta_reader` session (distinct cookie) and records an `access_records` row + `reader_identities` row; a returning reader with a valid session skips verification (FR23); a revoked/expired share is handled (the neutral page is 3.5, but the gate must not serve a published doc without a live share); rate limiting engages on repeated attempts; the realm-parameterized session refactor leaves author-realm behavior unchanged (1.4 tests still green).

## Dev Notes

- Authority: FR18 (email -> magic link, single-use, hashed, 15-min TTL), FR22 (verified identity recorded per access), FR23 (persistent reader session, no re-verification), NFR6 (token entropy/hash), NFR9 (enumeration-safe, no authorization leak), NFR12 (two strictly separated session realms), architecture D4 (two realms, hand-rolled DB sessions), D5 (token strength/TTL), D6 (in-memory rate limit), D17 (SMTP - via 3.1), UX Flow C + VerifyCard (Component Strategy). Scopes touched: `auth` (session realm core), `share`/`mail` consumers, `db` (two migrations). THE big Epic 3 story.
- DEPENDS ON 3.1 (mail: `sendMail` + magic-link template from `src/lib/server/mail/`) AND 3.2 (shares table + `getShareByToken`/`isExpired`). Implement 3.1 and 3.2 first.
- Seam reuse: session core is the 1.4 `src/lib/server/auth/sessions.ts` (the refactor target), cookie handling `auth/cookies.ts` (`acta_author` is the template for `acta_reader`), rate limiter `auth/rate-limit.ts` (`TokenBucketLimiter` + the global failure brake from 1.4 QA), token hashing/UUIDv7 the 1.4/3.2 pattern (`db/ids.ts`). Reader-served document is `getPublishedDocument(id)` (1.7) - NEVER the draft `document`. Realm resolution is wired in `hooks.server.ts` (1.4 `authorRealm` handle is the template for a `readerRealm` handle populating `event.locals.readerSession`, typed in `app.d.ts`). Error model: throw `AppError`, mapped by `handleError` (1.4 `problem.ts`).
- Reverse-proxy contract (backlog item): `ADDRESS_HEADER` is honored only behind a trusted proxy that strips inbound XFF; per-IP limiting collapses behind a shared proxy, so keep the global failure brake (1.4 QA) as the second line for the verification endpoints.
- Reader-path JS budget (NFR, 200 KB): VerifyCard is reader-tier (`lib/render/`); keep it SSR-complete and light. Verification pages have no loading states (SSR-complete, UX rule).
- AMBIGUITY for the product owner (do not invent): (a) the reader session TTL is not specified by the FRs (the author realm is a fixed 7 days; the backlog says reader TTL is "configurable" but gives no default) - the dev must surface the chosen default + whether it is env-configurable; (b) `reader_identities` uniqueness grain (one global row per email vs per-share) is a modeling decision FR22/FR24 do not pin - recommend global-per-email, but confirm before the migration freezes it; (c) whether a reader session is bound to ONE share or spans all shares the reader has verified (FR23 "the session and share remain valid" reads as per-share binding - recommend per-share). Surface all three before writing the migration.
