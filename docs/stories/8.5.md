# Story 8.5: Reader Domain Whitelist (multi mode, optional)

## Status

Done

## Story

As an operator,
I want to restrict reader verification to allowed destination domains,
So that share links can only ever verify recipients from domains I trust.

## Acceptance Criteria

**Given** MULTI mode with `READER_EMAIL_DOMAINS` set (one or more domain patterns, e.g. `*.example.com`)
**When** a reader submits an email for verification
**Then** an email NOT matching an allowed pattern is refused with the SAME neutral "check your email" (enumeration-safe) and no link is sent - a destination allow-list complementing the per-share recipient list

**Given** `READER_EMAIL_DOMAINS` unset
**When** a reader verifies
**Then** behavior is unchanged (any verified email may read, subject to the per-share recipient list)

**Given** the whitelist
**When** it is evaluated
**Then** the match is on the normalized email domain against the configured patterns, applied behind the neutral return (no timing or response oracle, NFR9)

## Dev Notes

### Where the gate sits and why it is enumeration-safe

The whitelist is the membership half of an enumeration-safe gate, exactly like the 3.4 per-share recipient list: its result decides whether a token is minted, but it sits BEHIND the caller's neutral `{state:'sent'}` confirmation, never in front of it. In `requestVerification` the order is:

1. `isReaderEmailDomainAllowed(email)` - a pure env read, no DB. First because it is the cheapest check and short-circuits before any DB work.
2. `isAuthorizedReader(share, email)` - the per-share recipient list (3.4).
3. `hasLiveVerification(...)` - the dedup-before-issue guard.

All three return the SAME `void`/`undefined` on refusal as the success path returns, so the route's `{ state: 'sent' }` is byte-identical whether the email was allowed, off-domain, off-list, or deduped. The mail send is fire-and-forget on the success path (the response never awaits SMTP), so no path carries the network-scale SMTP round-trip in its timing; the residual is sub-millisecond local work below the network noise floor, the same band NFR9 accepts from the 3.3/3.4 splits. The domain check is purely synchronous and adds no I/O at all, so it introduces no new timing separator.

### Layering with the per-share recipient list

The whitelist is an ADDITIONAL gate, not a replacement: in restricted mode BOTH the destination domain AND the per-share recipient list must pass. In open mode the recipient check is always true, so the whitelist (when set) is the only effective gate; when the whitelist is unset, open mode admits any verified email exactly as before. The two are independent operator controls - the whitelist is instance-wide (every share), the recipient list is per-share.

### Wildcard match semantics (the decision)

`READER_EMAIL_DOMAINS` is parsed at boot (story 8.1, `env.ts`) to a trimmed, lowercased, non-empty pattern list. The match is case-insensitive on the normalized email domain (the email is already lowercased at the `/r/[token]` boundary; the helper re-lowercases the domain defensively).

- **Exact** (`example.org`): matches that domain only. `a.example.org` does NOT match - an operator listing a bare domain means that domain, not its subtree.
- **Leading-`*.` wildcard** (`*.example.com`): matches any subdomain (`a.example.com`, `a.b.example.com`) AND the apex (`example.com`). The reasoning: an operator who allows a domain's subdomains means "everyone at that organization", so including the apex avoids forcing them to list `example.com` and `*.example.com` separately. This is the standard subdomain-wildcard convention and is the more permissive, less-surprising reading for an allow-list whose purpose is "trust this org's domains". A lookalike suffix (`notexample.com` against `*.example.com`) does NOT match - the wildcard requires either equality with the suffix or a real dot-boundary subdomain.

This is intentionally MORE permissive than `auth/author-domain.ts` (story 8.3), which is exact-match only with no wildcard. The author domain is a single bare domain by env contract (`AUTHOR_EMAIL_DOMAIN` is validated as one bare domain at boot) and gates SELF-SERVICE AUTHOR PROVISIONING, where the tighter exact match is the safer default. The reader whitelist is a list of operator-chosen patterns whose documented example is `*.example.com`, so it carries the wildcard. The two helpers stay separate rather than sharing a matcher because their semantics deliberately differ.

### Single mode is inert

A single-mode instance serves consultation-token shares (story 8.4): the `/r/[token]` load direct-serves an open consultation share and never reaches `requestVerification`, and the `request-verification` action early-returns the neutral `sent` before calling the gate. So the whitelist only ever runs on the MULTI-mode verification path. `READER_EMAIL_DOMAINS` has no boot-time multi-mode requirement (it is optional in every mode); if set on a single-mode instance it simply never fires.

## Dev Agent Record

### Debug Log

- The new helper lives in the `sharing` domain (it complements the per-share recipient allow-list) rather than `auth`, so it is exported from the sharing barrel and imported by the gate alongside `isAuthorizedReader`. The gate test's `$lib/server/sharing` mock therefore gained the `isReaderEmailDomainAllowed` entry; defaulting it to `true` in `beforeEach` keeps every pre-existing gate test unaffected (unset-whitelist behavior).
- The helper is synchronous (a pure env read + string match), unlike `isAuthorizedReader` (async, DB-backed). The gate calls it without `await`; the negation `!isReaderEmailDomainAllowed(...)` is the early return.
- `READER_EMAIL_DOMAINS` was already parsed to `string[] | undefined` at boot (story 8.1). The helper reads it as-is; `undefined` is the unset/no-op signal, an array (always non-empty after the env filter) is the active list.

### Completion Notes

- All four gates green (verbatim in the session report): `pnpm lint`, `pnpm check`, `pnpm test`, `pnpm build`.
- No schema change, no migration, no new dependency. Three files of source change (the helper, the barrel export, the gate wiring) plus two test files.
- The change is additive and env-gated: with `READER_EMAIL_DOMAINS` unset, the reader verification path is byte-identical to 8.4.

### Unverified / could not run end to end

- The full multi-mode browser flow (set `READER_EMAIL_DOMAINS`, boot with SMTP, submit an off-domain email at a share, confirm the neutral "check your email" with no mail actually sent, then an in-domain email that receives the link) needs an e2e harness with a real DB and SMTP relay and is not run here. The paths are unit-tested by mocking the helper in the gate and by direct helper tests, not against a live instance.
- The timing-equivalence claim is argued structurally (the domain check is synchronous and the SMTP send is fire-and-forget on the only token-minting path) and asserted via the identical-void-result tests, not measured against a live network.
