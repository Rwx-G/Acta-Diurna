# Story 1.7: Publish Lifecycle & Version-Aware Rendering

Status: Review

## Story

As the author,
I want explicit draft/publish control and version-tolerant rendering,
So that only finished reports circulate and old documents keep rendering after schema upgrades.

## Acceptance Criteria

**Given** a draft
**When** I publish it
**Then** its status changes, publishing is idempotent, and only published reports are eligible for sharing (FR6)

**Given** a document with a supported earlier schema version
**When** rendered
**Then** version dispatch renders it correctly (N/N-1 mechanism exercised with v1 + a synthetic fixture) (FR7)

**Given** an unsupported version
**When** rendered or validated
**Then** a clear problem-details error states the supported range

## Tasks / Subtasks

- [x] Publish/unpublish-to-draft service operations on reports (validate document on publish - a draft can be invalid, a published report never); morphing primary action in the editor header (Validate -> Publish per UX)
- [x] Status surfaced in reports list and editor (StatusChip)
- [x] Version dispatch in the render path wired to the schema `versions/` registry (1.2 groundwork): synthetic v0 fixture + migration v0->v1 used in tests to exercise the real N-1 mechanism
- [x] Unsupported version: problem-details error naming the supported range, rendered as a neutral error state in reader/preview
- [x] Tests: publish idempotency, invalid-draft publish refusal, v0 fixture renders, unsupported version error (Vitest); publish flow e2e (Playwright)

### Completion Notes

- **Snapshot-at-publish (approach a)**: `reports` gains `published_document jsonb` + `published_at timestamptz`, both nullable. `document` is always the authoring draft; `publishReport` validates it and freezes a copy into `published_document` with `published_at`. Draft edits (after unpublish, per the 1.5 read-only guard) evolve `document` while a reader is served the frozen snapshot until the next publish. This is the architecture-correct choice from 1.6's handoff (status-only would leak in-progress edits to readers).
- **Service ops** (`src/lib/server/documents/reports.ts`): `publishReport(id, expectedUpdatedAt?)` - validates the draft (422 with actionable paths if invalid), snapshots, flips status; **idempotent** (publishing a published report returns it unchanged, no re-snapshot, no DB write); optional optimistic-concurrency 409. `unpublishToDraft(id)` - published -> draft, **clears** the snapshot (an unpublished report is not shareable, so no stale frozen copy is served); idempotent on a draft. `assertShareable(report)` - throws 409 `/problems/report-not-published` unless `status === 'published'` (FR6; Epic 3's share service consumes it). `getPublishedDocument(id)` - the reader-served document: the snapshot, run through `validateStoredDocument` (migrate + validate), 409 when not published. The `Report` interface now carries `publishedDocument`/`publishedAt`.
- **Version-aware rendering (FR7)**: a new `versions/migrations.ts` holds the N/N-1 migration chain. `DOCUMENT_MIGRATIONS` is **empty** (v1 is current; a v1 doc migrates to itself by identity). `migrateToVersion(input, target?, migrations?)` walks single-step migrations forward; an unreachable version throws `MigrationPathError`. `validateStoredDocument` (in `errors.ts`) is the render-path contract: migrate-to-current then validate; an unsupported version returns the same `{path:'version'}` actionable error as `validateDocument`, naming the supported range. The `migrations` param is **injectable purely for tests** so the real walk is exercised without a fake production version.
- **Synthetic v0 (TEST ARTIFACT ONLY)**: `versions/synthetic-v0.fixture.ts` - a pretend v0 document (`version: 0`, title field named `name`) plus a `v0 -> v1` migration (renames `name -> title`, stamps `version: 1`). **Never registered** in `schemaRegistry` or `DOCUMENT_MIGRATIONS`. Tests inject `[syntheticV0Migration]` to prove the mechanism end to end: `validateStoredDocument(syntheticV0Document, [syntheticV0Migration])` renders; without the injected migration it returns the unsupported-version error. This is the FR7 N-1 proof before a real v2 exists.
- **View route wiring** (`[id]/view/+page.server.ts`): runs the stored document through `validateStoredDocument`; returns `{document, renderError: null}` on success or `{document: null, renderError}` on a version/validation failure. The page (`+page@.svelte`) renders the `Report` for the happy path and a **neutral error state** (heading + the actionable issues, no crash) otherwise. Author intent preserved: `/view` shows the live DRAFT (the author's preview); the "what readers see" frozen-snapshot path is `getPublishedDocument`, left for Epic 3's `/r/[token]`.
- **Editor morphing CTA** (`ReportEditor.svelte`): `editable` is now `$derived(report.status === 'draft')` (was captured-once) so publish/unpublish flip the editor read-only/editable via `invalidateAll()` without a remount (the cloned `doc` state survives). The lifecycle controls live **outside** the disabled fieldset: a draft shows a primary `Publish` button (server-side validation means an invalid draft comes back as the inline errors[] the save path already renders at the failing blocks); a published report shows "Published - unpublish to edit" + an `Unpublish` button. Publishing is blocked while a draft save is in flight or pending (avoids freezing a stale snapshot). StatusChip unchanged from 1.5.
- **For Epic 2/3**: a published report's reader document is `getPublishedDocument(id)` (the frozen, migrated, validated snapshot) - never read `document` for readers (that is the draft). `assertShareable(report)` is the sharing gate. Editing/deleting a published report requires `unpublishToDraft` first (the 1.5 409 guards still hold). The FR7 render path for any stored document is `validateStoredDocument`; a real v2 needs only a `versions/v2.ts` + `schemaRegistry` entry + one `DOCUMENT_MIGRATIONS` step, and every consumer already routes through the chain.
