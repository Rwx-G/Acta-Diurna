# Story 4.2: Reports API with Workspace Parity

Status: Review

## Story

As an agent or script,
I want full report CRUD and publish through `/api/v1`,
So that programmatic authoring matches everything the workspace can do.

## Acceptance Criteria

**Given** a valid PAT
**When** I create, read, update, publish, or delete a report via `/api/v1/reports`
**Then** behavior matches the workspace exactly - same service layer, same validation, same actionable problem+json errors (FR30, AR4/AR5)

**Given** an invalid document submitted via API
**When** validated
**Then** the problem+json response carries the block path, field, and hint (FR2 parity)

**Given** the API
**When** `/api/v1/openapi.json` is fetched
**Then** a valid OpenAPI 3.1 spec generated from the Zod schemas describes all endpoints (D8)

## Tasks / Subtasks

- [x] `/api/v1/reports` endpoints as THIN ADAPTERS over the existing documents/publish services (the "workspace parity" contract: one service layer, two surfaces - line 299 of architecture). NO business logic, NO validation, NO Drizzle in the route handlers - they parse the request, call the SAME service the workspace calls, and serialize the result. Endpoints (architecture tree `api/v1/reports/`, "CRUD + [id]/publish"):
  - `POST /api/v1/reports` -> `createReport(title)` (1.5); `201` with the created report resource.
  - `GET /api/v1/reports` -> `listReports()` (1.5); `200` with `{ items, total }` ONLY if pagination exists, else the list (architecture: lists return the envelope only when paginated).
  - `GET /api/v1/reports/[id]` -> `getReport(id)` (1.5); `200` or `404` problem+json.
  - `PATCH/PUT /api/v1/reports/[id]` -> `updateReportDocument(id, document, expectedUpdatedAt?)` and/or `updateReportTitle(id, title)` (1.5); document validation runs INSIDE the service and a bad document throws the FR2 actionable `AppError` (block path/field/hint), mapped by the `/api/*` boundary. Decide PATCH (partial: title or document) vs PUT (full replace) and document it.
  - `POST /api/v1/reports/[id]/publish` -> `publishReport(id, expectedUpdatedAt?)` (1.7); `POST /api/v1/reports/[id]/unpublish` -> `unpublishToDraft(id)` (1.7). A non-publishable report surfaces the existing publish-lifecycle `AppError` unchanged.
  - `DELETE /api/v1/reports/[id]` -> `deleteDraft(id)` (1.5); `204` on success, the existing 409 if the report is not a deletable draft.
  - Every endpoint is PAT-authenticated (4.1 `event.locals.apiIdentity`); an unauthenticated call is the 4.1 `401` problem+json, never a redirect (the API never redirects to `/login` - that is a cookie-realm behavior the API path must not inherit).
- [x] Optimistic-concurrency parity: the workspace passes `expectedUpdatedAt` to guard against lost updates (1.5/1.7 emit a 409 on mismatch). The API accepts the same token (an `If-Unmodified-Since`-style field or a body field - decide and document) and returns the SAME 409 problem+json. A script that omits it gets the same last-write-wins behavior the workspace would on an omitted guard.
- [x] FR2 validation parity: an invalid document via the API yields the EXACT problem+json the workspace save produces - `{type, title, status, errors: [{path, message, hint?}]}` with the block path, field, and hint (the 1.2 `errors.ts` actionable layer / 1.5 humanized paths). This is automatic if the route is a thin adapter (the service throws, the boundary maps); the test asserts byte-parity of the `errors[]` shape between the workspace action and the API endpoint for the same bad document.
- [x] `/api/v1/openapi.json` (D8): a valid OpenAPI 3.1 document describing every `/api/v1` path, generated FROM THE ZOD SCHEMAS (the document schema is already Zod 4 in `src/lib/schema/`). APPROACH (flag for the dev/product owner - see Dev Notes): HAND-ASSEMBLE the OpenAPI paths object and `$ref` the existing `z.toJSONSchema()` output for request/response component schemas, rather than adding a Zod-to-OpenAPI generator dependency. The `static/schema/v1.json` artifact (1.2) is the document component schema; the spec references it. The spec advertises the PAT bearer security scheme (`type: http, scheme: bearer`), the problem+json error responses (a shared `Problem` component matching the RFC 9457 shape), and every status code the endpoints return. Served at `/api/v1/openapi.json/+server.ts` - NO auth required on the spec itself (a discovery surface; it leaks no data), consistent with the 4.3 public `/api/v1/schema`.
- [x] OpenAPI validity gate: a test asserts the generated document is valid OpenAPI 3.1 (structural assertions on `openapi: '3.1.0'`, every path present, the security scheme, the `Problem` component, the document `$ref` resolves). If a validator is added it is a DEV dependency only, not runtime - flag it; prefer hand-rolled structural assertions to avoid even a dev dep unless the dev judges a validator clearly better.
- [x] Tests: each endpoint calls its exact service and serializes the result (mock the service, assert the call + the status/body, assert NO business logic in the handler); create/read/list/update/publish/unpublish/delete happy paths + their error statuses; an invalid document returns FR2 problem+json with path/field/hint identical to the workspace; an unauthenticated request returns the 4.1 401 (not a redirect); the optimistic-concurrency 409 round-trips; `/api/v1/openapi.json` returns a valid OpenAPI 3.1 doc covering all paths with the bearer scheme + Problem component + resolvable document `$ref`; the spec endpoint needs no PAT.

- The "thin adapter" rule is the load-bearing architectural contract of this story. If a route handler grows a validation branch, an ownership check, or a Drizzle call, the parity is broken - that logic belongs in the service so the workspace and the API share it. The test strategy (mock the service, assert the call) enforces this structurally.
- OpenAPI-generation decision (RECOMMENDATION, confirm with the dev/product owner): hand-assemble the paths + `$ref` the existing `z.toJSONSchema()` output. Rationale: the document schema is the large, complex one and it is ALREADY exported to JSON Schema (draft 2020-12, which OpenAPI 3.1 is a superset of - 3.1 aligns with JSON Schema 2020-12, so the export `$ref`s cleanly with no translation). The request/response wrappers (create/update payloads, the report resource, the Problem shape) are small and stable - hand-writing them is less code and ZERO new dependency than wiring a Zod-OpenAPI generator (`@asteasolutions/zod-to-openapi` or `zod-openapi`) which would be a runtime dependency requiring CLAUDE.md "no new dependencies without explicit approval" sign-off and would still need the document schema bridged. Prefer hand-assemble; escalate to the product owner only if the endpoint surface grows enough that a generator clearly pays for itself.
- AMBIGUITY for the product owner (do not invent): (a) PATCH vs PUT semantics on update (partial title-or-document vs full replace) - recommend PATCH with an explicit `{title?, document?}` body, but confirm; (b) the optimistic-concurrency token transport (a `version`/`expectedUpdatedAt` body field vs an `If-Unmodified-Since` header) - recommend a body field for agent ergonomics (one JSON payload, no header juggling), but confirm; (c) whether list pagination ships now (driving the `{items,total}` envelope) or lists return a bare array for V1 - recommend bare array for V1 (single-author, few reports) and add pagination when volume demands it, but flag that adding the envelope later is a breaking response-shape change agents must adapt to.

## Dev Agent Record

### Debug Log

- **The load-bearing discovery: the 4.1 `/api/*` handle boundary does NOT catch endpoint throws.** SvelteKit 2.64's internal `resolve()` (kit `runtime/server/respond.js`) wraps endpoint execution in its OWN try/catch and routes any thrown error through `handleError` (always status 500, via `get_status` which returns 500 for a non-`HttpError`) BEFORE the throw ever propagates to a `handle` hook. So an endpoint that just `throw`s an `AppError` produced a 500, not the AppError's status - caught by the e2e (DELETE on a published report returned 500, expected 409). Verified by reading `render_endpoint` (re-throws non-redirect errors) and the inner `resolve()` catch (`handle_fatal_error`). The 4.1 boundary test passed only because it injected a `resolve` that throws synchronously, which does not match the real call path.
- **Fix: a `runApi(handler)` wrapper** (`src/lib/server/api.ts`) every `/api/v1` endpoint composes: it catches `AppError` INSIDE the endpoint (where the throw is still an AppError) and returns `problemResponse(error)`; a non-AppError re-throws to the framework's 500 path. This keeps handlers thin (one `runApi(...)` call, no inline catch discipline) and works WITH SvelteKit. The handle-level `apiErrorBoundary` stays as the backstop for throws OUTSIDE an endpoint (the auth stage) - its docstring now records the scope. 4.3's endpoints must use `runApi` too.
- OpenAPI document `$ref` check: the generated `toJsonSchema()` output is FULLY INLINED (no `$ref`, no `$defs`), so embedding it under `components/schemas/Document` needs no ref rewriting - confirmed by grepping `static/schema/v1.json`. The inner `$schema` (dialect) key is stripped from the embedded copy; OpenAPI 3.1's default dialect is JSON Schema 2020-12, the same the export targets.
- `DEFAULT_REPORT_TITLE` moved from `routes/(workspace)/reports/new/constants.ts` to a shared `$lib/server/documents/defaults.ts` so the workspace action and the API endpoint seed a blank draft with the same title (one constant, two surfaces); the old `constants.ts` now re-exports it (the 1.5 test import stays valid).
- Gates (final): `pnpm lint` clean; `pnpm check` 1035 files 0 errors / 0 warnings; `pnpm test` 702 unit (76 files, +36 from 666); `pnpm build` adapter-node done; `pnpm reader:budget` 64.1 KB (unchanged - the API is server-only, never in the reader closure); `pnpm test:e2e` 30 passed / 11 mobile-skip, including the new desktop reports-api lifecycle; `pnpm audit` unchanged (pre-existing esbuild moderate dev-only + cookie low via kit, documented 1.3/1.4/4.1; no new dependency added).
- **QA iteration 1 (2026-06-12)**: combined PATCH `{title, document}` was two non-atomic writes (`updateReportDocument` guarded, then `updateReportTitle` UNguarded), so a concurrent edit landing between them was silently overwritten - the `expectedUpdatedAt` guard covered only the document write. Confirmed the title is canonically `document.title` (the documents service writes the row `title` from `document.title` in `writeDocument`), so the combined case now sets `document.title = title` and does a SINGLE guarded `updateReportDocument` call - the whole update is atomic under one guard, and `updateReportTitle` is no longer called when a document is present. Gates re-run green: lint/check clean, 704 unit (+2 net), build done, reader 64.1 KB, e2e 30 passed / 11 mobile-skip.

### Completion Notes

- **Endpoints (thin adapters over the EXACT workspace services, story line 27)**: `POST /api/v1/reports` -> `createReport(title)` (blank starter, optional title) or `createReportWithDocument(document)` (an initial document) -> 201; `GET /api/v1/reports` -> `listReports()` -> 200 `{ items }`; `GET /api/v1/reports/:id` -> `getReport(id)` -> 200/404; `PATCH /api/v1/reports/:id` -> `updateReportDocument(id, document, expectedUpdatedAt?)` and/or `updateReportTitle(id, title)` -> 200 (document then title when both present); `POST /api/v1/reports/:id/publish` -> `publishReport(id, expectedUpdatedAt?)` -> 200; `POST /api/v1/reports/:id/unpublish` -> `unpublishToDraft(id)` -> 200; `DELETE /api/v1/reports/:id` -> `deleteDraft(id)` -> 204. The route handlers contain ZERO business logic, validation, or Drizzle - only request parsing (`body.ts`) and a `runApi` call; every error (404/409/422) is the service's `AppError` formatted by `runApi`. All PAT-authed via the 4.1 `apiAuth` (`locals.apiIdentity` non-null), except the public openapi.json.
- **Update verb = PATCH `{title?, document?, expectedUpdatedAt?}`** (backlog Epic 4 decision): PUT implies full replace, which does not match the granular `updateReportTitle`/`updateReportDocument` services. At least one of title/document is required (else 400).
- **Optimistic concurrency = a body field `expectedUpdatedAt`** (backlog Epic 4 decision, NOT `If-Unmodified-Since`): an ISO 8601 string the caller last saw, parsed to the `Date` the service signature already takes. Absent -> last-write-wins (the same omitted-guard behavior the workspace has); a present-but-invalid value -> 400 (a typo fails loudly rather than silently disabling the guard). A stale value -> the service's 409 `/problems/report-conflict`. On publish the body is optional (a bare POST publishes with no guard); unpublish takes no token (reverting to draft is not a lost-update hazard).
- **List envelope = `{ items: [...] }`** (backlog Epic 4 decision, the one with forward-compat weight): an envelope from day one leaves room for `total`/pagination later without the breaking response-shape change a bare-array-to-envelope migration would force on agents.
- **FR2 validation parity (the AC)**: proven by `parity.test.ts` - the REAL `POST` handler over the REAL `createReportWithDocument` (whose `validateOrThrow` runs before any DB access) returns a 422 problem+json whose `errors[]` is asserted byte-identical to `toProblemDetails(validateDocument(doc).errors)` - the one validation contract both surfaces share. The test also asserts an `alt`-field error carries its accessibility hint, so path + message + hint all travel intact. This is automatic precisely because the route is a thin adapter; the e2e re-confirms it over real HTTP.
- **Thin-adapter proof**: every endpoint test mocks the service and asserts the endpoint calls it with the exact args and serializes the result, with NO duplicated logic - and that a service `AppError` (404/409/422) surfaces as the matching problem+json status (via `runApi`).
- **OpenAPI (D8): HAND-ASSEMBLED, refs the generated schema** (`src/lib/server/openapi.ts`, served at `/api/v1/openapi.json`). No zod-to-openapi dependency (CLAUDE.md "no new dependencies" + the story recommendation): OpenAPI 3.1 is a JSON Schema 2020-12 superset, so the large complex document schema is embedded straight from the existing `toJsonSchema()` export (the single source of truth, story 1.2) as `components/schemas/Document`; the small stable wrappers (Report, ReportSummary, Problem, the request bodies) are written by hand. The spec advertises the `patBearer` security scheme (`type: http, scheme: bearer`, D10), the RFC 9457 `Problem` component with the FR2 `errors[]`, and every status code. The validity gate (`openapi.test.ts`) asserts `openapi: '3.1.0'`, every 4.1/4.2 path, the bearer scheme, the Problem component, the Document `$ref` resolving, and NO dangling `$ref` - hand-rolled structural assertions, no validator dependency.
- **openapi.json is PUBLIC (decision)**: added to `isPublicApiPath` in hooks.server.ts so `apiAuth` lets it through with a null identity. An OpenAPI spec is a discovery surface that leaks no report data - the standard choice, and consistent with the 4.3 public `/api/v1/schema`. The endpoints it describes remain PAT-authed.
- **QA iteration 1 (2026-06-12) - two fixes applied**:
  - **(Medium) Combined PATCH `{title, document}` made atomic and guarded**: the handler previously did two separate writes (`updateReportDocument` with `expectedUpdatedAt`, then an UNguarded `updateReportTitle`), leaving the title write outside the concurrency guard - a concurrent edit between the two could be silently lost. Since the report title is canonically `document.title` (the documents service derives the row title from it), the combined case now sets `document.title = title` and performs a SINGLE guarded `updateReportDocument(id, documentWithTitle, expectedUpdatedAt)` call. Precedence: the explicit `title` arg wins over any `document.title` in the body when they differ (documented in the handler comment). Title-only still calls `updateReportTitle` (read-then-write, no `expectedUpdatedAt` param on its signature), document-only unchanged. New tests: a stale token on a combined update 409s and writes nothing (atomic), a valid combined update calls `updateReportDocument` once with `document.title === ` the new title and never calls `updateReportTitle`, explicit title wins over document title, and the title-only/document-only paths still route correctly.
  - **(Low) Doc comment corrected**: the PATCH docstring claimed the endpoint calls "the EXACT services the workspace editor calls" - inaccurate, since the workspace renames by saving the whole document via `updateReportDocument`; `updateReportTitle` is called only by this API. Reworded to "the same granular documents services (validate-on-write), composed to match the workspace's behavior."
- **For 4.3 (the seams this story establishes)**: (1) a `/api/v1/<resource>/+server.ts` endpoint wraps its body in `runApi(async () => { ... })` from `$lib/server/api` and `throw`s an `AppError` on failure - `runApi` formats it to problem+json (the handle boundary does NOT catch endpoint throws; see Debug Log). (2) To make a route public (e.g. `/api/v1/schema`), add its pathname to `isPublicApiPath` in hooks.server.ts - `apiAuth` then passes it through with a null identity. (3) The OpenAPI builder is `buildOpenApiDocument()` in `$lib/server/openapi`; add 4.3's paths/components there so the spec stays complete. (4) `locals.apiIdentity` carries the authenticated author on every guarded `/api/*` request.
