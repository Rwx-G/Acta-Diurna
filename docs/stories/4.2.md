# Story 4.2: Reports API with Workspace Parity

Status: Approved

## Story

As an agent or script,
I want full report CRUD and publish through `/api/v1`,
So that programmatic authoring matches everything the workspace can do.

## Acceptance Criteria

**Given** a valid PAT
**When** I create, read, update, publish, or delete a report via `/api/v1/reports`
**Then** behavior matches the workspace exactly - same service layer, same validation, same actionable problem+json errors (FR30, AR4/AR5)

**Given** an invalid document submitted via API
**When** validated
**Then** the problem+json response carries the block path, field, and hint (FR2 parity)

**Given** the API
**When** `/api/v1/openapi.json` is fetched
**Then** a valid OpenAPI 3.1 spec generated from the Zod schemas describes all endpoints (D8)

## Tasks / Subtasks

- [ ] `/api/v1/reports` endpoints as THIN ADAPTERS over the existing documents/publish services (the "workspace parity" contract: one service layer, two surfaces - line 299 of architecture). NO business logic, NO validation, NO Drizzle in the route handlers - they parse the request, call the SAME service the workspace calls, and serialize the result. Endpoints (architecture tree `api/v1/reports/`, "CRUD + [id]/publish"):
  - `POST /api/v1/reports` -> `createReport(title)` (1.5); `201` with the created report resource.
  - `GET /api/v1/reports` -> `listReports()` (1.5); `200` with `{ items, total }` ONLY if pagination exists, else the list (architecture: lists return the envelope only when paginated).
  - `GET /api/v1/reports/[id]` -> `getReport(id)` (1.5); `200` or `404` problem+json.
  - `PATCH/PUT /api/v1/reports/[id]` -> `updateReportDocument(id, document, expectedUpdatedAt?)` and/or `updateReportTitle(id, title)` (1.5); document validation runs INSIDE the service and a bad document throws the FR2 actionable `AppError` (block path/field/hint), mapped by the `/api/*` boundary. Decide PATCH (partial: title or document) vs PUT (full replace) and document it.
  - `POST /api/v1/reports/[id]/publish` -> `publishReport(id, expectedUpdatedAt?)` (1.7); `POST /api/v1/reports/[id]/unpublish` -> `unpublishToDraft(id)` (1.7). A non-publishable report surfaces the existing publish-lifecycle `AppError` unchanged.
  - `DELETE /api/v1/reports/[id]` -> `deleteDraft(id)` (1.5); `204` on success, the existing 409 if the report is not a deletable draft.
  - Every endpoint is PAT-authenticated (4.1 `event.locals.apiIdentity`); an unauthenticated call is the 4.1 `401` problem+json, never a redirect (the API never redirects to `/login` - that is a cookie-realm behavior the API path must not inherit).
- [ ] Optimistic-concurrency parity: the workspace passes `expectedUpdatedAt` to guard against lost updates (1.5/1.7 emit a 409 on mismatch). The API accepts the same token (an `If-Unmodified-Since`-style field or a body field - decide and document) and returns the SAME 409 problem+json. A script that omits it gets the same last-write-wins behavior the workspace would on an omitted guard.
- [ ] FR2 validation parity: an invalid document via the API yields the EXACT problem+json the workspace save produces - `{type, title, status, errors: [{path, message, hint?}]}` with the block path, field, and hint (the 1.2 `errors.ts` actionable layer / 1.5 humanized paths). This is automatic if the route is a thin adapter (the service throws, the boundary maps); the test asserts byte-parity of the `errors[]` shape between the workspace action and the API endpoint for the same bad document.
- [ ] `/api/v1/openapi.json` (D8): a valid OpenAPI 3.1 document describing every `/api/v1` path, generated FROM THE ZOD SCHEMAS (the document schema is already Zod 4 in `src/lib/schema/`). APPROACH (flag for the dev/product owner - see Dev Notes): HAND-ASSEMBLE the OpenAPI paths object and `$ref` the existing `z.toJSONSchema()` output for request/response component schemas, rather than adding a Zod-to-OpenAPI generator dependency. The `static/schema/v1.json` artifact (1.2) is the document component schema; the spec references it. The spec advertises the PAT bearer security scheme (`type: http, scheme: bearer`), the problem+json error responses (a shared `Problem` component matching the RFC 9457 shape), and every status code the endpoints return. Served at `/api/v1/openapi.json/+server.ts` - NO auth required on the spec itself (a discovery surface; it leaks no data), consistent with the 4.3 public `/api/v1/schema`.
- [ ] OpenAPI validity gate: a test asserts the generated document is valid OpenAPI 3.1 (structural assertions on `openapi: '3.1.0'`, every path present, the security scheme, the `Problem` component, the document `$ref` resolves). If a validator is added it is a DEV dependency only, not runtime - flag it; prefer hand-rolled structural assertions to avoid even a dev dep unless the dev judges a validator clearly better.
- [ ] Tests: each endpoint calls its exact service and serializes the result (mock the service, assert the call + the status/body, assert NO business logic in the handler); create/read/list/update/publish/unpublish/delete happy paths + their error statuses; an invalid document returns FR2 problem+json with path/field/hint identical to the workspace; an unauthenticated request returns the 4.1 401 (not a redirect); the optimistic-concurrency 409 round-trips; `/api/v1/openapi.json` returns a valid OpenAPI 3.1 doc covering all paths with the bearer scheme + Problem component + resolvable document `$ref`; the spec endpoint needs no PAT.

## Dev Notes

- Authority: AC verbatim from epics.md Epic 4 Story 4.2 (FR30 programmatic parity, AR4 problem+json, AR5 actionable errors, FR2 validation detail, D8 OpenAPI-from-Zod). Architecture line 299 (three surfaces, one service layer - "FR30 parity is structural"), line 219 ("Route every data mutation through the service layer - never Drizzle in a route or component"), line 195-196 (response/error conventions: no envelope except paginated lists, RFC 9457 everywhere), line 124 (D8 OpenAPI 3.1 from the same Zod schemas, single source of truth), line 155 (the Zod source of truth "feeds ... the API contracts (D8) ... and the OpenAPI spec"). Scopes: `api` (the routes), `schema` (the OpenAPI assembly reuses the schema export), `docs` (the spec is a contract).
- DEPENDS ON 4.1: every endpoint reads `event.locals.apiIdentity` (PAT auth) and relies on the `/api/*` error boundary to map thrown `AppError`s to problem+json (so handlers do not each catch). Implement 4.1 first. Independent of 4.3.
- Seam reuse - the EXACT workspace services, no new logic:
  - Documents (1.5, `src/lib/server/documents/`): `createReport(title)`, `getReport(id)`, `listReports()`, `updateReportDocument(...)`, `updateReportTitle(...)`, `deleteDraft(id)`.
  - Publish lifecycle (1.7, `src/lib/server/documents/reports.ts`): `publishReport(id, expectedUpdatedAt?)`, `unpublishToDraft(id)`. (`assertShareable`/`getPublishedDocument` are the sharing gates, not needed for CRUD - 4.3's `/api/v1/schema` is the published-surface story.)
  - Error model: services throw `AppError`; the 4.1 `/api/*` boundary maps to `problemResponse`. The FR2 actionable `errors[]` is produced by the 1.2 `src/lib/schema/errors.ts` layer inside `updateReportDocument` validation - the API inherits it for free because it is a thin adapter.
  - Schema export: `static/schema/v1.json` + `z.toJSONSchema()` (1.2) for the OpenAPI document component; `schemaRegistry`/`SUPPORTED_VERSIONS` (1.2 `versions/index.ts`) if the spec advertises versioned schemas.
- The "thin adapter" rule is the load-bearing architectural contract of this story. If a route handler grows a validation branch, an ownership check, or a Drizzle call, the parity is broken - that logic belongs in the service so the workspace and the API share it. The test strategy (mock the service, assert the call) enforces this structurally.
- OpenAPI-generation decision (RECOMMENDATION, confirm with the dev/product owner): hand-assemble the paths + `$ref` the existing `z.toJSONSchema()` output. Rationale: the document schema is the large, complex one and it is ALREADY exported to JSON Schema (draft 2020-12, which OpenAPI 3.1 is a superset of - 3.1 aligns with JSON Schema 2020-12, so the export `$ref`s cleanly with no translation). The request/response wrappers (create/update payloads, the report resource, the Problem shape) are small and stable - hand-writing them is less code and ZERO new dependency than wiring a Zod-OpenAPI generator (`@asteasolutions/zod-to-openapi` or `zod-openapi`) which would be a runtime dependency requiring CLAUDE.md "no new dependencies without explicit approval" sign-off and would still need the document schema bridged. Prefer hand-assemble; escalate to the product owner only if the endpoint surface grows enough that a generator clearly pays for itself.
- AMBIGUITY for the product owner (do not invent): (a) PATCH vs PUT semantics on update (partial title-or-document vs full replace) - recommend PATCH with an explicit `{title?, document?}` body, but confirm; (b) the optimistic-concurrency token transport (a `version`/`expectedUpdatedAt` body field vs an `If-Unmodified-Since` header) - recommend a body field for agent ergonomics (one JSON payload, no header juggling), but confirm; (c) whether list pagination ships now (driving the `{items,total}` envelope) or lists return a bare array for V1 - recommend bare array for V1 (single-author, few reports) and add pagination when volume demands it, but flag that adding the envelope later is a breaking response-shape change agents must adapt to.
