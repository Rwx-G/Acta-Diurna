# Story 8.2: Author Identity and Per-Report Ownership

## Status

Review

## Story

As the platform,
I want every report owned by exactly one author and every data access scoped to the authenticated author,
So that multiple authors share an instance without seeing or touching each other's reports (closing the multi-author IDOR).

## Acceptance Criteria

**Given** the author model
**When** the schema is migrated
**Then** an `authors` table identifies an author by normalized email (multi mode) or the single implicit password author (single mode), and `reports` (plus the ownership-relevant rows) carry an `owner_id` foreign key

**Given** an instance with password-era reports booting into MULTI mode for the first time
**When** the inheritance migration runs
**Then** every pre-existing report is assigned to the author identified by `INITIAL_OWNER_EMAIL` (deterministic, one-time, idempotent), so no report is orphaned and no "claim" race exists

**Given** an authenticated author in multi mode
**When** they list / read / update / publish / delete a report, a data set, a share, or an API token
**Then** the service filters by `owner_id = the author`: another author's resources are invisible (list) and a direct id access returns the same not-found the reader path uses (no existence oracle) - every service entry point (`getReport`, `listReports`, `rebindReport`, share + token services, the REST/MCP surfaces) enforces the owner predicate

**Given** single mode
**When** the same services run
**Then** there is exactly one implicit author who owns everything and the owner predicate is a no-op (today's behavior preserved); the migration and filtering must not change single-mode semantics

**Given** API tokens (PATs) in multi mode
**When** an author mints / uses / lists / revokes a token
**Then** the token is scoped to that author and authorizes only that author's resources; a PAT never crosses authors (the API identity carries the owner)

## Dev Notes

### Ownership graph (the decision)

- **Directly-owned roots:** `reports.owner_id` and `api_tokens.owner_id` (FK -> `authors.id`, ON DELETE RESTRICT). A report and a PAT each belong to exactly one author.
- **`data_sets`: a DIRECT `owner_id`,** not scope-through-report. `data_sets.report_id` is NULLABLE by design (a data set can precede or outlive a report), so a NULL-report data set has no report to inherit an owner from - it must carry its own owner column. Indexed.
- **`shares`: scope THROUGH the report,** no direct column. A share always has a non-null `report_id` (CASCADE on the report), so its owner is its report's owner. The author-facing share operations (`createShare`, `listShares`, `setShareMode`, `revokeShare`, `setShareRecipients`) gate on ownership by resolving the share's `report_id` and running the SCOPED `getReport` (helper `ownsShare`): an owned report resolves, a foreign or missing one is the same 404/silent no-op. This avoids a redundant column and a backfill on a CASCADE child while still siloing share management.
- **Reader path is NOT owner-scoped.** `getPublishedDocument` (the `/r/[token]` reader) reads the report UNSCOPED via `getRowUnscoped`: a verified reader is gated by the share, not by authorship, and a published snapshot is the same content for any authorized reader regardless of which author owns it. Likewise `getShareByToken`, `isAuthorizedReader`, `listShareRecipients`, `listRecipientsForShares` stay unscoped (reader/already-authorized).

### How the author context is threaded and resolves in single mode

- `AuthorScope = { authorId }` is a small value threaded as a parameter into every owning service entry point. The service asks `ownerFilter(scope, table.ownerId)` for the predicate to AND into its WHERE, and stamps `ownerForInsert(scope)` on new rows.
- The MODE decides whether the predicate exists. `ownerFilter` returns `undefined` in single mode (so the WHERE is the bare pre-8.2 clause - **byte-identical SQL**, existing drizzle-mock tests untouched) and `eq(ownerId, scope.authorId)` in multi mode. The list/getRow helpers branch so single mode never adds a `.where()` to the chain.
- Routes resolve the scope at the boundary: workspace routes call `resolveAuthorScope()`, REST/MCP call `resolveApiAuthorScope(locals.apiIdentity!)`. Today both resolve to the single implicit author (`implicitAuthorId()`), cached after the first read. In single mode this is exact; in multi mode it is a deliberate no-op pending story 8.3, which mints author sessions and a real per-author identity. The seam is in place and proven a no-op in single mode; only the resolver's multi branch changes in 8.3.

### Legacy-inheritance mechanism

- The `0013` migration adds `owner_id` NULLABLE so the DDL is safe against existing rows. The backfill is a boot-time step (`inheritLegacyOwnership`, run in `hooks.server.ts` init after migrations, before traffic, fatal on failure) because the target author is a function of the runtime env (resolved mode + `INITIAL_OWNER_EMAIL`), which SQL cannot read.
- It seeds the single implicit author (keyed on `INITIAL_OWNER_EMAIL` when set - so the first MULTI boot inherits to that email - else the sentinel) and runs `UPDATE ... SET owner_id = <implicit author> WHERE owner_id IS NULL` on reports, data_sets, and api_tokens. This is:
  - **idempotent:** a second boot finds no null rows and updates nothing (no flag needed);
  - **never-orphaning:** every legacy row gets an owner on the first boot;
  - **race-free:** the target is deterministic from the env, not first-writer-wins.
- A row inserted by the running app already carries its owner (`ownerForInsert`), so only genuine pre-8.2 rows are ever null and eligible.

### Scope note (what 8.2 does NOT do)

This story is the ownership MODEL and the filtering PLUMBING. The multi-author SESSION wiring (mapping a logged-in email to an author identity) is story 8.3; magic-link author login is not implemented here. The resolvers therefore return the implicit author in both modes for now.

## Dev Agent Record

### Debug Log

- The existing service unit tests use hand-rolled drizzle mocks that decode `eq()`/`and()` WHERE chunks. Adding the owner predicate unconditionally would have broken those mocks and single-mode SQL parity, so the predicate is applied ONLY in multi mode (the `ownerFilter`-undefined no-op). The list/getRow paths branch to keep the single-mode chain shape identical.
- Importing `ownerFilter` into the services pulls in `serverEnv()` via `isMultiAuthor()`; the existing unit tests do not provide a full env, so each affected test now mocks `$lib/server/mode` to force single mode (`isMultiAuthor: () => false`), which both avoids the env parse and keeps the predicate a no-op.
- Share-management tenancy is enforced through `ownsShare` (resolve the share's report, scoped `getReport`). The sharing tests gained a `getReport` resolve so the gate passes for a seeded share in single mode.

### Completion Notes

- Migration generated with `drizzle-kit generate --name authors_ownership` (`0013`); `_journal.json` and the `0013` snapshot are tool-written, not hand-edited.
- All four gates green: `pnpm lint`, `pnpm check`, `pnpm test` (1378 passed), `pnpm build`.
- New `authors` domain: `identity.ts` (implicit author seed/resolve), `scope.ts` (`ownerFilter`/`ownerForInsert`), `resolve.ts` (`resolveAuthorScope`/`resolveApiAuthorScope`), `inheritance.ts` (boot backfill), plus tests `scope.test.ts`, `identity.test.ts`, `inheritance.test.ts`, and the IDOR proof `tenancy.test.ts`.
- Post-audit remediation (2026-06-14): the `skeletons` table was missed in the original 8.2 pass - no `owner_id`, a GLOBAL unique-name index, and an unscoped service - so in multi mode any author could list/read/instantiate/delete another author's skeleton and the 409 `skeleton-name-taken` leaked existence cross-author. Brought to parity: `owner_id` (FK -> authors, RESTRICT, indexed; migration `0015`), the boot inheritance backfill extended to skeletons, an `AuthorScope` threaded through all five service functions (`saveSkeleton` stamps the owner; `listSkeletons`/`getSkeleton`/`deleteSkeleton`/`instantiateReport` apply `ownerFilter` -> a foreign id is the SAME 404), the unique index changed from global `name` to `(owner_id, name)` (two authors may reuse a name; the 409 only fires within one author), and every caller updated (workspace skeleton routes, MCP `list_skeletons`, AI `loadContext`). Single mode (one implicit author) stays byte-identical. New multi-mode proof `skeletons-tenancy.test.ts`.

### Unverified / could not run end to end

- The SQL DDL and the boot inheritance UPDATEs only execute against a real Postgres; they were not run against a live database here. The migration is drizzle-kit-generated and the inheritance logic is unit-tested with a db mock, but the actual on-disk migration apply and backfill are unverified end to end.
- The MULTI-mode tenancy paths are only fully exercisable once story 8.3 populates a real second author session. The cross-author isolation (list invisibility, 404 on direct id, PAT cross-author 404, backfill) is proven with a FORCED multi-mode mock and a fabricated second author scope (`tenancy.test.ts`), not with two real logged-in authors. Single-mode parity is proven by the unchanged existing suites.
