# Epic 8 QA Report - Identity & Multi-Author (SMTP-gated)

**Date:** 2026-06-14
**Author:** Romain G.
**Method:** per-story implementation, parallel auditors (security, attacker-mindset penetration, quality, architect, BMad gate), a remediation loop on the security findings, then completion. Auth is security-critical, so every story ran the dev -> QA -> auditor loop and the whole epic took a dedicated security + penetration pass with a remediation round before close. All work committed locally to `main`. The multi-mode browser/SMTP flow was unit-tested by forcing the mode, not run end to end against a live DB + SMTP relay (see Deferred / Backlog).

## Executive Summary

Epic 8 is complete: all 6 stories `Done`. The single-password instance becomes a multi-author one, and the operating mode is an OPS decision expressed entirely in the environment - configure SMTP and the instance runs multi-author, leave it unconfigured and it runs single-author, with no web-UI gate and no persisted "verified" flag. The mode is resolved once at boot from the SMTP env (`src/lib/server/mode.ts`, `operatingMode()` / `isMultiAuthor()`) and is the single source of truth every other surface branches on, so no separate mode flag can drift from the SMTP configuration.

The load-bearing change is **one report = one author** in both modes. Every report, data set, share, and API token carries an `owner_id`; in single mode there is exactly one implicit author owning everything (the password author, today's behavior preserved) and the owner predicate is a no-op, while in multi mode every owning read and write is scoped to the authenticated author. This **closes the multi-author IDOR** flagged back at story 1.5: authors are siloed, each sees only their own resources, and a cross-author id access returns the SAME not-found the reader path uses - no existence oracle.

Around that core: SMTP-gated author identity by **email magic link** (self-service within `AUTHOR_EMAIL_DOMAIN`, password login disabled in multi mode), reusing the Epic 3 reader-verification machinery in a strictly separate author realm; **mode-aware sharing** (single = unverified consultation token, multi = the Epic 3 verified flow) with a defined and tested transition rule that never escalates a stale share; an optional **reader-domain whitelist**; and the mode-aware login/workspace UX plus operator docs.

**Epic gate: PASS.** No Critical or High finding remained open at epic close. The security + penetration pass found one High (a skeleton tenancy gap, an IDOR variant the original 8.2 pass missed) and two Medium hardening items; all three are fixed and test-backed (the remediation summary below). The core multi-author tenancy - the read-path authorization that closes the IDOR - carried 0 Critical / 0 High through the audit.

**Single mode is byte-identical to before.** The whole change is invisible until SMTP is configured: the new env vars stay optional, the mode resolver returns `single`, the owner predicate is `undefined` (the bare pre-8.2 SQL), sharing keeps consultation tokens, and the login stays the password form. The existing suites prove single-mode parity by passing unchanged.

**No new dependency.** Author magic-link auth reuses the Epic 3 verification primitives and the existing nodemailer transport; the only transport change is hardening the bare-relay (`SMTP_TLS_MODE=none`, no auth) profile.

## Cross-Cutting Findings (multi-story signal)

- **The mode is one env-driven source of truth, never a drifting flag.** `operatingMode()` is a pure function of the SMTP env, reusing the same `SMTP_HOST` / `anySmtp` signal the env refine and the mailer already key on. There is no web-UI toggle, no persisted "verified" column, no second variable that could fall out of sync with the SMTP block. Turning multi-author on or off is a deliberate ops action (edit the compose env, restart), and the all-or-nothing SMTP refine guarantees a present SMTP block is a complete, multi-valid one.
- **Tenancy rides one seam across all four owning surfaces.** `AuthorScope = { authorId }` is threaded as a parameter into every owning service entry point; the service asks `ownerFilter(scope, table.ownerId)` for the predicate to AND into its WHERE and `ownerForInsert(scope)` to stamp new rows. The MODE decides whether the predicate exists - `ownerFilter` returns `undefined` in single mode (the bare pre-8.2 clause, byte-identical SQL) and `eq(ownerId, scope.authorId)` in multi mode. Documents, ingestion, sharing (through the report via `ownsShare`), and API tokens all gate through this one seam, so the IDOR close is a single auditable pattern, not a per-service reimplementation. A cross-author id raises the SAME not-found everywhere - no distinct 403, no existence oracle.
- **Realm separation held under audit (NFR12).** Three auth realms stay strictly separate: the author cookie (`__Host-acta_author`), the reader cookie (`__Host-acta_reader`), and the PAT bearer. The author magic-link store is a PHYSICALLY separate table (`author_verification_tokens`, email-bound, no `share_id`) from the reader store (`verification_tokens`, share-and-email bound) - chosen deliberately over reusing the reader table with a nullable `share_id`, which would have weakened the reader table's load-bearing NOT NULL `share_id` and risked a token from one realm verifying the other. A token from one store can never verify the other realm because the consume functions require structurally incompatible bindings. The PAT realm carries the owner from 8.2 and never crosses authors.
- **The Epic 3 verification machinery was reused, not reinvented.** Author magic-link auth reproduces the reader pattern - single-use atomic claim (`UPDATE ... WHERE consumed_at IS NULL RETURNING`), 15-minute TTL, SHA-256 hash-at-rest, dedup-before-issue, fire-and-forget send for timing-equivalence, the enumeration-safe neutral return, the realm-parameterized session core, and the per-IP + global-brake rate-limiter pattern. The author gate is the reader gate's shape with an email-only binding and a domain check behind the neutral return. This kept the auth-critical surface small and consistent.
- **Single mode is byte-identical, and that is the safety property.** The new env vars are optional when SMTP is absent, `operatingMode()` returns `single`, the owner predicate is a no-op, sharing keeps consultation tokens, the mailer's STARTTLS/TLS paths are unchanged, and the login stays the password form. The implicit author's sentinel email is never displayed. The existing suites pass unchanged, which is the proof: a no-SMTP instance behaves exactly as it did before Epic 8.

## Security Audit + Remediation

The epic ran a dedicated security + penetration pass after the six stories landed, then a remediation round. The result: **0 Critical / 0 High in the core multi-author tenancy** (the read-path authorization that closes the IDOR). The pass surfaced one High in an adjacent surface and two Medium hardening items, all now fixed and test-backed.

**High - skeleton cross-author IDOR (fixed).** The original 8.2 pass threaded `AuthorScope` through reports, data sets, shares, and API tokens but MISSED the `skeletons` table: it had no `owner_id`, a GLOBAL unique-name index, and an unscoped service. In multi mode any author could list / read / instantiate / delete another author's skeleton, and the `skeleton-name-taken` 409 leaked a skeleton's existence cross-author. This is the same IDOR class the epic exists to close, in a surface the first pass overlooked. Remediation brought skeletons to parity: `skeletons.owner_id` (FK -> authors, RESTRICT, indexed) via migration `0015`, the boot inheritance backfill extended to skeletons, an `AuthorScope` threaded through all five skeleton service functions and every caller (workspace routes, MCP `list_skeletons`, AI `loadContext`), and the unique index changed from global `name` to composite `(owner_id, name)` - two authors may now reuse a name and the 409 only fires within one author, closing the enumeration leak. Single mode (one implicit author) stays byte-identical. Proven by a new multi-mode `skeletons-tenancy.test.ts`.

**Medium - stale null-author session purge on mode flip (fixed).** A single-mode password session carries `authorId: null`. If an instance flips to multi mode, such a session would resolve (defensively) to the implicit author rather than a real per-author identity, a tenancy ambiguity at the mode boundary. Remediation purges stale null-author sessions on multi-mode boot, so a multi-mode instance only ever serves sessions that carry a real author id; an operator who flips the mode re-authenticates by magic link.

**Medium - ingest report-ownership validation (fixed).** The data-set push accepts an optional target `report_id`. Remediation validates that the target report is owned by the pushing author's scope before binding, so a multi-mode author cannot push a data set onto (or rebind) another author's report by supplying its id - the ingest path now enforces the same owner predicate as the rest of the tenancy seam.

**What the auditors verified sound (no change required):**

- **Realm separation (NFR12).** The three auth realms are physically and logically separate; the author and reader verification stores cannot cross-verify; the PAT realm carries its owner and never accepts a cookie.
- **Enumeration-safety (NFR9).** The author sign-in request returns the neutral `{ state: 'sent' }` for an in-domain, off-domain, or unknown email; the domain check sits behind the neutral return; the send is fire-and-forget so the SMTP round-trip is never on the response path; the magic-link landing returns the identical bounce for a used / expired / forged / throttled token. The reader-domain whitelist (8.5) sits behind the same neutral return, layered with the per-share recipient list, adding no new oracle. The cross-author not-found is byte-identical to the reader-path 404.
- **No-lockout boot guard.** Multi mode has no password fallback and no break-glass, so the fail-fast boot validation requires `AUTHOR_EMAIL_DOMAIN` and an in-domain `INITIAL_OWNER_EMAIL` when SMTP is set; a missing or out-of-domain value refuses the boot with an actionable message rather than starting an unauthenticatable instance. Recovery is the same env surface: remove the SMTP env and restart to regain single-password access.
- **Single-use token atomicity.** The author magic-link consume is a single-use atomic claim (`UPDATE ... WHERE consumed_at IS NULL RETURNING`) with a 15-minute TTL and SHA-256 hash-at-rest, the proven Epic 3 reader-token shape; a replayed or forged token consumes nothing and bounces to the neutral state.

## NFR Validation

- **Authorization / tenancy (the IDOR close, FR-multi-author).** Every owning read and write in multi mode is filtered by `owner_id = the authenticated author` through the one `ownerFilter` seam; another author's resources are invisible in lists and a direct id access is the same not-found the reader path uses. PATs are per-author. Single mode is the no-op predicate. The skeleton surface was brought into the same seam during remediation.
- **Authentication realms (NFR12).** Author cookie, reader cookie, and PAT bearer stay strictly separate; the author and reader verification stores are physically separate and cannot cross-verify.
- **Enumeration-safety (NFR9).** The author sign-in, the reader verification, and the reader-domain whitelist all decide membership behind the neutral confirmation; the cross-author not-found and the closed-share 404 are byte-identical to the reader-path neutral page.
- **No-lockout-by-misconfig.** The multi-mode fail-fast boot validation prevents an SMTP-on-but-no-valid-author-domain lockout; the documented recovery is to fix or remove the SMTP env and restart.
- **Leak-free reader posture (NFR9/NFR10), both modes.** The closed-share neutral 404, `no-store` on every serving exit, route-scoped `noindex` / `X-Robots-Tag`, the strict CSP, and revocation + expiry all hold identically in single and multi mode - the closed-share check runs BEFORE the mode branch, so a prober cannot tell a single-mode instance from a multi-mode one off a dead link.
- **Transition safety (8.4).** `servesConsultation` always honors the CURRENT mode: a consultation share under newly-enabled SMTP requires verification (a stricter gate, never an escalation), and a restricted share under removed SMTP falls back to closed (the neutral 404), never silently opening a recipient-gated link. Both directions tighten or hold access; neither escalates.
- **Performance / reader budget (NFR3).** Epic 8 is server-side auth and tenancy plumbing; the reader path is unaffected. Reader-path JS held at 71.9 KB / 200 KB at epic close.

## Deferred / Backlog

- **Live multi-mode end-to-end (the follow-up the deploy will prove).** The full multi-mode flow - boot with SMTP and a real relay, submit an in-domain email at the author login, receive the magic link, click it, mint the author, and confirm the workspace shows ONLY that author's reports / data sets / shares / tokens with a second author invisible - was NOT run against a live DB + SMTP. It is unit-tested by forcing the mode (mocking the resolver and the env and fabricating a second author scope). The same applies to the reader-side multi-mode paths (verified magic-link sharing, the reader-domain whitelist refusing an off-domain email with no mail sent) and to the live mode transition (boot single, mint a consultation share, add SMTP, restart, open the same link, land on the verify card - and the reverse). The migrations' on-disk apply and the boot legacy-inheritance backfill likewise execute only against a real Postgres. This is the honest gap: the logic is unit-proven and the single-mode parity is suite-proven, but the live multi-mode deploy is what will prove the end-to-end flow. It is the recommended first validation of the next deploy.
- **Author de-provisioning / lifecycle.** Self-service provisioning mints an author on first verified sign-in; there is no in-product flow to disable or remove an author (and its owned resources are FK-RESTRICT). An operator-facing lifecycle (disable an author, reassign or archive their reports) is a candidate for a future story if multi-author instances need it.
