**Date:** 2026-06-14

## Executive Summary

This is the deferred-backlog and end-to-end push the maintainer asked for after the planned roadmap closed. The standing recommendation from both the Epic 6 and Epic 8 reports was the same: the multi-author, reader-verification, presenter, audience and audit flows were unit-proven by FORCING state (mocking `operatingMode()` / `isMultiAuthor()`, fabricating a second author scope, asserting computed styles), but had not been run end to end against a live database and SMTP relay. This cycle closes that gap inside CI rather than waiting on a live deploy, by booting the app against real containers.

Five areas shipped:

1. **A Mailpit-backed multi-mode e2e harness.** A separate Playwright config boots the app in MULTI mode against a real PostgreSQL testcontainer and a real Mailpit SMTP testcontainer, with an email-interception helper that extracts magic links from the Mailpit HTTP API. New specs cover in-domain author sign-in, PAT-to-PAT tenancy isolation, and verified-reader sharing. CI now runs both single- and multi-mode e2e.
2. **Single-mode e2e coverage** for the Epic 6 surfaces that were unit-only: audience-level switching (with the deep-link regression guard), presenter view plus the speaker-notes privacy guard, the data-as-of caption, a non-default theme under axe-core, and the access audit plus a live-database retention DELETE.
3. **Three programmatic-surface additions** - the MCP `push_data_set` tool, and outline-first generation over REST (`POST /api/v1/reports/generate/outline` + `/fill`) and MCP (`generate_outline` + `generate_report`) - all thin owner-scoped adapters over the existing services.
4. **A security + penetration audit** of the new programmatic surfaces, with two remediated MCP availability/cost findings.
5. **A hardening reconciliation** confirming the body-size cap and orphaned-data-set GC were already implemented, leaving one open, hook-blocked `.env.example` documentation item.

**Cycle gate: PASS.** No Critical or High finding remained open at close. The security pass found owner-scoping sound on all three new surfaces (no cross-tenant read/write, 404 with no existence oracle), the generation approval-hash binding sound, and the AI gates / SSRF posture / key-redaction sound; the two MCP findings it surfaced (one High availability/cost, one Low/Med extra-copy) are fixed and test-backed. The new programmatic surfaces add no schema change, no migration, and no new dependency, and the reader budget is unaffected (72.8 KB / 200 KB).

**The honest framing is unchanged from the epic reports.** The planned roadmap was already complete; this cycle is backlog and test-coverage work, not new product scope. Where those reports said "unit-only, awaiting a live deploy," the multi-mode and Epic 6 flows are now exercised in CI against real Postgres and Mailpit containers - so their status moves from unit-only to covered in CI. ## Area 1 - Multi-mode end-to-end harness (Mailpit-backed)

The long-standing gap both prior reports carried was that multi-mode was only unit-tested by forcing state. This cycle stands the real flow up in CI.

- **Separate config and global setup.** `playwright.multi.config.ts` plus a multi-mode global setup boots the app in MULTI mode against a real PostgreSQL testcontainer AND a Mailpit SMTP testcontainer (`axllent/mailpit:v1.27`). The single-mode config is unchanged; the two configs run side by side, and CI runs both.
- **Email interception.** `e2e/mailpit.ts` extracts magic links from the Mailpit HTTP API, so a spec can drive the full passwordless flow - submit an email, receive the message, follow the link - end to end with no mock.
- **New multi-mode specs.**
  - `multi-author-signin` - an in-domain email completes the magic-link author sign-in; an off-domain email is refused (the neutral confirmation, no author minted).
  - `multi-tenancy-isolation` - PAT-A cannot see PAT-B's report in a list and cannot GET it by id: the same 404 the reader path uses, no existence oracle, proven in BOTH directions. This is the live exercise of the multi-author IDOR close that Epic 8 unit-proved.
  - `multi-reader-verification` - a verified reader share with an in-whitelist reader reads the report; an off-whitelist reader is refused, with no mail sent.

This is the recommended-first-validation the prior reports named, now running on every CI build instead of awaiting a manual deploy.

## Area 2 - Single-mode e2e coverage for unit-only Epic 6 surfaces

The Epic 6 report listed five flows asserted only by forced state (computed `display: none`, view-model exclusion, the pure cutoff math against a faked db). Each now has a browser-level or live-database e2e:

- **Audience-level switching** - the reader switcher toggles summary / full / technical in a real browser, including the regression guard that a deep link must NOT reveal a section hidden at the active level.
- **Presenter view** - the presenter window runs a published report, and the privacy guard asserts speaker notes never leak into the reader-served document.
- **Data-as-of caption** - the freshness caption renders on a bound block from a live ingest.
- **Non-default theme under axe-core** - the `meridian` theme is exercised under the accessibility gate (the `aurora` theme and the Phase B blocks were found already axe-covered, so no duplicate work).
- **Access audit + retention** - the owner-scoped audit view plus a live-database retention-purge DELETE on a real Postgres, exercising the actual `<`-cutoff delete the unit suite could only fake.

## Area 3 - Programmatic-surface additions (REST + MCP)

Three thin adapters over existing services, all owner-scoped through the same `resolveApiAuthorScope` -> `AuthorScope` seam the rest of the programmatic surface uses, so single mode resolves to the implicit author (a no-op) and multi mode can never reach another author's resources.

- **MCP `push_data_set`** - pushes CSV or JSON onto a report and auto-rebinds its blocks over `/api/mcp`, the FR13/14/15 parity of the REST `POST /api/v1/data-sets`. A thin delegation to the EXACT `ingestBytes` + `rebindReport` services REST and the workspace call; the only transport difference is that the file arrives as a JSON-RPC `content` string with an explicit `format` argument (no `Content-Type` header on a tool call). MCP server identity bumped to 0.7.0.
- **Outline-first generation over REST and MCP** - `POST /api/v1/reports/generate/outline` (intent -> bounded outline + approval hash) and `/generate/fill` (approved outline + hash -> schema-valid draft), with the matching MCP `generate_outline` and `generate_report` tools. Both surfaces are thin adapters over the EXACT two-stage `generateOutline` -> `fillFromOutline` service the workspace drives - no generation logic, prompt bounds, or validation duplicated - so the four surfaces cannot drift (AR5). MCP server identity bumped to 0.8.0. The REST `POST /api/v1/reports/:id/duplicate` endpoint already existed, so it was not re-added.

All three are server-only with no schema change, no migration, and no new dependency; the reader budget is unaffected.

## Area 4 - Security audit and remediation

The three new programmatic surfaces took a dedicated security + attacker-mindset penetration pass, since they widen the agent-reachable attack surface. **The auditors' verdict: owner-scoping is SOUND on all three** (no cross-tenant read or write, a foreign or unknown id is the scoped 404 with no existence oracle, both directions), **and the generation approval-hash binding is SOUND** (a stateless SHA-256 content hash re-checked before any LLM call; owner-scope is the real tenancy boundary, and because a single PAT identity drives outline -> fill against no shared state, the content-hash binding is sufficient and no server-minted nonce was needed). The AI gates (`AI_GENERATION_ENABLED` + endpoint-configured, asserted before any outbound call), the SSRF posture (the connector talks only to the configured `LLM_BASE_URL`, no phone-home), and key-redaction were all verified sound, requiring no change.

Two findings were surfaced and remediated:

- **High - MCP generation tools were unmetered.** `generate_outline` and `generate_report` issued metered `chatComplete` calls with no rate limit: the `apiAuth` hook consumes a rate token only on an auth FAILURE, so an authenticated PAT could drive unbounded paid LLM calls through `/api/mcp` - the cost/DoS brake the REST routes already had via `aiGenerationLimiter`. Both tools now consume the SAME `aiGenerationLimiter` BEFORE any LLM call, keyed per AUTHOR (`mcpGenerationRateKey(scope.authorId)`), so one author's MCP burst is capped across all their PATs and a single logical call costs exactly one token on whichever surface issued it. On deny the tools return the standard RFC 9457 429 via the MCP tool error channel and make no call.
- **Low/Med - `push_data_set` buffered an oversize body before checking the cap.** The tool encoded the full JSON-RPC `content` string to bytes before `ingestBytes` enforced the 50 MB cap, an extra full UTF-8 copy on an over-cap push (bounded already by `BODY_SIZE_LIMIT`, so residual, not unbounded). The tool now rejects an over-`MAX_UPLOAD_BYTES` body up front with a cheap `Buffer.byteLength` measure, returning the same `tooLarge` 413 the REST push returns before the encode.

Both fixes are test-backed and recorded under Security in the changelog. No Critical or High finding remained open at close.

## Area 5 - Hardening reconciliation

A sweep of the standing hardening backlog found two items ALREADY implemented and tested in the repo, and one genuinely open:

- **Body-size cap - already done.** The stream-and-abort cap plus the operator-tunable `BODY_SIZE_LIMIT` is in place and tested across the ingestion and API-write entries.
- **Orphaned-data-set GC - already done.** `DATA_SET_ORPHAN_RETENTION_DAYS` and `purgeOrphanDataSets` on the boot sweep are implemented and tested; the migration-0011 `report_id` index supports the orphan scan.
- **`.env.example` full env reference - OPEN, blocked.** Completing `.env.example` as a full annotated env reference is blocked by the `secrets-fence.py` hook, which has no `.env.example` carve-out: the file matches the hook's secret-path patterns and cannot be read or edited by tooling. Closing it needs one of two maintainer actions: a manual edit of the file by hand (outside the agent toolchain), OR a `\.env\.example` exemption added to the hook's allow-list so tooling can author it. This is the one open hardening item this cycle carries.

## Verified vs Unverified

- **Verified in CI (real services).** The multi-mode author sign-in, the PAT-to-PAT tenancy isolation, and the verified-reader whitelist flow run against a real PostgreSQL testcontainer and a real Mailpit SMTP testcontainer. The Epic 6 single-mode flows (audience switch, presenter, data-as-of, non-default-theme axe, audit + the retention DELETE) run against a real Postgres. These are no longer "forced state" - they exercise the live wiring end to end.
- **Verified by unit test (connector mocked).** The outline-first generation happy-path is unit-covered with the LLM connector mocked - the two-stage orchestration, the defensive parse of untrusted model output, the approval-hash re-check, and the validate-on-write are all asserted, but **no real LLM call runs in CI, by design** (there is no embedded model and no outbound endpoint in the test environment). The generation REST/MCP adapters' owner-scoping, AI-gate behaviour, and rate-metering are unit-asserted with the connector and limiter mocked.
- **Not run here.** The `.env.example` completion (hook-blocked) and any flow needing an externally-reachable real LLM endpoint were not exercised.

## Still Deferred

- **Live-deploy dogfooding that genuinely needs a real instance.** The multi-mode author / reader / tenancy flows and the Epic 6 reader / presenter / audit flows are NOW covered in CI via the Mailpit + Postgres containers, so their status moves from "unit-only" to "covered in CI." What remains for a real deploy is operational rather than functional: the on-disk migration apply and the boot legacy-inheritance backfill against production-shaped password-era data, behaviour against a real external SMTP relay (Mailpit stands in for the protocol, not for a given provider's quirks), and behaviour against a real external LLM endpoint (mocked in CI by design). These are deploy-posture validations, not unproven logic.
- **Author de-provisioning / lifecycle (feature gap).** Self-service provisioning mints an author on first verified sign-in; there is still no in-product flow to disable or remove an author, and owned resources are FK-RESTRICT. An operator-facing lifecycle (disable an author, reassign or archive their reports) remains a candidate future story for multi-author instances. This cycle did not address it.
- **The open `.env.example` item (Area 5).** Completing the annotated full env reference is blocked by the `secrets-fence.py` hook with no `.env.example` carve-out; close it by a manual maintainer edit OR a `\.env\.example` hook exemption.
- **v2 vision items - explicitly OUT of scope.** In-browser WYSIWYG editor, PDF / PPTX export, SQL connectors, multi-tenant spaces, scheduled email delivery, viewer analytics, and report series with auto-diff remain v2 roadmap and were not touched here.

## Recommendations

- **Immediate:** none blocking. The two MCP audit findings are fixed and test-backed; owner-scoping and the approval-hash binding held across all three new surfaces.
- **Next:** close the `.env.example` item by adding a `\.env\.example` exemption to `secrets-fence.py` (the lower-friction of the two options) so the annotated env reference can be authored by tooling.
- **Then:** a live deploy to run the remaining operational validations (migration apply + inheritance backfill on real data, a real SMTP relay, a real LLM endpoint), and - if multi-author instances need it - the author de-provisioning / lifecycle story.
