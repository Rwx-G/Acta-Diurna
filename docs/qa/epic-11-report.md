# Epic 11 QA Report - Internal Links & Drill-Down Detail Pages

**Date:** 2026-06-14
**Author:** Romain G.
**Method:** per-story implementation, parallel auditors (security, attacker-mindset penetration, quality, architect, BMad gate), then a dedicated security + penetration pass over the whole epic before close. The epic adds a hidden-but-addressable section kind, a typed internal-link reference that renders as an anchor, and reader navigation to and from a detail page - so the linkTo injection surface, the "reachable only via a link" boundary, and the speaker-notes-on-a-detail-page privacy each took explicit attacker review. All work committed locally to `main`. The reader render + navigation flows were unit-tested by forcing state (computed-style on the CSS `:target` reveal, view-model partition assertions, fragment-resolution helpers) and exercised by the single-mode and Mailpit multi-mode e2e suites, not walked by hand against a live deployment (see Deferred / Backlog).

## Executive Summary

Epic 11 is complete: all 5 stories `Done`. A report can now carry deep detail behind an internal link - a reader scanning a findings table clicks a finding, lands on a page dedicated to that finding (its evidence, reproduction, remediation), then steps back to the table and keeps reading. That detail page is part of the SAME document, but it is not in the main slide/scroll flow and not in the table of contents: it is reachable ONLY through that internal link. The author keeps the cover-to-close narrative tight while the depth lives one click away.

The epic delivers three layers, all renderer-pure, all within the reader JS budget. The schema gains a `kind: 'detail'` section (story 11.1): rendered and addressable by its stable id, excluded from the main sequence and the TOC, mutually exclusive with `annex`, surfaced as a separate `view.detailSections`. A typed `linkTo` (story 11.2) lands on three carriers - an inline run (XOR the external `href`), a table row, a comparison-matrix finding - validated against the document by a cross-reference pass that rejects a dangling target, and rendered as an escaped `<a href="#id">`. The reader navigation (story 11.3) is a CSS `:target`-driven detail reveal with zero-JS reveal, a small focus / origin-tracking script, a "back to origin" anchor that works no-JS, and deep-linkable detail fragments; the main-flow nav, TOC, and progress rail exclude detail sections. Audience levels compose with the reveal (story 11.4) by promotion, not specificity escalation, preserving FR28. And producer parity (story 11.5) lands the detail section and the linkTo through the one validated service across the workspace, REST, and MCP, with the editor preview tolerating a dangling linkTo as a gentle notice while save/publish stays strict.

**Epic gate: PASS.** The security + penetration pass returned 0 Critical / 0 High and one Medium (section-id uniqueness), now REMEDIATED and green. Every change is additive to schema v1 (`kind` on a section, `linkTo` on three carriers - all optional, every existing document validates and renders byte-unchanged, no version bump), renderer-pure (no `$lib/server`, no `{@html}`, internal anchors only), and within the reader JS budget (74.6 KB / 200 KB - the epic added ~1.7 KB, mostly markup plus the minimal CSS `:target` reveal and the small origin/focus glue). No new dependency.

**The load-bearing distinction of the epic is what "reachable only via an internal link" IS and is NOT.** A detail page is "inaccessible otherwise" only in the sense that nothing in the main flow or the TOC links to it - that is NAVIGATION, not a confidentiality boundary. Every detail page is server-rendered into the authorized reader's DOM under the SAME share/gate as the rest of the report: if the report is gated, every byte of every detail page is gated with it; a reader holding the share who knows or guesses a detail section id can open it. This is exactly the posture Epic 6 established for audience tags (a reading-comfort filter, not a secrecy control): the share is the boundary, not the link. This invariant is recorded plainly in the epic design and carried in the code at the detail-section partition so a future contributor cannot mistake "not in the flow" for "not readable". The one genuinely author-private field, section speaker notes, is NOT exposed by a detail page: notes on a detail section are stripped server-side at the same `getPublishedDocument` chokepoint that strips them from flow sections.

## Cross-Cutting Findings (multi-story signal)

- **The detail-section model reuses the one section list the whole pipeline already walks.** A detail page is a `kind` on the existing section, not a second `detailSections` array on the document (considered and rejected at planning: more schema surface, a second list to validate, migrate, and keep in sync, for no authoring gain). A `detail` section keeps its `id`, `title`, `audiences`, `notes`, and `blocks` exactly like a flow section, so every block type in the catalogue renders inside it with no new render path. The view-model (`toReportView`, and the workspace `toPreviewView` identically) is where "hidden from flow and TOC" is realized: it partitions the document sections into a main-flow `sections` sequence (what the navigation, progress rail, TOC, and keyboard paging count) and a separate `detailSections` array rendered after the flow, so a detail page is present in the DOM with its anchor but never appears between the cover and the close. `annex` and `detail` are orthogonal placements that may not both be set (an annex is in the flow and the TOC; a detail is in neither), enforced by a section-level refine that names the offending section by id.
- **"Reachable only via a link is navigation, not a confidentiality boundary" is the epic's invariant, and it is stated plainly.** A detail page is hidden from the flow and the TOC; it is NOT gated separately. It serves under the same share, the same revoked/expired/unknown neutral page, the same `noindex` / `no-store` as the rest of the report. A reader holding the share who guesses a detail id can open it. Treat detail content as fully readable by anyone holding the share - exactly as an audience tag is a reading-comfort filter and not a secrecy control (Epic 6). This is the corollary of the SSR-everything render: every detail page is in the bytes shipped to the authorized reader, hidden from the navigation by the view-model partition, not withheld. Confidential or per-reader-restricted content must never live behind an internal link expecting the link to gate it; the share is the boundary.
- **The linkTo injection surface is closed at three independent layers.** A `linkTo` is never a free URL. (1) The SCHEMA constrains it to a section-id slug, and the cross-reference pass requires that id to resolve to a section in the same document - a value that is not a known id fails validation before the document is ever served, so a `linkTo` can only ever be a known intra-document id, never an arbitrary or scriptable string. (2) The RENDER emits `href="#" + id` through Svelte attribute interpolation, which escapes - the carrier is `<a href="#<section-id>">`, never `{@html}`, never a raw URL, so even a hypothetical hostile id slug is inert escaped text in an attribute. (3) A RENDER-TIME guard keeps the anchor an in-page fragment only (the `#` prefix is fixed in the renderer, the id is the sole variable), so there is no path by which a `linkTo` becomes an off-document navigation, a `javascript:` URL, or markup. Renderer purity holds across all three carriers (inline run, table row, matrix finding): no `$lib/server`, no `{@html}`, internal anchors only.
- **Speaker notes on a detail page are stripped at the same chokepoint as flow sections.** A detail section may carry the author-private `notes` field exactly like a flow section, and the privacy guarantee is unchanged from Epic 6: the reader view-model maps a section (flow or detail) to a `SectionView` shape with no `notes`, and `getPublishedDocument` - the single chokepoint every reader path funnels through - runs `stripSpeakerNotes` over EVERY section, flow and detail alike, before the document leaves the server. There is no detail-specific serving path that bypasses the strip. The presenter deck is the main-flow sections only (a detail page is not presented), and its notes are paired by section id rather than positional index now that `view.sections` can be a subset of the document once a detail section is dropped from the flow.
- **The reveal is pure CSS `:target`, zero added JS, and the budget held.** A detail section is visually hidden until its `#id` fragment is targeted; a pure-CSS `:target` rule (no JS) shows it full-view as a fixed overlay while the flow is hidden underneath - a dedicated view the reader navigates TO and returns FROM, not an inline expansion or a modal. The detail section's own `<section id>` is the native `:target`, so the no-JS reader reaches the content by the browser's `#id` jump (the detail sections SSR-render since 11.1). The only added reader JS is small a11y + bookkeeping glue: it records the origin section on a `data-internal-link` activation and moves focus into the detail page's labelled `tabindex="-1"` region (NFR15), and the "back to origin" affordance is a plain anchor to the recorded origin (falling back to the first flow section), so back works without JS and, with JS, also restores focus. Reader-path JS sat at 74.6 KB / 200 KB at epic close - the epic added ~1.7 KB across the five stories, mostly the linkTo anchors and the CSS reveal markup plus the minimal origin/focus script.
- **Audience composition is by promotion, never by specificity escalation.** A detail page respects the reader's chosen depth via the same `data-level` CSS the flow uses (FR28 parity), content staying SSR with only visibility toggling. The load-bearing edge: the audience hide rule (`display: none` for a level-excluded element) OUT-SPECIFIES the `:target` reveal on the same detail host, so a detail that is BOTH targeted AND audience-excluded would stay hidden. The correct composition is to PROMOTE the reading level so the hide rule stops matching (then the reveal applies cleanly), never to escalate the reveal's specificity, which would force-show content the level excludes and break FR28. A pure, isomorphic `levelRevealingDetail(section, level)` helper (next to `isVisibleAtLevel` / `hasAudienceTags`, the single source the switcher, the preview, and the no-JS fallback share) returns the level that reveals a detail page's CONTENT - covering both a section-level tag (the whole host hidden) and a block-level tag (the host shows but its only block is excluded, an empty box). `Report.svelte` calls it on BOTH the load-time deep-link path and the click-time activation, so a deep link to a technical-only detail page promotes to technical before navigating, and an in-report drill-down to a hidden target promotes the same way - a drill-down never dead-ends on a hidden box. Detail-only audience tags surface the level switcher (the kickoff default), since `hasAudienceTags` walks detail sections.
- **Producer parity is real because every surface writes through the one validated service, and the editor preview tolerates what save rejects.** The detail section (`kind: 'detail'`) and the `linkTo` reference author identically from the workspace, the REST API, and MCP - no producer-specific authoring path - because all four surfaces funnel through `validateDocument`, so the schema, the document-level cross-reference validation, and the actionable RFC 9457 errors are byte-identical regardless of who authors (confirmed by REST and MCP e2e each authoring a valid detail + linkTo, a dangling linkTo, and an annex+detail section, getting the same accept / 422 / 422). The one deliberate asymmetry is the workspace live preview: it TOLERATES a not-yet-existing `linkTo` target while the author edits, rendering what it can and surfacing the dangling reference as a gentle, actionable notice naming the missing section rather than throwing - consistent with the existing per-block preview tolerance, and PREVIEW-ONLY. The validate-on-write path still rejects a dangling linkTo at save/publish, so a reader never reaches a dead link. The published `/api/v1/schema` describes `kind` and the three carriers and ships a `drilldown` example so an agent discovers the shape.

## Security Audit

The epic ran a dedicated security + attacker-mindset penetration pass after the five stories landed. **The result is 0 Critical / 0 High and one Medium, now remediated and green.** The auditors stress-tested the surfaces the epic adds - the linkTo injection vector, the "reachable only via a link" boundary, the notes-on-a-detail-page path, and the validate-on-write parity across producers - and found the following.

- **The one Medium: section-id uniqueness, now remediated.** Epic 11 made the section id load-bearing: it is the primitive behind the CSS `:target` detail reveal, deep-link and internal-link resolution, and presenter notes-by-id pairing - all of which assume an id names EXACTLY one section. Nothing below the schema enforced that, so a document with two sections sharing an id validated, then silently misdirected a drill-down (the wrong detail revealed) or mis-paired presenter notes at read time. This is a correctness-and-misdirection issue, not an escalation (no content is exposed beyond the share), hence Medium. Remediated by a document-level uniqueness pass (`validateSectionIds`, the structural twin of `validateInternalLinks`, isomorphic with no `$lib/server` / `$lib/ui` imports, wired into the v1 document `superRefine`) that walks the sections and rejects any reused id with an actionable RFC 9457 error at the offending `sections[n].id`, naming the duplicated id and stating that ids must be unique so an internal link, deep link, or notes pairing resolves to one section. It runs on every write path (workspace, REST, MCP, AI all funnel through `validateDocument`), and is ordered BEFORE the internal-link pass so a duplicate-id error is the clear one even when a linkTo also targets the duplicated id. A refine only - no schema-shape change, no version bump, no published-artifact change. The remediation is green.
- **No linkTo XSS.** The auditors confirmed the three-layer closure holds: a `linkTo` is constrained to a section-id slug by the schema, required to resolve to a real section by the cross-reference pass before serving, rendered as `href="#" + id` through escaping Svelte attribute interpolation (never `{@html}`, never a raw URL), and fixed to an in-page fragment by the renderer. There is no path by which a `linkTo` reaches the DOM as markup, an off-document navigation, or a scriptable scheme - across all three carriers.
- **No notes leak via a detail page.** A detail section's author-private `notes` are stripped at the same single `getPublishedDocument` chokepoint as flow sections, and the reader view-model carries no `notes` field for any section kind. The auditors confirmed there is no detail-specific serving path that bypasses the strip, and the presenter deck (the only path that reads notes) is the main-flow owner-scoped route, not a reader path.
- **No validation bypass across producers.** A dangling linkTo and an annex+detail section are rejected with the same cross-reference / mutual-exclusion 422 whether authored from the workspace, REST, or MCP, because validation lives in the shared service. The editor preview's dangling-linkTo tolerance is preview-only and does not weaken the save/publish gate. The auditors verified no producer can serve a document with a dead internal link or an ambiguous duplicate id.
- **The documented not-a-confidentiality-boundary invariant.** The auditors flagged that "reachable only via an internal link" ships every detail page into the authorized reader's DOM under the report's own share, and must never be mistaken for an access boundary; the invariant ("the share is the boundary, not the link") is stated plainly in the epic design and held by the SSR-everything render plus the view-model partition. The auditors confirmed there is no per-detail token, no separate access path, and no detail-only gate - a detail page is served exactly as gated as the report.

## NFR Validation

- **Accessibility (NFR15, NFR14).** Activating an internal link moves focus INTO the detail page's labelled `tabindex="-1"` region, so a screen-reader / keyboard user lands on the content rather than the top of the document; the "back to origin" affordance restores focus to the origin section. The reveal uses the browser's native `:target`, so the no-JS reader reaches the content by the `#id` jump. Detail content is held to the same axe-core report-content contract (AAA) the flow is, on the default theme. The level switcher remains a real labelled radio group, and detail-only audience tags surface it consistently with the flow rule.
- **Performance / reader budget (NFR3).** Reader-path JS held at 74.6 KB / 200 KB at epic close - the epic added ~1.7 KB across the five stories. The reveal is pure CSS `:target` (zero JS); the linkTo anchors are static SSR markup; the only added JS is the small origin-tracking + focus-management glue (11.3) and the `levelRevealingDetail` helper plus the back-handler hardening (11.4). No client charting, no new dependency, no hydration on the detail content itself.
- **Renderer purity and the leak-free reader posture (NFR10).** Every carrier renders an escaped internal anchor; no `$lib/server`, no `{@html}`, no off-document URL, no new external surface, no new fetch, no third-party asset. A detail page serves under the same share gate, the same revoked/expired/unknown neutral page, the same `noindex` / `no-store` as the report. Author-private speaker notes on a detail section are stripped at the publish-serving chokepoint identical to flow sections.
- **Schema additivity / version tolerance (FR7).** `kind: 'detail'` on a section and `linkTo` on the three carriers (plus the `rowLinks` parallel array on a table) are optional and additive: a document with no detail sections and no internal links validates and renders byte-unchanged, no migration, no version bump - the published `static/schema/v1.json` gains only the optional `kind` enum and the optional `linkTo` / `rowLinks` properties. The section-id uniqueness remediation is a refine with no shape change.
- **Audience composition (FR28).** A detail page's blocks show/hide by the same `data-level` CSS the flow uses, content staying SSR with only visibility toggling, composing with the `:target` reveal by level promotion (never specificity escalation), so FR28 holds on detail pages exactly as in the flow.
