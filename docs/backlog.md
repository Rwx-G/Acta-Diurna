Architect review recommends pinning this by a short decision before Epic 2: extend `bindingSchema` with per-field target slots (schema change, version-safe since additive) vs keep the mapping resolver-side by convention. Recommendation: additive schema extension. (Raised: 1.2 QA, 2026-06-12) -> RESOLVED in 2.4 (additive per-field target slot).

Recommendation: evaluate a lightweight maintained reader (e.g. a minimal SheetJS pin with the advisory reviewed, or a smaller xlsx-only reader) and approve the exact version; then a short follow-up wires the Excel branch into the existing parser interface. (Raised: 2.4, 2026-06-12)

## Decided autonomously during Epic 3 (confirm or override)

These 5 Epic 3 design points had no explicit FR/spec answer; resolved with security-best-practice defaults during the autonomous run so implementation could proceed. Each is cheap to change before the relevant migration/story freezes. Override any.

1. **Reader session TTL** (3.3): default 30 days, env-configurable via `READER_SESSION_TTL`. Rationale: readers are low-privilege and FR23 wants "verify once, read freely"; the author realm stays at 7 days. (override: shorten if confidential-report posture wants it)
2. **`reader_identities` uniqueness grain** (3.3): one global row per verified email; the per-access audit trail lives in `access_records` (many per identity). Normalized, avoids duplicate identity rows across shares.
3. **Reader session scope** (3.3): per-share. A verified reader session for report A does NOT grant report B; each share verifies independently. Matches FR23's per-report reading and is the safer default.
4. **Restricted-mode magic-link forwarding** (3.4): the verification token is bound to the email that requested it. Forwarding a raw magic link to an unlisted third party does NOT verify them (the token only validates for its requested address). Closes the restricted-mode bypass.
5. **Neutral-page HTTP status** (3.5): uniform `404` with a neutral body and `Cache-Control: no-store` for revoked, expired, AND nonexistent tokens alike - the three are byte-for-byte indistinguishable (enumeration-safety, NFR9/FR20). An active share serves the verify gate (200); everything closed/unknown is one identical 404.

## Decided autonomously during Epic 4 (confirm or override)

API-design points with no explicit FR/spec answer; resolved with REST/API best-practice defaults during the autonomous run. The list-envelope one (4.2) has real forward-compat weight; the rest are cheap to change.

- **4.1 PAT format**: GitHub-style prefix `acta_pat_` + a stored non-secret display fragment (e.g. last 4 chars) shown in the token list to distinguish tokens. **Revoke-only**, no expiry for V1 (expiry is a later add). **No timing-flat 401s** - PATs are high-entropy bearer tokens, not the reader-email enumeration concern, so a fast invalid-token 401 leaks nothing.
- **4.2 update verb**: `PATCH /api/v1/reports/:id` accepting `{title?, document?}` routed to the existing `updateReportTitle`/`updateReportDocument` services (PUT implies full replace, which does not match the service granularity). **Optimistic concurrency via a body field** carrying the expected `updatedAt`/version the service already takes (not `If-Unmodified-Since`), to match the service signature exactly.
- **4.2 list envelope (forward-compat)**: list endpoints return a `{ items: [...] }` envelope from day one (room for `total`/pagination later) rather than a bare array - adding the envelope after release would be a breaking response-shape change. This is the one to confirm.
- **4.3 data transport**: the data-set push accepts the raw file bytes in the request body with the format derived from `Content-Type` (`text/csv`, `application/json`), target report id in the path/query - cleaner for scripts/agents than multipart. The ingestion service already takes bytes+format+filename, so this is a thin adapter.
- **4.3 remap**: the push returns binding diagnostics (FR14/15 parity); a programmatic remap is "read the drift diagnostic, re-push corrected data" - no separate remap endpoint for V1.
- **4.3 skeleton target**: data-push targets a **report** (the real inject-and-render cycle, exact parity with the upload flow). The workspace has no bind-data-to-a-skeleton flow (skeletons are structure-only), so "push onto a skeleton" is satisfied by instantiate-then-push. The dev mirrors the actual workspace flow and does not invent a skeleton-binding path; if a skeleton-scoped data set is genuinely wanted, raise it as a product decision.

## QA Findings (non-blocking)

- **API error boundary: endpoints MUST use `runApi`, not the handle (4.2 correction).** The 4.1 seam description (and the 4.1 Completion Note) said an `/api/v1` endpoint can just `throw` an `AppError` and the `/api/*` handle boundary formats it. That is WRONG for `+server.ts` endpoints: SvelteKit's internal `resolve()` routes endpoint throws through `handleError` (always a 500 error-page shape) before any `handle` hook sees them, so an AppError thrown in an endpoint would 500 instead of returning its problem+json status. 4.2 fixed this with `runApi(handler)` (`src/lib/server/api.ts`) that each endpoint composes (catches AppError -> problemResponse, re-throws others to the safe 500). The handle boundary remains the auth-stage backstop + opaque-500 redactor. **Every future `/api/v1` endpoint (4.3, and the Phase-2 MCP adapter) MUST wrap its body in `runApi`** or it will 500 on AppError. (Caught: 4.2 e2e, DELETE-published returned 500 not 409.)
- **Reports API lacks a duplicate endpoint (4.2, out-of-AC parity gap, Low).** The workspace has a Duplicate action (FR10, `duplicateReport`); `/api/v1/reports` has no `:id/duplicate`. Not in the 4.2 AC, but a genuine workspace-vs-API asymmetry; add `POST /api/v1/reports/:id/duplicate` over the existing `duplicateReport` service in an API-parity follow-up.
- **adapter-node `BODY_SIZE_LIMIT` (512K default) is below the 1 MB document budget (4.2, Low/ops).** A valid document between 512K and `MAX_DOCUMENT_BYTES` (1 MB) is rejected at the transport layer with a generic framework error instead of the actionable 413 the service would give. Fails closed (no security issue) but a confusing operator/agent experience. Set `BODY_SIZE_LIMIT` comfortably above `MAX_DOCUMENT_BYTES` (e.g. 2 MB) in the deploy env, or align the two. Pairs with the existing body-size ops items. -> RESOLVED (4.3 QA iter 1): `BODY_SIZE_LIMIT` is now set to 52428800 (50 MB) in `docker-compose.yml`, well above `MAX_DOCUMENT_BYTES` (1 MB) and aligned with the `MAX_UPLOAD_BYTES` push cap, so the app-level 413 is the one that fires for both documents and data pushes.
- **Uploads-volume retention / orphan data sets** (2.4 architect+security, Low). `data_sets.report_id` is `ON DELETE SET NULL`, so deleting a report orphans its data-set rows and their files on the uploads volume; nothing garbage-collects them, so the volume grows unbounded across report deletions. Deliberate for V1 (a data set can outlive/precede a report). Needs a retention/GC story: a sweep of orphaned data sets + their files, or a cascade once ownership semantics are fixed. Add a `report_id` index when per-report data-set listing arrives (2.5).
- **HTTP-boundary body-size limit before multipart parse** (2.4 security, Low/ops). The 50MB upload cap is enforced on `file.size` after the adapter has already buffered the multipart body; there is no `Content-Length`-based rejection at the HTTP boundary, so a multi-GB body is consumed by the body parser before ingestion sees it. Set adapter-node `BODY_SIZE_LIMIT` (env) and/or a reverse-proxy `client_max_body_size` in the deploy. Pairs with the existing reverse-proxy ops item and the 1.2/1.5 body-size theme. -> PARTIAL (4.3 QA iter 1): `BODY_SIZE_LIMIT` is now set in `docker-compose.yml` (52428800, aligned with `MAX_UPLOAD_BYTES`), and the **API push** path (4.3 `readBodyBytes`) now streams-and-aborts at the cap so an oversized API push is never fully buffered. The **2.4 upload form** path (the multipart form action) still has the SAME post-buffer pattern (`file.size` checked after `arrayBuffer()`); it remains bounded only by adapter-node's `BODY_SIZE_LIMIT`. Follow-up: give the upload form action the same streaming/early-abort treatment for parity, so both ingestion entries enforce the cap before buffering, not just the API push.

- **Reader-verification deploy-posture & DoS hardening** (3.3 penetration audit). Three related items, all deploy/operations, none an access bypass (the access-control core passed): (1) **XFF-spoof rate-limit bypass + global-brake starvation (Medium)** - per-IP limit keys on `getClientAddress()`; a directly-exposed instance (the "trivial deploy" default) lets an attacker spoof `X-Forwarded-For` for a fresh bucket each request, leaving only the shared global brake, which one attacker can drain to DoS verification for all readers. Fix: ship a hardened compose/reverse-proxy default that strips inbound XFF unless `ADDRESS_HEADER` is set, and add a per-share sub-brake so one share's flood cannot starve all shares. Extends the existing reverse-proxy ops item. (2) **No sweep of expired/consumed verification_tokens and old access_records (Medium DoS)** - both tables grow with attacker traffic up to the rate-limit ceiling; add a periodic purge job (pairs with the uploads-volume GC retention story). (3) **Reader/author cookie `Secure` depends solely on `ORIGIN` scheme (Low)** - if an operator sets `ORIGIN=http://...` behind a TLS-terminating proxy, session cookies ship without `Secure`. Document `ORIGIN` must be https in the deploy contract, or guard the mismatch at env validation. Inherited 1.4 behavior, now also carries reader sessions.
- **`.env.example` is missing `READER_SESSION_TTL=` (3.3, manual)**. The secrets-fence hook blocks `.env*` writes for the agent, so the operator-facing example line could not be added. The env schema, `docker-compose.yml`, and tests carry it (default 30 days when unset), so the app works; only the example doc line is missing. Add `READER_SESSION_TTL=30` (days) to `.env.example` manually before release. (Same hook also blocked the main loop, not just subagents - the documented "exactly .env.example is writable" narrowing is not in effect this session; review the hook.)
- **3.4 design constraint - constant-work unauthorized path (3.3 penetration audit, carry into 3.4)**: when 3.4 adds the restricted-mode recipient check, the unauthorized-email path must perform equivalent work to the authorized path (or a matched delay) so response TIMING does not separate "on the list" from "off the list" - otherwise a timing oracle reintroduces the enumeration leak NFR9 forbids. The recipient check must sit behind the existing neutral `{state:'sent'}` return AND not short-circuit before the equivalent work. This is a 3.4 implementation requirement, recorded here so it is not lost. -> RESOLVED in 3.4: the allow-list check sits behind the neutral return, and the magic-link send is fire-and-forget on EVERY path, so the SMTP round-trip (the one large, network-variable cost) is off the response timing for both on-list and off-list; the residual is fast local DB work in the same timing class. Proven by gate.test.ts ("returns before sendMail settles", identical-void-result) and the restricted-share e2e (on-list and off-list responses deep-equal; only on-list creates a token row).
- **Test-send rate limiting** (3.1 security audit, Low): the workspace `?/test-send` action sends to an arbitrary author-chosen recipient with no rate limit (only `/login` is limited). Acceptable for single-trusted-author V1, but a spam/reputation vector if a session is hijacked. Add a per-session token-bucket (reuse `src/lib/server/.../rate-limit.ts`, e.g. 5/hour) returning the same 429 problem shape. Constraining the recipient is not viable (operator legitimately tests arbitrary addresses), so rate-limit is the lever.
- **Multi-author IDOR prep** (1.5 security audit, Info): reports have no owner column; fine for single-author MVP. When multi-author/tenancy lands, add owner/tenant column, filter getRow/listReports by identity, do not rely on UUIDv7 unguessability (timestamp-prefixed).
- **App-level document size cap before JSON.parse** (1.5 security audit, Low): currently relies on adapter-node BODY_SIZE_LIMIT (512KB default, env-overridable). Add explicit raw.length check -> 413 in the save action, pin BODY_SIZE_LIMIT in deploy env. Pairs with the 1.2 body-size backlog item.
- **Global JSON body-size cap on the HTTP layer** - the schema now carries DoS bounds, but `JSON.parse` cost is pre-validation; add a request body limit in hooks before the API stories (target: story 1.4 hooks or 4.2). (1.2 security audit)
- **Renderer string-sink checklist for story 1.6** - every schema string field (cells, labels, captions, axis labels, kpi values) must reach the DOM via escaped bindings only; `rel="noopener noreferrer"` on external links; consider rejecting cleartext `http://` links later. (1.2 security audit)
- **CI first-run verification** - the GitHub Actions pipeline is structurally validated but unproven until the next push to main. (1.1 gate)
- **.npmrc content unverifiable by agents** (secrets-fence blocks reads by design) - product owner should eyeball it once; expected content is scaffold defaults only. (1.1 security audit)
